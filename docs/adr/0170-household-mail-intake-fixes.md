# ADR 0170: 利用通知メールの取り込みの不具合 4 件の修正（家計簿 段階 1 の見直し）

- 日付: 2026-11-26
- 状態: ADR 0159・0160・0163 の見直しで見つかった不具合 4 件の修正。**模擬の試験だけ**で、実在のメール・実機での確かめは未実施。
- 根拠: ADR 0159（通知の読み取りの規則）・0160（同期したメールからの取り込み、U327「初めて取り込むときに過去のメールを読まない」）・0163（止める・再開する）、`apps/core/src/device-time-zone.ts` の方針（読めないときに UTC などで代用しない）。
- 対象: マイグレーション 0020、`packages/storage/src/household-store.ts`（`household.mail_pending`）、`packages/domain/src/household-notice.ts`、`apps/core/src/household-mail-intake.ts`・`core.ts`。契約（`packages/contracts`）・画面・`api-household.ts`・`household-ledger.ts` は変えない。

## 背景

1. 取り込みは本人のタイムゾーンを読めないとき `UTC` で代用していた。受信日が 1 日ずれ、年のない日付の年も狂うおそれがある。
2. 年のない日付（11/26）は、受信日より月日が後なら前の年としていた。タイムゾーンの違いで 1 日先になっただけで、1 年前の日付になった（例: 受信日 2026-11-30 に対する `12/01 00:10` が 2025-12-01 になる）。
3. 項目名の表で「ご利用金額」「利用金額」と「お支払い金額」「お支払金額」「支払金額」「決済金額」がどれも同じ金額の項目だったため、両方が並ぶ本文では 2 件目の利用として二重に記録された。
4. 取り込みの基準が口座ごとで、取得集合（scope）ごとではなかった。口座の基準ができた後に足した取得集合の過去のメールを、すべて未確認として読んだ（U327 に反する）。

## 決めたこと

| 対象           | 決定                                                                                                                                                                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| タイムゾーン   | `createHouseholdMailIntake` の `timeZone` を `() => string \| null` にする。`null` ならその回は読まず、`skipped`（理由 `zone_unavailable`）で返す。基準も作らない。`core.ts` は `deviceTimeZone()` をそのまま渡し、`UTC` で代用しない                                    |
| 年のない日付   | 受信日の年の同じ月日が受信日より **7 日を超えて**後のときだけ前の年とする。7 日以内（ちょうど 7 日を含む）なら受信日の年のままにする。年末年始に 12/31 の利用を 1/2 に受け取る場合は前の年になる                                                                         |
| 金額の項目     | 利用の金額の項目（ご利用金額・利用金額）と、支払いの金額の項目（お支払い金額・お支払金額・支払金額・決済金額）を分ける。本文に利用の金額の項目が一つでもあれば、支払いの金額の項目は読まない。なければ支払いの金額を利用の金額として読む。利用の金額が二つあれば 2 件    |
| 基準           | `household_mail_baselines` を (provider, account_id, scope_id) の主キーで作り直す（マイグレーション 0020）。基準がない取得集合では、その取得集合の同期済みのメールを確かめ済みにして空を返す。0163 の再開（切→入）で基準を消す処理は、新しい表の全行を消すので変更なし   |
| 作り直しの扱い | この表はバックアップに含めない `source_cache`（`backup-plan.ts`・`policy.ts` の分類は変えない）。古い中身は引き継がず捨てる。捨てると次の取り込みで全部の取得集合の基準を作り直し、過去のメールは読まない（安全側）。確かめ済みの表（`household_mail_checks`）は変えない |

## 試験

- `apps/core/src/household-mail-intake.test.ts`: タイムゾーンを読めない回は読まずに `zone_unavailable` で返し、基準も作らない。読めるようになった回から通常どおり基準を作る。
- `scripts/household-notice.test.mjs`: 年のない日付の境目（ちょうど 7 日・8 日・月またぎ・年またぎ・受信日と同じ日・過去の日付）。ご利用金額とお支払い金額が並ぶ本文は 1 件、支払いの金額だけの本文は 1 件、利用の金額が二つの本文は 2 件。
- `packages/storage/src/household-store.test.ts`: 口座の基準があっても、新しい取得集合の過去のメールは読まない。
- `packages/storage/src/migrations.test.ts` ほか: DB の版を 19 から 20 にした各試験（表の数は 63 のまま）。
- 修正前に、日付・金額の試験は失敗することを確かめた。

## 残ること

- 実在のメール・実機での確かめは未実施。
- 取得集合の基準は、取得集合を作り直す（同期の設定を変える）と、その取得集合だけ基準が作り直される。過去のメールを読まない側に倒れるので許容する。
