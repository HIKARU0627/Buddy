# ADR 0179: 請求予定を消す操作と、レシートの写真の読み取りの設定の保存（家計簿 段階 2・3 の一部）

- 日付: 2026-11-27

## 背景

ADR 0176 は、請求予定を消す・直す操作を作らなかった（U360 の暫定 (a)）。請求予定はどの合計にも入らないので、誤った請求予定が残っても家計の数字は狂わない。しかし、読み違えた金額や訂正前の金額の請求予定が「請求予定」の一覧と合計に残り続けると、いつ・いくら引き落とされるかという、請求予定を出す目的そのものが損なわれる。本人は、請求予定を消す操作を作ると判断した。

ADR 0177 は、レシートの写真を外部へ送る設定を中枢のメモリーにだけ持ち、中枢を起動し直すと切に戻るようにした（U364 の暫定 (a)）。中枢（Mac mini）を起動し直すたびに、本人が入にし直して OS の確認ダイアログに答える手間がかかる。本人は、設定を保存すると判断した。既定は切のままにする。

### 直す操作を作らない理由

請求予定を直す操作（金額・引き落とし日・会社の表示名の変更）は作らない（U376）。

- 請求予定は、カード会社のお知らせに書かれた値を写したものである。本人が値を直すと、お知らせに書かれていない値が請求予定として残り、どこから来た値かが分からなくなる。
- 誤りの種類（読み違い・訂正のお知らせ・別のカード）は、実在のメールで確かめないと分からない（U356・U358）。読み違いなら読み取りの規則を直すのが本筋で、訂正のお知らせなら訂正後の請求予定が別に作られる（今は訂正のお知らせを読まない）。どちらも、本人が手で値を直す操作では解決しない。
- 誤った請求予定は消せば一覧と合計から外れるので、本人が困るのは「誤った値が残ること」だけで、それは消す操作で足りる。正しい値は会員サイトで確かめられる。
- 直す操作を作ると、新しい内容版の暗号文・入力欄・値の検査・API・IPC が増える。必要が分かってから、家計の記録の中身の変更（ADR 0169）と同じ形で足せる。

### レシートの写真の読み取りの設定を保存する

| 対象                   | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 置き場所               | 家計簿の設定の表（`household_settings`、ADR 0163）に列 `receipt_reading`（`on`・`off`）を足す（マイグレーション 0022）。既定は切（行がないとき・列を足したときの値）。バックアップの対象（この表はもともと含める）                                                                                                                                                                                                                                                                                                            |
| 版                     | 利用通知の取り込みの入・切と共通の `settings_revision` で照合する（U378）。変える要求（`HouseholdReceiptSettingRequest`）に `expected_settings_revision` を足し、結果（`HouseholdReceiptSetting`）に保存した後の `settings_revision` を返す。入にする要求は、版が違えば 409（同じ要求の再送も、版が進んでいるので 409）。切にする要求は、版が違っても保存する（安全な向きなので。今の版から 1 進める）。同じ値でも版は進める                                                                                                  |
| 起動し直したとき       | 中枢は DB に保存した値を読む。読み取りの口があり入にしていれば、起動し直しても入のまま。読み取りの口がなければ、入だった値を切に倒して保存する（下の「起動のときに口がなければ切に倒す」）                                                                                                                                                                                                                                                                                                                                    |
| 読み取りの口がないとき | 保存した値によらず unavailable（ADR 0177）。入にする要求は 503 で、保存しない。切にする要求は保存する（版は進み、見せる値は unavailable のまま）。読み取りの口が戻ったときに、本人が切にした後なら切のまま。ADR 0178 の配線では、起動の環境に鍵（`BUDDY_GEMINI_API_KEY`）がない・鍵の形が違う・確認済みの単価の版がない・送り先が決めたホストでないときが、読み取りの口がないときに当たる。入のまま鍵を外して起動し直すと、起動のときに切に倒して保存するので、鍵を戻しても切のままで、入にするには OS の確認ダイアログが要る |
| 読み取りの前の確かめ   | 送る前に保存した値を DB から読む（読めなければ送らずに 503 `not_sent`）。保存した値を読む間・保存期限の掃除の門を通る間に切にする要求を受けたら、読み出した値が入でも送らない（403）。切にする要求は、保存の結果を待たずに、送っている途中の読み取りを止める（切にする要求は版が違っても保存するので、古い表示からでも切にできる）。ADR 0178 の読み取りの口は、止められると送っている途中の HTTPS の接続を切る                                                                                                                |
| 月ごとの合計           | `settings` は今までどおり利用通知の取り込みの入・切と版だけを返す（`HouseholdSettings` の形は変えない）。`receipt_reading` は保存した値から決めた今の設定（on・off・unavailable）。端末は `settings.settings_revision` を版として送る                                                                                                                                                                                                                                                                                         |
| 設定を変える経路       | ADR 0177 のまま。入にするときは main が OS の確認ダイアログを出し、本人が「送る設定にする」を選んだときだけ送る。画面操作だけ（チャット窓口・音声からは受けない）。端末は 409 を `preview_stale` にして読み直し、送り直さない                                                                                                                                                                                                                                                                                                 |
| 同意の記録             | ADR 0177 のまま（U369）。入にする確かめは OS の確認ダイアログだけで、`ExternalSendConsent` には書かない。設定を保存するので、起動し直したときに確かめを出し直すことはなくなった                                                                                                                                                                                                                                                                                                                                               |

Core では、保存の口を `household-receipt-setting.ts`（`ReceiptSettingStore`。本番は `receiptSettingStoreOf` で DB、試験は `memoryReceiptSettingStore`）に分けた。`createHouseholdReceiptRoutes` は保存の口を受け取り、省略すると中枢のメモリーにだけ持つ（試験と、保存先を渡さない組み立てのため。製品の起動の `core.ts` は DB の口を渡す）。

## 退けた案

| 案                                                                                       | 退けた理由                                                                                                                                                                                                                       |
| ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 請求予定の行を DB から消す（DELETE）                                                     | 出所の鍵が消えるので、同じメールの読み直し（同期の掃除の後の再取得など）で作り直される。家計の記録の削除と考え方がそろわない                                                                                                     |
| 消した請求予定の暗号文を残す                                                             | 消した後も会社・金額・引き落とし日が DB とバックアップに残る。家計の記録の削除は暗号文を消しているので、扱いがそろわない。残せば別のメールの同じ請求を見分けられるが（U377）、その利点のために本人が消した値を持ち続けない       |
| 列の追加（`ALTER TABLE ADD COLUMN`）で状態と内容版を足す                                 | 月と暗号文の列が NOT NULL のままで、消したときに月と暗号文を消せない。有効と消したの組み合わせを表の CHECK で確かめられない                                                                                                      |
| 請求予定を直す操作も作る                                                                 | 上の「直す操作を作らない理由」のとおり                                                                                                                                                                                           |
| レシートの設定に別の版（`receipt_revision`）を持つ                                       | 設定の表は 1 行で、版の trigger（1 ずつだけ進む）も 1 つ。版を分けると列と trigger が増える。共通の版にすると、取り込みの入・切を変えた直後の古い表示からレシートの設定を変えると 409 になるが、端末は読み直すだけで済む（U378） |
| 月ごとの合計の `HouseholdSettings` に `receipt_reading`（保存した値）を足す              | `receipt_reading`（今の設定。unavailable を含む）と二つの値が並び、どちらを見るか分かりにくい。保存した値と読み取りの口から決めた今の設定は一つの値で返す                                                                        |
| 中枢のメモリーに設定の写しを持ち、起動のときに DB から読んで、読み取りではメモリーを見る | 起動のときに DB を読めないと写しが切のままになり、DB と食い違う。バックアップから戻したときも食い違う。読み取りは 1 回ずつの本人の操作なので、送る前に DB を読む手間は小さい                                                     |

## 原本に決めがない項目

- U360（更新）: 請求予定を消す・直す画面の操作。暫定を (a) から (b)（消す操作だけを作る）に変えた。
- U364（更新）: レシートの写真の読み取りの設定の置き場所。暫定を (a) から (b)（`household_settings` に列を足して保存する）に変えた。
- U376: 請求予定を直す操作を作らないこと。
- U377: 消した請求予定と同じ請求を別のメールが知らせたとき、新しい請求予定として作ること。
- U378: レシートの設定の版を、利用通知の取り込みの入・切と共通にすること。切にする要求だけは版を照合しない（追補）。
- U379（更新）: バックアップから戻すと、レシートの設定は切にすること（ADR 0038 に合わせる。暫定を (a) から (b) に変えた）。
- U380: 消した請求予定を元に戻す操作を作らないこと。

## 追補（見直しの修正）

本人の判断の暫定として、閉じた側（外部へ送らない側）に倒す。

### 起動のときに口がなければ切に倒す

- 中枢の起動のとき、読み取りの口がなく（鍵がない・鍵の形が違う・確認済みの単価の版がない・送り先が違う・受付の期限との関係が破れる）、保存した値が入なら、切に倒して保存する（`closeWhenUnavailable`。`core.ts` が HTTPS の受付を始める前に呼ぶ）。記録には理由の名前（`receipt_reader_unavailable_at_start`）だけを出し、鍵・単価・値は出さない。保存できなかったときは `receipt_setting_close_failed`。
- 版は、切に倒すときに今の版から 1 進める。古い表示から入にする要求は、版の違いで 409 になる。
- 理由: 口がない間は画面から切にできず（`unavailable` では画面が切の要求を送らず、入・切のボタンも出ない）、保存した値も見えない。入のまま残すと、鍵や単価の版が戻ったときに OS の確認ダイアログを経ずに入で始まる（単価の版がないことは本人が何もしなくても起こり得る）。ADR 0038 の「復元ではすべての同意を取り直す」と同じく、確かめを経ない入にしない。
- 口があるときと、保存した値を読めないときは何もしない（読めなければ読み取りは送らず 503 `not_sent`）。保存の失敗が続いた状態で、口が戻った次の起動が入のまま始まり得る（未解決。DB が壊れている場合で、起動の他の検査が先に止める）。

### 切にする要求は版を照合しない

- 保存層（`applyReceiptSetting`）と Core の口は、切にする要求の版の照合をやめた（版の形は検査する）。保存したら今の版から 1 進める。入にする要求は今までどおり照合する。
- 理由: 設定の版を取り込みの入・切と共通にした（U378）ので、別の端末で取り込みを変えた後に古い表示から「切にする」を押すと 409 になり、保存が入のままだった。安全な向き（切）は、版が違っても保存する。端末は結果の設定を読み直す。
- 送っている途中の読み取りは、切にする要求を受けた時点で止める（これまでと同じ。保存の結果は待たない）。

### バックアップから戻したとき

- 復元の後処理の `reset_send_consents` で、レシートの写真の読み取りが入なら切にする（版は 1 進める）。作業用の DB に、他の取り直しと同じ transaction で書く（`restore-aftermath-store.ts`。結果の `receipt_settings_closed_count` は 0 か 1）。0022 より前のバックアップは列がないので何もしない。U379 を、戻すと切にする形に更新した。

### 既知の制約

- 0022 の `household_bills` は、`INSERT OR REPLACE` で衝突した行を置き換えられないよう、`household_bills_no_replace`（ID か出所の鍵が既にあれば INSERT を拒む BEFORE INSERT）を足した。`recursive_triggers` が 0 のため、削除の trigger は `INSERT OR REPLACE` の置き換えでは動かない。家計の記録（0016 の `household_entries`）にも同じ穴があったが、マイグレーション 0023 で塞いだ（追補を参照）。
- DB は、有効から消したへの `UPDATE` だけを打ち `sealed_blobs` の行を消さないことを拒まない（保存層は一つの transaction で消すので、今の経路では起きない。家計の記録と同じ作り）。
- 復号できない請求予定は ID を返さないので、画面から消せない。

## 追補: 家計の記録の置き換えの穴（マイグレーション 0023）

0016 の `household_entries` は、同じ出所の鍵（source_key）または同じ ID（entry_id）で `INSERT OR REPLACE` を打つと、消した印（state = 'deleted'）の行を新しい有効な行で置き換えられた。`recursive_triggers` が 0 のため、置き換えで衝突した行の削除では `household_entries_no_delete` が動かないからである。保存層は普通の `INSERT` しか使わないので今の経路では起きないが、DB の最終ガードとして、マイグレーション 0023（DB の版 23）で `household_entries_no_replace`（entry_id か source_key が既にあれば INSERT を拒む BEFORE INSERT の trigger）を足した。表は作り直さず trigger を足すだけなので、既存の行は変わらず、表の数（STRICT の表は 64）と分類も変わらない。

ほかの家計簿の表は塞がない。行の削除を拒む trigger を持つのは `household_entries` と `household_bills`（0022 で塞いだ）だけである。`household_category_rules`・`household_settings`・`household_budgets` は削除を拒む trigger を持たず、置き換えで消えて困る印の行もない。`household_mail_checks`・`household_mail_baselines` は trigger を持たず、取得し直せる source_cache である。なお `household_category_rules` の「本人の規則を取込みの規則で置き換えない」と、`household_settings`・`household_budgets` の「版を 1 ずつだけ進める」は更新の trigger であり、`INSERT OR REPLACE` でも避けられる。ただし保存層はこれらの表へ普通の `INSERT` と `UPDATE` しか使わず、置き換えても出所の鍵のような作り直しを止める印は失われないので、今回は扱わない。
