# ADR 0150: B13-04 気づきの候補から既存のラベルを自動で付ける配線

- 日付: 2026-11-26
- 状態: B13-04（親 #24）の Core の配線の部分。ADR 0149 の配線に、既存のラベルの付与（`label_mail`、RemoteMutation）を足す。下書き・予定の書込み、Outlook のカテゴリを承認待ちの案にする経路、取り消しの補償の中身、候補の生成の入口からの呼び出しは未着手。実データ・実機・実 API は未実施。
- 根拠: 設計 11 §5・§5A・§5B（F05）、設計 08 §1・§9、設計 04（自動実行の範囲と既定 OFF）、設計 06 B13、ADR 0030・0146・0148・0149。原本の参照手順は `docs/design/README.md`。
- 対象: `apps/core/src/candidate-auto-execution.ts` とその試験、`apps/core/src/retention-entries.test.ts` の表。契約（`packages/contracts`）・保存層・マイグレーションは変えない。

## 背景

ADR 0149 は判定表の 4 行のうち用事の登録だけ操作を作り、ラベルの付与は判定が通っても `not_wired` を返していた。付けるラベルを受け取る口と、provider の接続・許可の版・対象のメールを読み直す口が無かった。会話から作るラベルの変更（`api-turns.ts`、ADR 0030）には、同じ確定 intent（`LabelOperationIntent`）を作る経路がすでにある。

## 決めたこと

| 対象                   | 決定                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 付けるラベルの受け取り | 呼び出し側が、本人が割り当てた既存のラベルの ID（provider のラベル ID）を `label_id` で渡す。無ければ null。ラベルの名前から ID を探したり、新しいラベルを作ったりしない（U307）                                                                                                                                                                                                                          |
| 判定への反映           | `label_id` が null のときは、判定の事実「ラベルを割り当て済み」を偽にして判定する。判定は `label_not_assigned` で気づきだけになり、操作を作らない（予定のカレンダーと同じ扱い）                                                                                                                                                                                                                           |
| 対象にする元サービス   | 判定が `auto_eligible` になるのは Gmail と模擬だけ（ADR 0146、Outlook のカテゴリは承認待ち）。配線でも元サービスが Gmail か模擬でなければ作らない（`label_provider_unsupported`）                                                                                                                                                                                                                         |
| 掃除のゲート           | provider を読み直す前に、保存期限の掃除が済むのを待つ（ADR 0053・0058）。検索・クラウドへの送信・自動利用のどれかが閉じていれば作らない（`retention_blocked`）。ゲートの確認と貸し出しの取得は同じ同期の区間で行い、読み直しの間だけ貸し出しを持ち、保存と実行の開始の前に返す。発言の入口（`api-turns.ts`）と同じ口で、`retention-entries.test.ts` の表に載せる。用事の登録は Buddy 内だけなので通さない |
| 作る前の読み直し       | 接続（有効・同じアカウント・`mail.labels.change` の書込みと `mail.message` の読み取りが許可の範囲内）、許可の版、対象のメールを今読み直す。使えなければ `connection_unavailable`、接続の元サービスが判定に使った値と違えば `label_provider_changed`、メールが読めなければ `target_not_found` で作らない                                                                                                   |
| 変化のないとき         | 対象のメールに同じラベルがすでに付いていれば作らない（`no_change`）。一度だけの記録も残らないので、後でラベルが外れた場合は次の判定で作れる                                                                                                                                                                                                                                                               |
| 確定 intent            | 会話からのラベルの変更と同じ形。足すラベルはその 1 つ、外すラベルは空、対象は元のメールの ID と今の版、許可の版は読み直した値、照合は対象だけ（`exact_target`）、外部の宛先は空                                                                                                                                                                                                                           |
| 作成の命令             | 用事と同じ手順（ADR 0149）。契約で確かめて暗号化し、方針による自動承認と候補の起点（カレンダーなし）を付けて `operation.create` へ送る。経路は `remote_mutation`、許可の版は読み直した値。保存できたら実行器の `afterApproval` で実行を始め、送出の直前に実行器が対象の版と許可の版をもう一度確かめる（ADR 0030）                                                                                         |
| 同じ対象の鍵と一度だけ | 同じ対象の鍵は操作の種類・アカウント・元のメールから作る（U304）。一度だけの記録は保存層が `label_mail` として残し、二度目の判定は `already_created` で気づきだけになる                                                                                                                                                                                                                                   |

## 原本に決めがない項目

- 自動で付けるラベルを何が決めるかは書かれていない（U307）。設計 11 §5A は「既存のラベルの付与」を判定表の 1 行とするだけで、どのラベルかの出所を決めていない。

## 対象外

- 付けるラベルを決める処理（本人の振り分けの設定など）と、候補の生成の入口からの呼び出し（製品の起動で掃除のゲートを渡す配線を含む）。
- Outlook のカテゴリを承認待ちの案にする経路（`needs_approval` の案の作成）。
- 下書き・予定の書込み、取り消しの補償の操作の中身と対象の現在版の検査、照合で拒否した操作の後始末と画面（B13-05）。

## 試験（模擬だけ）

- `apps/core/src/candidate-auto-execution.test.ts`: 期待値はすべて手書き。DB は実物の SQLite、provider は模擬の読み取り。ラベルだけ方針で有効なときに操作を作ること（経路・許可の版・同じ対象の鍵・確定 intent の全体・実行の開始・一度だけの記録・二度目は `already_created`）、すでに付いている・provider が無い・読み取りだけの接続・別のアカウント・元サービスの変化・メールが読めないときは作らないこと、ラベルの ID が無ければ気づきだけにすること、掃除のゲートが閉じていれば provider を読まずに作らないこと、開いていれば貸し出しを 1 回取って返すこと。試験のアカウントは契約の Id の形（UUID v4）にした。

**模擬の期待値だけ**。候補の生成の入口からの呼び出し・実際の Gmail への送出・画面・実データ・実機・実 API は未実施で、合格扱いにしない。

## 残ること
