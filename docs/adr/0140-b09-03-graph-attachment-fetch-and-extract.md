# ADR 0140: B09-03 Outlook（Graph）添付の取得と抽出（列挙・個別取得・Gmail と共通の抽出）

- 日付: 2026-11-23
- 状態: B09-03（親 #17）。connector の添付の列挙・個別取得、Core の取得・抽出手続きと模擬試験まで。実 API・OAuth の実接続・実アカウントは未実施（B15 と本人の承認）。解析計画が保存済みメールから抽出入力を組み立てる配線は B10・B11 の後続処理（Gmail 側と同じ持ち越しで、本 ADR の対象外）。
- 根拠: 設計 04 取得する対象（J16: 添付は本人が選んだ種類だけ、初期値は PDF とテキスト系、1 件 10MB まで。Outlook は選択した種類・サイズだけを個別に取得する。選択外は最小限のメタデータだけ）、設計 11 §1・§2（対象添付が未取得・読取失敗・切り詰めなら条件Bは未確定）・§3（根拠の対応付け、添付は取得済みの許可対象の ID だけを使う、添付の抽出テキストは最大 2,000 トークン）、ADR 0071・0086（取得範囲の検査の正本は domain の fetch-scope）・0087・0134（添付の取得と抽出は B09-03）・0139（Gmail 側の添付取得と抽出。判断の多くを共有する）、本人の決定 D5。
- 対象: `packages/connectors/src/adapter/graph-mail-connector.ts`（listAttachments・getAttachment・parseAttachmentContent）、`packages/connectors/src/index.ts` の出口、`packages/connectors/src/graph-mail-connector.test.ts`、`apps/core/src/mail-attachments.ts`（抽出の共通化: extractMailAttachmentText）、`apps/core/src/graph-mail-attachments.ts`、`apps/core/src/graph-mail-attachments.test.ts`、`apps/core/src/graph-sync-executor.test.ts`（偽 connector へ新しい口の stub を追加）、`apps/core/src/retention-entries.test.ts`（入口表へ両 loader を gated 登録）。

## 在庫確認（済んでいたもの）

- 取得可否の規則は B08-02 の domain（`classifyAttachment`・`checkAttachment`）で完成しており、入力は MIME・ファイル名・申告サイズだけで provider に依存しない。Graph 側でもそのまま使える（本 ADR で検証した）。
- 抽出入力の受け口は B10-05 で定義済み（`MailAttachmentInput`、provider 非依存）。テキスト・PDF の抽出（charset を見た復号・unpdf）は B08-04 の Gmail 用 loader の中にあり、Core 内で共有できる形だった。
- Graph のメッセージの最小 select には `hasAttachments` が含まれていて、添付の有無は同期の時点で分かる。
- 能力宣言は変えていない。添付の取得はメッセージの読み取りの一部で、`GRAPH_CONNECTOR_CAPABILITY` の `mail.message` に含まれる（Gmail と同じ判断。新しい読み取り種別は足さない）。

## 決めたこと

| 対象           | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 添付の列挙     | connector に `listAttachments`（GET /me/messages/{id}/attachments、全ページ）を足す。`$select` は id・name・contentType・size・isInline の最小集合で、内容（contentBytes）は一覧では取らない（Graph の一覧では返らず、設計 04 の「個別に取得」とも一致）。id の無い・空の項目は同一と断定せず `skipped_without_id` に数える（メッセージと同じ扱い、QA23）                                                                                                                                                                                                                                         |
| 添付の種別     | `'@odata.type'` を `file`・`item`・`reference`・`unknown` に写して持つ。バイト列として内容を取れるのは `file`（fileAttachment の contentBytes）だけ。`item`（埋め込みアイテム）・`reference`（リンク）は内容を持たない                                                                                                                                                                                                                                                                                                                                                                            |
| 添付の取得     | connector に `getAttachment`（GET /me/messages/{id}/attachments/{attachmentId}）を足す。contentBytes は標準 base64（Graph は base64url ではない）を厳密に復号し（符号化し直して一致するものだけ）、申告サイズと実バイト数が一致しない応答は `invalid_response` で拒否する（Gmail の attachments.get と同じ検証）。`file` なのに contentBytes が無い応答も不正。`item`・`reference` は失敗ではなく `data: null` で返す                                                                                                                                                                             |
| 取得の手続き   | Core に `createGraphMailAttachmentLoader`（`apps/core/src/graph-mail-attachments.ts`）を新設する。接続の保存済みの取得範囲（FetchScope）を受け、列挙した添付ごとに `checkAttachment` を通し、通ったものだけを個別に取得する。範囲外は取得せず `permitted: false`・`unread`。取得は出現順に 1 件ずつ（並列にしない。Gmail と同じ）                                                                                                                                                                                                                                                                 |
| 入力の形の違い | Gmail 用 loader は payload の木を受けるが、Graph は添付が別経路のため、この loader はメッセージ ID と版と `hasAttachments` を受けて列挙から持つ。`hasAttachments` が false なら列挙を呼ばず空を返す。provider の API の形の違いによるもので、出力（MailAttachmentInput の並び）の意味は揃える                                                                                                                                                                                                                                                                                                     |
| 列挙の失敗     | 列挙が失敗し、添付があることだけが分かっている場合は、位置だけの ID（`attachment-0`）の `failed` を 1 件返す。空配列を返すと「添付なし・全部読めた」ことになり条件Bが誤って確定する（設計 11 §2）ため、未読を表す側に倒す。`permitted` は未読として数える側（true）にする                                                                                                                                                                                                                                                                                                                         |
| 名前の無い添付 | 列挙には含めるが、loader では添付として扱わない（インライン等。Gmail の列挙がファイル名のあるパートだけを添付とするのと同じ）。名前が無いと分類（拡張子との照合）ができず、本文側のパートを添付として取り込む事故を避ける                                                                                                                                                                                                                                                                                                                                                                         |
| 抽出の共有     | テキスト・PDF の抽出は Gmail 用 loader から `extractMailAttachmentText` として切り出して共通化した（charset は contentType の宣言に従う。Graph の contentType に charset が付いていればそれが効き、無ければ UTF-8）。Gmail 用 loader の振る舞いは変えていない（既存の試験が担保）。テキストが取れない PDF は未読（failed）に倒す（設計 11 §2）                                                                                                                                                                                                                                                    |
| 失敗の写し     | 取得の失敗（拒否・認証切れ・通信）と、バイト列で取れない添付（`item`・`reference`）は、許可対象なら `failed`（source_revision はメッセージの版）にする。申告サイズで検査を通っていても実物が上限を超えていたら使わず failed にする（Gmail と同じ）                                                                                                                                                                                                                                                                                                                                                |
| 添付 ID と版   | 抽出入力の attachment_id は Graph の添付 ID（メッセージ内で安定）、source_revision はメッセージの版（lastModifiedDateTime 由来。同期の実行器と同じ版）を使う（設計 11 §3 の根拠の対応付け）                                                                                                                                                                                                                                                                                                                                                                                                       |
| 保存しない     | 添付のバイト列と抽出テキストはこの手続きでは保存しない（Gmail と同じ。保存層に添付の置き場所は無く、設計も永続化を指定していない）                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 掃除ゲート     | 両 loader とも保存期限の掃除ゲート（ADR 0053・0058）を通す。`retention`（ready／gate／lease）を任意引数で受け、load の冒頭で確認し、閉じていれば外部取得をせず許可対象を failed に倒す（Graph は列挙もしないので未読 1 件）。貸し出しは取得・抽出の間保持する。入口表（retention-entries.test.ts）へ両ファイルを gated 登録した。core.ts への配線は接続作成（B03-04）と解析計画の配線（B10・B11）に合わせる。※ `mail-attachments.ts` のゲートは、B08-04 が PR #291 で main へ入れた形と同型に本作業コピー側でも揃えたもの。統合時は main の現行版を正とし、本コピーの抽出共通化だけを取り込むこと |

## 残ること

- 解析計画が保存済みメール（source_items）から抽出入力を組み立てる配線は B10・B11 の後続処理。本文（body）の組み立ても同じ持ち越しで、この loader はそのときに呼ばれる想定の部品として置く（Gmail 用 loader と対）。
- 大きい fileAttachment で Graph が contentBytes を返さない場合の `$value` 経路は、実 API の応答の形が未検証のため作っていない。実測は B15（10MB 上限までの添付で contentBytes が返るかを確かめる）。
- 埋め込みアイテム（itemAttachment）の中身の取得・抽出は設計に指定が無く、対象外のまま（未読として数える）。
- 接続画面の表示（アカウント種別・拒否の理由）は B09-05。接続の作成・OAuth・トークン保存は B03-04 で、この loader は呼び出し側から connector と保存済みの範囲を受けるだけ。
