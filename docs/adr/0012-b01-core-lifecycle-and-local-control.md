## Core のライフサイクル

Core は Electron に依存しない独立した Node.js プロセスで、`buddy-core start | status | stop` で操作します（02）。Electron の utilityProcess を唯一の起動経路にしません。クライアントの終了・端末の入出力停止・中枢の停止は別の操作で、制御チャネルのクライアントが終了しても Core の状態は変わりません。

| 状態     | 意味                                                             |
| -------- | ---------------------------------------------------------------- |
| starting | 起動前の検査・データディレクトリ・排他・状態・制御チャネルの準備 |
| running  | 新しい要求を受け付ける                                           |
| stopping | 新しい要求の受付を止め、終了処理をしている                       |
| stopped  | ソケット・ロックを解放した                                       |

- 遷移は `apps/core/src/lifecycle.ts` の表で、副作用を持たずに試験します。終了処理中の二度目の停止は遷移にせず、進行中の終了処理に合流させます。
- 停止の手順は「受付停止（stopping）→ 制御チャネルを閉じて残りの接続を待つ（期限を過ぎたら切断）→ ソケット・ロックの解放 → stopped」です。
- 停止の入口は SIGINT・SIGTERM（Windows は SIGINT・SIGBREAK）と制御チャネルの stop です。Windows では子プロセスへの SIGTERM が即時終了になるため、停止は制御チャネルを正とします。二度目のシグナルでは終了処理を待たずに終了します。
- 終了コード: 0 正常、1 障害、2 使い方の誤り、3 動いている Core がない（status / stop）、4 排他による拒否、5 起動前の検査による拒否。

## 制御チャネルの約束

- 接続先: Unix socket はデータディレクトリ内の `control.sock`（0600）。Windows は `\\.\pipe\buddy-core-<データディレクトリの絶対パスの SHA-256 の先頭 16 桁>`。
- 形式: 改行区切りの JSON で、1 接続につき 1 要求。要求は `{"op":"status"|"stop","request_id":"<小文字の UUID>"}` だけです。
- 拒否: 未知の op・未知の項目・欠けた項目・型違い・UUID でない request_id・1 行 4 KiB 超・不正な UTF-8・不正な JSON・重複キーは `{"ok":false,"error":"invalid_request","reason":...}` を返して接続を閉じます。重複キーを拒否するため、JSON は自前の厳格な読み取りで検査します（scripts/contract-tools.mjs の parseStrictJson と同じ考え方。Core は scripts を import しない）。
- status の応答: `ok`・`request_id`・`state`・`core_instance_id`・`store_generation`・`started_at`・`uptime_ms`・`pid`。stop は同じ形の応答（state は stopping）を書き終えてから終了処理に入ります。
- 本文・秘密は扱いません。要求を送らない接続は 2 秒で切り、同時接続は 16 までです。

## 単一起動の排他

同じデータディレクトリを使う中枢を一つに限ります（08 §4）。

1. データディレクトリの `core.lock` を排他作成（O_CREAT | O_EXCL、0600）し、pid・core_instance_id・起動時刻を書きます。
2. 既存のロックがあれば制御チャネルへ status を問い合わせ、応答があれば二重起動として拒否します。
3. 応答がなく pid も存在しなければ古いロックとして片付け（判定した内容と同じときだけ消す）、残ったソケットファイルも消して起動します。
4. pid が存在するのに応答がない、またはロックの内容を読めないときは、旧担当の終了を確認できないので起動を拒否します。

ロックの解放は自分の core_instance_id のロックだけです。POSIX の listen 自体も同じ接続先を二重に使えないため、二つ目の守りになります。

## 状態の仮置き

`core-state.json` に store_generation（ランダム UUID）と作成時刻だけを原子的に書きます（一時ファイル → fsync → rename → ディレクトリの fsync）。初回起動で作り、通常の再起動では維持します。core_instance_id は起動ごとの新しい UUID です（07 §1・§4）。B02 で DB に置き換えるまでの最小の仮置きです。読めない状態ファイルを作り直すと世代が変わって復元・新規作成と区別できなくなるため、起動を拒否します。

## 起動前の検査

`startCore({ preflight })` に理由の配列を返す検査を渡し、理由が一つでもあれば何も作らずに起動を拒否します（06「鍵保護不能時の停止」）。鍵保護の実検査は B01-02（ADR 0013）が提供し、CLI の既定はその検査です。`--mock-key-protection` は試験・模擬起動用です。平文の保存へ切り替える経路は作りません。

## 読み取り（レビュー対象）

原本に定めがなく、実装で決めた点です。

- データディレクトリの既定値: macOS `~/Library/Application Support/Buddy/core`、Windows `%APPDATA%\Buddy\core`、Linux `$XDG_DATA_HOME/buddy/core`（なければ `~/.local/share/buddy/core`）。POSIX では所有者を確かめて 0700 にそろえます。
- Windows の名前付きパイプは Node.js 既定のセキュリティ記述子のまま（`readableAll` / `writableAll` は付けない）で、ACL を明示していません。データディレクトリも %APPDATA% 既定の ACL に任せています。B01-02 の配置・鍵保護の検討で確認します。
- Unix socket のパスは 103 バイトまで（macOS の sun_path に合わせる）で、超えたら起動を拒否します。
- 1 接続 1 要求、要求なしの接続は 2 秒、同時接続 16、停止時に残りの接続を待つのは 2 秒、ロックの問い合わせの待ち時間は 1 秒としました。
- status の応答に `request_id` を含めました（要求との対応づけのため）。
- pid が他のプロセスに再利用されている場合も「生きている」とみなして拒否します（安全側）。利用者はプロセスを確かめてからロックを消します。
