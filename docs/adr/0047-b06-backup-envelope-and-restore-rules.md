# ADR 0047: B06 のバックアップの中身と世代・鍵の運用・復元の 6 段階・復元の後の保留（domain の純粋な規則）

- 日付: 2026-10-24
- 状態: B06-05（#141、親 #11）の判断。`packages/domain/src/` の `backup-plan.ts`・`backup-keys.ts`・`restore-plan.ts`・`restore-aftermath.ts` の純粋な関数と、手書きの期待値（`tests/fixtures/backup-restore-cases.json`）による模擬の試験だけ。スナップショットの取得・暗号化・鍵の包みと開封（HKDF・AES-GCM の計算）・ファイルの削除・復元の実行・DB の差し替え・trigger は Core と storage（B06-06・B06-08）。実際のバックアップと鍵の復元・実機の Mac mini は未実施（B15）。
- 根拠: 設計 03（バックアップ・復元・忘却と再取り込み・保存期限）、08 §3・§4、09（X15・X16・X17・T06）、ADR 0008・0012・0016〜0019・0040・0043、本人の判断 J1〜J6（2026-10-24、#11 のコメント）と司令塔の判断（同日、#11 の 2 つ目のコメント）、B06-01（PR #148）の Codex の最終確認の P3（#141 のコメント）。原本は権限のある接続で読み取りだけ行い、全文は写していない。原本に決めがないことは「原本に決めなし」と書き、docs/b00/contract-map.md の U73〜U77 に記録した。
- ADR 0040 で決めたこと（封筒・6 段階・3 種類の結果・7 状態の隔離・解除の 2 条件・3 つの鍵の包み）は変えていない。変えたのは次の 2 点で、どちらも下の「判断が要る点」に挙げた: (1) 復元の直後の記録の検査で、承認の失効を**印の有無・経路によらず**検査する（B06-01 の P3。ADR 0040 の表の文言「承認は失効」を全操作に広げた）。(2) LocalCommand の `approved`・`preparing` を、復元の後に**承認待ちへ戻す**（ADR 0040 の表は「そのまま」。J3 で承認を失効させると、承認済みのまま再承認の経路がなくなるため）。

## 決めたこと

### バックアップの中身（`backup-plan.ts`）

| 未知の表                       | 含める・含めないのどちらの一覧にもない表があれば、**バックアップを取らない**（`unknown_table`）。何が入っているか分からない表を黙って含めも捨てもしない。表を足すマイグレーション（B06-06 の 0008 以降）は一覧に必ず載せる。試験がマイグレーションの `CREATE TABLE` と一覧を照合する                                                                                                                                                                                                                                    |

| 世代の数                       | 期限内の封筒のうち新しい方から `keep_generations` 個を残し、残りを消す（`beyond_generations`）                                                                                                                                                                                                                                                                                                                                                                                                                          |

### 鍵の運用（`backup-keys.ts`。B06-01 の P3）

| 対象                                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 包みの一部の欠け・取り違え           | 3 つの包みが用途ごとにちょうど 1 つ・同じ復旧キー・形が正しいこと（`keyWrapProblems`）。欠け（`key_wrap_missing`・`key_wrap_count`）、同じ用途が 2 つ（`key_wrap_duplicated`）、知らない用途、別の復旧キー（`recovery_key_mismatch`）を拒否する。用途の包みを推測で選ばない（`keyWrapFor` はちょうど 1 つのときだけ返す）                                                                                                                                                            |
| 包む鍵の導き方（U76）                | HKDF-SHA256(ikm = 復旧キーの 32 バイト, salt = 包みの `kdf.salt` の 16 バイト, info = `buddy/backup/key-wrap/v1` ‖ 0x00 ‖ purpose ‖ 0x00 ‖ key_id, L = 32)。用途を info に入れるので用途ごとに鍵が変わる                                                                                                                                                                                                                                                                             |
| AES-GCM の追加認証データ（U76）      | `buddy/backup/key-wrap/v1` ‖ 0x00 ‖ purpose ‖ 0x00 ‖ key_id ‖ 0x00 ‖ recovery_key_id。包みを別の用途・別の鍵の ID・別の復旧キーの欄へ入れ替えると認証タグが合わず開けない（試験で node:crypto により確かめた）                                                                                                                                                                                                                                                                       |
| 台帳の用途別の鍵                     | HKDF-SHA256(ikm = `ledger_hmac_key`, salt = 空, info = `buddy/ledger/source-id/v1` または `buddy/memory/dedupe/v1`, L = 32)。ADR 0040 の info のとおりで、salt は原本・ADR 0040 に決めがなく空にした（RFC 5869 で 32 個の 0 と同じ）                                                                                                                                                                                                                                                 |
| 復旧キーの確認値（U76）              | HKDF-SHA256(ikm = 復旧キー, salt = 空, info = `buddy/recovery-key/check/v1`, L = 4) を大文字の 16 進 8 桁（`RecoveryKeyRecord.check_value`）                                                                                                                                                                                                                                                                                                                                         |
| HKDF の入力の検査                    | domain は入力（salt・info・長さ）を組み立てて検査する（`backupHkdfInputProblems`: sha256・salt は 0 か 16 バイト・info は `buddy/` で始まる 1〜1024 バイト・長さ 1〜32）。計算は Core。domain は Node の Buffer・TextEncoder を使わず、値は ASCII だけ                                                                                                                                                                                                                               |
| 復旧キーの文字列                     | Crockford base32 の 52 文字（4 × 13）の先頭 256 ビット。末尾の 4 ビットは 0。入力では区切り・空白を無視し、小文字と Crockford の読み替え（I・L → 1、O → 0）だけを許す。U・文字数の違い・末尾のビットが 0 でないものは読まない                                                                                                                                                                                                                                                        |
| 設定のやり直しで鍵を保つ             | ある鍵は作り直さない（`reuse`）。包み直しだけ。台帳に項目がある・台帳の鍵を記録したのに KeyStore にない（**欠落**）、KeyStore の鍵が記録と違う（**取り違え**）、台帳に項目があるのに鍵を記録していない、ときは新しい鍵を作らずに止める（作ると台帳と記憶の HMAC を照合できず、忘れた元情報の再取り込みを止められない）。データ鍵は CLI が作らない（ADR 0040）                                                                                                                        |
| 台帳の鍵の記録                       | Core は台帳と記憶の HMAC に使っている鍵の ID を DB（`schema_meta`）に記録する（B06-06・B06-08 で列・キーを足す。ADR 0040 の `ForgetLedgerFile` は鍵の ID を持たない）。同じ系譜の中では台帳の鍵は変えない                                                                                                                                                                                                                                                                            |

| 復元で鍵を入れる順序                 | **足すだけで上書き・削除をしない**（`keyInstallPlan`）。封筒の鍵を自分の ID で足す → 読み戻して確かめる → DB を差し替え、同じ transaction で今使う鍵の ID を記録する → 使わなくなった既存の鍵は消さずに残す。差し替えより前のどこで失敗しても、この計画で足した鍵だけを消せば元どおり（稼働中の鍵と DB は変わらない）。同じ ID で素材が違う鍵（取り違え）・素材を比べていない鍵・別の ID の台帳の鍵がすでにあるときは入れない。順序の入れ替えは `keyInstallOrderProblems` で見つける |

### 復元の 6 段階（`restore-plan.ts`）

| 段階                 | 判定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 台帳の確認         | 封筒の意味の検査に通らなければ `manifest_invalid` だけ。中枢の台帳の系譜が違う（中枢がなく全部の複製が違うときも）・封筒の台帳の鍵が違う → `ledger_lineage_mismatch`。中枢の台帳の連鎖が壊れている → `ledger_chain_invalid`。使える台帳（同じ系譜・連鎖が正しい・全体）で ADR 0008 の `restoreReasons`（最新は「知っている最新」と使える台帳の head の大きい方）。使える台帳の、封筒の世代の hash が封筒と違う → `backup_ledger_hash_mismatch`。同じ持ち主の台帳が 2 つ → `latest_ledger_unconfirmed`。通れば最も新しい台帳（同じ世代は中枢を優先）を段階 3 で当てる |
| 2 期限切れの削除     | 開けない（復旧キーの確認値の不一致・包みの認証の失敗・鍵の入れ方の衝突・本体の hash の不一致）→ `backup_unreadable`。時計が最終確認時刻・復元の開始・バックアップの作成より前、または読めない → `clock_regression`（期限を判定できない。掃除と違い、復元は戻った時計で進めない）                                                                                                                                                                                                                                                                                     |
| 3 忘却の適用         | 段階 1 で選んだ台帳の head まで当てていなければ `forget_apply_failed`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 4 DB の検証          | 版がこのコードより新しい → `schema_newer_than_code`（ADR 0016）。整合性・外部キー・取り出した DB と封筒の版の不一致・操作の隔離の計画が立たない（読めない状態・経路）→ `db_integrity_failed`                                                                                                                                                                                                                                                                                                                                                                         |
| 5 作り直し・6 照合   | 作り直しの失敗は `rebuild_failed`。外部の照合は失敗で止めず、再認証が済むまで `pending`（OAuth トークンは封筒にないので、復元の直後はいつも `pending`）                                                                                                                                                                                                                                                                                                                                                                                                              |
| 結果の組み立て       | `buildRestoreResult` が契約の形を作る。止まった段階より後は `not_run`。段階の順序・止まった後の実行・理由の段階の組・`after_restore` の有無・世代の更新・保留と隔離の件数・時刻の逆転（期限切れの削除の `clock_regression` だけ許す）が食い違う入力は組み立てない。組み立てた結果は契約の Schema と意味検査に通る（試験で照合した）                                                                                                                                                                                                                                  |
| settings_only（U75） | 台帳の確認で止まり、理由が「最新の台帳がない・確認できない・台帳が巻き戻った」の 3 つだけで、本体を開けて設定を読めたときだけ。系譜・連鎖・hash・封筒の不一致は、別の・壊れた・書き換えたバックアップの印なので設定も戻さない。戻す表は `deployments` だけ（本文・個人の内容・認可・実行の状態・予算を持たず、他の表を参照しない）。`user_directives`（会話に由来し忘却の対象になり得る）・`home_networks`（端末を参照）・`safety_breaker`（停止の状態を古い値へ戻し得る）は戻さない                                                                                 |

### 復元の後の保留（`restore-aftermath.ts`）

| 対象                         | 決定                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| J3 承認はすべて失効          | 経路・状態・印の有無によらず、有効な承認を 0 にする（`approvals_revoked_count` は全操作の合計）。検査（`restoredOperationProblems`）と契約の意味検査（`scripts/contract-tools.mjs`）は、印のない LocalCommand・終端の操作でも `valid_approval_count > 0` を `approval_not_revoked` で拒否する（B06-01 の P3）                                                                                                 |
| 7 状態の隔離                 | 外部変更の `awaiting_approval`・`approved`・`preparing`・`dispatching`・`reconciling`・`unknown_held`・`not_executed` に印（差し替えの時刻）。進行中の 4 つは `unknown_held`。終端と LocalCommand は印なし（ADR 0040 の表）。読めない状態・経路・重複した操作があれば計画しない（段階 4 で止める）                                                                                                            |
| LocalCommand（U77）          | 承認が失効するので、`approved`・`preparing` は `awaiting_approval` へ戻す（本人がもう一度承認する経路を残す）。ほかの状態はそのまま                                                                                                                                                                                                                                                                           |
| 解除の条件                   | 印だけを見た判定（`restoreMarkGuard`）は契約の `restoreGuard` と同じ結果（全ての出来事 × 印の有無 × 観測の組で照合した）。結果を取り込むのは目印つきの作成物がちょうど一つ・目印の内容版が同じ・内容を照合できたときだけ。見つからない・複数・読めない・照合の手段がない・内容版が違う・内容を照合できないは保留。本人の決着は印を外す。知らない観測の種類は保留                                              |
| 状態を重ねた判定             | `applyRestoreEvent` は印の判定に状態の遷移を重ねる。内容の更新は印では止めないが、送出の境界を越えた状態（`unknown_held` など）では状態の規則で拒否する。内容を更新すると内容版が上がるので、旧版の目印の作成物は `content_version_mismatch` で取り込まない。本人の決着は「実行済み」「未実行」「取り消す」のどれかが要り、取り消しは遷移として許される状態（承認待ち）だけ。決着の中身がなければ印を外さない |
| 予算の保留（U77）            | バックアップの月から復元の月まで（予算のタイムゾーンの暦月）を保留の月にする。予約中（`reserved`）の行は、バックアップの後に送られた可能性があるので使用量不明にする（未送信として解放しない）。今の予算月が保留の月で本人が確かめていない・保留の月より前（時計の戻り）・読めない月は、有料の受付を止める（`budget_restore_hold`）。保留の月を過ぎた新しい月は止めない                                       |
| 取り直し（`RESTORE_RESETS`） | 差し替えと同じ transaction で: 全承認の失効・操作の隔離・送信の同意の取り直し（ADR 0038）・DB の世代の更新・音声と出力先の世代を進める・接続範囲の失効・接続の再認証・同期のカーソルを捨てて全体を走査し直す・候補を起点にした自動実行の停止・予算の保留                                                                                                                                                      |
| 候補を起点にした自動実行     | 取得範囲ごとに、復元の後に全体の走査を公開し、その世代の対象の列挙（11 §5B の `analysis_plan_complete_generation`）が済むまで止める（`restore_resync_pending`）。知らない取得範囲は止める                                                                                                                                                                                                                     |
| 新しい DB の世代             | バックアップの世代とも、復元の前の今の世代とも違う値（`buildRestoreAftermath`）                                                                                                                                                                                                                                                                                                                               |

## 原本に書いてあること（読み取り）

- 03 バックアップ・復元: 本人が選んだ場所に 1 日 1 回、暗号化して作る。生音声・記録しない会話・OAuth トークン・API キーを含めない。復元後の外部サービスは再認証。鍵は本人が管理する復旧用秘密で保護。DB は整合したスナップショット。保持は初期 7 世代。アプリ管理下の古いバックアップにも忘却・期限を適用し、必要に応じて置換または削除。忘却台帳は本文なしの別ファイルで、端末にも複製。復元は最新台帳の確認 → 期限切れの削除 → 忘却の適用 → DB 検証 → 画面・索引の再生成 → 外部状態照合の順。最新の台帳を確認できないときは記憶・会話の復元を許可せず、新規開始か安全に分離できる非機密設定の復元だけ。
- 03 保存期限: 時計が大きく巻き戻った場合は期限を延ばさず、最終確認時刻との不整合を解消するまで自動利用を止める。
- 08 §4: 設定違反・DB 破損・古いバックアップからの復元では、`preparing` という状態名だけで未送出と判断せず、外部変更を保留して 03 の復元後の照合を行う。dispatching 以降は自動再送しない。

## 判断が要る点

1. **承認の失効を全操作で検査する**（B06-01 の P3 の反映）: 契約の意味検査を変えた。印のない LocalCommand・終端の操作に承認が残る記録も拒否する。
2. **LocalCommand の承認済み・準備中を承認待ちへ戻す**（U77）: ADR 0040 の表は「そのまま」だった。そのままにすると、承認が失効した承認済みの操作を本人が再承認できない。
3. **古いバックアップを世代の数 × 1 日で消す**（U74）: バックアップが長く失敗し続けると、残るバックアップが 0 になる（期限を延ばさない側）。最新の 1 つだけは期限を過ぎても残す案もある。
4. **settings_only で戻すのは `deployments` だけ**（U75）: 実質は「新規開始」に近い。`user_directives` の「今後は」の指示や `safety_breaker` を戻す案もあるが、忘却・停止の状態に触れるので外した。
5. **台帳の鍵の取り違えの理由に `ledger_lineage_mismatch` を使う**（U76）: 契約の理由を増やさなかった。専用の理由（例: `ledger_key_mismatch`）を足す案もある。
