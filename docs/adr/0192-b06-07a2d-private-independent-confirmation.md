# ADR 0192: B06-07a-2 の 2d 記録しない会話の独立した確認の Core の経路と最小の操作記録

- 日付: 2026-11-27
- 追記（2026-11-27、2d の見直し）: 見直しの指摘に対応した（下の「見直しの対応」）。記録しない経路でも入力の時点の許可の版を最初の await の前に控え、画面の承認の `preview_id` に確認の ID ではなく記録のために新しく作った ID を使い（確認の ID を DB に残さない）、保存層でも `private_minimal` をラベルの変更だけに限り、承認の結果の控えを保存境界の保持者の排他区間の中で書くようにした。ADR 0045 の判断の変更（下の「ADR 0045 の判断の変更」）を ADR 0045 の追記にも書いた。
- 状態: B06-07a-2（Issue #143 の一部、親 #11）の**段階 2d** の判断と実装。ADR 0190 の「2d への口」に書いた範囲（記録しない間の外部の変更を、断る代わりに独立した確認へ切り出す分岐を `privatePlan` に足し、保存境界の保持者の命令 `show_independent_confirmation`・`record_minimal_operation` を Core が受け、承認の後に最小の操作記録だけを保存する）。`apps/core` の `private-confirmations.ts`（新規）・`storage-gate.ts`・`api-turns.ts`・`core.ts`、`packages/storage` の `operation.create` の欄（`private_minimal`）、模擬の試験だけ。**確認を画面に出して承認を受ける経路（契約・API・画面）は作っていない**（U503）。そのため製品の組み立てでは口を閉じたまま（`PRIVATE_CONFIRMATION_SCREEN_OPEN` は `false`）で、記録しない間の外部の変更は今までどおり決まった文で断る（ADR 0190 の U483 のまま）。**契約（JSON Schema・OpenAPI・生成型・fixture）は変えていない**。マイグレーションは足していない（`operations.record_kind` と `private_minimal` の制約は 0010 にある）。実機の Mac mini・Windows・macOS の端末、実際の Gmail などの実 API・実請求は未実施。
- 根拠: ADR 0045（許可表の `record_minimal_operation` の行「独立した確認の承認の後だけ」・独立した確認の中身・最小の操作記録・確認の ID と承認の結び付け・U42・U64〜U67）、ADR 0040（最小の操作記録の確定内容の暗号文は J5 で完了から 7 日後に消え、hash とレシートは 90 日残る）、ADR 0059（保存境界の保持者と命令の実行）、ADR 0060（発言の由来）、ADR 0190（記録しない区切りの RAM・U482・U483・「2d への口」）、0010 のマイグレーション（`operations.record_kind`・`private_minimal` の行は `workflow_id` を持てず `normal` へ戻せない）、ADR 0030（実行担当）。設計 03 の原本の要約（ADR 0045 の「原本に書いてあること」）: 外部変更は、会話本文を保存せず、必要な操作記録を残す独立した確認画面へ切り出し、その記録内容を示して一度承認を得る。要約メモとして黙って保存しない。非公開の原本はこの環境になく、新しく参照していない。原本と ADR に決めのない点は、安全側（断る・保存しない・口を閉じる）の暫定で決め、`docs/b00/contract-map.md` の U502〜U508 に記録した。
- 番号: ADR は 0192、未決事項は U502〜U508。

## ADR 0045 の判断の変更

ADR 0045 の次の 2 点を、この ADR で変えた（ADR 0045 にも追記した）。どちらも暫定で、U502・U506 に記録した。

- **切り出す範囲（U64 → U502）**: ADR 0045 はラベルの変更と返信の下書きを切り出せる型とした。2d ではラベルの変更だけを切り出し、返信の下書きは断る（本文が本人の発言そのもので、確定済みの変更の暗号文に 7 日残るため）。保存層も `private_minimal` をラベルの変更だけに限る。
- **承認の受付の書き方（U506）**: ADR 0045 は「独立した確認の承認の受付（受付の ID と結果）は `command_receipts` に別に書かず、最小の記録の欄にする」とした。実装では、端末の要求の受付（接続範囲・要求 ID）は書かず、最小の記録の欄も足していない。その代わり、DB worker の共通の仕組みが、命令ごとの内部の受付（`command_receipts` の内部の接続範囲・命令の ID・操作の ID）と操作のイベント（`event_outbox` の `operation.updated`）を書く。承認の結果は、`approvals` の行（`screen`・端末・DB の時刻）と操作の状態で表す。どちらも会話・区切り・確認の ID を持たない。

## 端末

変えていない。確認を画面に出す経路がない（U503）ので、端末は `private_confirmation` の参照を受け取らない（製品では口が閉じている）。

## 契約

変えていない。応答は既存の `StreamTurnResponse`・`TurnResponse` の形のまま（口を開いた試験の組み立てで、`item_refs` の種類が `private_confirmation` の参照を返す）。最小の操作記録は既存の `operations`・`operation_versions`・`approvals` の列と 0010 の制約で表し、マイグレーションは足していない。

## 試験（模擬だけ）

期待値は手で書いた値（状態・件数・文・理由・確定済みの変更）。内容の hash は、試験の中でキーを並べ替えた区切りのない JSON と `node:crypto` の SHA-256 で別に求め、実装の関数（`intentContentHash`・`sealOperationIntent`）から作っていない。

- `apps/core/src/private-confirmation.test.ts`（10 件、新規。見直しで 4 件を足し、既存の 2 件を強めた。下の「見直しの対応」。製品の Core の HTTPS・合成の読み書きの provider・口を開いた試験の組み立て）: 製品の口が閉じていること。記録しない間のラベルの変更が確認になり（応答の種類と決まった文、確認の中身・内容の hash・世代、DB の行が 1 行も増えず外部へも送らない）、hash の違う承認は通らず、正しい承認で最小の操作記録を書き（増えた表は操作の記録の表だけ。`operations` は `private_minimal`・依頼なし・実行担当が `succeeded` まで進めた、`approvals` は `screen`・端末・確認の ID）、外部の変更は 1 回だけ、同じ承認の再送は書き直さない、ラベル（目印）の平文がデータディレクトリ（DB・WAL）とログにない（停止の前と後）、終えた後の承認は通らない。取り下げ・ロックの申告・承認の前に終える、のどれでも後の承認は `confirmation_not_found` で、操作の記録は増えず外部へも送らない。別の世代の承認・形の違う端末・登録されていない端末（`record_failed`、再送も同じ結果で外部へ送らない）。口を開いていても返信の下書きは断り、口が閉じていればラベルの変更も断る。口を開いても通常の区切りのラベルの変更は通常の承認待ちの操作（`normal`・依頼あり）のまま。
- `apps/core/src/storage-gate.test.ts`（1 件）: 通常の区切りでは確認にしない（命令を実行しない）、形の違う確定済みの変更は確認にしない、確認を 2 件出す、ロック・忘却の取り下げで承認前の確認をすべて取り下げ、後の承認は `confirmation_not_found`、閉じた後は `closed`。
- `packages/storage/src/operation-store.test.ts`（2 件。見直しで拒否の組み合わせを足した）: `private_minimal` の作成で `operations`・`approvals` の行が手で書いた値になり、準備へ進め、`normal` へ戻せないこと。依頼・方針の自動承認・LocalCommand・端末の要求の受付と一緒の作成は `private_minimal_conflict`、形の違う欄は `private_minimal_invalid`、登録されていない端末は `device_not_registered` で、どれも行を作らないこと。
- 既存の試験（`private-conversation.test.ts`・`private-turns.test.ts`・`canvas-stream.test.ts`・`api-turns.test.ts`・`voice-private.test.ts`・`storage-gate-core.test.ts`）はそのまま通る（記録しない間のラベルの変更を断る試験は、口を渡さない組み立てなので変えていない）。
- B06-09 の実行器（`tests/integration/b06*`）のケースと期待値は変えていない（製品の組み立てでは口が閉じているので、X17 の観測は変わらない）。`apps/core`・`packages/storage` のソースが変わったので、証拠（`evidence-b06-simulated.json`）は実行器で作り直した。

### 感度

次の欠陥を一時的に入れて（ビルド後の `dist` を書き換え、終わったら戻した。コミットしていない）、該当の試験が落ちることを確かめた。

- ロック・忘却の取り下げで保存境界の保持者の確認を取り下げない（RAM の確認だけ捨てる）→ 取り下げ・ロック・終えるの試験が落ちる（ロックの後の承認が記録される）。
- 保存層が `record_kind` を `private_minimal` にしない → 保存層の試験と Core の 1 件目の試験が落ちる。
- 口の判定を常に開く → 口が閉じているときに断る試験が落ちる。
- Core が封じた hash と命令の hash の照合は、domain が承認の hash を保留中の確認と照合しているので、通常の経路では食い違いが起きない（重なった守り）。

| 1. 記録しない経路で入力の時点の許可の版を控えていない | `postPrivateTurn` の最初（await の前）に控え、`processPrivateTurn` から `privatePlan` へ渡す。解釈の間に別の発言が新しい版を読むと、先に届いた発言は聞き返し（「今は進められません。…」）になる試験を足した                        |
| 2. 確認の ID を `approvals.preview_id` に保存している | `preview_id` は記録のために新しく作った ID にした。確認の ID がデータディレクトリ（DB・WAL）とログにないことを試験で確かめる（U506）                                                                                               |
| 3. ADR 0045 側に変更の追記がない                      | ADR 0045 に追記し、この ADR に「ADR 0045 の判断の変更」を足した。U506 の結論と contract-map の U42 の結論に書いた                                                                                                                  |
| 4. 記録の結果が不明なとき                             | U505 のとおり。本人がもう一度頼むと操作が 2 つできうることを U505 に書き足した                                                                                                                                                     |
| 5. 保存層でも種類を限る                               | `private_minimal` はラベルの変更だけ。ほかの種類（返信の下書きを含む）は `private_minimal_conflict`                                                                                                                                |
| 6. 承認する端末の ID                                  | U503 に「認証した要求の端末から取る」条件を書き足した                                                                                                                                                                              |
| 7. 結果の控えの書き込みの場所                         | 保存境界の保持者の排他区間の中で書く。同時の二重の承認の試験を足した（変更の前の実装でも、続きの順序で同じ結果になっていた。この試験だけでは変更の前後を区別できない）                                                             |
| 8. `approvals.approved_at`                            | DB の書き込みの時刻であることを書いた                                                                                                                                                                                              |
| 試験の抜け                                            | 承認の前の忘却の知らせ、確認を出す間のロック・終える（409 と取り下げ。発言の経路を直接組み立てた試験）、失効した端末、保存層の取り消し・候補の起点との組み合わせ、口が閉じているときに操作・承認・受付の行が増えないこと、を足した |

見直しの感度: 記録しない経路で入力の時点の版の代わりに今の控えの値を使う（`dist` を書き換え、戻した）→ 許可の版の試験が落ちる。

## 範囲の外と残り

- 確認を画面に出して承認を受ける経路（契約・API・画面。U503）と、記録しない会話から作った操作の結果の示し方（U508）。その経路ができるまで、製品では記録しない間の外部の変更を断る（U483 のまま）。
- 返信の下書きを切り出すか（U502）。切り出すなら、本文の暗号文が 7 日残ることを確認の画面で示すかを一緒に決める。
- 送信・予定・ごみ箱など、契約の `OperationIntent` に確定した型のない外部変更（ADR 0045 のまま切り出さない）。
- 実機の Mac mini・Windows・macOS の端末、実際の Gmail などの実 API・実請求（B15）。
