## 予算の門（apps/core/src/budget-gate.ts）

LLM・検索・音声のアダプターが有料の provider へ送る前に通る口です。判定は domain の純粋な規則と DB worker の予算の命令に任せ、門は設定・時計・順序だけを持ちます。

| 段階                   | 決定                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 枠（`admit`）          | 起点（`BudgetOrigin`）とサービス（LLM・検索・音声）から、設定の `routing` で葉の枠を決める（domain の `routePool`）。経路が null なら `route_missing`。本人の依頼は本人の依頼の枠、自発的な解析・自動実行・初回の読み込み・影モードは自発の枠（本人の判断）                                                                                                                                 |
| 超過枠へ回せる枠       | 許可リストは本人の依頼（owner_request）の LLM・検索の枠から作る（`overageRouteOf`。音声は入れない）。超過枠がない・許可リストが空なら回さない。経路は起点によらず DB の受付へ渡し、本人の依頼でない・許可リストにない枠の拒否は domain の `admitWithOverage` が決める（二重に守らず、拒否の理由が残る）                                                                                     |
| R と M                 | domain の `computeReservation`。課金され得る期間は受付の時刻から応答の期限（要求の `timeout_ms`）まで。ADR 0035 で B07-04 に残した「期間の終わり」はこの値にした。p95 で予約してよい profile は Core の設定で渡す（既定は空。05 は意図判定の比較 profile だけに限る）                                                                                                                       |
| 予算月                 | 受付のたびに本人が設定したタイムゾーンで進める（`budget.calendar_advance`）。受付の間に月を越えたら一度だけ進めて受け付け直す。時計の戻り・tz データの食い違い・経路を解けない予約のときは受け付けない                                                                                                                                                                                      |
| 送る直前（`dispatch`） | 新しい命令 `budget.dispatch_intent`。予約が reserved で、まだ送出意図がなく、安全停止していないときだけ送出意図を記録し、記録できたときだけ一度送る（domain の `dispatchReasons`、08 §3 P01 の reservation_valid）。記録の成否が不明なら送らず、解放もしない                                                                                                                                |
| 送った後               | usage が分かれば精算（`settle`）。応答の喪失・例外・不正な応答は usage 不明（`unknown`）で R と M を保持する。timeout（注入できる timer）と結果の破棄（呼び出し側の AbortSignal）は待つのをやめて usage 不明にし、その後に届いた usage は usage 不明の記録の後に精算する（費用は捨てない）。送り直さない                                                                                    |
| 未送信の解放           | 送出意図を記録する前に止めたとき（呼び出し側の中断・最終検査の拒否）だけ解放する（`release`）。送出意図のある予約は DB が拒否する（`possibly_sent`）                                                                                                                                                                                                                                        |
| 追加予約（`topUp`）    | 同じ行の R と M を版の CAS で増やす（B05 の会話の延長が使う）。超過の承認で受け付けた予約は追加予約しない（ADR 0036）                                                                                                                                                                                                                                                                       |
| 再起動の照合           | 受付中（reserved）の予約のうち、送出意図のないものは解放し、あるもの（会話の接続を作ったもの、送出の記録がない 0001 の行を含む）は provider の照合の口（`UsageReconciler`）で usage が分かれば精算、分からなければ usage 不明にする（X28 の仕組み）。provider へ送り直さない。製品の照合の口はまだなく、送出意図のある予約は usage 不明として保持する（本人の手での精算を待つ。本人の判断） |
| 月替わりの知らせ       | 予算月が替わったとき・本人の確かめ直しで保留が解けたときに `onResumable` で知らせる（予算を待っている解析の再開に使う。B10 がつなぐ）。Core は 1 分ごとに予算月を確かめる                                                                                                                                                                                                                   |

Core は起動時に門を作り（`CoreHandle.budget`）、再起動の照合をしてから予算月を進めます。照合・月の失敗では起動を止めません（受付は DB の検査で閉じた側に倒れる）。

## 予算月の確かめ直し（承認を伴う操作）

時計の戻り（`clock_regressed`）と tz データの食い違い（`invalid_calendar_state`、U23）は有料の受付を止め、状態欄の予算保留に出します。本人は中枢のローカルの CLI で状態を見て、見た値を明示して確かめ直します。制御チャネルは OS の本人の利用者だけが使える（ソケットは 0600、データディレクトリは 0700）ので、これを承認の操作とします（端末の失効と同じ保守の手段）。画面からの操作はキャンバス UI の後です。

```text
buddy-core budget calendar status
buddy-core budget calendar confirm --reason calendar_mismatch --month 2030-10 --month-start 2030-09-30T15:00:00.000Z \
  --revision 0 --observed-at 2030-10-15T00:00:00.000Z
```

| 理由                                 | 確かめ直すこと                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `calendar_mismatch`（U23）           | tz データで求め直した始まりを、今の月の始まりにする。本人が渡した月と始まりが、今の月と求め直した値に一致し、前の月の始まりより後のときだけ記録する                                                                                                                                                                                                                                                                  |
| `clock_regressed`（U24、新しい判断） | 予算月を戻さず、今の月のまま受け付けを続ける。本人が status で見た時計（`checked_at`）を下限にし、下限よりさらに戻れば再び保留する。正しい時刻が次の月の始まりを越えれば普通に進む。誤って未来の月へ進んでいた間とその後の費用は、進んだ月に数える（記録の月を戻して数え直すと、予約の月を固定する規則と月ごとの記録を変える必要がある。進んだ月に数えれば少なく数えることはない）。本人の判断（2026-10-23）で確定。 |

要求には status で見た状態の版（`confirmation_revision`。記録した確かめ直しの件数）と時計（`checked_at`）も渡します。見た後に別の確かめ直しが記録された・今の時計が見た時計よりさらに戻った入力は古い入力（`confirmation_stale`）で、送り直しが新しい時計の戻りを承認しません。渡した値が今の状態と違う（`confirmation_mismatch`）、その理由で止まっていない（`nothing_to_confirm`）なら記録しません。保留が解ければ `onResumable` で知らせます。

## レビューの反映（PR #123、Codex P1 1 件・P2 5 件）

| 指摘                                                       | 直したこと                                                                                                                                                                                                                                                                                                                                                                      |

| P1: 最終判定の後に timer 用に読み直した時計が期限を過ぎても送る | 送る直前の時計は 1 回だけ読み、期限の判定と timer の残り時間に同じ値を使う（残りが 0 以下なら送らず usage 不明で保持）。timer と listener を用意する間に中断されたときも送らない。読むたびに進む時計で、残り 1 ミリ秒の読みで送り timer に 1 を渡すこと・残り 0 の読みで送らないことを確かめる |
| P2: 本人の LLM の経路が null だと自発の枠の制約が効かない       | 自発の LLM の経路があるのに本人の LLM の経路が null なら `autonomous_not_under_owner_pool` で拒否する（閉じた側）。契約の意味検査と domain の両方。schema-cases に拒否例 1 件、設定の試験に 1 件                                                                                               |

3 回目の確認（Codex、P1 の残り・P3）の反映: 送る直前の期限の判定を、準備（中断の controller・呼び出し側の中断の listener・timeout の timer）をすべて終えた後、`send()` を呼ぶ文の直前に移した。順番は「準備の前の判定（timer の残り時間はこの読み）→ 準備 → 時計を読む → 判定 → send」。最後の判定で期限に達した・呼び出し側が中断した・timer がすぐ発火したなら、準備を外して送らず usage 不明で保持する。timer は準備の前の読みで決めるので、準備にかかる時間だけ遅れて発火し得る。送る直前に読んだ時刻が期限以上なら送らない（同期の処理の間も実時間は進み、GC・OS の停止まで含めて時刻の確認と送信を不可分にはできないので、それ以上の保証はしない）。試験: 準備の途中で時計が期限に達する・呼び出し側が中断する・timer がすぐ発火する 3 つの場合で受信 0 件、準備の前は期限の 1 ミリ秒前でも send の直前が期限ちょうどなら送らない。

## 判断が要る点

- U24（時計が進んでから戻ったとき）: 本人の判断（2026-10-23）で、予算月を戻さず進んだ月のまま受け付ける形に確定した。費用を少なく数えることはないが、正しい月の予算が使われずに残る（進んだ月の上限で止まる）。予算月を戻して数え直す形を望むなら、予約の月の固定（ADR 0006）と月の記録（ADR 0036）の変更が要る。

## 残ること

- HTTP の 4 経路の処理（B07-05）。承認の期限の長さ、OS の確認ダイアログ。
- 実際のアダプター（LLM・検索・音声）を門につなぐこと（B05・B10 ほか）と、provider の usage の照合の口（再起動の照合で使う）。B04 の操作の送出意図（`operation.dispatch_intent` の reservation_id）と予約の送出意図をそろえる方法は、有料の操作ができるときに決める。
- デスクトップの状態欄の「予算保留」をスナップショットの `budget_hold` につなぐこと（表示はキャンバス UI。本人の判断）。
- クレジットの区分（B07-07）、実請求との照合（B15）。
- 送出意図の記録の成否が不明（DB worker の応答の喪失）のときは、送らず解放もしない。次の起動の照合が、記録があれば usage 不明、なければ解放にする。
