# ADR 0201: 気づきの根拠を許可範囲から取り直す（由来の位置の保存・connector への接続・「根拠を見る」）

- 日付: 2026-11-28

## 由来の位置を保存する形

今の保存で足りるかを調べた。

- 候補の由来の辺（`derivations`）は元情報の `remote_id` だけで、予定のカレンダー・接続・口座・取得集合を持たない。
- 元情報の行（`source_items`）は口座と取得集合を持つが、カレンダーの ID を持たない。さらに、行は取得から 24 時間の期限（`source_body`）で行ごと消える（`expiry-store`）。候補は閉じてから 97 日まで残る（U280）ので、`source_items` に列を足しても、根拠を取り直す時にはたいてい無い。
- 予定の ID は、招待された同じ予定なら別の口座のカレンダーでも同じになる。口座・接続を知らずにすべての接続を探すと、別の口座の写しを根拠にしてしまう（口座の付け替えも見分けられない）。

足りないので、候補の側に別の表を足した（U684）。

| 対象        | 決定                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 表          | `candidate_origin_locations`（0026）。候補と由来の元情報ごとに 1 行: 提供元・接続・口座・取得集合・資源の種類（calendar・mail）・カレンダーの ID（メールは空文字）・メールの引用の位置（件名か本文と、コードポイントの範囲。引用そのものは持たない）。本文・題・引用は持たない                                                                                                                |
| 書く時      | 候補の作成（`candidate.create`）と同じ transaction で、由来の辺の後に書く（`locations` は省略できる）。由来の辺のある元情報だけを受ける trigger、書いた後は変えない trigger。予定の重複の取り込みは、この接続・口座・取得集合と予定を読んだカレンダーを控える。メールの取り込みの入口は、口座を渡されたときだけ控え、引用の位置は抄録と同じ根拠（要約の根拠、無ければ最初の根拠）の位置を写す |
| 消える時    | 候補の行と一緒（97 日の掃除・忘却の削除。外部キーの `ON DELETE CASCADE`）。閉じた候補の題・抄録を消す時（7 日の掃除）も trigger で消す（閉じた候補の根拠は取り直さない）。元情報の期限（`source_items` の 24 時間）では消えない（由来の辺と同じ。U280）                                                                                                                                       |
| 0026 より前 | 位置を持たない候補は取り直さず、未確認のまま（期限・本人の操作で終わる）。推測で取り直し先を作らない                                                                                                                                                                                                                                                                                          |
| 分類        | 本文なし（`policy.ts` は `candidate_excerpt`・`analysis`）。バックアップに候補と一緒に含める（`backup-plan.ts`）。取り直すときは今の接続と照合するので、復元の後に接続が変わっていれば取り直さない                                                                                                                                                                                            |

カレンダーの ID は本人の口座のアドレスと同じことがある（主カレンダー）。接続の取得対象（`connections` の選んだカレンダー）がすでに同じ値を平文で持っているので、同じ扱いにした。寿命は候補の題・抄録と同じ（閉じてから 7 日）。

## 取り直し（Core）

`apps/core/src/candidate-evidence.ts` の `createCandidateEvidenceSource` が `fetchEvidence`（根拠の経路）と `checkEvidence`（保守）を作る。

| 対象               | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 許可範囲           | 控えた接続が今もあり（無い・切断済み・別の提供元は取得範囲外）、有効で取得対象が完全で、今の口座・取得集合（同期の対象 `targetsFor` と同じ出所）が控えたものと同じこと。口座の付け替え・取得集合の作り直し・その資源を読まなくなったときは取得範囲外。予定は控えたカレンダーが今も選ばれていること。要再認証・要対応・取得対象が読めない・口座の封筒を開けない・トークンが無いときは取り直せない（未確認）で、解決しない。外れたら読まない                                                                                        |
| 予定の重複         | 控えたカレンダーと予定の ID で `events.get`（connector に足した `getEvent`。本文・場所・参加者のアドレスは求めない）を 1 件ずつ読む。404・410・取り消し（cancelled）は削除（`removed`）。時刻付きの予定が取得の窓の外へ動いたら取得範囲外。読んだ予定から今の時刻・状態・出欠・空き時間の別で重複を求め直し（domain の `findScheduleOverlaps`・`notificationKey`）、候補の識別子と同じ重複があれば有効、無ければ重複の解消（`overlap_resolved`）。本人の持ち物（U550）は作ったときの判定を使う（U687）                            |
| メール             | 控えた口座で `messages.get` を読み、404 は削除。今も選んだラベルにあり受信が取得の窓の中（domain の `checkMailMessage`）でなければ取得範囲外。版（同期と同じ `historyId`）が候補を作ったときと違えば新しい版（`revised`）。有効なときの未読は候補を作ったときの完全性（`unread_partial`）。引用は、本文の作り方（`mailText`）を渡されたときだけ本文を読み（format full）、控えた位置を切り出す。位置が本文の外・空白だけなら入れない。製品では本文の作り方を渡さない（U683）ので、メールの引用は出さず、本文も読まない（minimal） |
| 引用（`sources`）  | 予定の重複は重なる予定ごとの題（`summary`。位置は 0 から題の長さ、題の無い予定は入れない）。メールは控えた位置の引用。照合できたものが無ければ空。引用は応答に載せるだけで、DB・ログ・main・画面の状態に残さない（画面は行を開いている間だけ）                                                                                                                                                                                                                                                                                    |
| 記録しない会話     | 間は何も読まず未確認（U680）。保守の再確認も読まない                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 本人のタイムゾーン | 読めなければ予定の重複を求め直せないので未確認。タイムゾーンが変わって識別子が変わった重複は解消になる（U549 の (a) と同じ）                                                                                                                                                                                                                                                                                                                                                                                                      |
| 状態の遷移         | 既存の規則のまま（ADR 0116・0130・0120）。有効: 200。新しい版: 状態を変えず 409（作り直し要・資格の失効）。取り直せない: 状態を変えず 503（未確認・保留・資格の失効）。取得範囲外・削除: 活動中なら `source_out_of_scope` で resolved（409）。重複の解消: `overlap_resolved`（409）。忘却の観測はここでは出ない（忘却は候補と取り直す先を消すので、その後の根拠の経路は 422）                                                                                                                                                     |
| 保守               | 一覧を開く前の保守（`candidate-list-refresh.ts`）に `checkEvidence` を渡す。前の再確認を始めてから 15 分空いた回だけ（U681。時計が戻ったら渡さない）。結果の扱いは ADR 0120 のまま（取得範囲外・削除・解消は resolved、それ以外は資格の失効を報告するだけ）                                                                                                                                                                                                                                                                       |
| 掃除のゲート       | 取り直しは保存しない読み取りだが、自動実行の読み直し（ADR 0150・0153）と同じく掃除のゲート（ADR 0053）を通す。掃除が済むまで読まず未確認にし、読む間は貸し出しを持つ（U688。`retention-entries.test.ts` の表に gated で載せた）                                                                                                                                                                                                                                                                                                   |
| 製品の配線         | `core.ts` は Google のトークンの口と同期の対象があるときだけ作り、根拠の経路と一覧の前の保守へ渡す。無い組み立ての根拠の経路は従来どおり 503                                                                                                                                                                                                                                                                                                                                                                                      |

U545 の「取得範囲外の resolved は作らない」は、予定の重複の取り込み（`calendar-candidate-intake.ts`）の回の判断で、変えていない。根拠の経路と一覧の前の保守は、控えた位置で取得範囲外を判定できるので resolved にする（U685）。

## 契約

- `CandidateEvidence.source`（1 つ）を `sources`（`SourceRef` の配列、0〜8 個）に変えた。予定の重複は 2 つの予定の題を示すので 1 つでは足りず、照合できないときに推測で埋めないため空も許す。根拠の経路は製品で 503 のままだった（使う側が無かった）ので、形を変えた。意味の検査（引用の範囲）は根拠の位置ごとに行う（`contract-tools.mjs`）。
- 端末の IPC に `desktop.candidate_evidence`（要求は `ref` だけ）と応答の `DesktopCandidateEvidenceView`（`ref`・`status`（confirmed・unconfirmed・changed）・`quotes`（引用だけ、8 個まで、1 つ 2000 文字まで）・`unread`・`excerpt`）を足した。候補 ID・元情報の ID・版・位置は画面へ渡さない。受付はロック解除済みの画面操作（前面）で、入出力の停止中も受け付ける（保存も外部への変更もしない）。チャネルは気づきの欄と同じ窓（従来の窓と状態の層）。
- fixture: `candidate-cases.json`（2 つの題・空の引用・旧形の `source` と 9 個の拒否）、`api-cases.json`（応答の形）、`desktop-ipc-cases.json`（受付 6 件）、`schema-cases.json`（要求・応答の許可と拒否 7 件）。
- `tests/test-map.json` は変えていない。設計 09 の写しが手元に無く、X・QA との対応を推測で足せないため（ADR 0132 と同じ）。

## 端末（apps/desktop）

- main の `CandidateBridge.evidence(ref)`: 参照から候補 ID を引き、`POST /v1/candidates/{candidate_id}/evidence` を接続範囲付きで送る。200 で形が正しく同じ候補の根拠なら confirmed（引用・未読・抄録）。409 は一覧を読み直して changed。422 は一覧を読み直して `entry_not_found`。503・結果が分からない・形の違う 2xx・別の候補の根拠は unconfirmed（ログはコードだけ）。ほかの拒否は `core_rejected`。ロック・切断をまたいだ根拠は渡さない。引用は main に持たない。
- 画面: 気づきの行に「根拠を見る」（状態を変えないので対応済みの行にも出す。結果待ちの行は出さない）。押すたびに取り直し、行の下に、確かめた根拠（引用・「元の情報の一部は未読です」・作ったときの抄録・「引用の位置は示せません」）、または「根拠を確かめられませんでした（未確認）」「根拠の元が変わったか、気づきの状態が変わりました（未確認）」を出す。未確認・変わったときは引用を出さない。閉じる・一覧から消える・ロックで引用を捨てる。別の行を開いた後の前の行の答えは反映しない。

## 残り

- Outlook（B09）: connector に 1 通を ID で読む口（本文・フォルダー）が無い。足すときにつなぐ（U682）。
- メールの引用の本文の作り方と版（U683）: 抽出を製品につなぐ（U546）ときに、抽出の入力と同じ本文の作り方を `mailText` に渡し、ラベルの変化（既読など）で変わらない版を決める。
- 本人の指定した再通知（スヌーズの終わり）の OS 通知（U587）: 根拠の経路ができたので、再通知の ID と一緒に配線できる。今回は配線していない。
- 予定の重複の取り込みの回の取得範囲外の resolved（U545）は変えていない。一覧の前の保守が控えた位置で判定する。
- 0026 より前に作った候補の位置の補い（作り直さないので未確認のまま）。
