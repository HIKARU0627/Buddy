# ADR 0061: B06-07b-1 系譜の読み方を全件読みから部分読みにする（U110・U143 の不合格への対応）

- 日付: 2026-11-01
- 状態: B06-07（Issue #143 の一部、親 #11）の 07b-1。`packages/domain/src/forget-plan.ts`（閉包を `computeForgetClosure` に切り出し）、`packages/storage/src/forget-store.ts`（`readForgetSubgraph` を足し、`readLineageEdges` の `RangeError` を直す）・`memory-store.ts`（`forget.graph` に `instruction_turn_id`）、`scripts/forget-lineage-benchmark.mjs`、模擬の試験だけ。マイグレーションは足していない。忘却の Core の経路（07b-2）・公開ゲートは未着手。実機の Mac mini・実データ・実 API・実請求は未実施。
- 根拠: ADR 0054（閉包の規則 A〜D、「U110 の実測」）、`docs/b00/contract-map.md` の U110・U143、本人の基準（2026-11-01 Q9: 1 年相当で `forget.apply` の保持 1 秒以内、10 倍で 5 秒以内、どちらもメインのイベントループ遅延 p99 50 ms 以内）。設計 03 は忘却の閉包の読み方・性能を決めていない（原本に決めなし）。
- 番号: ADR は 0061、未決事項は U156〜U158。マイグレーションは使っていない（0014 は予約のまま）。

## 判断

### 1. 部分読みの方式（U156）

忘却の起点（対象・「〇〇を忘れて」の発言）から、**閉包に触れる辺・範囲だけを索引で辿る**。方式は、domain の閉包の関数を storage の読み出しの決定に使う反復にした。

| 案                                              | 採否     | 理由                                                                                                                                                            |
| ----------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 起点から閉包に触れる辺だけを索引で辿る（反復）  | 採用     | main に渡す系譜・main の計画・worker の transaction の読みが、すべて閉包の大きさに比例する。件数（辺 50 万）に依らない。閉包の意味は domain の 1 つの関数のまま |
| ページ分けして worker の中で閉包を作る          | 不採用   | 読みは全件のまま。transaction の保持が件数に比例して伸びる（10 倍で 1.7 秒超）。閉包を worker 側に作り直すので domain の計画と二重になる                        |
| worker の中で計画と照合し、差分だけ main へ返す | 不採用   | 適用の transaction の全件読みが残る。main の負荷は下がるが、基準の「保持」を満たす保証がない                                                                    |
| 索引を足す（マイグレーション 0014）             | 今は不要 | 索引なしで基準を大きく下回った。0013 が main になく、0014 だけでは版の連続の検査（`checkMigrationSequence`）で DB を開けない。大きい閉包では効く見込み（U158）  |

**手順**（`readForgetSubgraph`）: 今読んだ辺・未帰属の一覧・会話の発言で、domain の `computeForgetClosure`（計画と同じ関数）を求める。閉包に入った節点について、足りない辺を足して読む。足すものがなくなったら（固定点）終わる。

- 規則 A・C: 消す物と除外する由来（origins）を**由来にする辺**（`LINEAGE_EDGE_TABLES` の 3 表。`derivations` と `user_directives.turn_id` は索引、`memory_sources` は主キーの索引の走査）。
- 規則 B: 忘れる記憶（core）の**由来の辺**。
- 規則 D: 閉包の発言が属する会話の要約と、その発言を入力にした影モードの記録のうち、由来の辺を持たないもの（未帰属）と、その会話の全発言（`turn_sessions`）。
- 残す操作の由来の探索（`provenanceOf`）: 消える操作の確定内容の**上流**（由来の辺と、未帰属の範囲の構成要素）。
- 記憶（対象と消える記憶）の内容の HMAC と、辺に出る操作の状態。

`forget.graph`（Core が計画を作る読み）と `forget.apply`（transaction の中の照合）は同じ関数を使う。`forget.graph` に **`instruction_turn_id`**（省略可）を足した。指示の発言は閉包の起点なので、計画に渡す値と同じものを渡す。違うと適用が `forget_plan_stale` で拒否される（安全側。試験あり）。

### 2. 閉包の意味を変えないこと

部分読みで作った計画は、全件読み（`readForgetGraph`）で作った計画と**同じ**になる。根拠:

- 閉包の規則は変えていない。`planForget` の閉包の部分を `computeForgetClosure` に切り出しただけで、既存の試験（fixture）は変更なしで通る。
- 部分読みは、全件読みの辺・未帰属の部分列を渡す（U157 の修正で閉包は並びに依らなくなった）。読んでいない辺は、全件読みの閉包の途中で一度も働かない（働く辺は、そのときの閉包の節点を由来にするか、core の記憶の由来であり、固定点まで読むので漏れない）。したがって両者は同じ手順をたどる。
- **性質試験**（`packages/storage/src/forget-subgraph.test.ts`）: 手書きの種で 16 の合成の世界（発言・会話・記憶・元情報・操作 6 状態・影モード・本人の指示・合流・循環・由来の行のない記憶・由来の辺を持たない要約と影モード）を 1 つの DB に積み、すべての発言・記憶・元情報を対象に、指示の発言なしと 1 つありで、部分読みの計画と全件読みの計画が一致することを 672 通りで確かめる。部分読みの辺が全件読みの辺の部分集合であることも確かめる。世界が規則を通っていること（拒否 32・広がり 536・除外する由来 468・指示 414・残す操作 254・暗号文を消す操作 131・共有する範囲 502）を件数で確かめ、一致が自明な世界だけではないことを保証する。
- **試験の弱さの確認**: 部分読みに変異を入れると試験が落ちる。発言の範囲を読まない、core の記憶の由来を読まない、残す操作の上流を読まない、のそれぞれで落ちた（確かめた後に戻した）。閉包の規則 D を旧い形（先に消えた要約を飛ばす）に戻すと、U157 の最小の例と並びを入れ替える性質試験が落ちる。
- 無関係な辺 5 万があっても、手で組んだ系譜（元情報 → 記憶 → 気づき → つないだ要約）で触る辺は手で数えた 3 本だけ。

**全件読みとの違い（閉包の意味ではなく入力の検査）**: 全件読みは、閉包に触れない行の検査（知らない種類の辺・全記憶の内容の HMAC の形）でも拒否していた。種類は DB の CHECK が守る。記憶の内容の HMAC は `length = 64` だけが CHECK で、16 進の形は検査していないので、壊れた無関係な記憶があると全件読みでは全ての忘却が拒否されたが、部分読みでは触れる記憶の検査だけが効く。無関係な壊れた行で忘却が止まらなくなる側の変更で、触れた行の検査は同じ。

### 3. 閉包の規則 D の辺の並びへの依存（U157。修正済み）

性質試験が見つけた。旧い `computeForgetClosure` の規則 D は、範囲（会話）の要約を、**先に**「範囲の発言が除外する由来に触れる」側（第 2 分岐。core に上げず、範囲を広げない）で消すと、**後から**範囲の発言が core になっても、要約が消す物なので第 1 分岐（範囲全体を除外する由来にする）に入らなかった（`doomed.has → continue`）。同じ辺の集合でも、辺の並びで、除外する由来（＝再登録を禁じる発言）が変わりうる。手で組んだ最小の例（`forget-subgraph.test.ts`）: 記憶 X が発言 B から、X → 発言 T1 → 発言 C の 2 段で、C が要約を持つ会話 {A, B, C} に属し、辺の並びで C ← T1 が T1 ← X より先にあると、1 巡目で B が除外する由来になって要約が消える物になり、2 巡目で C が core になっても A は除外されなかった。

- **本人の決定（2026-11-01）: 直す。この PR で修正**（部分読みの PR（#186）のマージ後）。規則 D の先頭で「もう消える物なら飛ばす」のをやめ、範囲が忘れる物（core）に触れるなら、**すでに消える物になった要約も** core に上げ、範囲の全発言を除外する由来にする。固定点までのループなので、辺・未帰属の並びに依らない。**除外が増える方向（再登録を禁じる元の発言が増え、それを共有する派生物がさらに消える）で、閉包の意味が変わる**。
- 最小の例の期待値: 直す前は除外する由来が B だけ、直した後は A と B（`blocked_source_hmacs` が 1 件増える）。消す物は変わらない。
- 並びに依らなくなったので、`readForgetSubgraph` が部分読みの辺・未帰属を全件読みと同じ並びにそろえる処理（`snapshot` の並べ替えと `LineageEdgeRow.part`）は外した。部分読みと全件読みが一致することは、乱択の世界で辺・未帰属・会話の発言を入れ替える性質試験で確かめる。

### 4. `readLineageEdges` の `RangeError`（U143）

`rows.push(...全件)` は、1 つの表が約 12 万行を超えると、引数の数の上限で `RangeError: Maximum call stack size exceeded` になった（Node.js v24.19.0 の素の関数で、10 万行は通り 12.5 万行で失敗した。呼び出しが深いほど少ない）。行を 1 件ずつ足す形に直した。試験: 1 つの表に 20 万行を入れ、全件読みが通ること。部分読みは節点を種類ごとにまとめ、ID を 400 件ずつ `IN` で引く（変数の数の上限を超えない）。

### 5. 索引（マイグレーション）は使わなかった

索引なしで基準を満たしたので、0014 は使っていない。`memory_sources (source_kind, source_id)`・`user_directives (turn_id)`・`turns (session_id)`・`input_snapshots (turn_id)`・`intent_shadow (input_id, request_revision)` には索引がなく、部分読みはこれらを走査する。0013 が main にないため、0014 だけを足すと版の連続の検査で DB を開けない。大きい閉包では下の実測のとおり表の大きさにも比例する。要否は U158。

## 実測（2026-11-01、Windows の模擬。Mac mini の実機は未実施で B15）

環境と道具は ADR 0054 の「U110 の実測」と同じ（`scripts/forget-lineage-benchmark.mjs`。Windows 10.0.26300・Ryzen 7 7800X3D 16 論理・31.2 GB・Node.js v24.19.0・better-sqlite3 13.0.3）。合成データの形（1 記憶あたり 25 辺、閉包は 1 記憶の下流だけで約 24 節点）も同じ。判定に「部分読みの計画が全件読みの計画と一致」を足した。

| 規模                                    | 部分読みの辺 / 閉包の節点 | 部分読み（同じプロセス） | `planForget` | 適用 `forget.apply` の transaction | 適用の往復（worker） | 忘却 1 回の流れ | メインのイベントループ p99 / 最大      | 判定               |
| --------------------------------------- | ------------------------- | ------------------------ | ------------ | ---------------------------------- | -------------------- | --------------- | -------------------------------------- | ------------------ |
| 1 年相当（記憶 2,000・辺 5 万）         | 25 / 24                   | 4.4 ms                   | 0.2 ms       | **10.4 ms**（基準 1,000 ms 内）    | 20.8 ms              | 24.9 ms         | **20.3 ms / 20.3 ms**（基準 50 ms 内） | 合格               |
| 10 倍（記憶 2 万・辺 50 万）            | 25 / 24                   | 34.7 ms                  | 0.2 ms       | **47 ms**（基準 5,000 ms 内）      | 42.8 ms              | 68.3 ms         | **20.8 ms / 20.8 ms**（基準 50 ms 内） | 合格               |
| 参考: 1 年相当・元情報を 100 記憶で共有 | 2,104 / 2,004             | 35.5 ms                  | 6.5 ms       | 502.4 ms                           | 389.7 ms             | 464.5 ms        | 19.3 ms / 21.6 ms                      | 1 年相当の基準の内 |
| 参考: 10 倍・元情報を 100 記憶で共有    | 2,104 / 2,004             | 71 ms                    | 6.9 ms       | 1,730.4 ms                         | 1,724.5 ms           | 1,839.1 ms      | 21.5 ms / 25.8 ms                      | 10 倍の基準の内    |

- 何もしないときの床は p99 16.1〜16.5 ms（Windows のタイマーの粒度。ADR 0054 と同じ）。基準の判定は、忘却 1 回の流れ（系譜の読み → 計画 → 適用）の区間の p99 と、同じ区間の最大を併記した。どの規模でも最大が基準（50 ms）の内。
- 前の全件読み（ADR 0054）: 1 年相当は適用 120.6 ms・p99 146.1 ms（不合格）、10 倍は main で `RangeError`・最大停止 1,480.6 ms（不合格）。
- ばらつき（実行 2 回）: 1 年相当の適用は 10.4〜12.6 ms・p99 20.3〜21.0 ms、10 倍の適用は 47〜62 ms・p99 19.5〜20.8 ms。
- main に渡す系譜が閉包の大きさ（25 辺）になったので、構造化複製と `planForget` の止まりは床に埋もれる。参考の共有する規模（閉包 2,004 節点）でも p99 は床と同じ。
- **大きい閉包は適用の transaction が節点の数と表の大きさに比例する**: 同じ閉包（2,004 節点）で、表が 10 倍になると 502 ms → 1,730 ms。節点ごとの整理（`pruneDeadLineage` の下流の探索）が `memory_sources` と `user_directives` を走査するためと見ている（未検証。索引で確かめる）。10 倍の表で閉包が約 6,000 節点を超えると 5 秒の基準を超える見込み。本人の基準の形（1 記憶 ≒ 24 節点）では起きない。1 つの元情報を非常に多くの記憶が共有する系譜は、実データの形が分かった後に測り直す（U158）。

## 原本に決めがない項目

| 項目                                                | この ADR の扱い                                                                                          | 記録 |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---- |
| 系譜の部分読みの方式                                | 起点から閉包に触れる辺・範囲を、domain の閉包の関数で決めながら読む。意味は全件読みと同じ（性質試験）    | U156 |
| 閉包の規則 D の辺の並びへの依存                     | 直した（規則 D を、すでに消える物になった要約にも適用する）。本人が 2026-11-01 に決定。この PR で修正    | U157 |
| 索引（マイグレーション 0014）と大きい閉包の適用時間 | 今は足さない。基準の形では 10 ms 台〜60 ms。閉包が数千節点になる系譜は実データの形が分かった後に測り直す | U158 |

## 試験（模擬だけ）

- `packages/storage/src/forget-subgraph.test.ts`（7 件）: 乱択の合成の世界で部分読みの計画が全件読みと一致（672 通り）。無関係な辺 5 万があっても触る辺が 3 本。規則 D が並びに依らないこと（最小の例で A と B を除外する手で導いた期待値と、乱択の世界で辺・未帰属・会話の発言を入れ替えても全件読み・部分読みの計画が同じになる性質試験）。20 万行で全件読みが `RangeError` にならない。指示の発言なしで読んだ系譜から作った計画は `forget_plan_stale`。共有の手書きの世界（`seedWorld`）の全ノードで一致。
- 既存の試験（`forget-store.test.ts`・`memory-lineage.test.ts`・`derivation-lineage.test.ts` ほか）は、`forget.graph` に指示の発言を渡すよう `planFor` を直した以外は変更なしで通る。
- **実機・実 API・実請求は未実施**。`tests/test-map.json` は変えない（性能は X/QA のケースではない。X15・X16・X17・X44・X59・QA34 の `product_test` は `not_run` のまま）。

## 引き継ぎ

- **07b-2**: Core の忘却の経路は、`forget.graph` に計画へ渡すのと同じ `instruction_turn_id` を渡す。返った系譜を `planForget` に渡す（全件読みを要求しない）。
- **U157（修正済み。本人が 2026-11-01 に決定。この PR で修正）**: 規則 D を並びに依らない形に直した。閉包の意味が変わる（除外が増える側）ので、ADR と `forget-plan-cases.json` の新しいケースを一緒に更新した。部分読みの並びをそろえる処理は外した。
- **U158**: 閉包が数千節点になる系譜を測り直す。要るなら索引のマイグレーション（0013 の予約者のマージ後の 0014）。
