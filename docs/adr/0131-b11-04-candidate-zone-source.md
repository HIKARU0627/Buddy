# ADR 0131: B11-04 本人のタイムゾーンの出所（端末（OS）のタイムゾーン）

- 日付: 2026-11-21
- 状態: B11-04（親 #23、Issue #271）の残件。**本人のタイムゾーンの出所は端末（OS）のタイムゾーン（本人の決定、2026-11-21）**。ADR 0130 の残件（本人の IANA タイムゾーンの出所）を解決し、製品の配線（`apps/core/src/core.ts` の候補の経路）で `zone` を開いた。根拠を取り直す実 connector（B08・B09）、画面（B11-05）は未着手。実機は未実施。
- 根拠: 本人の決定（2026-11-21）、ADR 0130（候補の経路。zone の出所が決まるまで 503 で閉じた）、ADR 0037・`apps/core/src/budget-config.ts`（予算での OS のタイムゾーンの読み取りと正規化の流儀）。
- 対象: `apps/core/src/device-time-zone.ts`（新設）、`apps/core/src/core.ts`（候補の経路の `zone` の配線）、`apps/core/src/device-time-zone.test.ts`（新設）。契約・domain・保存は変えない。検証は domain の `normalizeTimeZone` をそのまま使う。

## 決めたこと

| 対象             | 決定                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 出所             | 中枢の端末（OS）のタイムゾーン。`Intl.DateTimeFormat().resolvedOptions().timeZone` で読む（予算の `defaultOsTimeZone` と同じ方法）。予算の設定の `timeZone` は予算月の用途のまま流用しない（意味を変えない）                                                                                                                                         |
| 読む時点         | 要求ごとに読み直す（起動時に固定しない）。候補の経路の処理は要求のたびに `zone()` を呼ぶので、配線は `zone: () => deviceTimeZone()` とし、OS の設定の変更をそのまま反映する                                                                                                                                                                          |
| 検証             | domain の `normalizeTimeZone` で検証・正規化する（予算と同じ。Etc/\* は拒否、旧別名は正規の名前にする）。正規化した名前を本人のタイムゾーンとして使う                                                                                                                                                                                                |
| 読めない・不正   | `deviceTimeZone()` は null を返し、候補の経路は ADR 0130 の扱いのまま 503 で閉じる。UTC や予算月のタイムゾーンで黙って代替しない                                                                                                                                                                                                                     |
| 明示設定の上書き | 将来、明示設定で上書きする余地は残す（本人の決定）。今回は設定を作らず、「設定があれば優先」の配線もしない                                                                                                                                                                                                                                           |
| 差し替えの範囲   | 製品の配線で zone の出所を必要とするのは候補の経路（`createCandidateRoutes`）だけだったので、そこだけを差し替えた。候補の生成・保守（`candidate-intake.ts`・`candidate-maintenance.ts`）は製品の呼び出し側がまだ無く（試験だけが呼ぶ）、差し替え対象が無い。将来、製品の呼び出し側を配線するときは、同じ `deviceTimeZone()` を要求ごとに評価して渡す |
| 根拠の経路       | `fetchEvidence` は B08・B09 の connector が担当で、今回も渡さない。根拠の再取得の経路は、zone が開いても引き続き 503（ポートが無いため）                                                                                                                                                                                                             |

## 試験（模擬だけ）

- `apps/core/src/device-time-zone.test.ts`（8 件）: 読み取りを差し替えて確かめる。正規の名前（Asia/Tokyo）はそのまま、旧別名（Japan）は Asia/Tokyo に正規化、読めない（undefined）・読み取りの例外・存在しない名前（Mars/Olympus）・Etc/\*（Etc/GMT+9）は null、読み取りの返す値が変われば結果も変わる（要求ごとに読み直す）。既定の読み取りは `process.env.TZ` を差し替えて確かめる（Asia/Tokyo → Asia/Tokyo、Invalid/Zone → null。TZ は試験の前後で元に戻す）。期待値は手で書いた。

**模擬の期待値だけ**。実機（macOS・Windows）での OS のタイムゾーンの読み取り、候補の経路を HTTPS で通した確認は未実施で、合格扱いにしない。

## 残ること
