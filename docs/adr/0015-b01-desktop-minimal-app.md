# ADR 0015: デスクトップの最小アプリ（トレイ常駐・端末状態の記録）

- 日付: 2026-10-20
- 状態: B01-04（#46）の判断と実装。`apps/desktop`（`@buddy/desktop`）に Electron の main・preload・React / Vite の UI レンダラーを作り、開発起動までを用意した。試験は main の純粋なモジュールの node:test（CI の 3 OS）で、Electron 本体は CI で起動しない。実機（Windows / macOS）でのロック・スリープの確認は B01-05 で行う。
- 根拠: 設計 02 処理の配置・技術比較と結論・停止、10 §1・§1A、07 §2・§5、01 いつも見える状態・停止・取消・終了。Electron・React・Vite を着手時点の最新安定版で固定することと、B01 では Core に接続せず開発起動までとすることは本人の決定（ADR 0012）、IPC の契約は ADR 0014、起動直後の扱いと io_epoch の保存は司令塔の決定（2026-10-20）に従う。原本の参照手順は docs/design/README.md。

## 決めたこと

| 対象             | 決定                                                                                                                                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| プロセスの分け方 | main（端末状態・トレイ・限定 IPC の受付・保存）、preload（限定 API の公開だけ）、UI レンダラー（画面だけ）。音声レンダラーは B05。B01 の main は中枢に接続せず、端末トークンも持たない                                                                      |
| main の内部      | Electron を import しない純粋なモジュール（`src/main/*.ts`）と、Electron に依存する薄いアダプター（`src/main/electron/main.ts`）に分ける。判断はすべて純粋なモジュールに置き、node:test で試験する                                                          |
| 受付の順         | Ajv で `DesktopIpcRequest` を検査 → Electron のチャネルと要求の channel の一致 → domain の `admitDesktopRequest` → `nextDesktopIoState` → 保存 → 応答・通知・状態欄を schema と意味検査に通してから送る。自分の応答が契約に反すれば送らずに例外にする       |
| 画面の読み込み   | 特権スキーム `buddy://app/` を登録し、ビルド済みの `dist/renderer` の中のファイルだけを返す（file:// と http の画面を使わない）。応答に Content-Security-Policy を付け、画面の meta にも同じ方針を書く                                                      |
| 安全な設定       | すべてのレンダラーを sandbox（`app.enableSandbox()`）、contextIsolation 有効、nodeIntegration 無効、webview 無効。画面内の遷移はアプリの画面だけ、新しいウィンドウはすべて拒否し、https のリンクだけを通常のブラウザーへ渡す。権限の要求はすべて拒否        |
| 送信元の検査     | 送信元の webContents が main の作った UI レンダラーで、主フレーム（親なし・同じ processId / routingId）で、URL がアプリのスキームのときだけ trustedSender とする。画面操作は「ウィンドウが表示中・最小化でない・前面」                                      |
| トレイ           | ウィンドウを閉じる操作はウィンドウを隠してトレイに残す。トレイのメニューは「Buddy を表示」「この端末の入出力を停止」「クライアントを終了（中枢は止めません）」だけで、再開（画面操作だけ）と中枢の停止は置かない                                            |
| 単一起動         | 同じ userData の保存を二つのクライアントで書かないよう、`requestSingleInstanceLock` で二つ目の起動は既存のウィンドウを出して終わる                                                                                                                          |
| 開発起動         | `pnpm --filter @buddy/desktop dev` で依存のワークスペースと desktop をビルドしてから `electron .` を起動する。Vite の開発サーバー（HMR）は使わない（インラインのスクリプトを許す CSP と http の画面を避けるため）。インストーラー・署名・自動更新は作らない |

## 起動直後と保存（司令塔の決定 1・2）

- **起動直後**: ロック状態を `unknown`、停止の範囲を前回の保存値（なければ `none`）とし、入出力を許可しません。状態欄は内容を隠します。main は起動時・スリープからの復帰後・ロック状態が解除済みでないときにウィンドウが前面に来たときに、`powerMonitor.getSystemIdleState(60)` で OS へ問い合わせます。macOS・Windows で `locked` なら `lock_screen`、`active` / `idle` なら `unlock_screen` として、`source: os_query` で記録してから規則どおりに遷移します。それ以外の OS と `unknown` は何も変えません（解除済みと扱わない）。同じ結果の問い合わせはロック状態が変わらないので記録しません。`unlock-screen` の OS の通知でも解除を確かめます。
- **保存**: io_epoch とこの端末の停止の範囲（`none` / `local`）だけを、Electron の userData 配下の `device-io-state.json` に置きます（例 `{"io_epoch":"7","stop_scope":"local"}`。秘密・本文・端末 ID を含めない）。両方のどちらかが変わったときに、一時ファイル → fsync → rename（macOS / Linux はディレクトリも fsync）で同期して書き、書き終えてから通知・応答を送ります。保存に失敗しても状態の変更（停止）は戻さず、記録だけ残します。
- **壊れた保存**: 読めない・UTF-8 でない・4 KiB 超・JSON でない・項目がちょうど `io_epoch` と `stop_scope` でない・値が範囲外のときは、停止中（`local`）とし、io_epoch を「現在の UTC ミリ秒」と「読み取れた io_epoch + 1」の大きい方にして、その値ですぐに保存し直します。io_epoch は停止のたびに 1 ずつ進むため、通常の利用でミリ秒の値に届くことはなく、保存値より小さい世代へ巻き戻りません。黙って許可状態には戻さず、画面の「この端末で再開する」で再開します。
- 来客モード・全体停止は中枢が正本なので保存しません（B01 では起こりません）。

## 電源・ロックの記録

- `lock-screen`・`unlock-screen`・`suspend`・`resume`・`shutdown` を `source: os_event` で記録し、規則（ADR 0014）どおりに遷移します。ロック・スリープ・シャットダウンではこの端末を止め、解除・復帰では自動で再開しません。
- 記録は main が直近 100 件を持ち、画面の読み込みが終わったときにまとめて送ってから現在の状態欄を送ります（読み込み前の記録を失わないため）。記録の通知で、停止・再開の命令ではありません。
- 画面は状態欄が表示できるとき（ロック解除済み）だけ記録の一覧を描画し、ロック中・不明では描画しません。会話・候補などの内容の欄は「この端末で再開する」まで受付・表示を再開しない旨を出します（内容は B02 以降）。

## CI の負荷と pnpm の build スクリプト

- Electron 44 の npm パッケージには install 時のスクリプトがなく、バイナリは `electron` を初めて実行したとき（`index.js` の読み込み時）に取得されます。そのため `pnpm install --frozen-lockfile` と CI の `pnpm run check` では Electron のバイナリを取得しません。
- 今回の依存に build スクリプトを持つものはなく、pnpm 12 の `allowBuilds`（build スクリプトの許可の一覧）の設定は不要でした。ルートの package.json・pnpm-workspace.yaml の build 設定は変えていません。
- CI に足したのは desktop の型検査・tsc・`vite build`（数秒）と、純粋なモジュールの試験です。試験は Electron を import しないモジュールだけを読み込むので（lint で強制）、試験からバイナリの取得は起きません。CI の設定（.github/workflows/ci.yml）の変更は不要です。
- ローカルの開発起動では、初回の `electron .` で約 100 MB のバイナリを GitHub から取得し、OS のキャッシュ（macOS `~/Library/Caches/electron`、Windows `%LOCALAPPDATA%\electron\Cache`）に置きます。取得に失敗した場合は `apps/desktop` で `pnpm exec install-electron` を実行します。

## 読み取り（レビュー対象）

原本に明記がなく、実装で決めた点です。

- **Electron の版**: 本人の決定は「着手時点の最新安定版」ですが、最新の 44.9.1 は当日公開で pnpm 12 の既定の方針（公開から一定期間たっていない版を拒否する）に掛かりました。除外の設定を足すと供給網の検査を弱めるため、方針を満たす最新の 44.9.0 にしました。44.9.1 へ上げる場合は、公開から期間がたってから `electron` の版だけを更新します。
- **schema の読み込み**: `@buddy/contracts` の公開出口は型だけで、schema の JSON を出口にしていません。main は公開出口（`dist/index.js`）を `import.meta.resolve` で解決し、そこから `../schemas/buddy.schema.json` を読みます（別ワークスペースの src は参照しない）。contracts に schema の出口を足すかは後続で判断します。
- **意味検査の重複**: 状態欄・応答・通知の意味検査は scripts/contract-tools.mjs の semanticErrors と同じ意味を desktop に持ちます（scripts を import しないため）。片方だけを変えないよう、両方の試験に同じ意味の例を置いています。
- **トレイからの停止**: トレイの「この端末の入出力を停止」は main の中の本人の操作として、IPC を通さずに停止します（停止は安全側の操作のため）。再開はトレイに置かず、画面のボタンだけです。
- **画面が自分で閉じた場合**: 画面のスクリプトの `window.close()` は Electron ではウィンドウの close の処理を通らずにウィンドウが閉じます。クライアントはトレイに残り、トレイの「Buddy を表示」でウィンドウを作り直します（ローカルの開発起動で確認）。
- **OS への問い合わせの範囲**: `getSystemIdleState` の `locked` は macOS・Windows だけを信頼し、Linux などでは問い合わせの結果を使いません（ロック状態は unknown のまま）。設計の対象は Windows / macOS のクライアントです。
- **OS の終了**: Windows には powerMonitor の `shutdown` がないため、OS の終了はクライアントの終了（`before-quit`）として扱います。停止の保存は停止の時点で済んでいるので、終了の時点で書き足すものはありません。
- **userData の場所**: `productName` を `Buddy Desktop` にし、Core のデータディレクトリ（`Buddy/core`。ADR 0012）と分けました。

## 残ること

- インストーラー・コード署名・公証・自動更新・配布（後の工程）。
- 音声レンダラーと、その限定 IPC（B05）。UI レンダラーはマイク・WebRTC を持たないまま。
- 中枢との接続・端末登録・端末トークン（main だけが持つ）・来客モードと全体停止の解除（B03）。
- 実機（Windows / macOS）でのロック・解除・スリープ・復帰・トレイの確認と記録（B01-05）。今回のローカルの開発起動は macOS で、ロックとスリープの実操作は行っていません。
