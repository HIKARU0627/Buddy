# ADR 0198: B13-05 自動で作った予定の取り消しの経路（予定の削除）と、状態欄の安全停止の知らせ

- 日付: 2026-11-28
- 状態: B13（親 #24）の残り 2 つ。(1) U310 のうち予定の補償の経路を作ったが、本人の決定が無いので製品では閉じたまま（`unavailable`）。(2) U315 を (c)（Core から端末への知らせ）で作り、状態欄に安全停止を出す。**模擬・同じプロセスの統合試験だけ**で、Electron の画面の実機確認・実データ・実 API（Google Calendar・Microsoft）は未実施。
- 根拠: 設計 01（いつも見える状態）、設計 03「取り消しと安全停止」（予定の取り消しは作成物の削除）、J12、設計 07 §2、設計 08 §3・§9、設計 11 §6（本人が手を加えた作成物）、ADR 0146・0147（判定表の `create_event` と `event.create_own`）、0153・0154・0155・0156・0157・0187・0196。非公開の原本（設計 01・03・11、J12）はこの環境に無く、原本の本文は読んでいない。決めの無い点は ADR と contract-map の記述から暫定で決め、U620〜U629 に記録した。
- 対象: 契約（`OperationKind`・`OperationStepKind`・`CalendarEventCreateOperationIntent`・`CalendarEventDeleteOperationIntent`・`SafetyNotice`、`EventStreamMessage` の `notice`、OpenAPI の説明）、`packages/domain`（種類の表・自動実行の種類）、`packages/storage`（取り消しだけの種類・工程・`onSafetyWrite`）、`apps/core`（`turn-ports.ts`・`operation-runner.ts`・`api-auto-actions.ts`・`safety-notices.ts`・`notice-relay.ts`・`core.ts`）、`apps/desktop`（`auto-action-bridge.ts`・`core-link.ts`・`status-bar.ts`・文言）。マイグレーションは足さない。気づき（candidate）の配線・画面には触れていない。

## 1. 予定の取り消し（U310 の予定）

### 背景

ADR 0153 は、契約に予定の削除の種類が無いので、自動で作った予定を取り消せない（`unavailable`）と見せた（暫定 (b)）。下書き（ADR 0156）と用事（ADR 0157）は本人の決定で (a) にした。さらに、自分だけの予定の作成は操作の種類がまだ無く、自動実行の一覧に載らなかった（ADR 0147:「予定の書込みを足すときに `create_event` を対応表へ加える」）。

### 本人の決定の記録の読み方（製品で開くか）

ADR 0156 は「本人に確かめ、下書きについては削除を足すと決まった」、ADR 0157 は「本人に確かめ、用事も削除で取り消すと決まった」と書き、どちらも状態の欄に「予定は ADR 0153 の暫定 (b) のまま」と書いている。決定は種類ごとに本人に確かめて出ており、「予定も同じに」とは読めない。そこで経路は作るが、製品では閉じる（`CALENDAR_EVENT_UNDO_OPEN = false`）。**U310 の予定は本人の決定待ち**。

### 決めたこと

| 対象               | 決定                                                                                                                                                                                                                                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作成の種類         | `calendar.event.create`（RemoteMutation、工程 `create_event`、照合 `operation_marker`）。参加者のいない自分だけの予定（参加者がいれば従来の `calendar.event.create_with_attendees`）。`target` は null、`external_recipients` は空。判定表の `create_event`（方針 `event.create_own`）に当たり、自動承認の対応表に加えた（U625）         |
| 作成の実行         | 実行担当の送出と、候補からの予定の自動作成の配線はまだ無い（気づきの配線は別の作業が触るので触れない）。製品では誰もこの種類を作らないので、自動実行の一覧に予定は載らない                                                                                                                                                               |
| 削除の種類         | `calendar.event.delete`（RemoteMutation、工程 `delete_event`、照合 `exact_target`・`by_remote_id`、前提は `conditional_request` と `recheck_before_dispatch`）。target は予定の id と押下のときに読んだ版、action はカレンダーと予定を作った操作と内容版（`created_by`）。`created_by` が自分自身なら意味検査の誤り（`created_by_self`） |
| 使える場面         | 自動実行の取り消しの補償だけ。取り消しに結び付かない作成は保存層が `undo_only_kind` で拒否する（下書き・用事と同じ一覧）。方針の自動承認では作らない。ADR 0075 の「完全削除の種類を作らない」は、取り消しの 3 つの種類だけを除いて続く                                                                                                   |
| 取り消しの押下の時 | 元の操作の作成物の id（試行の `external_id`）とカレンダーで予定を読む。取り消されておらず、目印（`buddy-op:<操作>:<内容版>`）・カレンダー・題・開始・終了・タイムゾーンが保存した内容と同じで、参加者がいない・繰り返しでない・場所と説明が空のときだけ補償を作る（U620〜U622）。違えば 409 `target_changed` で消さない                  |
| 送る直前           | 実行担当が予定をもう一度読み、取り消されていない・目印とカレンダーが同じ・版が押下の時と同じ・参加者がいない・繰り返しでない・許可の版が同じことを確かめる。違えば送らず準備のまま残す（U317 と同じ扱い。内容版は上げない）                                                                                                              |
| 送り方             | 版を条件にした削除を 1 回だけ送る（Google では If-Match を想定。実 API は未確認）。版が違う・無いは相手が断り、未実行として記録する。参加者がいないので相手への取り消しの知らせは無い                                                                                                                                                    |
| 結果不明           | 1 回だけ予定を id で読む。無い・取り消し済み（`cancelled`）なら消えた（成功）、残っていれば `unknown_held` で止める。自動では送り直さない。以後は本人の照合（U623）                                                                                                                                                                      |
| 安全停止の間       | 押下は受け付けて補償を作るが、送出の直前の門（`commandGuard` の `safety_stopped`）で送らず準備のまま残る（ADR 0153・U313 の「安全停止の間は補償の送出も止まる」のまま）                                                                                                                                                                  |
| 製品で閉じる方法   | `CALENDAR_EVENT_UNDO_OPEN = false`（`apps/core/src/api-auto-actions.ts`）。閉じている間は一覧で予定の行を `unavailable` にし、押下は提供元を読まずに 409 `conflict`。試験の組み立てだけが `CoreTurnOptions.calendarEventUndo` で開く。開いていても、提供元が予定を id で読めなければ取り消せるように見せない                             |
| 端末               | 取り消せる予定の行に「取り消すと、Buddy が作った予定を削除します。」と添える（製品では取り消せる行が出ないので、開いたときのための文言）。操作の一覧の見出しは「自動で作った予定の削除」、種類の名前は「予定の削除」                                                                                                                     |
| 提供元の口         | `ProviderReader.readEvent`（予定の中身。参加者は数だけ）と `ProviderWriter.deleteEvent`（版つき）を任意の口として足した。模擬の提供元（`packages/connectors`）と Google Calendar のアダプターにはまだ書込みが無い（読み取りだけ）ので、Core の試験は合成の口で行った                                                                     |

### 有効にする条件（U624）

1. 本人が U310 の予定を (a)（Buddy が作り、その後に変わっていない予定だけを削除する）に決める。
2. 実際の提供元（Google Calendar・Microsoft）で、予定の版（etag など）の読み方、版を条件にした削除（If-Match）と断られたときの応答、取り消し済みの予定の見え方、時刻の書き方の正規化（作ったときの値と読み直した値が同じ形か）を確かめる。
3. 予定を自動で作る経路（`calendar.event.create` の送出と候補からの配線）ができ、自動実行の一覧に予定が載る。

この 3 つが揃ったら `CALENDAR_EVENT_UNDO_OPEN` を true にし、U310・U624 を更新する。

## 2. 状態欄の安全停止の知らせ（U315）

### 背景

ADR 0154 は、端末が安全停止を知る経路が自動実行の一覧の読み取りだけで、常に正しい値を出せないため、状態欄の安全停止を埋めなかった（暫定 (a)）。ADR 0187 で WSS の `notice`（開いている購読へだけ流し、溜めない・再送しない）ができ、ADR 0196 で気づきの知らせ（`CandidateNotice`。中身は数だけで、端末が読み直す）が同じ経路に載った。

### 決めたこと

| 対象                | 決定                                                                                                                                                                                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| U315                | (c) Core から端末への知らせを足し、状態欄に安全停止を出す                                                                                                                                                                                                                                         |
| 知らせの形          | `SafetyNotice`（`buddy.safety-notice.v1`、`notice_id`・`occurred_at` だけ）。停止の理由・状態・版・操作の ID・本文を入れない（U627）。`EventStreamMessage` の `notice` に足した                                                                                                                   |
| Core が見つける方法 | 保存層の `onSafetyWrite`: 操作の命令（`operation.*`）と停止の解除（`safety.resume`）が終わるたびに、Core（`safety-notices.ts`）が安全停止の版を読み、前に読んだ版と違えば 1 回だけ知らせる（U626）。起動のときの版を基準にする。読めなければ送らない。読んでいる間の知らせはまとめて 1 回読み直す |
| 運び方              | `NoticeRelay.publishSafety`: 開いている購読へだけ渡す。表示の後始末・起動の設定の受け取り口へは渡さない。契約に合わなければ送らない。購読がない間の変化は溜めない（ADR 0187 の U168 と同じ）                                                                                                      |
| ロック中            | Core は送る（本文を持たない。U465 と同じ）。端末はロック中は読まず（ログのコード `safety_notice_deferred_locked` だけ）、ロックで値を捨てて不明にし、解除したときに読む。状態欄はロック中は隠れている（U628）                                                                                     |
| 記録しない会話      | 送る。安全停止は会話の中身ではなく、状態欄に常に出す値なので、記録しない会話の間も止まったことを知らせる（U628）。気づきの OS 通知（ADR 0196）は記録しない会話の間は出さないが、こちらは OS 通知ではなく状態欄の値                                                                                |
| 端末が読む時        | 中枢の安全停止の知らせ・接続した（ロック解除済みのとき）・ロックを解除した・自動実行の欄の操作のとき、`GET /v1/auto-actions` を読む（U629）。値が変わったときだけ状態欄を作り直す。読めなかったときは前の値のまま。読めたことがなければ・接続していなければ不明（null）                           |
| 状態欄              | `DesktopStatusBar.safety_stopped` を中枢の値で埋める（接続している間だけ。ADR 0025 の意味検査のまま）。従来の窓の状態欄と状態の層のパネルは、既にこの値を「安全停止中」「なし」で出す作りなので、画面の部品は変えていない                                                                         |

## 原本に決めがない項目

- U310: 予定は経路を作ったが本人の決定待ちで、製品では暫定 (b) のまま（ADR 0153）。
- U315: (c) にした（本 ADR）。
- U620〜U629（新規）: 予定の「作ったまま」の判定、参加者、繰り返し、削除の結果不明、予定の取り消しを開く条件、予定の作成の種類の範囲、安全停止の変化の見つけ方、知らせの中身、ロック中・記録しない会話、端末が読む時。

## 試験（模擬だけ）

- `apps/core/src/api-auto-actions-undo-event.test.ts`（8 件）: 製品の既定（閉じている）では予定の行が `unavailable` で、押下は提供元を読まずに 409。開いたときは、作ったままの予定が押下で作った補償で版つきで削除され、取り消し済みになる（同じ要求の再送は二つ目を作らない）。参加者を足した・繰り返しにした・題・時刻・場所・説明を変えた・取り消された・目印が違う・目印が無い・無い予定は 409 `target_changed` で消さない。押下の後に参加者が足され版が進めば実行担当が送らず準備のまま残す。結果不明は 1 回だけ読み、予定が残っていれば `unknown_held` で再送せず、取り消し直させない。結果不明でも予定が消えていれば取り消し済み。安全停止の間は押下を受けても削除を送らない。純粋な判定（取り消せる種類、作ったままの判定、削除の照合）。
- `apps/core/src/safety-notices.test.ts`（7 件）: 起動のときの版より後の変化だけを 1 回知らせ、中身は ID と時刻だけ。読めないときは送らない。重なった知らせは 1 回の読み直しにまとめる。止めた後は送らない。購読がなければ溜めない。中継は購読へだけ渡し、余分な欄・ほかの種類を送らない。製品の Core で、同じ対象への 3 回目の自動承認で止まると購読へ 1 回、本人の解除でもう 1 回届き、ロック中・記録しない会話の間も届き、状態を変えない拒否（古い版の解除）と止まらない書込みでは届かない。止まった後に開いた購読には前の知らせを送らない。
- `packages/storage/src/safety-store.test.ts`: 取り消しに結び付かない予定の削除は `undo_only_kind` で作らないこと、自分だけの予定の作成が方針で自動承認でき、一覧に `create_event` で載ること、取り消しの補償としては作れること。
- `apps/desktop/src/main/auto-action-bridge.test.ts`・`auto-action-link.test.ts`・`lock-query.test.ts`: 状態欄の安全停止の値が変わったときだけ知らせ、読めなかったときは前の値、ロックで不明。127.0.0.1 の Core で、接続のときに読み、中枢の知らせで読み直して停止を出し、ロック中は知らせが届いても読まず、解除で読み直す。状態欄は接続している間だけ値を持つ。
- `apps/desktop/src/renderer/screens/auto-actions/AutoActionsPanel.test.tsx`: 取り消せる予定の行だけに削除の説明が出ること。
- `packages/contracts/fixtures/schema-cases.json`（16 件）・`api-cases.json`（3 件）、`scripts/operation-kinds.test.mjs`・`scripts/approval-required-operations.test.mjs`: 新しい intent と知らせの正誤の例、意味検査（`event_time_order`・`created_by_self`）、種類と intent の対応、完全削除の除外が取り消しの 3 つの種類だけであること。

期待値は手で書いた。**模擬の期待値だけ**。Electron の画面の見た目・実データ・実機・実 API（Google Calendar・Microsoft の予定の削除）は未実施で、合格扱いにしない。

## 残ること

- U310（予定）・U620〜U629 の本人の確認。予定の取り消しを開く 3 つの条件（U624）。
- 予定の作成（`calendar.event.create`）の送出、模擬の提供元と Google Calendar・Microsoft のアダプターの予定の書込み（作成・id での読み取り・版つきの削除）。
- 状態欄・状態の層のパネルの安全停止の表示を実機（macOS・Windows）で確かめること。
