# Issue #108: 起動待ちと接続直後の発言の調査

2026-10-23。設計 02（配置・端末登録・運用境界）と 07 §2〜4 の現行本文、ADR 0012・0013・0023・0025 を照合した。原本の取得資料は非公開の `.local/design/notion/` に置いた。契約・認可・再送の規則は変えていない。

## 起動待ち

確定したこと:

- `first-device-cli.test.ts` は CLI の `running` 行を待っていたが、別の 15 秒タイマーで打ち切っていた。報告された約 15.6 秒の `start timeout` はこの分岐に対応する。`cli.test.ts` にも同じ待ち方があった。
- `running` は `startCore` が DB worker の起動・回復、TLS と HTTPS、制御チャネルの待受けまで完了してから出す。`https_listening` だけやプロセスの生成だけを完了にしてはいけない。
- 対象は新しい一時ディレクトリ。`acquireLock` の既存ロックへの問い合わせ・古いロックの回収は通常通らない。Windows の名前付きパイプも `listen` の完了通知を待つ。リトライによる 15 秒の待ちを持つ経路ではない。
- 模擬のデータ鍵と TLS 鍵はメモリー上の保護であり、Windows の資格情報保護や PowerShell は呼ばない。ただし P-256 鍵・証明書の作成、証明書ファイルの同期、SQLite のマイグレーション・耐久書込みは実際に行う。SQLite の `busy_timeout` は 0、DB worker 自体の起動期限は 30 秒で、旧ヘルパーの 15 秒はそれより短かった。

未特定のこと: 元の Windows CI で時間を使った段階は、Issue の記録にはない。子プロセス／モジュールの読込み、worker 起動、ファイルの排他作成・同期、並列試験との CPU・I/O の競合は候補であり、Windows のロックや鍵保護を原因と断定しない。

修正: `cli-test-support.ts` に待ち合わせを共通化した。成功時も `startCli` が `CLI 起動 elapsed_ms=…` を `t.diagnostic` に残し、CI の記録から時間の推移を追える。`running` の状態と子の PID を確認し、起動専用の固定期限を外して既存の試験全体の期限（`t.signal`）を使う。拒否・spawn エラー・早期終了・不正な出力・中断を区別し、固定の段階名と経過時間だけを診断する。生の出力や例外を診断へ載せない。失敗時の後始末も子の `close` を待ってから一時ディレクトリを消す。

ヘルパーの試験は、親からの指示まで子が `running` を出さない方式。模擬タイマーで 15 秒を進めても未完了で、`running` で初めて完了すること、HTTPS 準備だけでは進まないこと、拒否・壊れた出力・中断・spawn 失敗を確かめる。実時間の sleep は使わない。

## 接続直後の発言

確定したこと:

- macOS のローカル模擬統合でも、初回のキャンバスの発言が `outcome_unknown` になる現象を修正前に再現した。そのときの状態遷移は `live → waiting_retry:stream_closed → bootstrapping` で、`resnapshot` ではなかった。
- 共通の試験装置は WSS の ping 間隔を製品の 15 秒から 200ms に短縮していた。生成済みコードだけの診断用注入で「最初の ping → 次の期限まで同期処理を占有 → pong を読む前に次の tick」の順序を作ると、Core の未応答判定、1006 切断、上記の遷移を再現できた。2 クライアントの最初の `turn_submit` も `outcome_unknown` になった。注入はソース・コミットに含めない。
- Core の `event-stream.ts` は前の ping に pong がなければ切断する。`ClientConnection` は 1006 を `stream_closed` として再接続し、desktop の `core-link` は接続世代を進める。送信前なら `not_connected`、送信後に世代をまたいだ応答なら `outcome_unknown` となり、自動再送しない。これは既存の仕様どおりで、ガードを緩める製品修正はしない。
- `resnapshot` の別経路も確認した。Core は接続範囲なし・失効／期限切れ、DB 世代違い、再生できない cursor に対して通知と 4410 を返す。クライアントは bootstrap と snapshot を取り直す。自宅判定の統合では試験が全接続共通の `sameMachine` を切り替えるため、既存端末の自宅報告が範囲を失効させ、`scope_expired` となる場合がある。ペアリング成功そのものが再スナップショットを要求する経路はない。

未特定のこと: 元の Windows CI に切断コード・理由の記録がなく、各失敗が今回の heartbeat の筋書きだったとは断定できない。ローカルの自然再現でも、同期処理のどの箇所が遅れたかまでは測定していない。

修正: 発言の統合試験では heartbeat とクライアントの生存期限の短縮設定を外し、製品の既定を使う。起動待ちや発言前の固定待機を追加しない。確認時刻が 3 回進むまでの待ちと、未送信なら最大 20 回試す回避処理を削除した。最初の接続で発言を一度だけ送り、bootstrap・購読・発言の回数や状態遷移を検査する（失敗時の文言には、要求の方法・パス〔UUID・クエリは伏せる〕と `link:` の遷移だけを含める）。管理の入口の `adminWhenLive` も live を待って一度だけ送り、`not_connected` を送り直しで隠さない。自宅・接続範囲の定期再検査を目的とする 2 ケースだけは、明示して ping を 1 秒にする（200ms は使わない）。未応答、失効、期限切れ、再接続、送信後のロック／世代変更の拒否は既存の専用試験で引き続き検査する。

## 追加調査: Core の購読試験（PR #117 の Ubuntu）

2026-10-23。run `39916258624` の Ubuntu で、`canvas-stream.test.ts` の「今日の用事を見せて」の縦断試験が `Error: closed before: canvas notice` で一度失敗したという報告を受けた。設計 07 §2〜4 の取得済み現行本文と ADR 0023・0032 を再確認した。製品の heartbeat・切断条件・契約は変更していない。

確かめたこと:

- Core の `event-test-support.ts` にも既定 200ms の heartbeat が残っており、キャンバス・操作・イベント配信・B04 の模擬統合が利用していた。`api-hardening.test.ts` の共通装置も既定 100ms だった。
- 報告と同じ UI-03 試験の生成済み JS にだけ診断を注入した。購読の登録後、`setInterval` だけを模擬タイマーで 400ms 進め、ping の送出から次の tick まで I/O に処理を戻さない順序を作った。自動 pong は有効のままで、既定 200ms では同じ `closed before: canvas notice`、15 秒では同じ試験が成功した。pong を処理できる前に未応答と判定する筋書きを再現したもので、実際に 400ms の CPU 負荷を与えた測定ではない。注入は実行後に戻し、ソース・コミットには含めない。
- Ubuntu CI 当時の切断コード・理由と遅延箇所は未確認であり、その一回が heartbeat によるものだったとは断定しない。

修正と既存の検証の維持:

- 通常の Core 購読と API 強化試験は短縮設定を外し、製品既定の 15 秒を使う。通知待ちの期限や期待する通知の内容は変えない。
- WSS が最初の HTTP 要求の期限で切れない M1 は、heartbeat を試験全体の期限より長い 60 秒にした。300ms の要求期限を超えて 1.2 秒待ち、ping が 0 回でも購読が開いていることを確認する。無通信 TLS を切る拒否試験、keep-alive・遅い処理の試験も残す。
- 接続範囲・自宅判定・Tailscale の変化の定期再検査は、必要な明示設定を残して 1 秒に緩める。接続範囲の再発行・DB の失効・自宅判定の再検査は 5 秒以内、Tailscale の変化は従来どおり 10 秒以内に期待するコードと理由で閉じることを確かめる。即時の失効・自宅判定の差し込み口、未定義のクライアントメッセージ、停止時の検査も残す。
- pong 未応答の専用試験は 100ms と `autoPong: false` を残す。健全な接続の反対側として、100ms・自動 pong で ping を 5 回受けても open のままの短い試験（Core の購読の試験）を足した。実時間は Core の起動を含めて約 1 秒。ping を実際に受信したことと、5 秒以内の 1006 切断を確認する。

切断・時間切れの検証が弱くなっていないことも、生成済み JS だけへの一時的な故障注入で確認した。WSS の切り替え時に最初の要求のタイマーを解除しない変更では M1 が失敗し、定期再検査を呼ばない変更では接続範囲の切断待ちが失敗し、pong 未応答時の切断を省く変更では専用試験が失敗した。いずれも試験全体の打ち切りではなく、期待する接続状態か切断待ちの期限で検出した。診断の変更はすべて戻した。

対象 4 ファイル（イベント・API 強化・キャンバス・自宅判定）の 29 試験が成功した。今回は `event-test-support.ts` が B04 の `source_sha256` の対象に入るため、全体をビルドし直して固定 seed の 69 回の模擬観測を再実行し、`evidence-b04-simulated.json` を再生成した。対象一覧は 124 ファイルのままで、変更した対象の hash を含む証拠を保存した。

`node scripts/clean.mjs && pnpm run check` は成功し、993 件が合格（失敗・中断・skip は 0）。書式・契約・lint・ビルド・型・公開情報の検査と、保存済み B04 証拠の対象一覧・hash の一致も通過した。
