# ADR 0141: B12-05 公開 Web 調査の実行器と永続化（受付・実行・回復・完了の知らせ、B10-04 の受け口の製品配線）

- 日付: 2026-11-23
- 状態: B12-05（親 #27 [B12]）。受付器・実行器・保存層・製品配線と模擬試験まで。検索・取得の実アダプターは B12-03・B12-04 で、本 ADR では差し込み口（port）だけを置く。実 API・実アカウント・実課金は未実施（B15 と本人の承認）。
- 根拠: 設計 05（公開 Web 調査: 検索語の検査・試行の上限・出典の形・完了の知らせ）、設計 10 §5（裏のジョブ: 調査は最初から裏で受け、終わったら知らせる）、設計 11 §5A（候補の識別子）、ADR 0073（通知の識別子）・0077（調査の状態と試行の記録）・0125（U291: 完了の版は完了した応答の state_revision）・0126（U292〜U294 ほか: URL は保存しない＝本人の決定 A、抜粋 500 字・要約 4,000 字・content_hash）・0127（検索語の検査）・0128（予算の予約は検索アダプター側）・0129（最終状態の表）・0135（B10-04 の受け口 BackgroundJobAcceptor と planResearch。core.ts は未配線で、起動は B12-05 待ち）、contract-map の U254（裏のジョブの経路）・U291。
- 対象: `packages/storage/migrations/0014_research.sql`、`packages/storage/src/research-store.ts`・`research-store.test.ts`、`packages/storage/src/db-protocol.ts`・`db-worker.ts`・`db-client.ts`・`index.ts`・`policy.ts`、`apps/core/src/research-executor.ts`・`research-executor.test.ts`、`apps/core/src/core.ts`・`index.ts`・`retention-entries.test.ts`・`event-test-support.ts`・`api-turns.ts`（コメントのみ）、`docs/b00/contract-map.md`（U254・U291 の事実更新）。schema 版 13→14 に伴い、現行版を固定していた試験の期待値（migrations・backup・store-binding・db-worker・restore 系）を 14 へ更新した。

## 在庫確認（済んでいたもの）

- 受け口は ADR 0135 で完成していた。`BackgroundJobAcceptor`（turn-ports.ts、引数は workflow_id・intent 'research'・query・session_id・dedupe_key の 5 つ）、`planResearch()`（api-turns.ts: ゲート確認→受付→返ってきた ID の UUID 形の検証→`executing` で発言を記録。受付と記録は別 transaction で、受付が先）。
- 状態機械・試行の上限と最終状態の表・検索語の検査は domain で完成していた（web-research-status.ts、web-research-limits.ts、web-query-screening.ts）。出典の保存の形（URL を持たない、抜粋・要約・hash・取得時刻）も ADR 0126 で決まっていた。
- 完了の候補の種類 `research_done` と識別子の材料（kind・workflow_id・完了の版＝ state_revision）は domain（webResearchNotificationParts）と候補の保存（candidate-intake の persistCandidateDrafts）で用意されていた。ただし persistCandidateDrafts を呼ぶ製品の経路は無かった。
- 本当の残件は 5 つだけだった: ①調査の永続化（表と保存操作）、②受け口の実装（検査＋冪等な受付）、③実行器（検索→取得→要約→最終状態→完了の候補）、④再起動時の回復、⑤core.ts の製品配線。相談（consult）は思考レベルの信号が契約に無く、対象外（ADR 0135 のまま）。

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保存の形             | migration 0014 で 4 表を足す（research_jobs: 状態の行。dedupe_key は UNIQUE、request_revision は受付時に '1' で固定。research_screenings: passed の記録だけ。research_attempts: 試行を JSON で 1 行。research_sources: 出典。URL の列は無い）。保存操作は sync-store と同じ型（db-protocol の research/research_result、db-worker の handleResearch、db-client の research()、RESEARCH_WRITE_OPS）で、適用のたびに domain の規則（検査・試行・出典・遷移・最終状態）で検証する。検査の policy は url_storage: 'disallowed' で固定。バックアップの表の分類（domain の backup-plan）では 4 表とも「含める」に置く（完了の結果と出典は本人の記録。保持の期限で消えるのは復元後も同じ） |
| 抜粋・要約の置き場所 | 出典の抜粋と要約は公開ページの引用とその要約で、本人の私的な本文（メール本文・発言・記憶）ではない。検査済みの検索語やページの題と同じく平文で保存し、封筒（sealed_blobs）には入れない。列名は excerpt_text / summary_text とし、本文の列名（PLAINTEXT_COLUMN_NAMES: excerpt・summary 等）とは区別する（scripts/storage.test.mjs の「本文は sealed_blobs だけ」という検査は、本人の本文を守るためのものであることの切り分けをここに残す）                                                                                                                                                                                                                                           |
| 受付                 | 受付器は domain の `webQueryRejectReasons` で検索語を検査し、拒否なら `unavailable` を返して何も保存しない（拒否した検索語は保存しない。ADR 0127）。通れば検査の記録とジョブを 1 transaction で保存する。query_id は dedupe_key から決定的に導く（sha256→UUID 形。api-turns の derivedId と同じ作り）。dedupe は保存層が dedupe_key で担保し、重複の受付は最初に保存された workflow_id を返す。重複の受付でも実行のきっかけ（kick）は送る（止まった実行の立て直し）                                                                                                                                                                                                                 |
| 実行の戦略           | 検索は受付時に検査を通った検索語で 1 回だけ送る。上限（検索 3 回・ページ 5 件）は天井であってノルマではなく、再開時の再検索のために残す。ページはヒット順に最大 5 件まで読み、ページごとに試行と出典を保存する（落下しても読んだ分は残る）。複数クエリへの組み替えは、設計 05 と B12-03 の意味づけが要るため残件にする                                                                                                                                                                                                                                                                                                                                                              |
| 実行の入口           | 送る前に `webSearchAdmissionErrors` で検査の記録と検索語そのものを確かめ直す。口が返した拒否（budget_denied・query_rejected）は試行の search_denials に記録し、最終状態は domain の表（保留）に委ねる。予算の予約そのものは B12-03（ADR 0128）で、実行器は予約しない                                                                                                                                                                                                                                                                                                                                                                                                                |
| 取得と出典           | 取得の口はページ試行の欄（outcome・http_status・redirects・bytes・elapsed_ms）をそのまま返し、整合は domain が検査する。本文は保存せず、出典には先頭 500 字（コードポイント）の抜粋と本文の sha256 を置く。ヒットへの参照と本文は実行中のメモリーだけに置く                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 状態の進行           | 遷移は保存層の advance（state_revision の CAS）が担い、終端への遷移と同じ transaction で workflows.state を 'executing'→'done' にする（会話側にこの遷移を持つ操作が無いため。workflows の CHECK は 'done' を既に許す）。完了の結果は domain の最終状態から作り、要約の文は要約ができた時点で pending_summary として先に保存する（遷移の前に落ちても、再開で同じ文を使う）                                                                                                                                                                                                                                                                                                           |
| 完了の知らせ         | 実行器は notify の口を呼び、製品では core.ts が候補（research_done）を作る。題は固定の「調査の完了」、抄録は要約の先頭 200 字、期限は none、由来は input_snapshots から引いた発言（turn）。識別子は webResearchNotificationParts（U291 の (a)）。知らせに失敗したら通知済みにせず、回復でもう一度知らせる（候補の作成は notification_key で冪等）。notify の口が無ければ通知済みとして扱う                                                                                                                                                                                                                                                                                          |
| 回復                 | 起動時に保存層の research.recover を 1 回呼ぶ: 保持を過ぎた終端の削除、孤児の取消、実行できる調査の一覧、完了の未通知の一覧。孤児（受付だけが保存され、対応する依頼が無い調査）は canceled／superseded で取り消す（本人の要求として成立していない。ADR 0135 で B12-05 の判断に残されていた点）。実行できる調査は kick し直し、未通知の完了は知らせ直す                                                                                                                                                                                                                                                                                                                              |
| 保持                 | 終端の調査は finished_at ＋ workflow_result（7 日、domain の RETENTION_RULES）で delete_at を付け、回復のときに消す（出典・試行・検査も一緒に）。忘却（forget）の台帳との統合は残件                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 落下からの再開       | 試行と出典は増分で保存してあるので、再開は保存済みの続きから進める。本文とヒットへの参照は保存していないため、ページの続きを読むには検索し直す（試行の上限の中で数える。再検索のヒット順が前回と違う場合、同じページを読み直すことがある）。要約の入力は、本文が残っていない出典には保存済みの抜粋を渡す。検索の枠（3 回）を使い切り、ヒットへの参照も無いまま searching に残った調査は、最終状態を決めずに in_progress として残す（誤って完了にしない）                                                                                                                                                                                                                            |
| 保留の再開           | held の調査は自動では再開しない（予算の回復・本人の再依頼という、再開のきっかけの口がまだ無い）。回復の一覧にも含めない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 受付と記録の間       | 受付は発言の記録より先に保存されるため、実行器は対応する依頼がまだ無い間、短い間隔で数回だけ確かめ直して待つ（間隔は差し替え可能）。それでも無ければ実行せず、孤児として回復に委ねる                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ゲート               | 実行は外部への送出なので、同期の実行器と同じ作法で掃除のゲートを通す（ready→gate の search・cloud_send・auto_use→lease を実行の終わりまで保持）。`research-executor.ts` は retention-entries.test.ts に gated として登録した（anchors は options.retention.ready() / options.retention.lease()）                                                                                                                                                                                                                                                                                                                                                                                    |
| 製品配線             | core.ts は `research` の口（search・fetch・summarize）を渡されたときだけ実行器を作り、回復を HTTPS の受付より前に回し、受付器を startHttps 経由で createTurnRoutes の backgroundJobs へ渡す。CoreHandle には researchExecutor を出す（口が無ければ null）。CLI は変えない（実アダプターが無いので、製品はまだ口を渡さない）。停止時は実行中の調査の終わりを待ってから DB を閉じる                                                                                                                                                                                                                                                                                                   |

## 残ること

- 検索の実アダプター（Brave、予算の予約を含む）は B12-03、取得と抽出の実アダプターは B12-04。両方が揃うまで製品は口を渡さず、調査の受付は閉じたまま。
- 複数クエリへの組み替え（検索語の言い換え・絞り込み）は設計 05 と B12-03 の意味づけが要る。現状は 1 クエリだけ。
- held の再開のきっかけ（予算の回復の検知・本人の再依頼の経路）が無い。保留の調査は回復でも自動では動かない。
- 検索の枠を使い切ってヒットへの参照が無い searching の調査は in_progress のまま残る（最終状態を決める材料が無い）。運用で問題になれば、保持の対象に加えるか、失敗として閉じる判断が要る。
- 忘却（forget）の対象に調査の保存（出典・抜粋・要約）をどう含めるかは未決。現状は保持（7 日）の削除だけ。
- 調査の画面（デスクトップ）と U184（Brave の帰属表示・ロゴ）は未実装。設計 05 の原本が手元のコピーに無いため、画面は原本の確認が前提。
- 相談（consult）の裏ジョブ化は、思考レベルの信号が契約に無いため未対応のまま（ADR 0135）。
