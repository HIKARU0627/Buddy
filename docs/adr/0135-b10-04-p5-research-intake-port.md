# ADR 0135: B10-04 P5 調査を最初から裏のジョブへ回す口（受付の差し込み口）

- 日付: 2026-11-22
- 状態: B10-04（親 #18、Issue #246）P5 の判断。contract-map U254 の選択肢 (a) のうち、**Core 側の受付の口だけ**を実装する。製品の起動（`apps/core/src/core.ts`）には受付器を渡さないので、**製品の見える振る舞いは従来どおり「未対応」のまま**（U254 の暫定 (b) を維持）。有効化（受付器の製品配線）は B12 の受付・保存（B12-05）が前提。実音声・実 API・実請求・実機は未実施。
- 根拠: 設計 10 §5「裏のジョブ」、contract-map U254、ADR 0105〜0109（特に 0107 の `acceptedCommentary`、0108 の時間制御）、ADR 0053（保存期限の掃除のゲート）。契約の期待形は `packages/contracts/fixtures/response-plan-cases.json` の `plan-research`（`accepted_line`・`preparing`）。非公開の原本は権限のある接続で読み取りだけを行い、全文を写していない。
- 対象: `apps/core/src/turn-ports.ts`（`BackgroundJobAcceptance`・`BackgroundJobAcceptor`・模擬の解釈）、`apps/core/src/api-turns.ts`、`apps/core/src/live-conversation.ts`、`packages/storage/src/conversation-store.ts`（`WorkflowState` と検証）、各試験、`docs/b00/contract-map.md`（U254）。契約（`packages/contracts`）・マイグレーション・`core.ts`・`tests/test-map.json` は変えていない。

## 決めたこと

| 対象            | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 範囲            | 口だけを実装する。`createTurnRoutes` の options に `backgroundJobs?: BackgroundJobAcceptor` を足し、渡されたときだけ調査（`research`）を受け付ける。製品の起動は渡さない（実行器と受付の保存は B12。受け付けたのに実行されない約束を作らない）                                                                                                                                                                                                                                                                                      |
| 受付の項目      | `workflow_id`（Core の提案）・`intent: 'research'`・`query`（解釈が抜き出した調べる対象。前後の空白を除く）・`session_id`・`dedupe_key` の 5 つだけ。発言の全文・本人の情報・端末の情報は渡さない                                                                                                                                                                                                                                                                                                                                   |
| 受付器の契約    | 同じ `dedupe_key` の再呼び出しは新しいジョブを作らず、最初の受付の `workflow_id` で `accepted` を返す（冪等）。受け付けていないのに `accepted` を返してはならない（分からなければ `unavailable`）。例外は `unavailable` と同じに扱い、Core は自動で再送しない。返った `workflow_id` が ID の形でなければ受け付けたと扱わない                                                                                                                                                                                                        |
| 重複の鍵と ID   | `dedupe_key` は要求の `command_id`（接続範囲と `request_id` から決まる値）。文字入力は新しい UUID を、Live は Live が選んだ依頼の ID を提案する。記録する依頼の ID は**受付器が返した ID**（同じ鍵の最初の受付の ID）にし、受付と Core の依頼を一致させる。同じ `request_id` の再送は保存済みの応答を返し、受付器を呼ばない。同時の再送で受付器が複数回呼ばれても鍵は同じで、ジョブは 1 つ                                                                                                                                          |
| 判定の順        | 方式 C の全文の確定の判定（route が read の調査には当たらない）→ 返答文の分岐 → 調査の分岐（provider の意図の判定より前）。調査の分岐では、`query` が空・空白だけ → 足りない情報の聞き返し（`missing_other`）。受付器なし → 「未対応」（従来どおり）。確定前の Live の入力（`unverified`）→ 受け付けない（`blocked`。費用のかかる裏のジョブを確定していない文字起こしから始めない）。保存期限の掃除のゲートが閉じている → `blocked`（検索の入口。ADR 0053）。受付器が `unavailable`・例外・不正な ID → `blocked`。`accepted` → 受付 |
| 応答            | `status: 'background'`、`result_view` は `accepted_line`・`preparing`・`item_refs` なし、`reply_text` は「受け付けました。終わったら知らせます。」（`acceptedCommentary()` と同じ文）。コードの定型文でモデルの文ではないので、保存する応答（`response_json`）にも残す（再送でも同じ応答）。受付の文は受け付けたときだけ使う                                                                                                                                                                                                        |
| 依頼の状態      | 受け付けた依頼は `executing` で記録する。`workflows.state` の CHECK には 0001 から `executing` があるので、マイグレーションは作らず、storage の `WorkflowState` 型と `turn.record` の検証に足した。操作は従来どおり `ready` の依頼からだけ作る（`executing` の依頼に操作は付かない）。実行中から完了・失敗への遷移は B12 の実行器が持つ                                                                                                                                                                                             |
| Live の届け方   | `status: 'background'` の結果は、結果の画面回し（`ScreenResult`）を作らない。依頼を終える（つなぎ・背景化のタイマーを止める）→ 声で返せる（接続が開き、声の経路が有効で、背景化していない）ときだけ受付の文を 1 回追記する。閉じた接続・背景化済み・世代違いでは何も足さない（ジョブは受付済みで、完了は後続の工程が知らせる）。受け付けた後につなぎ・背景化の文を重ねない。受付の前に 1.5 秒を過ぎていたときのつなぎは、従来の時間制御（ADR 0108）のまま入りうる                                                                   |
| 相談（consult） | 今回も未対応のまま。設計 10 §5 は「思考レベル high の相談」を裏へ回すとするが、思考レベルの信号が ResponsePlan の契約になく、相談の文章の生成も後続の工程の範囲のため                                                                                                                                                                                                                                                                                                                                                               |

## 試験（模擬だけ）

- `packages/storage/src/conversation-store.test.ts`: `executing` の依頼を持つ発言が記録され、表の状態が `executing` になる。`executing` の依頼に操作を付けると `operation_without_workflow`、知らない状態は `workflow_invalid` で何も書かない。
- `apps/core/src/api-turns.test.ts`（`createTurnRoutes` を一時ディレクトリの DB worker に直接つなぐ。`core.ts` は受付器を渡さないため）:
  - 受付器ありの調査 → `background`・`accepted_line`・`preparing`・受付の文、受付器へ渡した項目は 5 つだけ、記録した依頼の ID は受付の ID と同じで `executing`、操作は 0。
  - 同じ `request_id` の再送 → 同じ応答で受付器の呼び出しは 1 回。同時の再送 3 件 → 応答はすべて同じ、鍵は 1 つ、ジョブ・実行中の依頼は 1 つ。
  - 受付器が `unavailable`・例外 → 「今は進められません」の聞き返しで、受付の文も実行中の依頼もない（聞き返しの依頼だけ）。不正な ID の `accepted` も同じ。
  - 受付器なし → 従来どおり「その依頼にはまだ対応していません。」。
  - `query` が null・空白だけ → 足りない情報の聞き返しで、受付器を呼ばない。
- `apps/core/src/live-conversation.test.ts`:
  - 声の調査の委譲 → 受付の文が 1 回だけ声に載り、10 秒たってもつなぎ・背景化を重ねない。`ScreenResult` は作らない。依頼は受付の ID で `executing`。同じ委譲の再送で受付も文も増えない。
  - 受付の後に接続を閉じても、閉じた接続への追記は増えない。
  - 解釈の間に接続を閉じ、その後に受け付けた → 追記 0、`ScreenResult` なし、依頼は `executing`。
  - 受付器なし → 従来どおり「未対応」の文。
- 期待値は手で書いた。`tests/test-map.json` の `product_test` は変えていない（ADR 0085・0109。証拠は B10-08）。

**模擬のみ**。実行器（B12）・実音声・実 API・実請求・実機は未実施で、合格扱いにしない。

## 残ること

- 有効化: B12 の受付・保存（B12-05）が受付器を実装し、`core.ts` から `backgroundJobs` を渡す。それまで製品の調査は「未対応」のまま（U254 の暫定 (b)）。
- 受付と発言の記録は別の transaction: 受付器が受け付けた後、発言の記録の前に失敗・失効（Live の依頼の失効・保存の失敗）すると、受付済みのジョブに対応する依頼が DB にない状態がありうる。同じ要求の再送は同じ `dedupe_key` で同じジョブに戻るが、再送されないときの扱い（受付の取り消し・孤立したジョブの照合）は B12-05 の受付の保存と合わせて決める。
- 受付を受けた後の実行中の状態の復元（再起動）、完了・失敗の遷移と、完了の気づき（B11）・次回の文脈要約（B10-06）への受け渡し。
- 相談（consult）の裏への回し方（思考レベルの信号の契約化と文章の生成）。
