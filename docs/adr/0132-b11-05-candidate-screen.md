# ADR 0132: B11-05 P1 気づきの画面（一覧前の見直し・見出しの基準・端末の経路）

- 日付: 2026-11-22
- 状態: B11-05 の P1。標準の端末画面（従来の窓）に「気づき」の欄を置き、一覧・開く・今回は扱わない・本人指定の再通知を Core まで通した。**模擬・同じプロセスの統合試験だけ**で、Electron の画面の実機確認・実メール・実 API は未実施。「根拠を見る」「相談する」と OS 通知は残論点（下記）。
- 根拠: 設計 01（「気づき」画面: 最終取得時刻と取得状態、操作は根拠を見る・相談する・今回は扱わない・本人指定の再通知。日付だけの期限は「日付のみの期限」。未取得を「予定なし」と表示しない）、設計 11 §4（表示順・見出し・初回取り込みの過去の期限の折りたたみ・行に出すもの・OS 通知の既定）、ADR 0073・0115・0116・0117・0119・0130・0131。
- 設計原本: 非公開 Notion から設計 01・04・06・11 を取得し、写しを `.local/design/notion/`（公開しない）に置いた。取得日と sha256 は同じ場所の manifest に記録し、`pnpm run design:check` で写しが取得時のままであることを確かめた（完全性だけで、原本の最新性は確かめていない）。原本の全文・内部 URL はリポジトリへ写さない（docs/public-release.md）。
- 対象: `apps/core/src/candidate-list-refresh.ts`（新設）・`core.ts`・`api-candidates.ts`、`packages/contracts`（`CandidateListResponse` の `zone`・`as_of`、IPC の 2 チャネルと `DesktopCandidateView`・`DesktopCandidateEntry`）、`packages/domain`（`desktop.ts` のチャネル・受付、`candidateSnoozeUntil`・`candidateLocalToUtc`）、`apps/desktop`（`main/candidate-bridge.ts`・`core-link.ts`・`electron/main.ts`・`preload.cts`、`renderer/state/candidate-state.ts`・`use-candidate-state.ts`・`screens/candidates/CandidatesPanel.tsx`・`App.tsx`）。

## 決めたこと

| 対象                           | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 開くたびの見直し               | 一覧（`GET /v1/candidates`）の前に、Core が保守（`runCandidateMaintenance`）の時間による遷移（期限切れ・スヌーズの終わり）と保持の掃除だけを回す（`candidate-list-refresh.ts`）。根拠の再確認（`checkEvidence`）は connector が無いので渡さない。定期の保守の製品の呼び出し側はまだ無いので、画面を開くたびの見直しはこれで満たす                                                                                                                                                                                                                                                |
| 見直しの止め方                 | 本人のタイムゾーンが無い（`zone()` が null）なら保守を回さず、一覧は 503 のまま（ADR 0131）。時計は掃除のゲート `retention.gate()` の理由のうち時計のもの（`clock_*`: 巻き戻り・時計の状態ファイルの欠け・不正・読めない時刻）で確かめ、該当すれば保守を保留して一覧だけ返す。掃除の進み具合（`sweep_*`）は見ない。前任の部分実装は `retention.clockStatus()` を使っていたが、これは掃除の完了を待つ（一覧を掃除の分だけ遅らせる）うえ、方針（`gate()` の理由で判断）と違うので差し替えた。保守の失敗・スキップは一覧を止めず、ログは段階と理由のコードだけ（題・ID を出さない） |
| 同時の要求                     | 進行中の保守があれば、それを待って相乗りする（保守を重ねない）。済んだ後の要求は新しく 1 回回す                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 契約への `zone`・`as_of`       | `CandidateListResponse` に、Core が並べるのに使った本人のタイムゾーン（`zone`）と並べた時刻（`as_of`、UTC）を必須で足した。見出しの計算には両方が要るが、デスクトップには本人のタイムゾーンの正本も中枢の時計も無く、端末の OS のタイムゾーン・時計で黙って代用すると、中枢と別のタイムゾーンの端末で見出しが食い違うため。見出しそのものは応答に入れない（ADR 0130 の「配列だけ」と矛盾しない）                                                                                                                                                                                 |
| 見出しは画面が domain で分ける | 画面は domain の `orderCandidates` に応答の `zone` と `as_of` を渡して見出しを分け、見出しの中は Core が並べた順（`position`）で並べ直す（受信の時刻は画面へ渡さないので使わない）。`zone`・`as_of` が無い・読めないときは見出しなしの 1 つにまとめ、その旨を出す                                                                                                                                                                                                                                                                                                                |
| 端末の経路                     | IPC は `desktop.candidates_list`（ロック解除済み。前面は求めない）と `desktop.candidate_state`（ロック解除済みの画面操作。`open`・`dismiss`・`snooze` だけ）。画面へは main が作る参照（ref）と表示用の値だけを渡し、候補 ID・通知キー・版・操作 ID・`expected_state` は main（`CandidateBridge`）が持つ。`command_scope_id` は接続が本文に付ける。世代（ロック・切断）が進んだら一覧・参照・保留を捨てる                                                                                                                                                                        |
| 状態の変更                     | 一覧で読んだ状態を `expected_state` にして送る。記録できたら一覧を読み直して件数と行を合わせる（読み直せなければ取得の状態を stale にする）。409 は読み直して `preview_stale`（画面も読み直す）。結果が分からない（届いたか不明・5xx・形の違う 2xx）は自動では送り直さず、その行を次の読み取りまで操作させない。外部へは送らない記録の操作なので、入出力の停止中も受け付ける                                                                                                                                                                                                     |
| 窓の役割                       | 2 チャネルは従来の窓（標準の端末画面）と状態の層の役割表に入れ、キャンバス・入力バーには渡さない（全チャネルがどれかの役割に属するという既存の不変条件に合わせた）。画面は従来の窓だけに置き、状態の層の画面は後の段階                                                                                                                                                                                                                                                                                                                                                           |
| 再通知の時刻                   | 「明日（同じ時刻）」「来週（同じ時刻）」「日時を指定」。本人のタイムゾーン（応答の `zone`）の現地の時刻で決め、domain の `candidateSnoozeUntil` で UTC にする（夏時間で 2 回ある時刻は後の回、存在しない時刻は直後。期限の解釈と同じ）。結果は `checkSnoozeUntil`（いまより後）に従い、main も送る前に同じ検査をする（正本は Core の検査）                                                                                                                                                                                                                                       |
| 取得の状態                     | 欄の頭に最終取得時刻（本人のタイムゾーン）・取得の状態（取得できています／前回の内容を表示／まだ取得できていません）・新着の件数を出す。未取得・取得の失敗を「気づきはありません」と言わない。切断中も欄を出し、未取得を示す                                                                                                                                                                                                                                                                                                                                                     |
| 行に出すもの                   | 題、期限（日付だけなら「日付のみの期限」で時刻を見せない。未確定は原文を添える）、種類、状態、メールの候補には「対応済みかは未確認」、`unread_partial` には「本文・添付の一部は未読」、操作が結び付いていれば自動実行の操作がある旨。操作のボタンは domain の遷移表で許されるものだけ（acted には出さない）                                                                                                                                                                                                                                                                      |
| 差出人                         | 設計 11 §4 は差出人の表示名を行に出すとするが、`CandidateSnapshot` に差出人が無い（封筒にも入れていない）ので出さない。足すなら保存・契約・取り込みを一緒に変える（残論点）                                                                                                                                                                                                                                                                                                                                                                                                      |

## 試験（模擬・同じプロセスの統合だけ）

- `apps/core/src/candidate-list-refresh.test.ts`（9 件）: 保守が一覧の前に 1 回走り、確かめた時刻と本人のタイムゾーンを渡す（根拠の再確認は渡さない）。zone が null・読み取りの例外・時計を確かめられない（巻き戻り）・時計の読み取りの例外では回さず一覧を返す。保守の失敗・一部の拒否でも一覧を返し、ログはコードだけ。同時の要求は 1 回にまとまる。
- `apps/core/src/api-candidates.test.ts`: 一覧の応答の `zone`・`as_of`。
- `scripts/candidate-lifecycle.test.mjs`: `candidateSnoozeUntil`（明日・来週・日時の指定・別のタイムゾーン・いまちょうどと過去・暦にない日時・夏時間の 2 回ある時刻と隙間）。
- `scripts/desktop-ipc.test.mjs`・`scripts/canvas.test.mjs`・`apps/desktop/src/main/preload.test.ts`・`window-roles.test.ts`: チャネルの一覧・受付・役割。fixture: `candidate-cases.json`（`zone`・`as_of` の欠け・UTC でない時刻）、`desktop-ipc-cases.json`（受付）、`schema-cases.json`（IPC の要求と応答。候補 ID・差出人・扱わない操作を拒否）。
- `apps/desktop/src/main/candidate-bridge.test.ts`（14 件、模擬の接続）と `candidate-link.test.ts`（3 件、127.0.0.1 の Core と `DesktopCoreLink`。一覧の前の保守を挟んだ空の一覧・受付の規則）。
- `apps/desktop/src/renderer/state/candidate-state.test.ts`（14 件）と `screens/candidates/CandidatesPanel.test.tsx`（8 件、サーバー描画）。

期待値は手で書いた。`tests/test-map.json` は設計 09 の X・QA との対応表で、設計 09 の写しが手元に無く対応を推測で足せないため変えていない。Electron の画面の見た目・クリック、実メール・実 API・実機は未実施で、合格扱いにしない。

## 残ること

- 「根拠を見る」: `fetchEvidence`（B08・B09 の connector）が無く、根拠の経路は 503 のまま。経路ができたら画面に足す。（追記 2026-11-28: ADR 0201 で経路をつなぎ、行に「根拠を見る」を足した。一覧の前の保守にも根拠の再確認を 15 分おきに渡す（U681）。）
- 「相談する」: 候補を会話の文脈として渡す仕組み（候補の参照を発言に結ぶ契約）が無いので、ボタンを出していない。
- OS 通知（設計 11 §4 の既定）と `candidateAlertDecision` の配線: 通知の ON/OFF の保存先が無いので配線していない。トレイの new の件数も同じ。（追記 2026-11-28: ADR 0196 で配線した。保存先は U580）
- 差出人の表示名を行に出すこと（上記）。自動実行の結果とその取り消しボタン（操作との結び付きは B13。`operation_ids` は今は常に空）。
- 状態の層（キャンバスのモード）の気づきの画面。
- 画面を開いたままの日付の変わり目: 見出しの基準は最後に読んだ一覧の `as_of` なので、読み直すまで前の日の見出しのまま。
- 候補の生成（candidate-intake）と定期の保守の製品の呼び出し側の配線。
