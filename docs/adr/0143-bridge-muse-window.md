# ADR 0143: Muse 窓口のブリッジ（外出先・モバイル向けの副次的な窓口、apps/bridge）

- 日付: 2026-11-23
- 状態: 本人の承認済みの方向（2026-11-23「『外出先・モバイル向けの副次的な窓口』という方向で作って」）を受けた実装。ブリッジ本体・契約と Core の小さな変更・試験（模擬）まで。実機のハブ（Mac mini）でのペアリング・Muse へのコネクタ登録・実接続は未実施（ハブ稼働後に本人が行う手順を残件に書く）。
- 根拠: ADR 0022（自宅ネットワークの判定。外出先からの接続経路は作らない）・0020（HTTPS の受付・経路検査）・0021（ペアリング）・0025（端末側の接続とロック申告）・0130（候補の経路）・0135（調べ物の受け口）・0141（調査の実行器と完了の知らせ）、設計 11 §10（自宅判定）、07 §2〜§3（経路の検査・接続範囲・受付の再送）。検討の経緯: Muse を Buddy の UI の一つにできるかの調査（2026-11-23）で、直接のクライアント化は自宅判定で塞がれること、承認・権限の正本は Core のままで衝突しないことを確認した。

## 位置づけ（本人の追加の制約、2026-11-23）

- **デスクトップアプリが主 UI のまま不変**。Live 音声会話・キャンバス・入力バーなど、デスクトップの既存機能は置き換えも弱体化もしない。ブリッジ／Muse 窓口は**追加**であり、副次的な窓口（外出先・モバイル向け）。
- 本 ADR の契約・Core の変更は候補の状態の変更の 1 経路だけに閉じ、デスクトップの経路・検査・試験は壊さない（音声・キャンバスの経路に変更は無い。試験の節で確認した範囲を書く）。

## 在庫確認（Core の全経路の棚卸し）

`apps/core/src/api-routes.ts` の全 50 経路と domain の `ROUTE_CHECKS` を棚卸しした。要点:

- 候補の状態の変更（changeCandidateState）は `screen_operation` 検査が必須で、実コードでは `Buddy-Input-Origin` が厳密に `screen` のときだけ通る（api-server の buildContext）。ブリッジが `screen` と申告するのは虚偽になるため、そのままでは状態変更を中継できない（下の「入力起源」）。
- 調べ物の専用経路は無い。受け口は発言（postTurn）の解釈が research の意図を裏ジョブへ回す形（ADR 0135）で、結果は完了の候補（research_done、ADR 0141）とイベントで返る。
- イベントは `GET /v1/events`（カーソル式）でも引けるため、WebSocket 常駐なしでポーリングできる。最初のカーソルは getSnapshot の `event_cursor`。
- ペアリングの受け取り（pickupPairingToken）は、接続元が中枢と同じマシンなら端末を `hub_local` として登録する（api-pairing の sameMachine）。ブリッジの登録は既存の経路だけで完結し、新しい経路は要らない。

| 入力起源（前提の判断）  | 候補の状態の変更に新しい起源 `chat` を正しく追加した。契約（OpenAPI の InputOrigin に chat を追加。説明に「受理するのは user_operation だけ」と明記）、domain に新しい検査 `user_operation`（起源が screen か chat）を追加し、changeCandidateState の検査を `screen_operation` から差し替えた。Core は INPUT_ORIGINS へ chat を足し、buildContext で user_operation を組み立てる。拒否は既存の 403 `screen_operation_required` を再利用し、ApiError のコードは増やさない。選定理由: 変更はこの 1 経路に閉じ、`screen_operation` を使う全経路（承認・音声・キャンバス等）は無変更。デスクトップは従来どおり screen を送り、user_operation は screen も受理するので既存クライアントの挙動は不変。状態変更を v1 から外す案は、承認済みの v1 範囲（候補の却下・スヌーズ）の中核が欠けるため採らない。なお起源の申告は宣言的なもので、信頼の錨は従来どおり端末トークン＋ペアリング＋自宅判定（ブリッジは hub_local）にある                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## 試験（模擬だけ）

- 契約と入口の試験（scripts/api.test.mjs、api-routes、api-route-order）: 10/10。chat 起源で候補の状態の変更だけが通ること、承認（approveOperation）が chat 起源を 403 screen_operation_required で断ること、OpenAPI と領域の検査表・INPUT_ORIGINS の一致を含む。音声・キャンバスを含む他の SCREEN 経路の検査は変更していない（状態変更以外の経路で chat が通ることは無い）。
- ブリッジの単体試験: 23/23（config 4、core-client 6、pairing 3、server 10）。公開しない経路（承認・ペアリング・端末管理・OAuth 開始・Live）が中枢へ届かないこと、監査にトークンと本文が残らないこと、設定ファイルに Muse 向けトークンの平文が無く権限が 0600 であることを含む。
- 全体（CI 方式の 4 シャードを逐次実行）: 3,448 件中 3,426 件合格。残りは負荷時のタイムアウトの連鎖だけ（シャード 2: X51/QA05・X58 が 20 秒で時間切れ。シャード 3: B04-06・07 が 300 秒で時間切れとなり配下 20 件が開始できなかった）。単体で再実行し、live-conversation 80/80・b04 70/70 とも全て合格した（既知の負荷フレークと同じ型）。
- 静的な検査: build・typecheck・lint・format:check・contracts:check・design:check・doctor は全て通過。security:check（check-public-content）は 1,005 ファイル通過（一時的に git 初期化した複写の上で実行）。

## 残ること

- ハブ稼働後の本人の手順: ①ブリッジをハブ機へ配置し `init`（トークンを控える）→ ②設定の listen.host をハブ機の Tailscale アドレスへ変更 → ③中枢の画面でペアリングを開始し `pair --code <8桁>`、指紋を比べて承認 → ④`serve` で窓口を開く → ⑤Muse 側で custom.buddy-bridge の資格情報（ブリッジの URL とトークン）を Secure Vault へ登録し、ヘルパーで疎通を確認する。実機・実接続は未実施で、模擬の成功を実接続の合格として扱わない。
- 操作の承認を窓口へ広げるかは、承認用の起源の設計判断が別途要る（上の「操作の承認」）。
- 端末トークンの OS キーチェーン保管、ブリッジ⇔Muse 間の TLS 終端（Tailscale Serve 前提の手順化）、listAutoActions の公開可否、相談（consult）の受け口（契約に信号が無い。ADR 0135 のまま）。
- ブリッジの常駐化（ハブ機の LaunchAgent 等）と、Core の再起動・端末の失効に追随する運用手順は、実機の段階で決める。
