# ADR 0026: 中枢の画面の端末で申請の承認と端末の失効を行う

- 日付: 2026-10-21
- 状態: B03-06（#74）の判断と実装。2 台目以降の端末の申請の承認・拒否と、端末の一覧・失効を、中枢の画面の端末（hub_screen）の HeroUI の画面で行えるようにした。中枢に承認待ちの申請の一覧の経路を足した。試験は模擬（CI の 3 OS）。実機（Mac mini・Tailscale・別のマシン）は未実施で、手順は [docs/b03/device-check.md](../b03/device-check.md) の D・E。
- 根拠: 本人の判断（2026-10-21、PR #73 のレビューの後）「2 台目以降の承認・失効は中枢の画面の UI で行う（CLI は作らない）」（ADR 0025 の「本人の承認」）。画面の約束は ADR 0024（UI レビュー 1 回目の後の骨格と約束）。

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 申請の一覧の経路     | `GET /v1/pairing/claims`（`listPairingClaims`）。経路の検査は `device_token`・`home_network`・`unlocked`・`hub_screen`（domain の `ROUTE_CHECKS`）。返すのは承認待ちの申請の claim_id・端末名・OS・申請と期限の時刻・確認コードだけで、申請用の秘密・その hash・コードは返さない                           |
| 確認コード           | `SHA-256("buddy/pairing-claim-check/v1\0" + claim_secret_hash の 16 進)` の先頭 8 桁。中枢（storage の `pairingClaimCheck`）と端末（申請した main）がそれぞれ求め、両方の画面に出す。本人は同じ確認コードの申請だけを承認する（同じ時刻に来た別の申請を取り違えない）。申請用の秘密そのものは出さない      |
| 画面を出す端末       | main が中枢に一覧の経路を問い合わせ、200 なら中枢の画面の端末（`DesktopConnectionView.hub_screen = true`）、403 `hub_screen_required` なら違う、と決める。判定は中枢（ADR 0021 の hub_local・同じマシン）が持ち、画面・main は推測しない。違う端末には Tabs・一覧・ボタンを出さない                        |
| IPC                  | `desktop.claims_list`・`desktop.claim_decide { ref, decision }`・`desktop.devices_list`・`desktop.device_revoke { ref }`・`desktop.pairing_open`。一覧はロック解除済み、承認・拒否・失効・ペアリングの開始は画面操作（ADR 0014 の再開と同じ判定）。main は中枢へ `scoped`・画面操作の要求として送る        |
| 参照（ref）          | 画面に申請 ID・端末 ID を渡さない。main が一覧ごとに不透明な UUID の参照を作り、ID との対応を main だけが持つ。同じ申請・端末には一覧を取り直しても同じ参照を使う（確認を開いている間の取り直しで参照が古くならない）。一覧から消えたもの・切断で対応を捨てる。知らない参照は `entry_not_found` で拒否する |
| 重い操作の確認       | 承認・拒否・失効は HeroUI の AlertDialog で確認してから送る。承認の確認には確認コードを出す。拒否・失効の確認は danger。停止（ADR 0014）だけは確認を挟まない                                                                                                                                               |
| 結果が分からないとき | 承認・拒否・失効の要求の結果が分からない（送った後に切れた）ときは `outcome_unknown` で「自動では送り直しません。一覧を取り直して確かめてください。」と出し、自動で再送しない                                                                                                                              |
| 一覧の更新           | 中枢は新しい申請を知らせないため、画面は承認待ちの申請を 3 秒ごとに取り直す（`CLAIMS_REFRESH_MS`）。端末の一覧は「取り直す」と操作の後に取り直す                                                                                                                                                           |
| コードの表示         | ペアリングの開始の応答（`desktop.pairing_open`）にだけワンタイムコードと指紋を入れ、ログ・他の応答には出さない。指紋は端末の画面・CLI と同じ 4 桁区切り・4 行                                                                                                                                              |
| 失効の経路           | 失効（`revokeDevice`）を中枢の画面だけに限る変更（`hub_screen` を経路の検査に足す）は、本人の判断で別の Issue（#75）で行う。このブランチでは `ROUTE_CHECKS` の失効を変えない                                                                                                                               |

## 画面

中枢の画面の端末では、端末の画面（ADR 0024 の骨格）の本体を Tabs にする。状態帯・停止・フッターは他の画面と同じ。

| タブ           | 内容                                                                                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 承認待ちの申請 | 「新しい端末を登録する」（ペアリングを始める・コードを出し直す。コード・期限と残り時間・指紋の 4 × 4 の格子）と、申請の一覧（端末名・OS・確認コード・申請の時刻・期限と残り時間、承認する・拒否する）。件数をタブに出す |
| 登録済みの端末 | 端末名・状態（この端末・有効・失効済み）・OS・中枢と同じマシンか・登録・最終接続または失効の時刻。失効は他の有効な端末だけに出す（この端末・失効済みには出さない）                                                      |
| この端末       | 中枢との接続の欄（ADR 0025）                                                                                                                                                                                            |

## 読み取り（レビュー対象）

- **一覧の取り直しの間隔**: 3 秒。中枢から申請の通知を配る経路を足すより小さな変更で、申請は 5 分で切れるため。配信（ADR 0023）に申請のイベントを足すかは後続で判断する。
- **確認コードの長さ**: 8 桁（32 ビット）。同じ時刻に来た申請の取り違えを防ぐためのもので、秘密ではない（申請用の秘密の hash から求めるため、秘密は推測できない）。
- **一覧の経路の lock 状態**: 一覧も `unlocked` を求める（端末名が出るため）。
- **中枢の画面かの判定のやり直し**: 接続のたび・ロックを解いたとき・経路が 403 `hub_screen_required` を返したときに問い合わせ直す。

## 残ること

- 実機の確認（device-check の D・E）。
- 失効を中枢の画面だけに限る経路の変更（#75）。
- 自宅の登録の UI。
