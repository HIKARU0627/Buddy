## 決めたこと（段階 1）

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自動の区切りの理由   | `idle_timeout`（前のやりとりから 30 分）と `date_changed`（本人の時間帯で日付が変わった）。区切りは Core だけが選び、端末は理由も保存モードも送らない（ADR 0032 のまま）                                                                                                                                                        |
| 経過の測り方         | 経過は**最後に受け付けた発言**から測る（まだ発言が無ければ区切りの始まり）。区切りの始まりから測ると、長い区切りの中で 30 分ごとに切れてしまう。時刻は保存した発言の `created_at`（保存の時点で確定した値）を使う                                                                                                               |
| 理由の選び方         | 評価した時点で両方が成り立ち得るので、**先に来ていた方**を理由にする（前の発言 + 30 分と、本人の時間帯の次の 0 時を比べ、早い方。同時刻は `idle_timeout`）。区切りは次の発言で遅れて評価されるため、実際に先に起きた出来事を記録する（U166。推奨どおり）                                                                        |
| 日付の判定           | UTC のミリ秒と `utc_offset`（Core の設定。発言の解釈と同じ値。既定 `+09:00`）から求める。端末の時計は使わない。形の違う差・読めない時刻では区切りを始めない（推測しない）                                                                                                                                                       |
| 要約のつなぎ         | 新しい区切りには、前の区切りの要約の**由来（区切りの ID）と期限だけ**をつなぐ（`D:nextCarriedSummary`。本文は持たない。契約の `S:CarriedSummary` のまま）。期限内の材料だけで作り直し、期限は由来の発言のうち最も早い期限。期限内の材料が無ければつながない。初回（`stream_started`）・忘却・記録しない会話の出入りはつながない |
| 発言の期限           | 区切りに属する発言の期限（`normal` 7 日・`extended` 30 日）を、受け付けた時点で一度だけ計算して区切りに持つ（`D:deleteAt`・`D:turnRetentionRule`）。区切りの継続・要約の作り直しで延ばさない。同じ発言の再送は二度数えない（区切りを始めたら数えた発言の ID を捨てる）                                                          |
| 区切りを作れないとき | 新しい会話（＝区切り）を作れなければ、**古い区切りで答えず 503** にする（区切りの理由を落とさない。発言の処理もしない）。応答の形式・意味の検査に通らない区切りも同じ                                                                                                                                                           |
| 同時の発言           | 区切りの切り替えは直列にし、直列にした後にもう一度区切りの要否を見る（先に別の発言が区切っていれば、その区切りを使う）                                                                                                                                                                                                          |
| 変えないもの         | 発言の処理（`postTurn`）・模擬の配置者・キャンバスの版・イベント・WSS の知らせ。端末から見える差は応答の `segment`（区切りの ID・理由・つないだ要約）だけ                                                                                                                                                                       |

## 試験（模擬だけ）

期待値は手で書いた値（UTC の時刻・期限）。実装の関数から作っていない。時計は注入する。実機・実 API・実請求は使っていない（**未実施**）。

- `scripts/canvas.test.mjs`: `automaticSegmentBoundary` の 30 分ちょうど・1 ms 前、まだ発言が無いとき、日付の変わり目（0 時ちょうど・1 ms 前）、30 分と 0 時の同時刻（`idle_timeout`）、30 分の方が先に来た場合、同じ日の中、負の差（`-05:00`）、形の違う差・読めない時刻では区切らないこと。`SEGMENT_IDLE_TIMEOUT_MS` が 1,800,000 であること。
- `apps/core/src/canvas-stream.test.ts`: 29 分 59 秒 999 ミリ秒では切らず、直前の発言から 30 分ちょうどで切ること（区切りの ID・理由・`opened_at`・つないだ要約の由来と期限）、日付が変わると 30 分前でも切ること、何回またいでも期限は由来の最も早い発言のままで、期限の切れた要約は材料にせず作り直すこと、区切りを作れないときは 503 で古い区切りで答えないこと。
- 区切りの切り替えは応答の `segment` だけに現れ、キャンバスの版・イベント・WSS の知らせは変えない（既存の UI-03 の試験が通ること）。

## 段階 2-i: 忘却の指示からの区切り（`fforget_requested`）

忘却の指示は、期限・日付・経過と関係なく新しい区切りを始め、前の要約をつながない（設計 03 のまま）。契約は変えない。

| 対象                 | 決定                                                                                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| どこで判断するか     | 発言の処理（`postTurn`）の結果が `status: 'answered'` かつ `result_view.intent === 'memory_forget'` のとき。解釈や照合表は Core の流れの側で作り直さない（発言の処理の結果だけを見る） |
| いつ区切るか         | 忘却の指示そのものは**その区切りで答える**。次の発言で新しい区切りを始める（理由 `fforget_requested`）。端末から見えるのは次の発言の `segment`                                         |
| 要約                 | つながない（`D:nextCarriedSummary` が `fforget_requested` を「つながない理由」に持つ）。由来の区切りも残さない                                                                         |
| 聞き返し             | `status: 'clarification'`（対象・語が決まらない）では忘却は成立していないので、区切りを始めない                                                                                        |
| 再送                 | 同じ要求の再送では始めない（受付の対応で元の応答を返す）                                                                                                                               |
| 二度消費しない       | 「忘却の指示を受けた区切り」を覚え、その区切りから切り替えた時点で消す。同じ発言の後で別の要求が並んでも、区切りを二度作らない                                                         |
| 保存中の発言との順序 | 段階 1 と同じく、旧区切りで保存中の発言が終わるのを待ってから切り替える                                                                                                                |

**到達できない経路（未実施）**: いまの Core の文字の発言は忘却をまだ受け付けない（B06-07b が未実装で、対象があっても `clarification` を返す）。そのため、製品の経路で `fforget_requested` の区切りが起きるのは B06-07b の後になる。段階 2-i の試験は、発言の処理の結果を差し替えた流れの側の試験（`canvas-stream.test.ts`）で固定している。

## AO レビューの指摘への対応

| 指摘                                                        | 対応                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1 再送の照合より先に区切りを切り替えている                 | 受け付けた発言の `request_id` → 区切り（会話）の対応を RAM に持ち、**区切りの要否を見る前に**元の区切りで `postTurn` を呼ぶ。新しい区切りで送ると `request_hash`（会話 ID を含む）が変わり 409 になるため。再送は区切りも切り替えず、やりとりにも数えない。応答の `segment` は今の区切り。境界ちょうどの再送と、別の発言で区切った後の再送の試験を足した（`canvas-stream.test.ts`）                                               |
| P2 要約の期限に、応答を返す時点の時計を使っている           | 発言の期限は、保存の命令に渡した時点で確定した値（`created_at`・`expires_at`）を `TurnRoutesOptions.onTurnRecorded` で受け取り、その値を区切りに記録する（`StreamRoutes.recordTurn`）。応答を作る時点で 7 日／30 日を計算し直さない。再送では渡さない。`api-turns.test.ts` で保存の値がそのまま渡ることと再送で渡らないこと、`canvas-stream.test.ts` で渡された期限（7 日後ではない値）が要約の期限になることを固定した           |
| P2 再送先の対応を応答キャッシュと一緒に破棄している         | 再送先（`request_id` → 区切り）の対応を、応答の束のキャッシュ（256 件）とは別に、受付レシートの保存期限（`command_receipt` の 7 日。`ACCEPTED_REQUEST_TTL_MS`）だけ保つ。期限の切れた対応だけを、件数が 512 を超えたときに片付ける。応答のキャッシュを破棄した後（256 件を超える別の発言の後）に 30 分を過ぎてから再送しても、元の `turn_id` を返し、区切りを増やさないことを既存の再送試験に足した（時計を進めて区切りをまたぐ） |
| P2 再送先のキーに接続範囲を含めていない                     | 保存側の `findReceipt` と同じく、対応の鍵を `command_scope_id` と `request_id` の組にした（`acceptedKeyOf`）。別の接続範囲で同じ要求 ID を使う新規の要求を再送と取り違えず、上書きもしない。接続範囲を変えて同じ要求 ID で送ると新しい発言として扱われることを試験した                                                                                                                                                            |
| P2 発言の保存の完了と区切りの切替を同じ直列化に入れていない | 区切りごとに「保存を待っている発言」の数を数え、切り替えは**旧区切りで保存中の発言が終わるまで待ってから**要約を確定する（`startTurnSave`・`settled`）。待つ間に発言が保存されて経過が延び、区切りが要らなくなっていれば切らない。保存を保留したまま日付をまたぐ同時要求の試験で、保留していた発言の期限がつないだ要約の期限になることを確かめた                                                                                  |
| P2 区切り切替の待機後に同じ要求の再送を再判定していない     | 切り替えの待機の後に**各要求が自分の再送と境界を判定し直す**（`postStreamTurn` のループ。最大 8 回）。保存を保留した要求を日付変更後に同じ `command_scope_id`・`request_id` で再送し、同じ `turn_id` が返り、会話が増えないことを試験した                                                                                                                                                                                         |
| P2 再送専用の区切り判定を別の新規要求へ共有している         | 共有するのは「旧区切りの保存を待つこと」（`settledOld`）と「切り替えの排他」（`rotating`）だけにした。切り替えの処理は要求ごとの再送・境界の判定を持たず、呼び出し側が待機の後に自分の再送と境界を判定し直し、切り替わらなければもう一度試す。保存中の A・A の再送・新規 B が並ぶ試験で、B が自分の区切りを開き、A の期限が要約に引き継がれることを確かめた                                                                       |
| P2 忘却の印を切り替えの理由に固定している                   | 切り替えの理由を呼び出し時の `forced` で固定せず、旧区切りの保存を待った後に**その時点の印**から決める（保存中の忘却の発言が終わった直後に印が付いても、自動の区切りがそれを取りこぼさない）。印を消すのは `forget_requested` で切り替えたときだけ。保存を保留した忘却の発言と 0 時をまたいだ発言 X が並ぶ試験で、X の区切りが `forget_requested` で要約が null になることを確かめた                                              |
