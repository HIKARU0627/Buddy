# ADR 0146: B13-02 候補起点の自動実行の判定表・重複キー・安全停止による保留

- 日付: 2026-11-26
- 状態: B13-02（親 #24）の domain の規則。保存（B13-03）・最終ガードと実行（B13-04）・画面（B13-05）は未着手。実データ・実機・実 API は未実施。
- 根拠: 設計 11 §5・§5A・§5B、設計 08 §1・§9、設計 04（自動実行の範囲と初回取り込み、Outlook のカテゴリ付与）、D6、質問 133、ADR 0007・0073・0074。原本の参照手順は `docs/design/README.md`。
- 対象: `packages/domain/src/auto-execution.ts` の `judgeAutoExecution`・`autoExecutionDuplicateKey`・`AUTO_OPERATION_RULES`・`GRAPH_CATEGORY_AUTO_VERIFIED`、`scripts/auto-execution-table.test.mjs`。契約（`packages/contracts`）は変えない。

## 背景

判定表の部品は B00 から domain にある（`candidateCommonReasons`・`autoOperationReasons` は ADR 0007、`analysisReadiness`・`autoCreationReasons` は 11 §5B、`autoApprovalAllowed`・`autoExecutionEnabled` は ADR 0074）。しかし、1 つの候補の 1 つの操作を「自動実行へ進める・承認へ回す・保留する・気づきだけにする」のどれにするかをまとめて決める口が無く、方針の規則（`task.register` など）と判定表の行（`create_task` など）の対応も無かった。B13-04 の最終ガードと B11-04 の候補の生成が同じ判定を使えるよう、この口を domain に置く。

## 決めたこと

| 対象               | 決定                                                                                                                                                                                                                                                                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 判定の結果         | `auto_eligible`（方針による自動承認へ進む資格。送出の許可ではない）・`needs_approval`（画面上の案）・`hold`（後で判定し直す）・`notice_only`（この候補の版からは気づきだけ）の 4 つ。契約の `ActionReadiness.state` には載せず、domain の型に留める                                                                               |
| 行と方針の対応     | `create_task`↔`task.register`、`create_event`↔`event.create_own`、`label_mail`↔`mail.apply_existing_label`、`draft_reply`↔`mail.save_draft`。方針で無効な行は気づきだけ（D6 の既定 OFF のままでは 4 種類とも気づきだけ）                                                                                                          |
| 理由を見る順       | ①この候補の版に資格が無い（方針で無効・初回取り込み・共通検査・行の条件）→ `notice_only`、②待てば変わる（安全停止・時間窓の上限・方針や許可の版の変化・関連解析の未完了）→ `hold`、③解析が済んだうえで取消・完了・抑止・作成済み → `notice_only`、④Outlook のカテゴリ付与 → `needs_approval`、⑤それ以外 → `auto_eligible`（U299） |
| 初回取り込み       | 初回取り込みの候補は候補起点の対象外（04）とし、保留ではなく気づきだけにする                                                                                                                                                                                                                                                      |
| 関連解析と取消     | 関連解析が済む前は、取消・完了の解決を確定させず保留にする（11 §5B の「列挙中は候補から自動実行を始めない」）。済んだ後に取消・完了が確定していれば気づきだけ                                                                                                                                                                     |
| 安全停止           | 停止中は `safety_stopped`、時間窓（10 分・20 件、ADR 0074）が埋まっていれば `rate_exceeded` で保留する。停止中は時間窓の理由を重ねない。資格の無い候補は停止中でも気づきだけ（保留で判定し直しても結果が変わらないため）                                                                                                          |
| 重複キー           | 用事は（依頼・`create_task`・アカウント）、予定は（依頼・`create_event`・アカウント・カレンダー）（11 §5）。ラベルと下書きは原本に記述が無く、（依頼・操作・アカウント）とした（U298）。キーは JSON の配列の文字列にし、区切り文字を含む値でも衝突させない                                                                        |
| Outlook のカテゴリ | If-Match の検証まで自動実行せず、画面上の案に留める（04・11 §5A・質問 133）。`GRAPH_CATEGORY_AUTO_VERIFIED` は false に固定し、検証（B13-04 の書込みと B15 の実 API）が済むまで変えない。Gmail のラベル追加は加算の操作として自動実行の対象                                                                                       |

## 原本に決めがない項目

- 判定を通らない候補の行き先（気づきだけか保留か）の分け方は U299 として暫定で決めた。どちらでも自動実行は 0 回で、違いは「解除・解析の完了の後に判定し直すか」だけ。
- ラベル・下書きの重複キーは U298 として暫定で決めた。同じ依頼に自動で付けるラベルは 1 つまでになる。

## 対象外

- 判定に入れる事実（方針・許可の版、安全停止の件数、関連解析の状態、作成済みの操作）を DB から読む処理と、判定の記録（B13-03）。
- 最終 transaction での再検査・方針による自動承認の記録・送出（B13-04）。この判定の `auto_eligible` は B13-04 の最終ガードを省略する理由にならない。
- 本人の依頼起点の判定（`assessReadiness`、設計 10 §5A）。本人の依頼は候補用の行の条件を通らない（11 §5）。
- 期限の形（日付だけの期限を日付のまま登録する、予定を期限の 30 分前から作る）など、作る内容の組み立て（B13-04）。

## 試験（模擬だけ）

- `node --test scripts/auto-execution-table.test.mjs`: 期待値はすべて手書き。4 行の資格と重複キー、既定の方針で 4 種類とも気づきだけ、初回取り込み、未読・切り詰め（ラベルを含む 4 種類）、日付だけの期限と確信度による行の違い、CC だけ・自動配信、下書きの重複と予算、ラベルの割り当てと元サービス、Outlook のカテゴリは承認へ、安全停止と 10 分・20 件の窓の境界（19 件・20 件・10 分ちょうど）、資格の無い候補は停止中でも気づきだけ、方針・許可の版の変化、関連解析の未完了では取消を確定させない、抑止・作成済み・別のカレンダー、重複キーの区切りの衝突。

**模擬の期待値だけ**。保存・実行・画面・実データ・実機・実 API は未実施で、合格扱いにしない。`tests/test-map.json` の X21〜X24・X39〜X41・X61〜X65 は、判定の口だけでは製品の試験にならないため更新していない（B13-03・B13-04 の統合試験で更新する）。
