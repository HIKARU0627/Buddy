# ADR 0028: 模擬 provider・故障注入・Core 側のアダプターを packages/connectors に置く

- 日付: 2026-10-22
- 状態: B04-02（#82）の判断と実装。模擬の試験のみ（実 provider・実 API・実請求は未実施、対象外）。Core の状態機械・承認・LocalCommand など B04 の残りは別の Issue。
- 根拠: 設計 09 §2・§4、08 §3、`tests/integration/fault-points.json`（模擬サービスの要件と故障点の正）。本人の判断（2026-10-22）D3・D4 は X10・結果不明の照合の扱いで、この Issue では装置だけを作る。

## 決めたこと

| 対象          | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 置き場        | 新しいワークスペース `packages/connectors`（`@buddy/connectors`）。Issue の `scope_paths` は `packages/connectors`・`tests/fixtures`・`docs` で、`packages/connectors` は含まれている。ただし設計 06 の配置（connectors）に従い、既存の `packages/platform`（OS アダプター）・`packages/storage` とは別の責務なので新しく作った。`pnpm-workspace.yaml`・`eslint.config.mjs`・README の追記はワークスペースを増やすための変更で、`scope_paths` の外に出る（下の「scope_paths の外」）。`tests/fixtures` は使わなかった（合成データは provider の定数。H01 の値は試験に手で写した） |
| 模擬 provider | `node:http` で `127.0.0.1` に待ち受け。状態と受信記録は注入したディレクトリの 1 つのファイル（`provider.json`）へ、一時ファイル + 置き換えで保存する。1 ファイルにしたのは、状態の変更と受信記録を食い違わせないため。受信記録は書込みの経路に届いた全要求（不正・拒否を含む）を届いた順に残し、`operation_id`・`attempt_id`・`step_id`・`receive_order`・`applied_change`・`responded` を持つ                                                                                                                                                                                    |
| 回数の分離    | 要求の回数 = 受信記録の件数、状態の変更の回数 = `state_changes`（適用した件数）。互いに導出しない。重複した要求は消さず冪等にもしない（同じラベルの追加を 2 回受けても 2 回の変更として数える。送信済みの下書きへの送信要求も数える）                                                                                                                                                                                                                                                                                                                                             |
| 真の結果      | `truth`（回数・受信記録・状態・保留の件数・遅れた適用・対象の版・許可の変更）は `@buddy/connectors/testing` だけが公開する。HTTP の経路にしない。Core 側のアダプターと `index.ts` からの `provider/`・`testing` の読み込みは ESLint で禁止し、模擬の応答を作った側が中枢へ真の結果を教えられない形にした                                                                                                                                                                                                                                                                          |
| 故障注入      | `FaultInjector`。地点名は fault-points.json の `fault_points` と同じで、試験が照合する。Core の地点は `hit()`（`pause`・`throw`・`barrier`）、provider の地点は `take()`（`drop_response`・`hold_then_apply`）。同時承認の境目は `barrier`（`parties` 件がそろったら一斉に解放。sleep を使わない）。応答の後に遅れて適用する故障は、provider が適用せずに保留し、`releaseLateApplies()` で適用する（応答は返さない。接続の状態に依存させない）。`core_restart` は試験装置がアダプターを作り直して表す                                                                             |
| アダプター    | `createMockMailConnector`。読み取り（許可・対象・予定・下書きの lookup）と、書込み 3 種（ラベル・下書きの作成・下書きの送信）。書込みは `node:http` で毎回新しい接続に 1 回だけ送り、自動再送 0（keep-alive も使わない）。結果は `applied`・`rejected`（4xx）・`not_sent`（接続できない）・`unknown`（時間切れ・切断・5xx・形の違う応答）で、`unknown` の再送・照合は Core の状態機械が決める                                                                                                                                                                                     |
| 能力の型      | 暫定。connector の能力の型は #81 で domain に置く予定のため、`src/adapter/capability.ts` に最小の型（`MinimalConnectorCapability`）を置いた。#81 の型ができたらこのファイルだけを差し替える                                                                                                                                                                                                                                                                                                                                                                                       |
| 書込みの経路  | Issue は「ラベルの追加（H01）・下書きの作成・工程の記録（step_id）」。X10 の `send` の工程（状態の変更が 2 件）を再現するため、「工程」は下書きの送信の経路（`step_id: send`）として作り、`step_id` は全ての書込みの受信記録に残す形にした（解釈。本人の確認待ち）                                                                                                                                                                                                                                                                                                                |
| 時計          | `2026-10-05T09:00:00+09:00`（注入できる）。fault-points.json の `clock` は `2030-10-05T00:00:00Z` で食い違うため、設計 09 §2 と Issue に合わせた。fault-points.json 側は変更していない（要確認）                                                                                                                                                                                                                                                                                                                                                                                  |

## scope_paths の外に変更したもの

`pnpm-workspace.yaml`（ワークスペースの追加）、`pnpm-lock.yaml`（必要な場合のみ）、`eslint.config.mjs`（依存方向の規則）、`README.md`（構成表と ADR の一覧）。いずれも新しいワークスペースを検査・ビルドの対象にするために必要で、既存の挙動は変えていない。

## 試験

`packages/connectors/src/*.test.ts`（17 件、模擬）: 合成データの読み取り、H01 の適用と受信記録の項目、アダプター・provider の作り直しの後の記録の保持と受信順の継続、同じ要求 2 回 = 要求 2・変更 2、拒否・不正な要求の記録、下書き・送信・lookup、X02（barrier）・X05/X06（pause・throw）・X07（応答前の切断）・X08（時間切れの後の遅れた適用）・X10（工程を絞った注入）、再送 0（切断・5xx・時間切れ）、接続できない場合。期待値は手書きで、実装の処理から作っていない。

## 未実施・残り

Core の状態機械・承認・結果不明の照合との結合（X01〜X11 の合格）、`core_restart` の実際の Core の再起動、別プロセスの provider（現在はプロセス内で起動し、ディレクトリを共有して作り直す）、#81 の能力の型への差し替え。
