# ADR 0127: B12-02 私的情報を検索語に混ぜない前提（検索語の検査の記録）

- 日付: 2026-11-14
- 状態: B12-02（親 #27、Issue #264）の P1。契約と、機械検査の下限だけ。検索の呼出し（B12-03）・意図の判定との接続（B12-05）は未着手。実データ・実 API は使っていない。
- 根拠: 設計 05「公開Web調査」（「検索語は本人の質問から必要な一般語を作り、メール全文、API キー、個人の詳細予定を含めません」）、Issue #27 の完了条件（「私的情報を検索語へ混入させず」）、Brave の利用条件 9(b)（検索語は Brave に取消不能・サブライセンス可能な使用権を与える）、設計 09 X18、ADR 0077。
- 対象: `packages/contracts/schemas/buddy.schema.json` の `WebQueryRejectReason`・`WebQueryScreening`、`packages/domain/src/web-query-screening.ts`、`packages/contracts/fixtures/web-research-status-cases.json`、`scripts/web-research-status.test.mjs`。

## 決めたこと

| 対象                   | 決定                                                                                                                                                                                                                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前提                   | 検索語は**本人の質問だけ**から作る。検査の記録 `WebQueryScreening.input_sources` は `["user_question"]` に固定し、メール・予定・記憶・取得済みページの本文を元にしない。この前提を変えるときは ADR で本人の決定を記録する                                                                                               |
| 検査の記録             | `WebQueryScreening`。`outcome` が `passed` のとき `screened_query` を持ち、拒否の理由は空。`rejected` のとき理由を持ち、**拒否した検索語は保存しない**（`screened_query` は null。私的情報の写しを残さない）                                                                                                            |
| 受け付ける条件         | `webSearchAdmissionErrors`。検査の記録が無い・別の `query_id`・`passed` でない・検索語が記録と食い違う・入力元が本人の質問だけでない・規則の版が古い、のどれかなら**検索を受け付けない**。記録を信用せず、**検索語そのものも検査し直す**（記録の取り違え・改ざんで私的情報を送らない）。B12-03 が毎回の呼出しの前に使う |
| 機械検査（規則の版 1） | 理由は 8 つ: `empty`・`too_long`（512 コードポイント超）・`too_many_words`（75 語超）・`line_break`（改行。メール本文や予定の貼り付けは複数行になる）・`email_address`・`phone_number`（区切りを除いて 10 桁以上）・`secret_like_token`（API キー・トークン・JWT・32 文字以上の英数字の連なり）・`contains_url`         |
| 正規化                 | 全角の英数字・記号は NFKC で半角にしてから検査する（全角の `＠` や数字で検査を避けられない）。長さの数え方はコードポイント（サロゲートペア 1 文字を 1 と数える）                                                                                                                                                        |
| 失敗側                 | 検査は安全側に倒す。誤って拒否した検索語は `held`／`query_rejected`（ADR 0125）として、本人に言い換えを聞き直す。自動で言い換えて再送しない                                                                                                                                                                             |

## 限界（隠さずに書く）

- 機械検査は**下限**で、氏名・社名・予定の詳細・住所・病名などの私的情報は見分けられない。これらは、検索語の入力元を本人の質問に限る前提（`input_sources`）と、本人が声や文字で自分から言った言葉だけが検索語の材料になる経路の設計（B12-05。意図の判定の入力は本人の発話だけ。設計 10 §5「外部内容」）で守る。検索語を LLM に作らせる場合も、LLM への入力は本人の質問だけにする。
- 本人が質問の中に私的情報を自分で書いた場合は、機械検査に当たらない限り検索語になりうる。Brave は検索語を保持・利用できる（9(b)）ので、Buddy は検索語に何を入れたかを本人に見せる画面を持つのが望ましい（B12-05 の判断。この ADR では決めない）。
- 規則の版 1 の正規表現は、誤検出（日付の並びを電話番号と見なす等）と見逃しの両方がありうる。T08・X18 の評価（B12-06）で合成データを使って見直し、見直したときは規則の版を上げる。

## 原本に決めがない項目

- 設計 05 は「メール全文、API キー、個人の詳細予定を含めません」と書くが、**どう検査するか・何を拒否するか**は書かれていない。この ADR の 8 つの理由と数値（512・75・10 桁・32 文字）は設計担当の判断で、初期値（U294、暫定）。512 と 75 は Brave の入力上限（600 文字・75 語）の内側に置いた。
- 拒否した検索語を保存するかも書かれていない。私的情報の写しを残さないため、保存しない側にした。

## 試験（模擬だけ）

- `scripts/web-research-status.test.mjs`: 8 つの理由、境界（512／513 コードポイント、75／76 語、31／32 文字、9／10 桁）、全角の回避、サロゲートペア、改行の 4 種、検査の記録の食い違い 8 通りを、手で書いた期待値と照合した。API キーに見える文字列は実行時に組み立て、試験のソースに置かない。
- 実データ・実メール・実予定は使っていない。合成の語だけ。

## 残ること

- 検索の呼出しの前の検査の接続と、検索の費用予約との順序は B12-03。
- 検索語を作る経路（意図の判定・LLM）の入力が本人の質問だけであることの確認は B12-05。
- 規則の見直しと合成データでの評価は B12-06。
