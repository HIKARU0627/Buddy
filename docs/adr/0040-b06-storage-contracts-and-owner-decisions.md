## 契約の追加

`packages/contracts/schemas/buddy.schema.json` に次を足した（生成型は `pnpm run contracts:generate`）。意味検査は `scripts/contract-tools.mjs` の `semanticErrors`（開発の検査）。製品の domain の関数は B06-03（台帳の検査）・B06-05（封筒と復元の判定）で、同じ理由コードで作る。

### 忘却台帳の別ファイル（`ForgetLedgerFile`・`ForgetLedgerChainEntry`・`ForgetLedgerReplica`）

設計 03 は「忘却台帳は本文なしの別ファイルとして世代管理し、登録済みの端末にも複製する」とだけ定める。形は次のとおり（原本に決めなし。この ADR の設計判断）。

- **版**: `schema` が `buddy.forget-ledger-file.v1`。DB の `forget_ledger`（0001）とは別に、本文なしで持つ。
- **連続した世代**: `entries` は世代 1 から欠番なく 1 つずつ。先頭を削らず、追記だけ（DB の表の trigger と同じ）。`head` は最新の世代と `entry_hash`（空なら世代 0 と 64 個の 0）。
- **本文なし**: 1 件の中身は既存の `ForgetLedgerEntry`（忘れた対象の ID・再登録を禁じる元の ID・内容の HMAC だけ）。Schema は追加の項目を拒否する。
- **ID の欄は ID の型に限る**（Codex P1）: 追加の項目を拒否するだけでは、ID の欄に文（忘れたい内容・検索語）を入れられた。`MemorySourceRef` を、発言（`turn`）と別の記憶（`memory`）は Buddy 内の ID（`Id`＝UUID v4）、元情報（`source_item`）は新しい `OriginalSourceId`（英数字と `. _ : = + ~ -` だけ・1〜256 文字）に限り、`ForgetLedgerEntry.blocked_source_ids` の各要素と `RetentionNoticeItem.item_id` も `OriginalSourceId` にした。台帳のファイル・複製が参照する ID の欄はこれで全部（`entry_id`・`ledger_id`・`device_id` は `Id`）。256 文字は、Outlook（Graph）のメッセージ ID が 150 文字を超える長さになり得ることを見込んだ上限で、実際の長さは B08・B09 の実測で確かめる（原本に決めなし）。
  - **影響の範囲**: 契約の fixture（`schema-cases.json`）の `MemoryCandidate`・`MemoryRecord`・台帳の例は、発言・記憶の ID が UUID、元情報の ID が `mail-001` などで、変更なしで通る。`memory-cases.json` の `turn-10`・`memory-1` は domain の関数（`memory.ts`。ID を文字列として扱う）だけが読み、Schema では検査しないので影響しない（Core が台帳・記憶へ書くときは UUID を使う）。`MemoryCandidateWire.source_turn_ids`（モデルの出力の 1 欄。`turn-1` を使う試験がある）はこの変更の対象外で、Core が検証して `MemoryCandidate` の `Id` へ変える段階で拒否する。生成型は `MemorySourceRef` が 2 つの形の和になる（利用側は `apps`・`packages` になかった）。
- **hash の連鎖**: `entry_hash` は `{entry, previous_hash}` を RFC 8785（JCS）で正規化した UTF-8 に SHA-256 を掛けた小文字 16 進。最初の世代の `previous_hash` は 64 個の 0。内容の hash（ADR 0003・0019）と同じ正規化・同じ関数を使う。
- **系譜**: `ledger_id` は台帳の系譜で、復元しても変わらない。バックアップの `ledger_id` と今の台帳が違えば別の系譜として拒否する（`ledger_lineage_mismatch`）。新しく作った中枢は新しい `ledger_id`。
- **端末への複製**（`ForgetLedgerReplica`）: 世代 1 から head までの全体だけを持つ。部分の複製は表せず、欠けた複製は意味検査に通らない（domain の `LedgerCopy.complete` は、この検査に通ったかどうか）。端末は複製を忘却の判定に使えるだけで、台帳の正本ではない（正本は中枢）。複製の頻度・取得の経路は後の工程（U40。OpenAPI に足す案）。
- **意味検査**: `generation_gap`（欠番・重複・順序の入れ替え）、`duplicate_entry_id`、`previous_hash_mismatch`（連鎖の切れ）、`entry_hash_mismatch`（内容の書き換え）、`head_mismatch`（末尾を隠す・先を指す）。1 件の中身の検査（`duplicate_forgotten`＝DB の `forget_ledger_items` の主キーと同じ規則）も、ファイル・複製の検査から 1 件ごとに必ず呼ぶ（Codex P2。包んだ状態でも通る）。
- **限界（hash の連鎖は真正性の証明にならない）**: 連鎖が示すのは「つながっていて、書かれた後に一部だけ変えると食い違う」ことだけで、**誰が書いたかは示さない**。鍵のない hash なので、内容を書き換えて `previous_hash`・`entry_hash`・`head` を最後まで計算し直せば、すべての検査を通る（Codex が確認した）。台帳の最後の数件を丸ごと切り落として `head` も合わせた複製も通る。この契約が見つけるのは、偶発的な破損・欠落・部分の複製・古い複製と、書き換えの食い違いだけで、書込みの権限を持つ攻撃者の改ざんは防げない。防ぐのは、ファイルの権限（中枢のデータディレクトリは所有者だけ。ADR 0016）、端末への複製との head の比較（複製が 1 つでも新しければ古い台帳を最新と扱わない）、封筒の `forgetting_generation`・`ledger_head_hash` との照合（下の「復元」）で、署名や HMAC は付けない。署名の秘密鍵を Core が持てば、Core を書き換えられる者は署名もできるので、得られる安全が増えないため（原本に決めなし。この ADR の設計判断）。

### バックアップの封筒（`BackupManifest`・`BackupKeyWrap`）

バックアップ ID・store_generation・DB の schema の版（`db_schema_version`）・忘却の世代と台帳の hash（`ledger_id`・`ledger_head_hash`）・除外したデータ（`excluded_data`）と表（`excluded_tables`）・本体の大きさと hash（`payload`）・鍵の包み（`key_wraps`）。本文を持たない（追加の項目は Schema が拒否する）。

- **private を含められない**: `included_storage_modes` は `normal`・`extended` だけで、`private` は Schema が拒否する。`excluded_data` は生音声・記録しない会話・OAuth トークン・API キーの 4 つを必ず記録する（03）。
- **除外した表**: 4 つのデータは表ではない（生音声は保存しない、記録しない会話は保存しない、OAuth・API キーは KeyStore）。表の除外は短命の運用データの案（`source_items`・`sync_staging`・`event_outbox` など）だが、一覧は原本に決めなし（B06-05 で決める）。忘却台帳の 2 つの表（`forget_ledger`・`forget_ledger_items`）は除外できない（`required_table_excluded`）。
- **store_generation**: 取った時点の DB の世代。復元では新しい値にする（ADR 0016 の `initStoreGeneration` は既存の値を書き換えないので、B06 は別に更新する関数を作る）。
- **台帳の hash**: `forgetting_generation` が 0 のときだけ `ledger_head_hash` は 64 個の 0（`genesis_ledger_hash_mismatch`）。
- **2 つの鍵を同じ復旧キーで包む**: `backup_file`（バックアップ本体の鍵）と `data_key`（DB の暗号文の鍵。ADR 0017 の `data-key-v1`）。どちらかが欠けた封筒は拒否する。KeyStore は同じ中枢にあり、中枢の機器を失うとデータ鍵も失うので、バックアップだけでは暗号文が読めない。復旧キーで包んだ鍵が封筒にあることで、実機を失った後の復元ができる（B15 の実機の確認）。別々の復旧キーで包んだ封筒は拒否する（`recovery_key_mismatch`）。**包みは設定のときに CLI のプロセスが 1 度だけ作り**（Core は復旧キーを知らないので毎回は包めない）、毎回の封筒には同じ包みを写す。毎回の暗号化は、設定のときに作ったバックアップ本体の鍵（KeyStore に置く）と `backup_id` から導いた鍵で行う。データ鍵を入れ替えたとき（`data-key-v2`。ADR 0017）は、CLI で包み直す。

### 復元の結果（`RestoreResult`・`RestoreStageResult`・`RestoreAftermath`・`RestoreRejectionReason`）

6 段階を、この順に必ず記録する（Schema は段階の名前・順序・個数を固定する）: 台帳の確認（`ledger_check`）→ 期限切れの削除（`expiry_purge`）→ 忘却の適用（`forget_apply`）→ DB の検証（`db_verify`）→ 画面と索引の作り直し（`rebuild_views`）→ 外部の状態の照合（`external_reconcile`）。各段階は `passed`・`failed`・`not_run`・`pending`（外部の照合だけ）と理由を持つ。

| 段階                 | 出せる理由（意味検査が段階と組で検査する）                                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ledger_check`       | `latest_ledger_unconfirmed`・`latest_ledger_missing`・`backup_newer_than_ledger`（3 つは ADR 0008 の `restoreReasons` と同じ）、`ledger_chain_invalid`・`ledger_lineage_mismatch`・`backup_ledger_hash_mismatch`・`manifest_invalid` |
| `expiry_purge`       | `backup_unreadable`（開けない・鍵がない）、`clock_regression`（時計が戻っていて期限を判定できない。03）                                                                                                                              |
| `forget_apply`       | `forget_apply_failed`                                                                                                                                                                                                                |
| `db_verify`          | `db_integrity_failed`、`schema_newer_than_code`（ADR 0016 のダウングレードしない）                                                                                                                                                   |
| `rebuild_views`      | `rebuild_failed`                                                                                                                                                                                                                     |
| `external_reconcile` | 理由なし。失敗で復元を止めない（照合できない操作は保留のまま残す）。再認証が済むまで `pending`                                                                                                                                       |

- **結果の 3 種類**: `restored`（全段階が成功。外部の照合は `pending` でもよい）、`settings_only`（台帳の確認で止まったときに、非機密の設定だけを戻す。03 の「新規開始または安全に分離できる非機密設定の復元だけ」）、`rejected`（何も戻さない）。`settings_only` が台帳の確認以外の失敗で出ることはない（`settings_only_without_ledger_stop`）。「非機密の設定」の範囲は原本に決めなし（B06-05 で決める。決めるまでは `settings_only` を選ばず `rejected` にする）。
- **止まった後の整合**: 失敗は 1 つだけで、それより前は `passed`、後は `not_run`。失敗には理由が必要で、失敗していない段階に理由は付かない。`restored` と `after_restore`（復元後の状態）は対になる。
- **作業は別の場所で行い、最後に差し替える**（案）: 段階 2〜5 は取り出した別の DB に対して行い、段階 5 まで成功してから現在の DB と差し替える。途中で止まれば今の DB に何も起きない。差し替えは 1 回で、`store_generation` を新しい値にする。
- **J3 の反映**（`RestoreAftermath`）: 新しい DB の世代・適用した台帳の世代・期限切れで消した件数・忘却を適用した件数・失効した承認の件数・結果不明として保留した操作の件数（`operations_held_count`）・バックアップの後に実行された可能性があるとして隔離した操作の件数（`operations_unverified_count`。保留した件数を含む総数で、保留の件数を超えない＝`held_exceeds_unverified`）・同意の取り直し（`consents_reset`。ADR 0038）・外部サービスの再認証（`connections_reauth_required`。03）。件数だけで ID と本文は持たない。
- **進行中の操作の保留と、バックアップの後に実行された可能性の隔離**（案。Codex P1）: 復元したバックアップは古い。バックアップの後に、本人が承認し、外部サービスへ送出され、変更が適用された可能性がある。**承認待ち（`awaiting_approval`）も例外ではない**（バックアップの後に承認・実行された操作が、復元した記録では承認待ちに見える）。そこで、外部サービスを変更する操作（RemoteMutation）のうち終わっていないもの（`awaiting_approval`・`approved`・`preparing`・`dispatching`・`reconciling`・`unknown_held`）すべてに、差し替えと同じ transaction で「復元後の未確認」の印（`operations.restore_unverified_at`。マイグレーションの案）を付け、**通常の承認・送出準備・送出から隔離する**（印のある操作への承認の作成・`approved` と `preparing` への遷移・試行の作成を DB の trigger で拒否する。最後の保証は DB）。有効な承認はすべて `revoked`（J3）。`approved`・`preparing`・`dispatching`・`reconciling` は `unknown_held` にする（`preparing` を未送出と判断しない。08 §4・ADR 0019）。LocalCommand（Buddy 内だけを変える）は外に出ないので対象外で、バックアップの後の変更は記録ごと戻る。
  - **印を外せるのは照合だけ**（書込みなし。読み取りだけ）: (1) 実行済みと確かめられた（元サービスに作成物の目印がある。たとえば下書きの目印に操作 ID を入れる方式。ADR 0030。ラベル変更なら対象の今のラベルが変更後と一致し、作成物でなければ変更前の状態との差が説明できる）→ 結果を取り込んで完了にする。再送しない。(2) 未実行と確かめられた（目印を一意に引く検索・正確な対象の列挙で、取りこぼしのない範囲で目印がないことを確認）→ 印を外して `awaiting_approval` に戻す。承認は失効済みなので、本人が承認し直す（内容版は変えない。送出の準備では通常どおり最新の対象と許可を確認する）。(3) どちらも確かめられない（目印を持てない操作の種類・元サービスに接続できない・再認証がまだ・列挙が不完全）→ `unknown_held`（結果不明）で保留する。自動では再送せず、本人が元サービスで確かめる（08 §3）。単に見つからないことは未実行の証拠にしない。
  - **ラベル変更の送出前の確認だけでは足りない**: 既存の送出準備の検査は、対象の版と許可の確認で、下書きの作成のように「作ったもの」の重複を、目印を探す照合の経路とは別に持つ。作成の操作は、この隔離と照合を通らない限り再承認・送出できない。
  - バックアップより後に作った操作の記録は復元で失われ、この照合の相手がない（下の「未解決」）。
- **時刻の規則**（Codex P2）: `started_at`・`finished_at` は実測の UTC。終わりが始まりより前になれるのは、**期限切れの削除の段階で `clock_regression`（処理中に時計が戻ったと判定した）で止めた拒否だけ**で、そのときは実測の値をそのまま記録する（時刻を補正せず、戻ったこと自体を結果に残す）。ほかの結果（復元できた結果、ほかの理由の拒否）の時刻の逆転は `finished_before_started` で拒否する。処理の長さは単調時計で別に測る（ログ。結果の契約には持たない）。

### 期限切れ・忘却の知らせ（`RetentionNotice`・`RetentionNoticeItem`）

キャンバス向け。**ID と理由だけ**で、本文・要約・検索語を持たない。

- 形は 2 通り（Schema の `oneOf`）: `expired`（理由は `retention_due`・`review_unanswered`・`summary_origin_expired`。世代は null）と `forgotten`（理由は `forgotten`・`derived_from_forgotten`。台帳の世代を持つ）。理由と種類の組が合わないものは拒否する。
- 対象は `turn`・`source_item`・`memory`・`carried_summary`（要約をつないだ区間の ID。ADR 0032 の `CarriedSummary` は由来の区間の ID と期限だけを持つ）。ID は空白・日本語を含められない文字種に限る（本文を ID の欄に入れられない）。1 件の知らせに最大 256 件。
- UI-05 は、知らせの対象を参照するキャンバスの物（`CanvasDataRef` の対象。由来から表示の物への対応は UI-05 が持つ）を表示から外す。期限の時刻の切り分け（最も早い由来の期限で要約全体を捨てる）は ADR 0032 のとおりで、B06 は期限が来た事実を知らせるだけ。
- **運び方は決めていない**（U40）: `EventEnvelope` は操作の ID を必須にしていて、操作に結び付かない知らせは載せられない。UI-05 の表示のリースと一緒に、キャンバスの応答に載せるか新しいイベントの種類にするかを決める。

### 保存モードの状態（`StorageModeState`）

区切りの保存モードごとに、何を保存し何を禁じるかを固定の値で持つ（Schema は `normal`・`extended`・`private` の 3 通りの値を `const` で固定する）。

| 項目                                                                                  | normal | extended | private                                                          |
| ------------------------------------------------------------------------------------- | ------ | -------- | ---------------------------------------------------------------- |
| 発言・要約の保存、記憶の保存・抽出、影モードの記録（`persist_*`・`save_memory` ほか） | する   | する     | しない（設計 03・10。X17・X59。要約は RAM だけで終了時に捨てる） |
| Live の接続（`open_live`）                                                            | 開ける | 開ける   | 開けない（既存の接続は開始時に閉じる。`admitLiveStart` は 409）  |
| 端末内の音声認識（`local_asr`。③）                                                    | 使う   | 使う     | 使う（質問 110）                                                 |
| 発言の保存期限（`turn_retention_days`）                                               | 7 日   | 30 日    | なし                                                             |
| 操作記録（`operation_record`）                                                        | full   | full     | `minimal_after_confirmation`（独立した確認の後の最小の記録だけ） |

クライアントは表示にだけ使う。判定は Core のコード（B06 の StorageModeGate）が持つ。`private` が `persist_turns: true` や `open_live: true` を名乗る状態は Schema が拒否する。区切りの選び方（`private_started`・`private_ended` など）は UI-05（ADR 0032）。

### 復旧キーと鍵の包み（`RecoveryKeyDisplay`・`RecoveryKeyRecord`・`BackupKeyWrap`）

J1 を次の形にした（原本は「本人が管理する復旧用秘密で保護」までで、形は原本に決めなし）。

- **復旧キー（司令塔の判断: 案 A）**: **CLI のプロセス**が OS の乱数で作る 256 ビット。人が書き写せるよう Crockford base32（4 文字 × 13 組。I・L・O・U を使わない）で、作った直後に 1 度だけ端末の画面へ出す（`RecoveryKeyDisplay`）。**Core には渡さない**（Core に渡すのは、包んだ鍵 `BackupKeyWrap` と確認値だけ）。制御チャネル・HTTP・イベント・ログ・DB・バックアップへ出さないので、ADR 0012 の「制御チャネルは秘密を扱わない」は緩めない。CLI のプロセスは、同じ OS の利用者として KeyStore からデータ鍵を読み（ADR 0017。読むだけで作らない）、バックアップ本体の鍵を作って KeyStore に置き、2 つの鍵を復旧キーで包んでから、復旧キーを破棄する（メモリ上の消去は保証できない。ADR 0017 のとおり）。
- **記録**（`RecoveryKeyRecord`）: 復旧キーの ID・作成時刻・確認値（`check_value`）・表示した時刻。Core は復旧キーを知らないので、確認値は CLI が復旧キーから別の用途ラベルで導いた 32 ビットを Core へ渡す。復元で入力したキーの打ち間違いを先に見つけるためだけに使う（32 ビットでは復旧キーを導けない）。表示済みの記録は再表示できない。表示した時刻と状態の組が合わないものと、復旧キーそのものを持つものは Schema が拒否する。
- **鍵の包み**: 復旧キーは高エントロピーの乱数なので、パスワード用の KDF（scrypt など）を使わず、HKDF-SHA256（salt 付き）で導いた鍵で AES-256-GCM により包む（Node.js の標準の `node:crypto` だけで足りる）。包んだ値は 12 バイトの nonce・32 バイトの暗号文・16 バイトの認証タグ。包む鍵は 2 つ（バックアップ本体の鍵・DB の暗号文の鍵）。包むのは設定のときの CLI（上の「バックアップの封筒」）。

### バックアップの置き場所（`BackupConfig`・`BackupLocationCheck`）

- 設定ファイルはリポジトリの外のローカルに置き、起動時に Schema で検査して読む（予算の設定と同じ方式。ADR 0034・0037）。ディレクトリは絶対パスで、`..` を含められない。保持する世代の数は 1〜30、初期値は 7（03）。知らない設定の項目は拒否する。ファイルの置き場所・読み込みは B06-08、編集の画面はキャンバス UI の置き場所が決まった後。
- 同期フォルダーは使えるが警告する。検査の結果は `warnings` に `sync_folder_detected` と種類の手がかり（`icloud`・`onedrive`・`dropbox`・`google_drive`・`other`）を持つ。判定の方法（パスの規則か OS の API か）は原本に決めなし（B06-08）。警告の理由は、同期の機能がクラウド側に古い版を残すと、忘却と期限で消したバックアップが残り得ること（03 の「利用者がアプリ外へ複製したファイルの物理消去までは保証しません」の範囲）。

## 経路: OpenAPI に足すか、ローカルの制御（CLI）だけにするか（U40）

設計 07 §2 の API 表に、記憶・台帳・バックアップの経路はない。設計判断として次のように分ける。経路は**この PR では足さない**（応答の形・認可・表示権限の確認を、実装の Issue で一緒に決めるため。司令塔の判断で U40 の知らせの運び方は UI-05 で決める）。

| 操作                                                                       | 経路                                 | 理由                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 記憶の一覧・見直し待ちの明示継続（U14）・ID を指定した忘却                 | OpenAPI（B06 の実装の Issue で足す） | D04・質問 17 は記憶を一覧で確認・訂正・忘却できるとする。クライアントは Windows・MacBook で、中枢の機器の前にいるとは限らない。本文を返す一覧は表示の権限が full の端末だけ（management_only・ロック中は 403）         |
| 忘却台帳の端末への複製の取得                                               | OpenAPI（同上）                      | 端末へ複製するための経路が必要。本文なしで、登録済み端末だけ。端末が持つ最新の世代以降の項目と head を返す案                                                                                                           |
| バックアップの実行・置き場所の検査・一覧、復元、復旧キーの表示、台帳の検証 | ローカルの制御（CLI）だけ            | 復旧キーは HTTP・イベント・ログに出さない（J1）。復元は DB の世代を新しくし全承認を失効させる破壊的な操作で、リモートの端末から起動させない（J3）。J6 のとおり全消去は作らない。操作は中枢の機器の前の本人の操作に限る |

- **ADR 0012 との関係**: ローカルの制御チャネルは今 `status`・`stop` だけで、「本文・秘密は扱わない」と決めている。復旧キーの表示はこの前提に触れるので、**司令塔の判断で案 A に確定**した: CLI のプロセスが乱数を作って端末の画面にだけ出し、包んだ値と確認値だけを Core に渡す（秘密は制御チャネルを通らない。ADR 0012 は緩めない）。復元・バックアップの実行の操作（制御チャネルの `op` の追加）は B06-08。
- 記憶の一覧の応答は `MemoryRecord`（本文を持つ）を使う想定で、ページ分けと表示権限の検査は実装の Issue で決める。`memory_forget` の操作は既存の LocalCommand（ADR 0004）の経路を使い、ID を渡す。

## memory_forget の確定内容に検索語を残さない（U41）

`memory_forget` の引数は対象の ID か検索語（ADR 0004・`IntentArgs` の `target_candidate_id`・`query`）。次を規則にする。

1. **検索語は解決のためだけに使う**: Core が検索語を RAM で記憶・由来に当てて対象を解決し、確定する操作の内容（`OperationIntent`。内容の hash・暗号文の対象）には、解決した対象の ID（`MemorySourceRef` の `source_kind`・`source_id`）だけを入れる。検索語の文字列は、確定内容・内容の hash・操作の受付・イベント・台帳・ログ・通知のどこにも残さない。
2. **曖昧なら聞き返す**: 検索語が複数の対象に当たる、または 0 件のときは、確定せずに聞き返す（候補は画面に出す。候補の本文は表示の権限の範囲）。本人が選んだ対象の ID だけが確定内容に入る。
3. **理由**: 内容の hash は J5 で 90 日残り、短い検索語の hash は辞書で当てられる。台帳は消さない（追記だけ）ので、検索語が残ると「何を忘れたか」が永続する。台帳には本文なしの ID と HMAC だけを置く（ADR 0008）。
4. **忘却の指示の発言そのもの**（原本に決めなし。**司令塔の判断で確定**）: 「〇〇を忘れて」という発言には〇〇が含まれ、通常の会話では全文が 7 日残る。この発言を、忘却の適用と同じ transaction で消す（対象の発言として台帳に記録し、文脈・要約から外す。設計 03 の「対象部分を文脈選択と自動要約から外す」と同じ扱い）。台帳にはその発言の ID だけが残る（`forgotten` の `turn`）。忘却の指示が音声（Live）の文字起こしなら同じ扱い。

## 記録しない会話の最小の操作記録（U42）

03 は「記録しない会話から外部変更を頼まれたら、会話本文を保存せず、必要な操作記録を残す独立した確認画面へ切り出し、その記録内容を示して一度承認を得る。要約メモとして黙って保存しない」とする。中身を次のように決める（原本に決めなし）。

- **残すもの**: 操作の ID・内容版・内容の hash・操作の種類（意図の名前）・接続の ID（外部サービスのアカウントを指す ID）・対象（元サービスの ID と版）・変更の内容（確認画面に出した、元サービスへ実際に渡す内容）・承認（経路・端末・時刻）・試行と工程の状態・外部 ID・結果・照合の根拠・作成と完了の時刻。これは通常の操作の記録（`operations`・`operation_versions`・`approvals`・`operation_attempts`）と同じ表で、確定内容の暗号文は J5 で完了の 7 日後に消え、hash とレシートは 90 日残る。
- **残さないもの**: 発言の本文・文字起こし・音声・要約・解釈の結果（意図の判定・LLM の出力）・発言の ID・会話（session）・依頼（workflow）・入力の版（input_snapshots）・影モードの記録・記憶の由来。操作から記録しない会話へたどれる ID を持たない。
- **確認画面に出すもの**: 上の「残すもの」の変更の内容と、「会話の内容は保存されない」こと。承認は一度。要約メモとして保存する経路はない。
- **0001 との関係**: `workflows.session_id` は NOT NULL で `sessions` を参照し、`sessions.storage_mode` に `private` がないので、記録しない会話からは `workflows`・`sessions` の行ができない。記録しない会話から出た操作は `operations.workflow_id` が NULL。これを DB の制約にする案: `operations.record_kind`（`normal`・`private_minimal`）を足し、`private_minimal` なら `workflow_id IS NULL` を CHECK にする（ほかの列に会話へのつながりを持たせない）。判定そのものは StorageModeGate が持ち、DB は private の会話の行がない形で最後の保証をする。
- 予算の予約の行（受付・精算の ID・金額・枠）は会話の内容を持たず、記録しない会話の LLM の呼び出しでも予算のために残す（J4 の規則）。診断ログは ID・状態・時間・件数・費用だけ（03）。

## 忘却の関連の判定（U43）

非同期の結果（要約・記憶の候補・表示・次の送信）を保存・表示・送信する直前の検査（08 §6）で、「忘却と関係があるか」を次のように判定する。実装は ADR 0008 の `memoryAdmission` が既にそのとおりで、ここでは規則として固定する。

| 結果の開始時の世代と今の台帳の世代 | 由来が忘却と関係する | 判定                                                                                                |
| ---------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------- |
| 等しい                             | しない               | 通す                                                                                                |
| 等しい                             | する                 | 破棄（`source_forgotten`・`content_forgotten`）。世代が同じでも、忘れた由来から作った結果は通さない |
| 開始より進んでいる                 | しない               | 通す。無関係な忘却で世代が進んだだけでは破棄しない                                                  |
| 開始より進んでいる                 | する                 | 破棄                                                                                                |
| 開始の後の世代が台帳に揃っていない | —                    | 破棄（`forget_ledger_gap`）。忘却済みかを判定できない                                               |
| 開始の世代が今の台帳より大きい     | —                    | 破棄（`generation_ahead`）。台帳が巻き戻っている                                                    |

- **「関係する」の定義**: 結果の由来（`MemorySourceRef`）のどれかが、台帳の `forgotten` と同じ（種類と ID）、または台帳の `blocked_source_ids` に元の ID がある（同じ元のメッセージ全体を自動記憶化から外す。03）、または自動抽出の候補の内容の HMAC が台帳の `blocked_content_keys` にある。台帳は全件を見る（世代の新旧によらない）。
- **派生**: 忘れた記憶から作った記憶は、忘却のときに台帳へ派生として記録する（`forgotten` に入れる）。台帳に載っていない派生物は由来を引けない（下の「派生物の系譜」）。
- **本人の明示の保存**（`memory_save`）は内容の禁止だけでは止めず、由来が忘却済みなら止める（ADR 0008）。

## J5 終わった操作の本文の削除（マイグレーション 0008 の案）

**SQL は B06-06 で書く。** 0001 の保存案に次の不足がある。

1. **不変の trigger**: `operation_versions_immutable` は `BEFORE UPDATE ON operation_versions` のすべての更新を拒否する。本文（確定 intent の暗号文）を消すための `intent_blob_id` の更新も拒否される。
2. **NOT NULL**: `operation_versions.intent_blob_id` は `NOT NULL UNIQUE REFERENCES sealed_blobs`。暗号文の行を消すと外部キーに違反し、列を NULL にもできない。
3. **参照する表**: `approvals`・`operation_attempts`・`tasks`（0005）が `operation_versions` を複合の外部キーで参照する。`operation_attempts`・`auto_actions`・`undo_records`（2 列）・`request_entity_operations` が `operations` を参照する。表の作り直しは、0006 の前例どおり子の表を先に作り直して値を移す必要がある。
4. **用事の正本が操作の暗号文にある**（Codex P1）: 0005・ADR 0030 の `tasks` は題名・期限・本文を持たず、確定 intent（`operation_versions` の暗号文）を参照する。`task.create` の操作は成功で完了するので、そのまま J5 の 7 日削除を当てると、**まだ open の用事の中身が消える**。さらに `tasks` は `operation_versions` を外部キーで参照するので、90 日の削除も外部キー違反で失敗する（`request_entity_operations` が `operations` を参照することも同じ）。

J5 の本人の意図は、**終わった操作の本文を長く残さない**こと。生きている用事（`tasks.status` が `open`、または本人が残している `done`）の正本を消すことではない。03 は「本人が確定保存したメモ・用事は本人の削除操作を正とし、元会話の全文をその中へ隠して保存しない」とする。

### 用事の正本の置き場所（決定: 操作のレシートから分ける）

- **採る案**: **用事の正本を操作のレシートから分ける**。`tasks` が自分の暗号文（題名・期限・本文。`tasks.content_blob_id`。`owner_table = 'tasks'`、`owner_id = task_id`）を持ち、操作の確定 intent の暗号文は J5 のとおり 7 日で消える。用事は本人の削除操作で消える（03）。メモ（`user_notes`。B09 以降の LocalCommand）など、これから増える「LocalCommand が作る本人の確定内容」も同じ形（その行が自分の暗号文を持つ）にそろえる。
- **理由**: (1) J5 を操作の種類によらず一様に当てられる（「結果の実体がまだ生きている操作は除く」という、別の表の状態に操作の行の寿命を結び付ける例外がいらない。例外は、メモ・予定の記録など LocalCommand が増えるたびに増える）。(2) 操作のレシートは 90 日で消すもので、用事の寿命（本人が消すまで）とは別。`tasks` が `operation_versions` を外部キーで参照していると、用事が生きている間は操作を消せず、90 日の削除が成り立たない。(3) 操作の内容に結び付いた承認・hash・試行の記録は、用事の内容とは別の監査の記録として 90 日で消えてよい。
- **移行**: 0005 の `tasks` の行は暗号文を持たず、確定 intent の暗号文を指している。owner が変わると暗号化の追加認証データ（所有者の表・ID・版・用途。ADR 0017）が変わるので、**SQL だけでは暗号文を写せない**。順序は、(1) Core の起動時のデータ移行で、確定 intent を復号して用事の内容（題名・期限・本文）だけを取り出し、`tasks` を所有者にして暗号化し直す、(2) 書き込んで復号して読み戻し、(3) その後で、`tasks` の外部キーを外す（表の作り直し。`operation_id` の UNIQUE は残す＝同じ操作から用事を二つ作らない最終の保証は消さない）、(4) 最後に J5 の本文の削除を有効にする。(1)〜(3) が済むまで J5 の削除の job を動かさない（起動時のゲート）。
- **purpose の追加**: `sealed_blobs.purpose` の CHECK（0001）に用事の本文の用途がない（`proposal`・`request_summary` などは別の意味）。新しい用途（`task_content`）を足すには `sealed_blobs` の CHECK を変える必要があり、参照する表が多いので表の作り直しは大きい。B06-06 で見積もり、B06 の範囲で終わらないときは下の代案を、その間だけ入れる。
- **代案（B の移行が間に合わないときの一時の形）**: 結果の実体がまだ生きている操作（`tasks` に行がある `task.create`）の確定 intent の暗号文と操作の行を、**J5 の 7 日・90 日の対象から除く**。用事の行が消えた後に、通常の規則（完了から 7 日・90 日。起点は用事を消した時刻ではなく操作の `completed_at` なので、消した時点で期限が過ぎていれば次の掃除で消える）を当てる。この形は用事の行が消えるまで確定 intent が残る（J5 の例外）。採らないのは上の理由のとおりだが、用事の暗号文を残したまま J5 を有効にしてしまう事故（未完了の用事を消す）を避ける安全側。

### 本文の削除と 90 日の削除

- **本文の削除（完了から 7 日）**: 対象は完了（`succeeded`・`not_executed`・`cancelled`・`superseded`）した操作。`unknown_held` は完了ではなく、照合のために本文を残す。操作の `completed_at` から 7 日（`workflow_result`）で、`operation_versions` の確定 intent の暗号文と、同じ依頼の `proposal`・`request_summary` の暗号文を消す。**用事（`tasks`）の暗号文は、操作の本文の削除の対象ではない**（上の移行の後は `tasks` が所有者）。
- **列の形**: `operation_versions.intent_blob_id` を NULL にできるようにし（表の作り直し）、`body_deleted_at` を足す。CHECK は `(intent_blob_id IS NULL) = (body_deleted_at IS NOT NULL)`。`content_hash` は NOT NULL のまま残す（90 日残す hash）。
- **trigger**: 全更新の拒否をやめ、「`intent_blob_id` が NULL でない状態から NULL になり、`body_deleted_at` が同時に NULL から値になり、ほかの列が同じ」更新だけを許す。内容版・hash・作成時刻の更新は引き続き拒否する。削除は同じ transaction で、`intent_blob_id` を NULL にしてから `sealed_blobs` の行を消す（外部キーの順序）。
- **90 日の削除の順序**: 操作 X（完了から 90 日。`unknown_held` でない。取り消しの相手の補償の操作が完了していない間は消さない）について、1 つの transaction で次の順に消す。どの時点でも外部キーの違反を作らない。
  1. `undo_records`（`operation_id = X`、または `compensation_operation_id = X`）
  2. `auto_actions`（`operation_id = X`）。`undo_records` が参照しているので 1 の後
  3. `operation_steps`（X の試行の）
  4. `operation_attempts`（`operation_id = X`）。`approvals` を参照しているので 3 の後、5 の前
  5. `approvals`（`operation_id = X`）。`operation_versions` を参照しているので 6 の前
  6. `operation_versions`（`operation_id = X`）。**`tasks` が参照していない**ことが条件（上の移行の後は参照がない。代案の間は、`tasks` に行がある操作を除く）
  7. `operations`（`operation_id = X`）。**`request_entity_operations` が参照していない**ことが条件
  - **`request_entity_operations`**: 「同じ依頼・操作種別・アカウントにつき自動作成は一度だけ」「取消後の再作成抑止」（11 §5A・X65）の記録で、寿命は依頼（`request_entities`）の `delete_at` に従う。操作の 90 日より長く残るので、`operation_id` の `REFERENCES operations` を外し（表の作り直し。UNIQUE は残す）、操作を消した後も残す。外さないと 90 日の削除が外部キーで失敗するか、再作成の抑止が 90 日で消えて同じ依頼から二重に作れてしまう。
  - **`undo_records`・`auto_actions`** は完了から 30 日（`undo_window`）で消すが、補償の操作がまだ終わっていなければ、補償の操作が終わるまで残す（`undo_records` が補償の操作を参照するため）。
  - 参照している表はこれで全部（`operations`・`operation_versions` を参照する外部キーを 0001〜0007 から洗い出した）。B06-06 の試験は、`tasks`・`request_entity_operations`・`auto_actions`・`undo_records`・承認・試行・工程の行をすべて持つ DB で、この順序の削除が外部キー違反なしに通ることと、順序を入れ替えると失敗することを確かめる。
- **旧内容版の本文**（原本に決めなし）: 内容が変わって `superseded` になった旧い内容版の本文は、その操作が完了するまで残る（案。早く消す案もあるが、旧版の取消・照合に使うかを実装の Issue で確かめてから）。
- **試験**: 本文の削除の後も、同じ hash の再送・承認の照合・結果の表示ができること。消えた本文から実行を始められないこと（`intent_blob_id` が NULL の内容版を送出しない）。open の用事の内容が、操作の本文の削除の後も読めること。

## J4 予算の記録の削除（マイグレーション 0008 の案）

対象は `budget_reservations`（ADR 0036）と、その行を指す `live_sessions`・`budget_overage_approvals`。本文を持たないので暗号文の削除は関係ない。

- **消してよい行**: 状態が `settled` または `released` で、`settled` の行は M 超過の確認が済んでいる（`overrun_reviewed = 1`、または実費が M 以内）もの。`reserved`・`usage_unknown`・M 超過の確認待ちの行は手で精算（または確認）するまで消さない（J4）。
- **起点と期限**: 予算月の締め（次の予算月の始まり。`budget_months` のその月のタイムゾーンで求める）から 13 か月後。期限は起点から一度だけ計算して行に保存する（`delete_at`。ADR 0010 の規約）。精算・解放・確認で消してよい状態になった時点で書き、それまでは NULL。
- **DB の最終ガード**: `BEFORE DELETE` の trigger で、`delete_at` が NULL の行（消してはいけない行）の削除を拒否する。時刻との比較は DB worker が持つ（`isDue`）。
- **外部キーの順序**: `live_sessions`（`reservation_id` が NOT NULL UNIQUE で予約を参照）→ `budget_overage_approvals`（`consumed_reservation_id` が予約を参照）→ `budget_reservations`。使われなかった承認（`pending`・`rejected`・`expired`）は承認を求めた月の同じ規則で消す。
- **`budget_months`・`budget_month_confirmations`**: 追記だけの記録（書き換え・削除の trigger がある）で、本文も金額も持たない。13 か月の対象にせず残す。
- **集計との関係**（不足の指摘）: 利用状況（`BudgetUsageSummary`）の月ごとの精算額・未精算額は予約の行から数える。行を消すと、その月の集計も消える。月の途中で一部の行だけが消えると、その月の使用額が少なく見える（手で精算するまで残る行だけが残り、精算済みの行が消えるため）。**司令塔の判断で、月ごとにまとめて消す**: その月のすべての行が消してよい状態になるまで、その月の行を 1 つも消さない。J4 の「月の締めから 13 か月」と同じ読みで、使用額が部分的に少なく見えるのを防ぐ。この規則は、手で精算するまで残る行がある月の精算済みの行を、13 か月より長く残すことがある（少なく数えない側）。行ごとに消す案は、集計に「この月は一部の記録が期限で消えている」の印（`budget_months` の列。契約の変更）が要るので採らない。
- **親子の枠**: 親の枠の数は子孫の枠の分を含む（ADR 0006）。消すのは行なので、子と親の数は同じ行の集合から数え続け、「子の合計が親を超えない」の検査は消した後も成り立つ。
- **今月の受付への影響**: 受付は今月の行だけを数える（ADR 0036）ので、13 か月前の行の削除は受付に影響しない。

## マイグレーション 0008 の案（そのほかの不足。SQL は B06-06）

0001 の保存案を B06 の規則に当てて見つけた不足を、次の案にまとめた。

- **memories の暗号文が NOT NULL**: `memories.text_blob_id`・`target_key_blob_id` は NOT NULL で、`status = 'deleted'` の行（CHECK）が暗号文なしで残る形にならない。**司令塔の判断で、物理削除に確定**: 期限・忘却で消すときは行ごと消す（`memory_sources` → `memories` → `sealed_blobs` の順）。台帳が「消した」記録の正本になる。`MemoryRecord.status` の `deleted` は DB の行の状態ではなく、操作の結果の表現に使う。存在しない由来は期限切れとして扱う（閉じた側。`source_expired`）。忘却は台帳が残る。ほかの案は暗号文の列を NULL 可にして `deleted` の行を残すが、`dedupe_key` が残り、期限切れ（再登録を禁じない）の再抽出を止めてしまう。
- **workflows.session_id と記録しない会話**: 上の「記録しない会話の最小の操作記録」のとおり。`operations.record_kind` を足し、`private_minimal` は `workflow_id` を持てない。
- **復元後の未確認の印**: 上の「復元の結果」のとおり。`operations.restore_unverified_at`（NULL でないとき、承認の作成・`approved` と `preparing` への遷移・試行の作成を拒否する trigger を付ける。外部サービスを変える操作だけに付く）を足す。
- **secure_delete**: 暗号文の行を消しても、WAL と空きページに暗号文が残る。暗号文なので鍵がなければ読めないが、忘却を「消した」と言えるように次を案にする。`connection.sql` に `PRAGMA secure_delete = ON`（`pragmaReasons` の読み戻しの対象に足す。ADR 0016）、削除の後に `PRAGMA wal_checkpoint(TRUNCATE)`、一定の間隔で `VACUUM`（マイグレーションの外の実行時の job。ADR 0016 はマイグレーションでの VACUUM を禁じている）。SSD の痕跡消去までは保証しない（03）。
- **派生物の系譜**: `memory_sources` の `source_kind` は `turn`・`source_item`・`memory` だけで、これらから作った派生物の多く（会話の要約 `sessions.summary_blob_id`、気づきの題・抄録 `notification_candidates`、依頼の抽出結果 `request_entities`・`related_analyses`、`async_context_guards.source_refs` の JSON、`intent_shadow`）が系譜に載っていない。忘却がこれらに届かない。案は、`memory_sources` を一般化した `derivations`（`artifact_kind`・`artifact_id`・`source_kind`・`source_id`）を足し、派生物を作る transaction で由来を必ず書く。忘却の transaction は由来をたどって派生物の暗号文・行を消す。台帳は根の由来（`turn`・`source_item`・`memory`）だけを持てばよく、復元の「忘却の適用」は復元した `derivations` をたどって派生物を消せる。**系譜が揃うまでの安全側**: 判別が不確かな派生物は、同じ元のメッセージ・会話全体を除外する（03）。台帳の項目の種類（`MemorySourceRef`）に派生物を足す契約の変更は、この案を採ったときに行う。
- **古いバックアップへの忘却**: 03 は「アプリ管理下の古いバックアップにも忘却・期限を適用し、必要に応じて置換または削除」とする。案は、忘却の後、新しいバックアップを作ってから、忘却の世代が古い封筒（`forgetting_generation` が今の台帳の世代より小さいもの）を削除する。世代の保持（初期 7）は忘却の後に一時的に少なくなる。復元の段階 3 でも台帳を適用するので、消し残した古いバックアップから忘れた内容が復活することはない。同期フォルダー側に古い版が残るかは保証しない（警告の理由）。

### 原本に書いてあること（読み取り）

- 03 保存期限: 通常会話は発言の生成から 7 日、継続相談は 30 日、許可された要約は 90 日で見直し待ち・30 日未応答で削除、生音声は保存しない、記録しない会話は全文・音声・要約を永続保存しない。完了した依頼の結果・未確定案は原則 7 日、完了後の本文なし操作レシートは 90 日、自動実行の取り消しの情報は 30 日。
- 03 忘却と再取り込み: 忘却時に対象と派生要約を削除し、元の由来 ID に再登録禁止を付ける。同じ元メッセージ全体を除外する保守的な扱い。HMAC で同じ情報の再取り込みを検出するが、言い換えまでは保証しない。
- 03 バックアップ・復元: 本人が選んだ場所に 1 日 1 回、暗号化して作る。生音声・記録しない会話・OAuth トークン・API キーを含めない。復元後の外部サービスは再認証。鍵は本人が管理する復旧用秘密で保護する。DB は整合したスナップショットを取る。保持は初期 7 世代。忘却台帳は本文なしの別ファイルで、端末にも複製する。復元は最新台帳の確認 → 期限切れの削除 → 忘却の適用 → DB 検証 → 画面・索引の再生成 → 外部状態照合の順。最新の台帳が確認できないときは記憶・会話の復元を許可せず、新規開始か非機密設定の復元だけにする。
- 03 記録しない会話の境界: Buddy 内に保存しない。クラウドへ送った情報までは保存ゼロにならない。音声（Live）は閉じる。③（端末内で文字にする）は使える。外部変更が要る場合は、会話本文を保存せず、必要な操作記録を残す独立した確認画面へ切り出す。
- 08 §4: 設定違反・DB 破損・古いバックアップからの復元では、`preparing` を未送出と判断せず、03 の復元後の照合を行う。08 §5: `operation_versions` の確定内容と hash は不変、本文を別の無期限ログへ複製しない。08 §6: 忘却と非同期結果の競合（遅着の結果の破棄）。
- 09: X15（遅着要約の保存・表示・送信 0、同じ由来から自動記憶が復活しない）、X16（古いバックアップと欠損した台帳で記憶・会話の復元を拒否）、X17（記録しない会話の永続保存 0、最小の操作記録だけ）。

## 試験

契約の fixture `packages/contracts/fixtures/storage-contract-cases.json`（92 件。Codex のレビューの再現を足した）を `pnpm run contracts:check` が Schema と意味検査で確かめる。期待値は手書きで、検査する関数から作っていない。台帳の hash は、`{entry, previous_hash}` を Python の `json.dumps`（キーの整列・区切りなし。値は ASCII だけで RFC 8785 と同じ正規形）で書き出し、`hashlib` の SHA-256 で別に求めた値を写した（検査するのは Node.js の `canonicalize` と `node:crypto`）。

- **正常例**: 台帳（3 世代・空）・複製・封筒（世代 3・空の台帳）・復元の結果（復元・外部の照合が保留・台帳が失われて設定だけ・台帳より新しいバックアップ・DB の版が新しい）・知らせ（期限切れ・忘却・派生）・保存モード 3 種・復旧キーの記録と表示・置き場所の設定と検査。
- **拒否例（依頼の 4 つ）**: **世代の欠番**（`x16-ledger-file-generation-gap`）、**hash の連鎖の不一致**（`x16-ledger-file-hash-chain-broken`。内容の書き換え `x16-ledger-file-entry-rewritten` と末尾を隠した head `x16-ledger-file-head-behind`、世代 1 のない部分の複製 `x16-ledger-replica-partial-copy` も）、**private を含むバックアップ**（`x17-backup-manifest-includes-private-rejected`・`only-private`・除外の記録に記録しない会話がない封筒）、**本文の混入**（台帳の entry・連鎖の 1 件・封筒・復旧キーの記録・知らせの対象と知らせ本体の追加の欄、知らせの `item_id` に文を入れた例）、**知らせに本文が入る**（`x15-notice-item-with-body-field-rejected`・`x15-notice-with-summary-field-rejected`・`x15-notice-item-id-is-sentence-rejected`）。
- **Codex のレビューの再現**（各件の入力を手書きで足した）: ID の欄への文（`x16-ledger-turn-id-sentence-rejected`・`memory-id-sentence`・`turn-id-not-internal-id`・`source-item-id-sentence`・`source-item-id-too-long`・`blocked-source-id-sentence`・`blocked-source-id-japanese`・`blocked-source-id-too-long`・複製 `x16-ledger-replica-id-sentence-rejected`）と 256 文字ちょうどの境界の正常例（`x16-ledger-file-boundary-256-char-source-ids`）、包んだ状態の `duplicate_forgotten`（ファイル・複製）、時計の巻き戻りの拒否の時刻の逆転（`x16-restore-clock-regression-rejected`）と、それ以外の逆転の拒否（`x16-restore-reversed-time-other-failure`・`x16-restore-ledger-stop-reversed-time`・`x16-restore-restored-reversed-time`）、隔離した操作の件数の欠落と保留との大小（`x16-restore-aftermath-without-unverified-count-rejected`・`x16-restore-held-exceeds-unverified`）。復元後の隔離・用事の正本の分離・90 日の削除の順序は SQL を書く B06-06 で試験する（この ADR は案）。
- **そのほかの拒否例**: 復元の段階の順序の入れ替え・欠け、失敗の後に実行された段階、設定だけの復元が台帳の確認以外で出る、DB の世代が新しくならない復元、段階と合わない理由、外部の照合の失敗、記録しない会話で Live・保存・記憶の抽出・完全な操作記録を名乗る保存モード、再表示を許す復旧キー、小文字・短い・読み間違えやすい文字を含む復旧キー、相対パス・`..` を含む置き場所。
- `scripts/common-contracts.test.mjs` に新しい版の項目（`backup_store_generation`・`new_store_generation`・`applied_forgetting_generation`・`db_schema_version`）の型を登録した（ADR 0003）。

**模擬の期待値だけ**。台帳の書き出し・複製・バックアップ・復元・期限処理・StorageModeGate・復旧キーの作成の製品の実装と試験は未実施。`tests/test-map.json` の X15・X16・X17 の `product_test` は `not_run` のまま（契約 fixture の合格を製品試験の合格として扱わない）。実機の Mac mini での実際のバックアップと鍵の復元は B15。

## 判断の記録

初版で「判断が要る点」にしていた事項は、司令塔の判断（上の「司令塔の判断」）で確定した。本文はその確定を前提に書いた。この PR のレビューで加わった判断は次のとおり。

1. **用事の正本を操作のレシートから分ける**（J5 の「用事の正本の置き場所」）。B06-06 で `sealed_blobs` の用途の追加が重すぎると分かったときだけ、一時の代案（用事の行がある操作を J5 の対象から除く）を入れる。
2. **台帳に署名・HMAC は付けない**（「限界」）。真正性ではなく、破損・欠落・古い複製の検出のための hash の連鎖と割り切る。
3. **隔離の印を DB の trigger で守る**（復元の結果）。実装の細かい形は B06-05・B06-06。

## 未解決

- バックアップより後に作った操作の記録は復元で失われ、同じ変更の重複を検出できない（元サービス側の目印、たとえば下書きの目印に操作 ID を入れる方式の範囲に限られる。原本に決めなし）。復元した記録にある未完了の操作は、上の隔離と照合で重複を防ぐ。
- hash の連鎖は真正性を証明しない（上の「限界」。内容を書き換えて連鎖を最後まで計算し直した台帳は、すべての検査を通る）。台帳の最後の数件を丸ごと切り落とした古い複製だけが残った場合も、連鎖は壊れない。封筒の `forgetting_generation`・`ledger_head_hash` と、中枢・端末の複製の head の比較で検出する（ADR 0008 の `restoreReasons`）。すべての複製が同じように古ければ、03 のとおり「最新の台帳が確認できない」ことになり、記憶・会話は戻さない。
- 台帳の大きさの上限・複製の失敗の再試行・端末が複製を持たないまま使われる期間は未決（実装の Issue）。
- 復元の「外部の状態の照合」は、OAuth トークンを持たない状態から始まる（再認証が先）。再認証前の結果不明の操作の表示は UI-05・B04。
- 実機の Mac mini での復旧キーによる鍵の復元（キーチェーンを失った状態）・同期フォルダーの挙動・SSD の削除の痕跡は B15。
