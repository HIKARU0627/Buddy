# ADR 0149: B13-04 気づきの候補から用事を自動で登録する配線（判定の事実の読み取りと操作の作成）

- 日付: 2026-11-26
- 状態: B13-04（親 #24）の Core の配線の部分。用事の登録（`create_task`、LocalCommand）だけをつなぐ。ラベル・下書き・予定の書込み、取り消しの補償の中身、候補の生成の入口からの呼び出しは未着手。実データ・実機・実 API は未実施。
- 根拠: 設計 11 §5・§5A・§5B（F05）、設計 08 §1・§9、設計 04（自動実行の範囲と既定 OFF・初回取り込み）、設計 06 B13、ADR 0103・0146・0147・0148。原本の参照手順は `docs/design/README.md`。
- 対象: `packages/storage/src/auto-execution-state.ts`（DB worker の読み取り `auto_execution_state`）、`apps/core/src/candidate-auto-execution.ts`、それぞれの試験。契約（`packages/contracts`）とマイグレーションは変えない。

## 背景

ADR 0146 は 1 つの候補の 1 つの操作の判定（`judgeAutoExecution`）を domain に置き、ADR 0148 は候補を起点にした自動承認の最終ガードを保存層に置いた。しかし判定に入れる事実のうち DB に正本があるもの（安全停止・時間窓の件数・候補の状態・依頼の版と作成済みの操作）を Core が読む口が無く、判定から操作を作る配線も無かった。

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 判定の事実の読み取り | DB worker の読み取り `auto_execution_state` を足す。安全停止・方針による自動承認の時間窓・忘却の世代・候補の行（種類・状態・依頼の ID と版）・依頼の現在値（状態・抑止・版・作成済みの操作）を一つの読み取り transaction で返す。作成済みの操作のカレンダーなし（DB では空文字）は null にして判定に渡す。本文は読まない |
| 読み取りと照合の関係 | 読み取った値は判定の材料にすぎない。作成の transaction で保存層が同じ値を読み直して照合する（ADR 0148）。Core の判定が通っても保存層が断れば作らない                                                                                                                                                                     |
| 判定しない候補       | 候補が無い・閉じた候補・依頼を持たない候補・依頼が無い・依頼の版が候補の版と違うときは、どの操作も判定しない（`skipped`）                                                                                                                                                                                                |
| 判定する操作と順     | 判定表の 4 行（用事・予定・ラベル・下書き）をこの順にすべて判定し、結果を返す。予定はカレンダーが無ければ選択済みとはせず、気づきだけにする（重複キーがカレンダーを必須にするため）                                                                                                                                      |
| つなぐ操作           | `auto_eligible` の用事の登録だけ操作を作る。ラベル・下書き・予定は判定が通っても作らない（`not_wired`）。付けるラベル・下書きの本文・予定の内容を決める口がまだない                                                                                                                                                      |
| 用事の内容           | 題は依頼の要約を候補の題と同じ検査（60 文字・断定の題の置き換え）に通し、期限と差出人は付けない（U306）。期限は日付だけなら日付のまま（D15）、時刻があれば地域日時。本文は空にし、メールの文を写さない                                                                                                                   |
| 期限のタイムゾーン   | 期限のタイムゾーンが本人の設定と違うときは変換せず、作らない（`deadline_zone_mismatch`、U305）。期限が未解決のときも作らない                                                                                                                                                                                             |
| 作成の命令           | 確定 intent を契約（`OperationIntent`）で確かめて暗号化し、方針による自動承認（方針の版・現在の版・同じ対象の鍵）と候補の起点（候補・アカウント・カレンダーなし）を付けて `operation.create` へ送る。保存できたら実行器の `afterApproval` で実行を始める                                                                 |
| 同じ対象の鍵         | 操作の種類・アカウント・元のメールの JSON の配列を SHA-256 にし、`auto:` を前に付ける（U304）。メールの ID を DB の平文の列に残さない                                                                                                                                                                                    |
| 拒否・成否不明       | 保存層が断った（`rejected`）・成否不明（`unknown`）の作成は、作り直さずに結果として返す（U302）                                                                                                                                                                                                                          |

## 原本に決めがない項目

- 同じ対象の反復（設計 03）の「対象」を、候補起点の自動実行では元のメールとした（U304）。用事の一覧やアカウント全体にすると、別々のメールからの用事で止まる。
- 期限のタイムゾーンが本人の設定と違うときの扱いは書かれていない。変換すると日付が変わることがあるため、自動では作らないとした（U305）。
- 自動で登録する用事の題に、期限と差出人を入れるかは書かれていない。期限は別の項目に入るため、要約だけにした（U306）。

## 対象外

- 候補の生成（`persistCandidateDrafts`）の後にこの配線を呼ぶ入口。抽出・関連解析の計画・方針・許可の版を揃えて渡す処理は、メールの取り込みの流れ（B08・B10・B11）とつなぐときに足す。
- ラベル・下書き・予定の書込みと、Outlook のカテゴリ付与を承認待ちの案にする経路（`needs_approval`）。
- 取り消しの補償の操作の中身と、対象の現在版の検査。照合で拒否した操作の後始末と画面（B13-05）。

## 試験（模擬だけ）

- `apps/core/src/candidate-auto-execution.test.ts`: 期待値はすべて手書き。DB は実物の SQLite で、worker の代わりに同期で命令を実行する。用事だけ方針で有効なときの 4 行の判定と理由・承認済みの操作・承認の行の版・一度だけの記録・確定 intent の中身（題・日付だけの期限・空の本文）・鍵にメールの ID が無いこと、既定の方針では何も作らないこと、二度目は作成済みで気づきだけ、安全停止中の保留、初回取り込みと関連解析の未完了、Core の判定が通っても DB の新しい解析の版で保存層が断ること（件数に数えない）、候補が無い・閉じた・依頼の版の変化、ラベルは `not_wired`、予定のカレンダー、期限のタイムゾーンと未解決、題と鍵の形。
- `packages/storage/src/auto-execution-state.test.ts`: worker を介した読み取りの値（時間窓・忘却の世代・作成済みの操作の並びとカレンダーなしの null）、候補が無い・依頼の無い候補・安全停止。

**模擬の期待値だけ**。候補の生成の入口からの呼び出し・ラベルと下書きの書込み・画面・実データ・実機・実 API は未実施で、合格扱いにしない。`tests/test-map.json` の X21〜X24・X39〜X41・X61〜X65 は、入口からの統合試験で更新する。
