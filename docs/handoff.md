## 家計簿の設計方針

本人の決定（本人の言葉の要旨）:

- 外部の家計簿サービス（マネーフォワード ME）を Buddy の内部機能で置き換え、将来は外部のサービスを使わない。家計の正本は Buddy の中に置く（U318）。
- 本人の手間をできる限り減らし、できるだけ早く（リアルタイムに近く）取り込む。
- 段階 1 から作り始める。
- 銀行・外部の家計簿サービスへはサインインしない（口座の直接の読み取りは事業者との契約が前提で、個人では作れない）。

段階の分け方:

- 段階 1: カード会社の利用通知メールからの自動登録（自動の分類、本人による分類の変更と削除）、暗号化した保存、月の集計、外部の家計簿サービスの CSV を一度だけ取り込む移行。
- 段階 2: 定期の支出（サブスクリプション・公共料金）を見つけて固定費と予算を出す。請求のメールは「請求予定」として支払い済みと分ける。
- 段階 3: メールの届かない支出の補い（レシートの写真、会話の一言、明細の CSV）と、突き合わせによる二重の登録の防止。

本人の一度きりの作業は、各カードの会員サイトで利用通知メールを有効にすることだけ、という前提で作っている。

設計の要点:

- 家計の記録は承認・自動実行の操作を通さず、Buddy 自身の記録として DB の命令で作る（ADR 0158）。
- 平文に置くのは月・状態・出所の種類・出所の鍵（SHA-256）だけ。金額・日付・分類・店名は暗号文。集計は Core が復号して計算する。
- 分類はマネーフォワード ME の大項目 16 個に「その他」「未分類」「収入」「振替」を足したもの（U319）。本人が分類を直すと、店名の HMAC を鍵にした規則として覚え、次の同じ店の未分類の利用に当てる。
- 利用通知の送り主は、公式の案内に載った送信元のドメインと、受信サーバーが付けた DMARC・DKIM の合格で確かめる（ADR 0159・0160）。

## 試験の動かし方

- 全体: `pnpm run check`（doctor・書式・契約・lint・ビルド・型検査・試験・情報管理の検査。手元で 15 分ほど）。
- 一部だけ: 対象の workspace で `pnpm run build` の後に `node --test dist/<名前>.test.js`。domain の規則の試験は `scripts/household-notice.test.mjs` などで、`packages/domain` のビルドの後に `node --test scripts/<名前>.test.mjs`。
- コミットの前に `pnpm run security:staged`、push の前に `pnpm run security:scan`。
- 公開物の検査は、`example.com`・`example.org`・`example.net`・`example.invalid` 以外のメールアドレスの形を拒む。試験の送り主は合成の一覧を引数で渡している（`checkHouseholdNoticeSender` の第 2 引数、`createHouseholdMailIntake` の `issuers`）。検査を避ける書き方はしない。
- マイグレーションを足すときは、試験の中の DB の版、`migrations.test.ts` の一覧と表の数、`packages/domain/src/backup-plan.ts` の表の分類、`packages/storage/src/policy.ts`、`tests/fixtures/backup-restore-cases.json`、`backup-store.test.ts` と `apps/core/src/backup.test.ts` の除外の一覧、`packages/storage/migrations/README.md` をそろえて直す。
