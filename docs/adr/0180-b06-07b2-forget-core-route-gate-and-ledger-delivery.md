### 忘却の途中・後の守り（U383）

- **途中**: 忘却は 1 つの `BEGIN IMMEDIATE` の transaction で、台帳の追記・物理削除・送出禁止の印を書く（ADR 0054）。COMMIT の前は何も消えておらず、COMMIT の後は消えている。途中の状態を外から読めない（SQLite の書込みの直列）ので、途中の間だけ閉じる門は要らない。計画と実行の間は、まだ何も忘れていない。
- **後（遅れて届いた結果）**: 記憶の保存（`memory.save`）は transaction の中で台帳の全件と照合する（ADR 0040 U43・0054）。進行中の操作は送出禁止の印で送出の直前に止まる（`operation_send_blocked`）。期限の掃除が済むまでの検索・クラウド送信・自動利用は掃除のゲート（`retention.gate()`、ADR 0053）が閉じている。
- **表示**: 消した物の ID を `RetentionNotice` で `NoticeSink` に渡す（運び方は UI-05）。画面の経路の忘却は、発言の忘却と違って流れの区切り（`forget_requested`、ADR 0068）を起こさない。区切りにつないだ要約（RAM）の扱いは残り（下の「残り」）。

## 範囲を区切った理由と残り

依頼の目安（3,000 行）と、Issue の工程の順（07b-2 の Core の経路と公開ゲートが先、画面 UI-10・端末側の保存 #179 はその後）に合わせて、次をこの段階に入れなかった。

- **memory_save・memory_correct の Core の経路**: 記憶の保存の API の応答で、保存しなかった理由（`memory_conflict_review_required` など。U111）を本人に返すこと、既存の記憶の利用保留の要否（U111 の条件）、保存してよい記憶の種類の設定（既定は空。#180 の Q10）。memory_correct は忘却の確認の画面を使う（#180 の Q3）ので、この段階の計画と実行をそのまま使える形にしてある。
- **発言（「〇〇を忘れて」）からの忘却**: 解釈から対象の解決（domain の `resolveForgetTarget`。0 件・複数は聞き返す）、指示の発言（`instruction_turn_id`）を計画に入れること、流れの区切り（`forget_requested`）とつなぐこと。今の文字の発言は忘却を受け付けず聞き返しを返す（ADR 0068）。
- **memory_forget の操作の LocalCommand への組み込み**（U389）と、`commandGuard` の絞り込み（U62）。
- **記憶の一覧の経路**（#180 の左の一覧）。本文を返すので表示の権限が full の端末だけ（ADR 0040）。
- **画面の経路での忘却の後の流れの区切り**（U383）と、知らせの運び方（UI-05、U40）。
- **端末側の台帳の保存**（#179）。配信の契約と Core 側までをこの段階で作った。
- **忘却の台帳の配信が全件を読む件**: `getForgetLedgerEntries` は要求のたびに DB の台帳の全件を書き出して（`forget.ledger_export`）から続きを切り出す。台帳は本文を持たず件数も小さいので今は直さない。件数が増えたら、端末の head 以降だけを DB で読む命令にする。
- **画面操作の根拠が端末の申告するヘッダーである件**: 計画・実行の「本人の画面操作だけ」の検査は、端末が申告する入力の起源のヘッダーを根拠にしている（端末トークンと自宅判定は別に通す）。直さず、UI-10 のときに hub_screen（中枢の画面だけ）を求めるか決める。
- **07a-2 の残り**（ADR 0059・0060 の引き継ぎのまま）: 2c（`StorageModeGate` の命令を保存先へ結び付け、記録しない区切りの発言を RAM で受け取り、出るときに捨てる。結果の由来の照合）、2d（独立した確認と最小の操作記録 `record_minimal_operation`）。
- **B06-09**（#145）: 統合試験・証拠・B06 の完了判定。

## 見直しでの追補（計画の数・成否不明の応答・結果の再送）

読むだけの見直しの軽微な指摘を、同じ段階で直した。新しい未決事項は足さず、U384 に追記した。

- **計画の数の上限**: 端末ごとの未実行の計画は 1 件。同じ端末が新しい計画を作ると、その端末の古い未実行の計画を捨てる（実行中・実行済みの計画は捨てない）。他の端末の未実行の計画が 64 件（`FORGET_MAX_PENDING_PLANS`）に達していれば、新しい計画を `too_many_plans` で断り（HTTP は 503 dependency_unavailable）、何も捨てない。上限ちょうどの 64 件目は作れる。同じ端末の置き換えは上限に数えない。
- **成否不明の応答**: 確定の成否が分からない実行（`outcome_unknown`）だけ、HTTP 503 のコード `outcome_unknown` を返す。既存の契約に成否不明を表す HTTP のコードはなかった（`outcome_unknown` は端末内の IPC の拒否にだけあった）ので、`ApiError.code` の値に足した。計画は捨てたので再試行しても残っておらず（409）、消えた可能性があることが端末に分かる。計画の照合以外の拒否（`apply_rejected`）・ゲートが閉じている（`forget_gate_closed`）は何も消していないので、従来どおり 503 dependency_unavailable。
- **結果の再送**: 結果を持つ計画は、期限の判定より先に同じ結果を返す。結果を持つ計画は期限から追加で 10 分（`FORGET_RESULT_RETENTION_MS`）控え、過ぎたら捨てる（`plan_not_found`）。結果を持たない計画の期限（10 分、`plan_expired`）は変えない。

## 試験（模擬だけ）

期待値は手で書いた（合成の世界から ADR 0044・0054 の閉包の規則で導いた件数・消える物・台帳の項目、手で組んだ台帳の連鎖）。計画の関数・配信の関数から期待値を作っていない。HMAC は試験用に決めた 64 桁の値。

- `scripts/forget-review.test.mjs`（10 件）: 計画の見せ方（種類ごとの件数・記憶と指示の ID・行のある操作と系譜だけの節点の区別・読めない状態の扱い・1000 件の境界と 1001 件の拒否）。配信の判定（空の端末に全件・head の続きだけ・追いついたら 0 件・256 件の頁と続き・hash の食い違い・系譜の違い・系譜のない部分の複製・端末が進んでいる・中枢の連鎖の欠番・空の台帳）。
- `apps/core/src/forget-service.test.ts`（14 件。DB は一時ディレクトリ、命令は同じプロセス）: ゲートが製品で閉じていること。ゲートが閉じている間は計画も実行もせず、適用の命令が 0 回・台帳が動かない・知らせが 0 件。鍵がなければ計画しない。対象がなければ計画しない。計画の時点では何も消えず、実行で消える物だけが消え、由来の発言・関係のない記憶は残り、進行中の操作は状態と版を変えずに送出禁止の印だけが付き、台帳の項目・ファイル・知らせが手で導いた値になる。同じ計画の再送・同時の実行で一度だけ消す。二重の忘却（同じ記憶の 2 つ目の計画は取り直しを求め、捨てた計画は使えず、取り直すと対象がない）。計画の後に派生物が増えたら何も消さずに取り直させ、取り直した計画で消える。関係のない忘却で世代が変わったら取り直させる。別の端末・違う世代・知らない計画・ちょうど 10 分の期限。成否不明の実行を送り直さない。台帳のファイルを書けなくても忘却は確定し、端末は DB の台帳から受け取れる。経路の処理の 503・409・200 と契約の形。配信の経路（空・2 世代・連鎖・head の続き・追いついた後・食い違い・進んだ複製）。
