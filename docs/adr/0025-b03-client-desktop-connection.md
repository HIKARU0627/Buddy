# ADR 0025: 端末側の接続（packages/client）とデスクトップの中枢への接続・2 クライアントの試験

- 日付: 2026-10-21
- 状態: B03-05（#66）の判断と実装。端末側の接続の状態機械（`packages/client`）、デスクトップの main の中枢への接続（TLS のピン留め・ws・ペアリング・safeStorage での保存・接続状態・ロック状態の申告・自宅の指紋の報告）、IPC の契約の追加、HeroUI のペアリング画面（UI-01 #71 の土台の上）、同じマシンの 2 クライアントの統合試験を作った。試験は模擬（CI の 3 OS）で、実機（別のマシン・Tailscale・Mac mini のキーチェーン・Windows の safeStorage）は未実施。手順は [docs/b03/device-check.md](../b03/device-check.md)。
- 根拠: 設計 02（端末登録と接続・保存と秘密情報）、07 §2〜§4、09 §2・§8、X04・X11・X42、ADR 0009・0014・0015・0020〜0024。設計本文は今回の作業環境に取得できず、Issue #66 の要約と ADR に基づく。原本との照合はレビューで行う。

## 接続の状態機械（packages/client）

```text
idle → bootstrapping → snapshotting → subscribing → live
          │  ↑ cursor があり DB 世代とロック状態の表示が同じなら snapshotting を省く
          ↓
   waiting_retry（間隔を空けて bootstrapping へ）・upgrade_required・reregistration_required（以後は要求を送らない）
```

| 対象             | 決定                                                                                                                                                                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| bootstrap        | 接続し直すたびに取り直し、新しい接続範囲（command_scope_id）を使う（07 §3）。形式は契約の Bootstrap で検査する                                                                                                                                                                                           |
| API の版         | `checkApiVersion`（domain の `apiCompatibility`、端末の major は `[1]`）。合わなければ `upgrade_required` で、スナップショット・購読・再接続をしない。形式の違う版（`01.0` など）も使わない                                                                                                              |
| スナップショット | ロック解除済みなら full、ロック中・不明なら management_only（中枢の判定。端末も表示しない）。bootstrap と DB 世代が違えば取り直す                                                                                                                                                                        |
| 購読と cursor    | WSS は `?cursor=`（ADR 0023）。受け取ったイベントの event_cursor を追い、再接続では DB 世代が同じなら cursor から購読して欠けたイベントを受け取る（スナップショットを省く）。DB 世代が違う・`resnapshot_required`・4410・cursor の 422 はスナップショットから                                            |
| イベントの反映   | domain の `applyEvents`（重複・古い版を捨てる。連番の飛びだけで欠落と判定しない）。版が進んだ操作は `getOperation` で表示用の値を取り直す（イベントは ID と版だけで状態を持たない）。同じ操作の取り直しは一つにまとめる                                                                                  |
| 閉じるコード     | 4410 → スナップショットから（1 回目はすぐ、続けば間隔を空ける。数は購読の ping・イベントを受け取ったら数え直す。live になっただけでは数え直さず、開いた直後に求められる繰り返しを間隔なしで続けない）、4401 → 再登録が必要、4403 → 自宅の外として待つ、1001・1011・1013・切断 → 間隔を空けて cursor から |
| HTTP の拒否      | 401 → 再登録が必要、403 `outside_home_network` → 待つ、429・503 → 待つ、それ以外 → protocol_error として待つ。証明書の不一致 → 再登録が必要（要求は送っていない）                                                                                                                                        |
| 再接続の間隔     | 1 秒から 2 倍ずつ、上限 60 秒、±20% の揺らぎ。live になれば数え直す                                                                                                                                                                                                                                      |
| 生存の確認       | 中枢の ping（15 秒）・メッセージを 45 秒受け取らなければ切れたとみなす                                                                                                                                                                                                                                   |
| 命令             | `send` は live でなければその場で `not_sent`（ためない。復帰しても送らない）。本人が見ていた接続範囲と今の接続範囲が違う・ロック中も送らない。送った後に結果が分からなければ `unknown` で、自動で再送しない                                                                                              |
| ロック状態       | `setLockState` でロック・不明になったら操作の表示をすぐ捨て、management_only のスナップショットを取り直す。解除で full を取り直す（購読は開き直さない）。購読の途中（live の前）に変わった分は、live になった直後に表示の範囲と今のロック状態を比べて取り直す（レビューの指摘 M1）                       |

## デスクトップの main

### TLS のピン留め（証明書の完全一致）

- 登録した中枢へは、TLS 1.3 の確立の後に、中枢が示した証明書が保存した証明書と **DER で完全に同じ**で、DER 全体の SHA-256 が指紋と同じときだけ要求を書く。照合の前には何も書かない（WSS も照合を終えた TLS の接続の上で切り替える）。TLS の確立で中枢がその証明書の秘密鍵を持つこと（CertificateVerify）は TLS が確かめる。
- 信頼の起点（`ca`）による連鎖の検証は使わない。**Electron の BoringSSL は、CA でない自己署名の証明書（ADR 0020 の中枢の証明書。基本制約 CA:FALSE）を信頼の起点として受け付けず、ピン留めした中枢でも `UNABLE_TO_VERIFY_LEAF_SIGNATURE` になる**（Node の OpenSSL では通るため node:test では見えず、ローカルの Electron で見つけた）。完全一致は連鎖の検証より狭い（その 1 枚だけを受け付ける）。この扱いはこのモジュールの接続だけで、アプリ全体の検証（`NODE_TLS_REJECT_UNAUTHORIZED`・既定のエージェント）は変えない。
- ペアリングの最初の接続（`fetchPeerCertificate`）は ADR 0021 と同じく、証明書を受け取ったら何も書かずに閉じる（この接続だけ `rejectUnauthorized: false`）。
- 証明書の不一致（再登録が必要）とするのは、この完全一致の照合で合わなかったときだけ。名前に CERT・SIGNATURE などを含む TLS・OpenSSL のエラーは、連鎖の検証をしないこの接続では中枢の証明書が変わった証拠にならないので、接続できない（待つ）として扱う（レビューの指摘 L6）。

### トークンの保存

- トークン・端末 ID・発行時刻と、中枢の宛先・証明書・指紋を一つの記録にし、safeStorage で暗号化して userData の `device-credential.bin`（0600、一時ファイル → fsync → rename）に置く。暗号化の結果に平文のトークンが残っていれば保存しない。
- 保存の前に、書く記録を読み戻せる（`parseCredential(serialize())` が通る）ことを確かめ、読み戻せなければ保存しない（`not_readable`）。宛先は domain の正規化（`normalizeHubHost`）を通した値だけを受け付ける（レビューの指摘 L2: 末尾のドット付きの名前でペアリングすると、契約では通るのに保存した記録を読み戻せず、毎回「再登録が必要」になっていた）。
- 保護の判定: macOS・Windows は `isEncryptionAvailable()`。Linux は加えて backend が `gnome_libsecret`・`kwallet`・`kwallet5`・`kwallet6` のときだけ。`basic_text`・不明・他の OS は保存せず、ペアリングも始めない（`secure_storage_unavailable`）。
- 復号できない・形が違う記録は「再登録が必要」。401・証明書の不一致の後も記録は消さない（再登録で上書きする）。
- トークンは `SecretText`（文字列化・JSON・inspect で `[redacted]`）に包み、Authorization ヘッダーにだけ入れる。画面・IPC・ログ（理由のコードだけ）に出さない。

### ロック状態を中枢へ伝える経路（Buddy-Lock-State）

ADR 0020・0023 ではロック状態の判定の元が中枢になく（既定 unknown）、ロック解除を求める経路は常に 403、スナップショットは常に management_only だった。端末の OS のロック状態の正本は端末にしかないため、**要求ヘッダー `Buddy-Lock-State: unlocked | locked`** を足した（OpenAPI の `components.parameters.LockState`、任意）。

- 端末の main が端末状態（ADR 0015 の OS の通知・問い合わせ）から付ける。unknown のときは付けない。Renderer は付けられない（要求は main が作る）。
- 中枢は端末トークンで認証した要求の申告だけを使い、ない・認証前は unknown（解除済みと扱わない）。列挙にない値・重複はどの経路でも 422。注入した環境（試験）が優先する。
- OpenAPI では、ロック解除を求める経路（`unlocked` の検査）と `getSnapshot` の 22 経路に宣言した（表と一致することを試験で確かめる）。
- 端末はロック状態が変わるとスナップショットを取り直すので、中枢の表示の範囲もそこで変わる。

### 接続状態と状態欄

- `DesktopConnectionView`（契約）: 登録（未登録・登録済み・再登録が必要・安全な保存なし）、接続（未接続・接続中・接続している・待つ・版違い・再登録が必要）、理由、最終確認時刻、次の接続の時刻、ペアリングの手順、自宅の判定（許可・免除・理由のコードだけ）、操作の表示用の値（接続しているときだけ）。ロック中・不明は `visibility: hidden` だけ。
- 状態欄の `hub_connection`・`hub_last_confirmed_at` は接続の状態機械から作る。**接続中でも中枢がまだ正本を配っていない値（表示先・保存モード・予算保留・安全停止）は null（不明）にできるよう、ADR 0014 の意味検査（connected_without_values）を変えた**（接続中は最終確認時刻だけ必須。接続していなければ中枢の値は必ず null のまま）。作り物の値を「接続中」の正本として見せないため。

### 自宅の指紋の報告

- 5 分ごと（中枢は 6 分の間だけ使う）、接続口の変化（`os.networkInterfaces()` の値の変化を 15 秒ごとに確かめる）、スリープからの復帰、自宅の外で拒否されたときに、`@buddy/platform/home-fingerprint` で集めて `POST /v1/home-network/reports` で送る。契約の形に合わない要素は null にする。
- 判定が通れば、自宅の外で待っていた接続をすぐに接続し直す。指紋の値は報告の本文にだけ入れ、画面・ログに出さない。
- 再登録が必要・版違い（upgrade_required）になれば報告を止める（以後は中枢へ要求を送らない。版違いはレビューの指摘 L4 で足した）。

### ペアリングの宛先（本人の判断 2026-10-21・レビューの指摘 L2・L3）

`desktop.pairing_begin` で受け付ける宛先を次に限り、それ以外は受付の段階で `pairing_host_not_allowed` で拒否する（最初の接続も行わない）。判定は domain の純粋な関数 `admitPairingHost`（`packages/domain/src/hub-host.ts`）で、境界の値を手書きの期待値で試験する（`scripts/hub-host.test.mjs`）。

| 宛先                                         | 理由                                                                                                                                                                                                                                                                                  |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 100.64.0.0/10（100.64.0.0〜100.127.255.255） | Tailscale が各端末に割り当てる IPv4（CGNAT の範囲）                                                                                                                                                                                                                                   |
| fd7a:115c:a1e0::/48                          | Tailscale が各端末に割り当てる IPv6（Tailscale の固定の ULA の接頭辞）。100.x と同じ Tailnet の中のアドレスで、信頼の扱いは同じ。除くと、Tailscale の IPv6 で中枢を指定した本人を拒否することになるため含めた（中枢が IPv6 で待ち受けていなければ接続できないだけで、危険は増えない） |
| 127.0.0.0/8・::1                             | 中枢と同じマシンのクライアント（最初の端末・中枢の画面）と、CI の模擬の試験                                                                                                                                                                                                           |
| `*.ts.net` の名前                            | Tailscale の MagicDNS の名前（`<マシン>.<Tailnet>.ts.net`）。`ts.net` そのもの・似た名前（`evilts.net`・ts.net の後ろにさらにラベルが続く名前）・短い名前（`mac-mini`）・`localhost` は受け付けない                                                                                   |

- 目的は、打ち間違い・誘導で Tailnet の外の宛先へ申請（ワンタイムコード・自宅の指紋を含む）を送らないこと。中枢の確かめは従来どおり、本人が比べた証明書の指紋とピン留めで行う（この制限は信頼の根拠ではない）。100.64.0.0/10 は ISP の CGNAT にも使われるため、範囲に入ることは Tailscale であることの証明にはならない。
- IPv4 射影の IPv6（`::ffff:100.64.0.1` など）・リンクローカル・私設のアドレスは受け付けない。
- 宛先は正規化して使う（名前は末尾のドットを一つ除いて小文字、IPv6 は小文字、IPv4 はそのまま）。画面の `pairing.host` と保存する宛先は正規化した値。
- 名前の形の正規表現は一つ（domain の `HUB_HOSTNAME_PATTERN`）。契約の `DesktopHubHost` の名前の分岐は `format: hostname` をやめ、同じ文字列を `pattern` に置いた（一致を試験で確かめる）。端末の保存は「正規化した値と同じか」で判定する。
- 画面の文言は「Tailscale のアドレス（100.x.x.x）か、〜.ts.net の名前を入れてください。」。

### 2 クライアントの試験（Issue #66 の完了条件）

同じプロセスの Core（127.0.0.1、模擬の KeyStore、Core の既定のロック状態の判定）と、デスクトップの main の部品の 2 つのクライアント A・B（模擬の safeStorage）。A は最初の端末の CLI の承認（制御の入口）、B は A を中枢の画面の端末として開始・承認する。どちらも画面の手順（指紋の確認の前の申請は拒否・違う指紋は拒否）を通る。

1. **未登録は 401・失効**: 形式の正しい未登録のトークンは 401 で再登録が必要。B が A を失効すると A は 4401 で切断されて再登録が必要（操作の表示を捨て、命令を送らない）、B は接続したまま取消を送れる。失効した A のトークンで起動し直しても 401。
2. **証明書の差し替え**: 鍵の項目を消した中枢（新しい鍵・証明書）に対し、A・B とも証明書の不一致で再登録が必要。中枢は前の証明書で登録した端末を失効している（有効な端末 0 台）。
3. **中枢の再起動**: 停止中は A・B とも待ち、切断中の取消は `not_sent`。再起動（起動時の回復で送出意図の操作が unknown_held）の後、A・B とも新しい接続範囲・新しい起動 ID・同じ DB 世代で再接続し、スナップショットを取らずに cursor から購読して欠けたイベントを受け取り、その操作だけを取り直して、同じ ID・版・状態（中枢の DB の値と同じ）を表示する。切断中の取消は送られていない（命令の要求なし・中枢の状態は変わらない）。
4. 各試験で、画面へ出した値（応答・通知）・ログ・保存したファイルにトークンの平文がないことを確かめる。

API の major の違いは、実際の中枢の版が一つのため `connection.test.ts` の模擬の通信で確かめる。期待値は手書きの値か、中枢（別の実装）の値・`X509Certificate#fingerprint256` で、検査対象のクライアントの関数から作っていない。各試験に時間の上限、後始末は後に登録したものから先に（閉じてから削除）。

`--use-mock-keychain`（実機のキーチェーンに書かない）と一時の userData で Electron を起動し、模擬の鍵保護の Core（CLI、127.0.0.1）と CDP で次を確かめた（スクリーンショット・記録はリポジトリに入れていない）。

## 読み取り（レビュー対象）

- **ピン留めを証明書の完全一致にした**: 本人の判断「アプリ全体で証明書の検証を無効にしない」を、この接続の連鎖の検証を完全一致に置き換える形で守った（連鎖の検証より狭い）。中枢の証明書を CA:TRUE にする案は、ADR 0020 の証明書の中身と全端末の指紋を変え、Node と BoringSSL の両方で別の確かめが要るため採らなかった。
- **Buddy-Lock-State は端末の申告**: 中枢はロック状態を確かめられない（端末の OS の状態）。端末トークンを持つ main の申告を、`Buddy-Input-Origin`（ADR 0009）と同じく信頼する。トークンを盗まれた場合はロック解除の申告もできるが、トークンの照合・自宅判定・接続範囲が先にある。
- **接続していないときは操作を画面に出さない**: 状態機械は値を持ち続け（再接続で cursor から続ける）、画面には接続している間だけ出す（古い値を今の値に見せない）。
- **再接続でスナップショットを省く**: DB 世代が同じでロック状態の表示も同じなら cursor から購読する（欠けたイベントを受け取り、変わった操作だけを取り直す）。中枢が cursor を使えないと判断すれば再スナップショットになる。
- **数値**: 再接続の間隔（1〜60 秒・±20%）、生存の確認 45 秒、受取りの間隔 3 秒、接続口の確認 15 秒、受け取ったイベント ID の記憶 1,000 件は設計に数値がないため仮に決めた。
- **再登録が必要の後も記録を消さない**: 再登録で上書きする。OS の鍵束の作り直しで読めなくなった記録も同じ扱い。
- **ペアリングの失敗は最初から**: コードの誤り（410）でも begin（証明書の受取りと指紋の確認）からやり直す。
- **自宅の指紋の報告は中枢と同じマシンの端末でも送る**: 中枢が免除と判定して返す（判定は中枢が持つ）。
- **未実装の経路の 503**（ADR 0020 の読み取り）: 端末は 503 を「待つ」として扱い、命令は自動で再送しない。
- **tests/test-map.json**: X04・X11・X42 の端末側を模擬で確かめたが、実機・B04 の模擬サービスを含む全体ではないので `product_test` は not_run のまま。
