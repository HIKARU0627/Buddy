# ADR 0011: 生成型・CI・試験対応表と B00 の完了判定

- 日付: 2026-10-20
- 状態: B00-10（#29）の判断。B00 の終了条件は揃ったと判定する。製品の実装・統合試験・実機・実 API・実請求の試験は、どれも未実施。
- 根拠: 設計 09 §1〜§8、06 の必須試験 T01〜T10 と B01〜B15、docs/b00/README.md の終了条件、ADR 0002〜0010。

## CI のゲート

`pnpm run check`（CI の 3 OS で実行）に、次の 2 段を含めています。

1. `contracts:check`: schema から型をクリーンに生成し、`packages/contracts/src/generated.ts` との差分がゼロであることを確かめる（`generate-contract-types.mjs --check`）。続いて、schema の厳格なコンパイル、全 schema の正常例・拒否例、OpenAPI の構文と参照を検査する（`check-contracts.mjs`）。
2. `scripts/contract-gate.test.mjs`: 作業ツリーの写しを一時ディレクトリに作り、わざと壊した 6 種類の契約をゲートが拒否することを確かめる。リポジトリのファイルは変えない。
   - 型が古いまま
   - schema の未解決の参照
   - schema の不正なキーワード
   - OpenAPI の未解決の参照
   - 拒否例を受理扱いにした fixture
   - 重複キーのある fixture

ゲートの検査が無効になっても CI が通り続けることがないように、2 段目では「壊れた契約が落ちること」自体を試験しています。

## 試験 ID の対応表

`tests/test-map.json` に、X01〜X66・QA01〜QA45・MA01〜MA06 の 117 件を記録しました。

| 項目                | 内容                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `phases`            | 担当工程（B01〜B15）。契約対応表の「利用」の列から取りました                                                              |
| `contract_fixtures` | 期待値を手で書いた契約 fixture（ファイル#ケース）。59 件にあります                                                        |

| `status`            | `contract_fixture`（契約 fixture で期待値を検査済み）か `specified`（仕様と担当工程だけ）。どちらも製品試験の合格ではない |
| `product_test`      | 116 件が `not_run`。QA29 は H03（確定前の先読み）を後回しにした決定のため `deferred`                                      |

試験（`scripts/test-map.test.mjs`）では、117 件が一度ずつあること、担当工程があること、fixture の参照先に試験 ID とケースが実在すること、契約対応表に出てくる試験 ID がすべて対応表にあることを確かめます。合格を表す値も置けません。

## B04 へ渡すもの

`tests/integration/fault-points.json` に、09 §4 の故障点と、X01〜X11 の故障の入れ方・期待値をまとめました。

- **模擬サービスの約束**: 中枢の再起動とは独立して状態と受信記録を保持し、重複要求を自動で消しません。記録は operation_id・attempt_id・step_id・受信順・適用した変更・応答の有無です。
- **期待値**: 要求回数と状態変更回数を分けます。試験装置だけが知る真の結果（`provider_truth`）と、中枢が観測できる結果（`core_observed`）も分けます（09 §5A の注記）。状態の並びは `operation-transitions.json` を正本とし、承認件数・外部要求の回数・最終状態が一致することを試験で確かめます。
- **証拠の形式**: `tests/integration/test-evidence.schema.json` は 09 §8 の項目（ケース ID・コミット・契約版・DB 版・構成・seed・故障点・要求回数・状態変更回数・承認件数・最終状態・観測時刻・期待との差・音声の停止時間）を持ちます。模擬・実機・実 API・実請求を `kind` で分け、本文・音声・鍵の項目は置けません。

| 代表的な正常入力と拒否入力を検証できる                                   | schema-cases 152 件、30 経路の要求・応答と拒否（ADR 0009）、各工程の手書き fixture                                                         |

| H01 と内容差分・不正 Unicode・重複 JSON キー・時刻・順序の検証例がある   | h01.json・content-hash-cases.json・生の JSON の拒否試験・時刻とイベント順の試験（ADR 0002・0003・0009）                                    |

| domain の境界と storage のキー・一意制約・暗号化範囲・削除期限が整合する | 保存案 0001 と domain の規則の対応表、node:sqlite での制約の試験（ADR 0010）                                                               |
| X01〜X66 / QA01〜QA45 の対応と実施状態を追跡できる                       | `tests/test-map.json` と試験（本 ADR）                                                                                                     |
| 実装者が推測する未決事項が残っていない                                   | 台帳の未決事項 U01〜U18 はすべて本人の回答で解決済み。残りは後続工程で実装する規則と実測・実接続の検証で、意味の判断は残していない（下記） |

判定: **B00 の終了条件は揃った**。B01（Electron 共通アプリと独立 Node.js 中枢、型付き端末内 IPC）に着手できる。B04 の X01〜X11 は、B01〜B03 の最小実装の後に、本 ADR の故障点と期待遷移で実行する。

## 後続へ残すもの（ブロッカーではない）
