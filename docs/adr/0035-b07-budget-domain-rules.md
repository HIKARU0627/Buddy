## 決めたこと

| 対象                               | 決定                                                                                                                                                                                                                                                                                                                                                                                                                             | 原本との関係                                                                                            |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| M（`computeLiability`）            | 課金区分ごとに「1 要求の最大量 × 単価 × 為替 × 安全係数」を求めて足す。最大量は、入力は実際に送る量、出力は profile の出力上限、ツール・検索・会話の秒は呼出し上限。量を示さない区分は版の `max_quantity_per_request`。最低課金量（会話の 15 秒）を下回る量は最低課金量にする。`cached_input_tokens` は M に入れず、入力はすべて非命中の単価で見積もる（キャッシュの区分の量を渡したら拒否 `cached_input_not_estimated`）        | 05 F02・固定部分の節の式どおり                                                                          |
| 単価の境界                         | 課金され得る期間（受付の時刻から応答の期限まで、両端を含む）に掛かる同じ系列の版をすべて選び、区分ごとに、換算と安全係数を掛けた後の金額が高い方を使う。版の適用期間は開始を含み終わりを含まない（ADR 0034）。期間の一部でも版がなければ `price_not_covered`、掛かる版のどれかが確認されていなければ `price_unverified:<版>`                                                                                                     | 05 F02 は「適用され得る単価の高い方」とだけ書く。区分ごとに選ぶこと・換算後に比べることは原本に決めなし |
| 拒否                               | 上限も送る量もない区分（`unbounded_category:<区分>`）、単価のない区分（`unpriced_category:<区分>`）、版の最大量を超える要求の量（`quantity_exceeds_max:<区分>`）、換算後の通貨が予算の通貨と違う（`currency_mismatch`）、合計が Amount の 18 桁を超える（`amount_overflow`）                                                                                                                                                     | 05 F02「価格・為替・課金上限を固定できない場合は開始しない」                                            |
| 丸め                               | 区分ごとに、予算の通貨の百万分の一の単位へ切り上げてから足す。合計を一度だけ切り上げるより少しだけ大きく、少なく見積もらない。計算は BigInt の分数で行い、浮動小数点数を使わない                                                                                                                                                                                                                                                 | 原本に決めなし（ADR 0034 で B07-02 に残していた）                                                       |
| R（`computeReservation`）          | 指定した profile（意図判定の比較 profile）だけ、出力の量を p95 × 1.2（token を切り上げ、profile の出力上限まで）にして M と同じ単価・同じ境界の規則で計算する。指定外は `not_designated`、測定がない・別の profile の測定は `p95_unmeasured`、測った後に profile の版（出力上限・思考設定・評価 suite の版）が変わったら `profile_changed` で、いずれも R = M。R は M を超えない                                                 | 05 固定部分の節（他用途へ自動で広げない、未測定・設定変更後は最大額）                                   |
| 予算月（`budgetMonthOf`）          | UTC の時刻を IANA タイムゾーンの暦月（YYYY-MM）にする。ECMAScript 標準の `Intl.DateTimeFormat`（グレゴリオ暦）を使い、Node 専用 API に依存しない。UTC オフセットの表記（`+09:00`）・実在しない名前・不正な時刻は null                                                                                                                                                                                                            | 本人の判断（月の境目は本人が設定する IANA タイムゾーン）                                                |
| タイムゾーンの変更（翌月から反映） | `advanceBudgetMonth(状態, 時刻, 設定のタイムゾーン)`。状態は使っている予算月・その月のタイムゾーン・前の月のタイムゾーン（月ごとに Core が記録する。ADR 0034）。今の月の終わりは今の月のタイムゾーンで決め、月が替わった時点から設定のタイムゾーンを使う。進んだタイムゾーンから遅れたタイムゾーンへ変えた月は、その月が少し長くなる（同じ時刻を 2 つの月に数えない）                                                            | 本人の判断（変えたら翌月から反映）。境目の決め方の細部は原本に決めなし                                  |
| 時計の戻り                         | 時刻が、今の月のタイムゾーンでも前の月のタイムゾーンでも、使っている予算月より前の月になるなら `clock_regressed` を返し、有料の受付を保留する。予算月は戻さない。同じ月の中の戻りは月を変えない。中枢が止まっていて数か月後に起動したら、その時刻の月へ進む                                                                                                                                                                      | 原本に決めなし。設計判断（司令塔の依頼、2026-10-23）。未決事項 U21                                      |
| 利用状況（`summarizeUsage`）       | 契約の `BudgetUsageSummary` の形で返す。月は今月と、未精算（reserved・usage_unknown）か M 超過の確認待ちが残る前の月だけ（今月を先頭に新しい順）。予約は元の予算月だけに数える。金額と usage 不明の件数は子孫の枠の分を含む。M 超過の確認待ちの件数はその枠に計上した予約だけ（保留はその枠と子孫に掛かり祖先に掛からないため。ADR 0006）。合計が 18 桁を超えたら `amount_overflow`、今月より後の月の予約があれば `future_month` | ADR 0006・0034 の数え方                                                                                 |
| 予算保留の理由                     | `limit_reached` は精算済み＋未精算の M が上限以上（ちょうどでも達した扱い）。`overrun_review_pending` は M 超過の確認待ちの予約がその枠にある（月を問わない。ADR 0006 の overrun_hold と同じ）。`ancestor_held` は祖先の枠が上限到達か確認待ち。`config_invalid` は実行時の設定の検査に通っていないとき全枠                                                                                                                      | 01 いつも見える状態の「予算保留」、ADR 0034                                                             |
| 承認待ちの承認と操作を待つ予約     | `overage_approvals` は pending で期限前の承認だけ。`pending_reservations` は usage 不明（手での精算を待つ）と、M 超過の確認待ちを、月の古い順に並べる。予約を契約へ写すときのクレジットの区分は B07-07 までの初期の規則（クレジット 0・追加の支出＝実費、ADR 0034）                                                                                                                                                              | ADR 0034                                                                                                |
| 超過枠への経路                     | `admitWithOverage`: 通常の枠で受付し、落ちたときだけ超過枠を検討する。回せるのは、本人の依頼（`owner_request`。本人が頼んだ背景の処理を含む）で、通常の受付の理由が上限（`r_limit`・`m_limit`）だけで `m_limit` を含み、経路に音声の枠を含まないとき。自発的な解析・自動実行・初回の読み込み・影モードは `not_owner_request`、音声は `voice_not_routable`、価格未確認・M 超過の保留・重複などを含めば `not_limit_only`           | 05 F02、X18・X26・X53、本人の判断（本人の依頼の枠）                                                     |
| 承認の照合                         | `matchOverageApproval`: 承認が承認済み（`approval_<状態>` で他の状態を拒否）、期限前（期限の時刻ちょうどは期限切れ）、同じ request_id、同じ M（通貨と金額が完全に一致。小さい M・大きい M のどちらにも使わない）、超過枠、同じ予算月のときだけ一致。承認済みでも超過枠の上限は M で守る（`admitBudget`）。1 つの依頼は通常の枠か超過枠のどちらか一方だけに計上する（ADR 0006）                                                   | 本人の判断（request_id と M に固定）                                                                    |
| 手での精算（`settleManually`）     | 照合 ID は契約と同じ形（`manual:` で始め英数字と `.`・`_`・`-`、64 文字まで）。usage 不明の予約だけに、元の月・元の枠のまま適用する。同じ照合 ID・同じ実費の再適用は変化なし。provider の精算の後・別の金額での二度目は `already_settled`、送信中（reserved）は `not_usage_unknown`。手で精算した後の provider の精算は既存の `settleReservation` が `settlement_conflict` にする。実費が M を超えれば M 超過として記録する      | 本人の判断（不明な費用は手で精算するまで保持）、ADR 0034                                                |
| M 超過の確認（`reviewOverrun`）    | 予約の版・本人が見た実費と M が記録と一致し、精算済みで実費が M を超えるときだけ確認済みにする。実費・月・枠は変えない。確認済みへの同じ確認は変化なし                                                                                                                                                                                                                                                                           | ADR 0034                                                                                                |
| 予約の版                           | 精算・手での精算・確認では版を上げない（版は追加予約で上げる。ADR 0006）。手での精算・確認の要求の版は照合する                                                                                                                                                                                                                                                                                                                   | ADR 0006 のまま                                                                                         |

## 試験と期待値

- `packages/contracts/fixtures/budget-rules.json`（新規）: 合成の実行時の設定（`BudgetRuntimeConfig`、通貨 XTS、換算の例の元の通貨は ISO の通貨なしコード XXX、縮めた単価と上限）で、M 21 件・R 10 件・予算月 10 件・タイムゾーンの変更と時計の戻り 9 件・経路 13 件・承認 13 件・手での精算 13 件・確認 7 件・利用状況 5 件。期待値は設計本文と手計算で書き、実装から作っていない（例: 入力 1001 token × 2/1000 × 2.5 × 1.2 = 6.006 → 7）。
- `packages/contracts/fixtures/budget-scenarios.json` に 6 シナリオを足した（手書き）。QA42 の usage の重複・欠落・timeout、月替わりと手での精算、手での精算の M 超過と確認、承認のない超過枠と音声の予算からの融通 0、X53、X18 の予算の行。
- `scripts/budget-rules.test.mjs`（新規）と `scripts/budget.test.mjs`（`admit_route`・`manual_settle`・`review` の手順を追加）が、ビルド後の domain の出力を期待値と比べる。作った利用状況は契約の Schema と意味検査にも通す。
- 単価の境界はミリ秒で確かめる（境目の 1 ミリ秒前は古い版だけ、境目ちょうどは新しい版も掛かる）。夏時間のあるタイムゾーン（Pacific/Auckland・America/New_York）と年の替わりも確かめる。2030 年のタイムゾーンの規則は実行環境の tz データの予測に依存する。

## 残ること

- DB の列（予算月ごとのタイムゾーンの記録、承認の表、手での精算の印）と単一 transaction での受付（B07-03）。
- 設定ファイルの置き場所と起動時の読み込み、処理をどの葉の枠に計上するかの門、時計の戻りを状態の「予算保留」に出すこと（B07-04）。
- 承認・確認・手での精算の経路の処理と、承認の consumed への更新（B07-05）。
- クレジットの区分（B07-07）、実請求との照合（B15）。
- 課金され得る期間の終わり（応答の期限）の決め方は profile の timeout に依存し、B07-04 で決める。
