# ADR 0119: B11-04 気づき（候補）の生成（P1）

- 日付: 2026-11-14
- 状態: B11-04（親 #23、Issue #271）の P1。Core に、抽出の結果と予定の重複から候補の下書きを作り、保存の命令へ渡す部分を作る。一覧・根拠の再取得・状態の変更の経路（P2）、根拠の失効・取得範囲外・忘却の反映（P3）は未着手。実メール・実 API・実機は未実施。
- 根拠: 設計 11 §4・§5A・§5B、設計 04 気づきの作成（予定重複・メールの期限・返信依頼）、設計 09 X12・X35、ADR 0073（B11-01）・0101・0102（B10-05）・0115〜0118。原本の参照手順は `docs/design/README.md`。
- 対象: `apps/core/src/candidate-intake.ts`、`candidate-intake.test.ts`、`docs/b00/contract-map.md`（U283・U284）。契約（schema・openapi・generated.ts・fixture）とマイグレーションは変えない。

## 決めたこと

| 対象           | 決定                                                                                                                                                                                                                                                                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 入口           | `mailCandidateDrafts`（抽出の結果 → メールの候補の下書き）、`scheduleOverlapDrafts`（予定の重複 → 下書き）、`persistCandidateDrafts`（下書き → 識別子・封筒 → DB worker の `candidate.create`）。下書きは純粋な値で、時計・鍵・ID の発行・DB は注入する                                                                                                         |
| 候補にする依頼 | 種類が `reply_required`（`mail_reply`）または `action_required`（`mail_deadline`）で、本人宛て、引用の外にあり、依頼 ID と版が決まっているものだけ（U284）。候補にしない依頼は理由 `not_a_request`・`not_addressed_to_me`・`in_quoted_text`・`entity_unresolved`・`revision_missing` で返す。依頼 ID が決まらない依頼は候補にせず、解決・保存は別に足す（U283） |
| 題             | 「依頼の要約：M/D H:MMまで（差出人の表示名）」。60 文字（コードポイント）に収め、長い要約を削る（末尾を `…`）。収まらないときは差出人、次に期限を外す。差出人の表示名は 12 文字までで、`@` を含むもの（アドレス）は使わない。未返信・未対応を断定する題（B11-02 の `candidateTitleErrors`）や空の要約は、固定の題「返信の依頼」「対応の依頼」に置き換える       |
| 抄録           | 要約の根拠の引用（無ければ最初の根拠の引用）を、空白をまとめて 200 文字に切ったもの。根拠が無ければ空。抄録は暗号化した別の封筒に置く                                                                                                                                                                                                                           |
| 封筒の中身     | 題の封筒に JSON `{ title, deadline_original_text }`（期限の原文は本文の断片なので封筒の中にだけ置く。U281）。抄録の封筒は引用の文字列。どちらも候補の ID・版 0・用途を所有者として結び付けて暗号化する（別の候補・別の用途に付け替えると開けない）。平文の列に題・原文・引用を置かない                                                                          |
| 識別子         | 種類・アカウント・依頼 ID・依頼の版・期限から B11-02 の `notificationKey`（SHA-256 は注入）で作る。同じ抽出の再保存・再接続・却下後の再同期は `duplicate`（封筒も作らない）。期限の訂正で依頼の版が上がると別の識別子になり、新しい候補になる                                                                                                                   |
| 一部未読       | 抽出の完全性の未読・切詰めが 1 件でもあれば `unread_partial`。関連解析の版（`related_analysis`）と初回取り込みの印は呼び出し側の値をそのまま渡す                                                                                                                                                                                                                |
| 予定の重複     | 題は「予定の重複：M/D H:MM–H:MM」（終日どうしは「M/D」）で、予定の題・参加者を載せない。期限は重複の始まり（P1 の表示順が使う）。同一性を確かめられない組（iCalUID なし）は固定の抄録「同じ予定の写しかどうかを確認できません（重複候補）」を付ける。由来の辺は予定ごとに 1 つ（元情報の呼び方は注入）                                                          |
| 失敗           | 1 件の拒否（由来が無い・識別子の材料が不正・封をできない）で残りを止めない。拒否は入力の添字と理由（ID・件数だけ）で返し、書かなかった候補の封筒を残さない（保存側が transaction で巻き戻す）                                                                                                                                                                   |
| 通知           | この層は通知を出さない。新しく作った候補（`created`）の識別子と初回取り込みの印を返し、通知を出すかは B11-02 の `candidateAlertDecision`（B11-05 で配線）                                                                                                                                                                                                       |

## 原本に決めがない項目

- 依頼 ID を一意に決められない依頼の扱いと、依頼 ID の解決・保存の担当（U283）、候補にしない依頼の範囲（U284）。暫定の置き方を試験で固定した。本人が決めたら変える。

## 試験（模擬だけ）

- `apps/core/src/candidate-intake.test.ts`（10 件）: 期待値は手で書いた。題（設計 11 §4 の例そのもの・日付だけ・期限なし・長い要約・時刻の桁・差出人の長さとアドレスの除外）、断定する題の置き換え、候補にしない理由の全種類と順序・同じ依頼の重なり、下書きの構造（一部未読・切詰め・関連解析・由来）、抄録の選び方と 200 文字、予定の重複の題・期限・抄録・由来の辺・重なりの除去。実際の DB の保存の命令と結び、識別子（手書きの材料の SHA-256）、封筒を候補の所有者・用途で開けて中身が JSON と引用であること、付け替えた封筒が開けないこと、平文の列に題・原文・引用が残らないこと、再保存・却下後・版が上がったときの `duplicate`／`created`、拒否した下書きが他を止めず封筒を残さないことを確かめた。

**模擬の期待値だけ**。実メール・実 API・実機・実際のデータ鍵の保管庫・DB worker 経由の呼び出しは未実施で、合格扱いにしない。

## 残ること

- P2: 一覧・根拠の再取得（許可範囲から取り直す）・既読／却下／保留の経路。API の経路は契約（OpenAPI・schema）の変更を伴うので、直列の順番を待つ。
- P3: 根拠の失効・取得範囲外・忘却の反映、時間による遷移（期限切れ・スヌーズの終わり）と `candidate.sweep` の定期の呼び出し。
- 依頼 ID の解決・保存（U283）。
