# ADR 0043: B06 の保存期限の掃除の規則（期限・時計の巻き戻り・派生物の期限・保存モードの変更・起動時のゲート）

- 日付: 2026-10-24
- 状態: B06-02（#138、親 #11）の判断。`packages/domain/src/retention-sweep.ts` の純粋な関数と、手書きの期待値（`tests/fixtures/retention-sweep-cases.json`）による模擬の試験だけ。削除の実行（transaction・外部キーの順序・secure_delete）は B06-06、ゲートの組み込み（StorageModeGate・起動の順序）は B06-07、忘却の計画は B06-03、記録しない会話の許可表は B06-04。実機の Mac mini・実際の時計の操作・実データは未実施。
- 根拠: 設計 03（保存期限・今回選ぶ会話以外の運用データの扱い・忘却と再取り込み・バックアップ・復元）、09（X15・X16・X44・T06）、ADR 0008・0010・0032・0040、本人の判断 J4・J5（2026-10-24、#11 のコメント）と司令塔の判断（同日。予算の記録は月ごとにまとめて消す）。原本は権限のある接続で読み取りだけ行い、全文は写していない。原本に決めがないことは「原本に決めなし」と書き、docs/b00/contract-map.md の U53〜U57 に記録した。
- 既存の `retention.ts`・`memory.ts` の関数（`deleteAt`・`isDue`・`turnRetentionRule`・`applyMemoryEvent` ほか）の動作は変えていない。`RETENTION_RULES` に 2 つの規則と、暦の月で数える規則の印（`months`・アンカー `month_closed`）を足し、`deleteAt` は暦の月の規則に使うと例外にした（新しい規則にだけ働く。ms の 0 を黙って足さないため）。

## 原本に書いてあること（読み取り）

- 03 保存期限: 通常会話は発言の生成から 7 日、継続相談は 30 日、許可された要約は新規自動保存から 90 日で見直し待ち・明示継続で次の 90 日・利用や再要約で延ばさない・見直し待ちは 30 日未応答で削除。「未分類は通常会話とし、混在部分を分離できなければ短い期限を採用」。「期限処理は起動時・復帰時に検索やクラウド送信より先に行い、起動中も定期実行」。「時計が大きく巻き戻った場合は期限を延ばさず、最終確認時刻との不整合を解消するまで対象の自動利用を止める」。完了した依頼の結果・未確定案は原則 7 日、完了後の本文なし操作レシートは 90 日、自動実行の取り消しの情報は 30 日。「本人が確定保存したメモ・用事は本人の削除操作を正」。
- 03 データの分離: 会話は「継続や再開で古い発言の期限を伸ばさない」。
- 03 忘却と再取り込み・ADR 0032: 忘却時に対象と派生要約を削除する。要約は由来のうち最も早い期限で捨て、要約し直すときは期限内の材料だけを使う。

## 試験（模擬だけ）

`tests/fixtures/retention-sweep-cases.json` と `scripts/retention-sweep.test.mjs`。期待値は手で書き、暦を数えて検算した（例: 2026-10-17 の 90 日後は 2027-01-15）。domain の出力から作っていない。

- **境界**: 期限ちょうど（消す）・1 ミリ秒前（残す）・1 ミリ秒後（消す）。発言・記憶の見直し・見直し待ちの削除・要約の由来・終わった操作の本文（7 日）・レシート（90 日）・予算の月（13 か月。東京・ニューヨークの夏時間と冬時間・年またぎ）・ゲートの古さ（15 分ちょうどは開く・1 ミリ秒超過で閉じる）・掃除の間隔。
- **時計の戻り**: 最終確認時刻より 1 ミリ秒でも前なら regressed。判定は最終確認時刻、次の最終確認時刻は戻らない、期限内の行は残り自動利用は止まる、予算の記録は消さない、追いつけば解ける。
- **オフラインの後の起動**: 4 か月止まった後に、発言・キャッシュ・見直しを過ぎた記憶・終わった操作の本文と行・取り消しの行・13 か月を過ぎた予算の月を一度に計画する。前の起動の掃除ではゲートは開かない。
- **継続と再開**: 古い発言は、後で再開して新しい発言を足しても元の期限で消える。記憶の明示継続は見直し待ちからだけで 90 日をやり直す（2026-11-01 の 90 日後は 2027-01-30）。利用・要約のし直し・重複の抽出では変わらない。
- **要約のし直し**: 期限ちょうどの材料は切れている・期限内の材料と前の期限の早い方・材料がなければ作らない・何回し直しても延びない。
- **拒否側**: 読めない now・最終確認時刻（語・日付だけ・タイムゾーン付き・2 月 30 日・空）、保存した期限が規則より遅い（1 ミリ秒でも）、予算の規則・操作の規則を `timed` に置く、用事・メモ、未完了・結果不明の操作、生きている用事が参照する操作、補償が終わっていない取り消し、消せない予約が混じる月（`reserved`・`usage_unknown`・M 超過の確認待ち・実費が空・実費が数でない）、求められないタイムゾーン・月・範囲外の月。
- 契約との一致: `StorageModeState` の `turn_retention_days`（7・30・なし）が domain の規則と一致すること、`RetentionNotice` の上限 256 と下書きの形（ID と理由だけ）。
- 試験の弱さの確認: 比較の `>=` を `>` にした場合と、最も早い期限を最も遅い期限にした場合に、試験が落ちることを確かめた（実装の変更で試験が通らなくなる）。

**模擬の期待値だけ**。`tests/test-map.json` の X15・X16・X44 の `product_test` は `not_run` のまま（契約 fixture・規則の試験の合格を製品試験の合格として扱わない）。実際の DB の削除・時計の操作・実機は B06-06・B15。

## 後続への引き継ぎ

- B06-06: `sweepPlan` の action を DB worker が実行する（`erase_body` は `operation_versions` の本文の削除、`delete_row` は ADR 0040 の外部キーの順序、`start_review` は見直し待ちへの更新）。予算の月は 1 つの transaction で消す。`budget_reservations` などに `delete_at` を書く場合は `budgetRecordDeleteAt` を使う。SQL の CHECK の定数は `RETENTION_RULES`（`operation_body` 7 日・`operation_receipt` 90 日）と一致させる。
- B06-07: `startupGate` を起動の順序に組み込む（検索・クラウドへの送信・Live の前に掃除を完了させる）。最終確認時刻の保存・復帰の検知・`epoch` の発行・定期実行の job。時計を進めすぎた後の復旧（U53 の採り直し）。
- B06-03・B06-04: 忘却の計画・記録しない会話の許可表は別の作業。この計画は忘却台帳を読まない（期限だけ）。

## 判断が要る点

1. **巻き戻り中の削除の側（U54）**: 個人の内容は消し続け、予算の記録は消さない案にした。時計を進めすぎた直後に戻した場合は、個人の内容が早く消える（取り返しがつかないが、プライバシーの側）。巻き戻り中はすべて消さない案もある。
2. **許容幅なし（U53）**: 少しの巻き戻りでも最終確認時刻に追いつくまで自動利用・検索・クラウド送信を止める。時計を大きく進めすぎると止まりつづけるので、本人の確認による採り直しの操作が要る（B06-07 以降）。
3. **モードを下げると既存の発言が短くなる（U56）**: extended から normal へ下げると、30 日で書いた発言が 7 日で消える（すでに 7 日を過ぎていれば次の掃除で消える）。保存した期限のままにする案もある。
4. **記憶は止まっていた間も絶対の期限（U57）**: 長く止まった後の起動では、見直し待ちを経ずに消える記憶がある。起動後に見直しの機会を設ける案もある。
