# ADR 0137: B08-06 同期の周期起動（起動時の回復と全量照合、60 秒ポーリング、掃除ゲートの製品配線）

- 日付: 2026-11-23
- 状態: B08-06（親 #16）。domain の回復の規則・保存層の `sync.recover`・Core の周期起動（sync-scheduler）と掃除ゲートの製品配線まで。実 API・実アカウントは未実施（B15 と本人の承認）。接続の作成・OAuth・トークンの供給は B03-04 で、実接続が無い間、製品の起動では実行器は呼ばれない（ADR 0136 と同じ）。
- 根拠: 設計 11 §1（60 秒ポーリング＋±10 秒のジッター、全量照合は Gmail が起動時・6 時間ごと、Calendar が起動時・15 分ごと、429／5xx は接続ごとに指数バックオフ上限 15 分）・§1A（再起動時は旧実行担当の終了を確認し、新しい担当世代で回復する）、設計 04 同期方式の選定、ADR 0053・0058（掃除のゲート）、ADR 0071（connector の再試行方針。Retry-After の優先はそちら）、ADR 0136（実行器と掃除ゲートの口。製品配線と周期の起動は B08-06 としていた）。原本の参照手順は `docs/design/README.md`。

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 回復の規則           | domain の `sync.ts` に `restartExecutor` を足す。担当世代を 1 つ進め、有効な走査が残っていれば `abandonScan` と同じ規則で abandoned にし、種類に応じた pending を立てる。世代が進んだ旧走査の遅着は、既存の `scanCurrentReasons`（stale_scan・executor_changed）で保存も公開も拒否される（11 §1A）                                                                                                                                                                                                                               |
| 保存層               | 新しい DB 経路は作らず、sync に操作 `sync.recover`（scope_id のみ）を足す（`packages/storage/src/sync-store.ts`）。世代の更新・旧走査の abandoned 化・staging の削除・pending の書換えを 1 つの短い transaction で行う。マイグレーションは要らない                                                                                                                                                                                                                                                                               |
| 回復の時点と前提     | 周期起動の起動時の処理で、接続ごとに全取得集合へ 1 回ずつ行う。「旧実行担当の終了の確認」は、Core のデータディレクトリの排他ロック（旧 Core が終わらなければ新しい Core は store を開けない）が担保する。回復は対象（targetsFor）の有無にかかわらず行う                                                                                                                                                                                                                                                                          |
| 周期起動             | `apps/core/src/sync-scheduler.ts` の `createSyncScheduler`。起動時は回復の後に全対象を全量で走査し、その後は 60 秒ごとに回す（周期へ ±10 秒のジッター。乱数は注入できる）。前の周期が終わっていない間は重ねない。種類の判定は、起動時 → pending_full → 全量照合の記録なし → 資源ごとの間隔（メール 6 時間・予定 15 分）の経過、の順で全量にし、それ以外は増分にする。全量の要否の最終判断は実行器側の pending_full の優先（ADR 0136）とも一致する                                                                                |
| バックオフ           | 設計 11 §1 は「接続ごとに指数バックオフ（上限 15 分）」までで、初項と倍率は書いていない。**初項はポーリングの間隔（60 秒）、倍率は 2、上限 15 分**と決める。数えは接続ごと・周期ごと（同じ周期で複数の対象が失敗しても 1 回分）。成功（published）があれば数え直す。queued・held・unavailable は provider の失敗ではないので数えない。Retry-After の優先は connector の再試行方針（ADR 0071）が担い、実行器は表面化しないので scheduler 側では重ねない。バックオフの状態はメモリ上だけに持ち、再起動で戻る（永続化は設計に無い） |
| 掃除ゲートの製品配線 | core.ts が実行器（`createSyncExecutor`）を常に作り、RetentionSweeper の ready／gate／lease を渡す。入口表（retention-entries.test.ts）の「ゲートを渡す入口は 3 つ」を 4 つへ更新した。周期起動は `options.sync.scheduler` を渡したときだけ動かし、CLI の start が有効にする（バックアップの周期実行と同じ形）                                                                                                                                                                                                                    |
| 対象とトークンの供給 | account_id・資源種別（targetsFor）とトークンの出所（tokenSourceFor）は Core の options から注入で受ける。どちらも接続の作成（B03-04）が持つ値で、ここは渡されたものだけを使う。渡されなければ対象は空で、実行器は呼ばれない                                                                                                                                                                                                                                                                                                      |
| 停止                 | scheduler の stop() は新しい周期を止めるだけにし、実行中の走査は中断しない（走査は継続位置まで保存され、次回の起動で回復・再開できる。11 §1A）。Core の終了処理では、DB を閉じる前に scheduler を止める                                                                                                                                                                                                                                                                                                                          |

## 残ること

- 接続の作成・OAuth・トークンの保存と更新、取得集合の作成、account_id の供給は B03-04。そちらが targetsFor・tokenSourceFor を製品へ供給するまでは、周期起動は回復だけを行い走査は走らない。
- Outlook（Graph）の走査は B09-04 が実行器と保存層の形を共有する。周期起動の対象の形は provider を持たないが、実行器は Google 用のため、Graph 用の実行器が入る時点で scheduler の実行器の差し替えが要る。
- 公開時の忘却チェック（設計 11 §1A）は ADR 0136 の持ち越しのまま（忘却台帳の HMAC 鍵の口が前提）。
- 同期の状態表示（「更新を確認できていません」など）は `getConnectionSync` の応答（B08-05）を使う画面側の扱いで、本 ADR の範囲外。
