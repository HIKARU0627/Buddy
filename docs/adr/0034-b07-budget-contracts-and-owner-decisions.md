## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 単価の版             | `PriceVersion`: 版の ID・単価の系列（`price_key`）・通貨・適用期間（`effective_from` 以上 `effective_to` 未満。null は終わり未定）・課金区分ごとの単価（`PriceRate`）・為替と安全係数の版（`CurrencyConversion`）。系列は「同じ課金対象の単価の並び」で、同じ系列の版は適用期間が重ならない（境界を跨ぐ要求で高い方を選ぶため、どの版が隣か分かる必要がある）。境目の時刻（`PriceTime`）は小数秒をミリ秒（3 桁）までに限り、期間の重なり・隣接をミリ秒で正確に比べる（JavaScript の Date はミリ秒より細かい桁を捨てるので、1 ミリ秒未満の重なりを見逃さないため）。原本は系列の表し方を決めていない（原本に決めなし）                                                                                                                                          |
| 課金区分             | `input_tokens`・`cached_input_tokens`・`output_tokens`（思考を含む）・`tool_calls`・`search_requests`・`live_seconds`。原本が明示する区分は入力・cache・出力／思考で、検索の回数・会話の接続秒・ツールの回数は 05 の費用の節の課金単位から足した。M は非命中の `input_tokens` の単価で見積もり、`cached_input_tokens` は精算だけに使う（05 の固定部分の節）                                                                                                                                                                                                                                                                                                                                                                                                    |
| 単価と最大の課金量   | 単価は版の通貨の百万分の一の整数（`Amount`）で、`per_quantity` 単位あたり。`minimum_quantity` は 1 回の最低課金量（会話の 15 秒など）。`max_quantity_per_request` は 1 要求で課金され得る最大量で、null は入力（送る量が要求の時点で決まる）にだけ許す。他の区分で null なら M を有限にできないので、その版の profile を有効にしない（意味検査 `unbounded_category`）                                                                                                                                                                                                                                                                                                                                                                                          |
| 金額の桁数           | `Amount`（と課金量 `QuantityString`）は 18 桁まで。SQLite の 64 ビット整数（約 9.22×10^18）に 1 つの値が収まる。合計の桁あふれ（利用状況の集計・DB の SUM）は、保存と集計の側で B07-02・03 が検査する                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 為替と安全係数       | 10 進の文字列（`DecimalString`、小数点以下 6 桁まで）。浮動小数点数にしない。rate は 0 より大きく、safety_factor は 1 以上、同じ通貨なら rate は 1。換算後の通貨は予算の通貨と同じ。金額の丸め方（切り上げなど）は原本に決めなし。B07-02 の M の算出で決める                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 実行時の設定ファイル | `BudgetRuntimeConfig`（`buddy.budget-runtime.v1`）: タイムゾーン・`BudgetConfig`（通貨・枠・確認済みの版）・単価の版の一覧。意味検査は、タイムゾーンの実在・枠の通貨と木・版の ID の重複・確認済みの版が一覧にあること・換算後の通貨・同じ系列の期間の重なり。未知の項目（API キー・メールアドレスなど）は形で拒否する。ファイルの置き場所と読み込みは B07-04                                                                                                                                                                                                                                                                                                                                                                                                  |
| 利用状況             | `BudgetUsageSummary`: 今月と、未精算・usage 不明・M 超過の確認待ちが残る前の月の、枠ごとの上限・精算済み（通常料金）・未精算の R と M・usage 不明の件数・M 超過の確認待ちの件数・予算保留の理由と、承認待ちの超過枠の承認。金額は `Money`（`Amount`）。親の枠の数は子孫の分を含む（ADR 0006）ので、直下の子の合計は精算済み・未精算の R・未精算の M のそれぞれで親以下で、親子は循環しない（意味検査 `children_exceed_parent`・`pool_cycle`）。`pending_reservations` に本人の操作を待つ予約（手での精算を待つ usage 不明と、M 超過の確認待ち）を `BudgetReservation` のまま並べる。手での精算・M 超過の確認の要求に要る reservation_id・予約の版・個別の R と M・実費・月・枠を、別の経路を足さずに読める。応答のタイムゾーンも実在を確かめる                 |
| 予算保留の理由       | `limit_reached`（精算済み＋未精算の M が上限に達した）・`overrun_review_pending`・`ancestor_held`・`config_invalid`。利用者には理由のコードを見せない（01）。クレジット不明による Claude の保留（MA05）は profile の保留で、枠の理由に入れない（B07-07）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 超過枠の承認         | `BudgetOverageApproval`: approval_id・request_id（予算の要求）・枠・予算月・M・承認を求めた時点の超過枠の残り・状態（pending・approved・rejected・expired・consumed）・期限。承認は別の M・期限後の予約に使わない。期限の長さは原本に決めなし（B07-05 で決める）。`BudgetOverageDecision` の命令では、命令の ID（`request_id`）と予算の要求（`budget_request_id`）を別の名前にした（HTTP の命令の request_id は再送の照合に使うため、ADR 0009）                                                                                                                                                                                                                                                                                                                |
| M 超過の確認         | `BudgetOverrunReview`: 本人が見た実費と M、予約行の版を送る。記録と一致して実費が M を超えるときだけ `overrun_reviewed` にする（ADR 0006 の overrun_hold を解く）。実費・月・枠は変えない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 手での精算           | `BudgetManualSettlement`: 照合 ID は `manual:` で始め、英数字と `.`・`_`・`-` だけ（メールアドレス・氏名・自由文を入れない）。provider の精算（`BudgetSettlement`）の照合 ID は `manual:` で始めない（意味検査 `manual_prefix_reserved`）ので、予約の `provider_reconciliation_id` を見れば手入力か分かる。精算の金額は provider の精算と同じ 3 つ（通常料金・クレジット・追加の支出）。usage 不明の予約だけに一度だけ適用するのは B07-04 の規則。クレジットの周期の ID（`CreditCycleId`）は provider と周期の開始日（UTC の日付）を `:` でつなぐ形（例 `anthropic:2030-10-01`）に限り、メールアドレス・自由文・キーを入れられないようにした（`CreditObservation.cycle_id` と予約・精算の `credit_cycle_id` で共通）。既知の周期との照合は状態の検査で、B07-07 |
| profile と単価の版   | `ProfileId`（`ModelProfile.profile_id` と同じ形）と `PriceVersionId`（不透明な ID、順序比較しない）を定義し、`BudgetReservation`・`BudgetAdmissionRequest`・`BudgetConfig.verified_price_versions`・`ModelProfile` で使う。予約の `profile_id` はこれまで UUID（`Id`）で、`ModelProfile.profile_id`（`intent.luna.v1` のような名前）と形が違っていた。予約は profile を指すので名前の形にそろえた（既存の例を書き換え、UUID の例を拒否例にした）                                                                                                                                                                                                                                                                                                               |

## domain の型をそろえる方向

`packages/domain/src/budget.ts` の `ReservationRecord` と契約の `BudgetReservation` の対応です。

| 契約                                                        | domain                                    | 扱い                                                                                                                                                                      |
| ----------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `profile_id`・`price_version`                               | `profileId`・`priceVersion`（今回足した） | 受付時に固定し、追加予約・精算で変えない。`AdmissionRequest` にも `profileId` を足した。既存の関数の判定は変えていない                                                    |
| `reserved_amount`・`max_liability`・`actual_gross`（Money） | `currency` と金額の文字列                 | domain は予約ごとに 1 つの通貨を持つ。契約の Money の通貨がそろうことは意味検査（`currency_mismatch`）で確かめる                                                          |
| `credit_applied`・`additional_spend`・`credit_cycle_id`     | なし                                      | クレジットの区分の決め方（MA03〜MA06）は B07-07。それまで domain は通常料金の実費だけを持ち、契約へ写すときは B07-07 の初期の規則（クレジット 0・追加の支出＝実費）を使う |
| `reservation_revision`                                      | `revision`                                | 合成シナリオは受付時を 0 とし、保存案（0001_initial.sql）は 1 以上の CHECK。どちらにそろえるかは B07-03 で決める                                                          |

## OpenAPI に足した経路（07 §2 にない経路の追加）

設計 07 §2 の API 表に予算の経路はない。U10（ADR 0009）の前例にならい、設計判断として次の 4 経路を足した。処理は B07-05 で作り、それまで Core は形と認可の検査（端末・自宅・接続範囲・ロック・画面操作）の後に 503 を返す。版を照合する経路（M 超過の確認・手での精算）も、照合する先（予約の行）がまだないので版を照合しない。Core の経路の表で未実装の経路に `pending` の印を付け、印のある経路では版の照合を飛ばして 503 で閉じる（実装した後の版の不一致 409 と区別する）。印のある経路に処理を渡すと `createApiServer` が拒否するので、処理を足すときは印を外し、版の照合を有効にする。既定の構成（版の照合を注入しない startCore）で 503 になることを `apps/core/src/api-budget-pending.test.ts` で確かめる。domain の ROUTE_CHECKS（契約としての検査）は変えていない。クエリーは使わない（秘密を URL に置かない規則と、月を Core が決めるため）。

| 経路                                                              | operationId          | Core の検査                                     | 理由                                                                                                        |
| ----------------------------------------------------------------- | -------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `GET /v1/budget/usage`                                            | getBudgetUsage       | 端末トークン・自宅・ロック解除                  | 01 の設定・運用で残りを見せ、状態欄に予算保留を出すため。金額を含むのでロック解除を求める（端末一覧と同じ） |
| `POST /v1/budget/overage-approvals/{approval_id}/decision`        | decideBudgetOverage  | 上に加えて接続範囲・画面操作                    | 01 の承認画面で個別に承認する。登録済みでロック解除済みの画面から。中枢の画面に限らない（操作の承認と同じ） |
| `POST /v1/budget/reservations/{reservation_id}/overrun-review`    | reviewBudgetOverrun  | 上に加えて版（`expected_reservation_revision`） | 05 F02 の M 超過の照合の後、本人の確認で受付の停止を解く                                                    |
| `POST /v1/budget/reservations/{reservation_id}/manual-settlement` | settleBudgetManually | 上に加えて版                                    | 本人の判断（不明な費用の手での精算）                                                                        |

設定ファイルの再読み込み・編集の経路は足していない（編集の画面はキャンバス UI の後、本人の判断）。

- クレジットの区分と保留（B07-07）。
- `ExtractionResult.profile_id` も UUID（`Id`）のままで、`ModelProfile.profile_id` と形が違う。抽出の契約は B10 の範囲なので今回は変えていない。
- 実請求との照合（B15）は模擬検証と分ける。
