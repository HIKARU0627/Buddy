## 判断してほしい点

1. **取消・再試行も OS の確認ダイアログで確かめる（本人の判断 2026-10-22、PR #91 のコードレビュー P1）**: 承認と同じく main が確認を 1 回だけ出す。前面だけでは本人の操作の証明にならない（侵害された画面が一覧の参照で取消・再試行を実行できるため）。確認は対象（内容の見出し・補足・種類）・今の状態・世代に結び付け、確認の前後で状態か状態版が変わっていれば送らない。
2. **予定の照会は件数だけ**: `ResultView` の `item_refs` は ID だけで、予定の題名・時刻を取る経路が B04 にない。件数・重なりの件数・ほか n 件（`more_count`）だけを見せた。題名・時刻を見せるには、予定の本文を許可範囲内で取る経路（B07 の同期）が要る。
3. **変更前の値**: 中枢の確定 intent は変更前の値を持たない。ラベルは「付けるラベルは付いていない・外すラベルは付いている」（ADR 0029 の no_change 判定と同じ前提）、新規作成は「なし」と書いた。実際の現在値を見せるなら、preview の応答に対象の現在値を足す契約の変更が要る。
4. **口座の表示名・対象のメール（PR #91 の見た目のレビュー 高 1）**: Core が外部変更の preview の応答に `display`（`account_label`・対象の件名・差出人・受信日時。確定 intent と hash には入れない任意の項目）を足した。provider の読み取り（`ProviderReader.connection` と `readTarget`）から読み、模擬 provider の合成データに `account_label`・`received_at` を足した。読めない項目は null で、main は `approvable: false` にして承認を出さず、承認の命令も送らない。
5. **承認の確認は 1 回で使い切る**: 承認を送った（受け付けられた・結果不明・拒否された）後は確認を捨てる。やり直しは、内容を確かめ直して新しい確認を出す。
6. **切断後の取消・再試行**: 上の内容の表示用の読み取りで戻る（解決済み）。
7. **停止中の取消・照合**: 実行を増やさないので止めなかった。止めるなら `desktop.operation_cancel`・`desktop.operation_reconcile` も `input_stopped` の対象にする。
