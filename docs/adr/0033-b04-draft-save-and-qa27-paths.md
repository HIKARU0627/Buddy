# ADR 0033: 外部の下書きの保存（RemoteMutation）と QA27 の 3 経路の比較

- 日付: 2026-10-23
- 状態: B04-07（#106）の判断と実装。B04-01〜05（ADR 0027〜0031）の上に、返信の下書きの保存を発言から結果まで通した。試験は同じプロセスの模擬だけ（127.0.0.1 の Core の HTTPS、模擬 provider、デスクトップの main の部品。OS の確認ダイアログは模擬の `confirmAdmin`）。実機（Mac mini・別のマシン・本物の OS 確認ダイアログ）・実 API・実メール・実請求は未実施。#105（B04-06）のマージの後、統合の実行器へ下書きの保存と QA27 のケースを足した（下の「統合の実行器のケース」）。判断してほしい点 1〜4 は、司令塔が提案どおりで進めると決めた（2026-10-23、PR #107）。
- 根拠: Issue #106 の要約、本人の判断 D1〜D6（2026-10-22）、設計 09 §16.2（H02 の 3 経路）・§16.7（QA27）、ADR 0004・0027〜0031。原本は権限のある接続で取得した非公開の資料で確認した。既存の ADR と D1〜D6 の判断は変えていない。

## 決めたこと

| 対象             | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約・domain     | 変更なし。確定 intent は ADR 0027 の `DraftReplyOperationIntent`、経路（RemoteMutation）・照合の範囲（operation_marker）・lookup（by_operation_marker）・工程（`1-create_draft`）は `OPERATION_KIND_RULES` が持つ。目印は domain の `operationMarker`（`buddy-op:<operation_id>:<content_version>`、試行 ID を含めない）                                                                                                                                                                                                                                                                                             |
| 模擬の解釈       | 「mail-001 に「本文」と返信の下書きを保存して」→ `draft_reply`（候補と本文）。「mail-001 に返信の下書きを保存して」→ 本文なしで聞き返し（「下書きの本文を教えてください。」）。モデルは使わない                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 下書きの内容     | 宛先は返信元の差出人、件名は返信元の件名に「Re: 」を付けた値（既に「Re:」で始まればそのまま）で、どちらも Core が provider の読み取りから決める（ADR 0004）。本文だけを発言から取る。CC は空。差出人か件名が読めなければ作らない（聞き返し）                                                                                                                                                                                                                                                                                                                                                                         |
| 意味検証         | ラベルと同じ: 候補から返信元を解決し、接続が active で下書きの書込みとメールの読み取りが許され（返信元を読む前に確かめる）、入力の時点と確定の直前の許可の版が同じ                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 書込みの範囲     | `ProviderConnection` に任意の `writable_kinds`（書込みできる操作の種類）と `readable_kinds`（読める対象）を足した。省略すれば従来どおり `access`・`status` だけで判断する。模擬のアダプターは範囲から決める（ラベル＝`mail.labels.change`、下書き＝`mail.drafts.create`、予定＝`calendar.read`、メール＝`mail.read`）。`access` は書込みの範囲が一つでもあれば read_write                                                                                                                                                                                                                                            |
| preview・display | 既存の経路のまま。下書きの返信元が `display.target`（件名・差出人・受信日時）、口座の表示名が `display.account_label`、本文は確定 intent。preview は種類ごとの書込みの可否（`canWrite`）とメールの読み取りの可否（`canRead`）で出す。読み取りの範囲がなければ preview は 409、display は件名・差出人を読まない（target は null）。接続先が確定 intent の口座と違えば preview は 409、display は表示用の値を null にする（ADR 0031 の規則）。承認のときの照合（`previewValid`）も、preview に結び付けた操作の種類で書込みの範囲を確かめ、読み取りの範囲も確かめる（許可の版が同じでも、その種類の範囲だけが外れうる） |
| 実行担当         | `runRemote` を種類で分けた。共通: 準備 → 接続・許可・返信元の版を読み直す → 送出意図 → 1 回だけ送る → 結果の記録。下書きは `createDraft`（返信元・宛先・CC・件名・本文・目印）で送る。読み直しで返信元か許可の版が変わっていれば送らず D1（内容版を上げる。新しい内容版は新しい目印）。下書きの D1 では、読み直した返信元から宛先・件名を作り直して新しい内容版に入れる（本文・CC はそのまま。差出人か件名が読めなければ内容版を上げず preparing のまま）。口座が違う・メールの読み取りの範囲がない（返信元を読む前に確かめる）・種類の書込みの範囲がない場合は送らず preparing のまま（ADR 0030 の判断 3 と同じ）   |
| 照合（D4）       | 応答を失ったら直後に 1 回だけ、目印で下書きを探す（`draftSaveObserved`）。同じ目印で返信元が同じ下書きがちょうど 1 件なら found（外部 ID は下書きの ID）、0 件は not_found（遅れて保存されうる）、2 件以上は multiple、目印が同じで返信元が違うものがあれば unreadable。found だけが成功。以後は本人の照合だけで、自動では再送しない                                                                                                                                                                                                                                                                                 |
| 差し込み口       | `ProviderWriter.createDraft` と `ProviderReader.findDrafts` は任意。持たない provider では下書きを実行しない（ログを残して承認済みのまま）                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 模擬 provider    | 下書きの作成の要求に任意の `marker`・`in_reply_to`・`cc` を足し、状態に保存する。返信元がなければ適用前に 404。下書きの一覧は `marker` でも探せる（条件のない一覧は 400）。受信記録・回数・故障注入はラベルと同じ仕組み。アダプターに `findDraftsByMarker` を足し、能力の照合の範囲を下書きの作成だけ `operation_marker` にした                                                                                                                                                                                                                                                                                      |
| デスクトップ     | 製品コードの変更なし（B04-05 の確認画面・main の確認ダイアログ 1 回のまま）。試験の中枢に模擬 provider をつなげるよう、試験の道具（`startHub`）に `turns` を足した                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 入力の許可の版   | ADR 0029 では発言を受けた直後（解釈の前）に接続と許可を読んでいた。QA27（LocalCommand に外部の HTTP がない）に合わせ、provider を使う意図（予定の照会・ラベル・下書き）だけ、解釈の直後（意味検証の前）に読むように変えた（PR #107 のレビュー）。用事の登録と聞き返しでは接続を照会しない。確定の直前の読み直しと照合する規則は変えていない                                                                                                                                                                                                                                                                          |

## QA27 の 3 経路

| 経路                           | 確かめたこと                                                                                                                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read（予定の照会）             | 操作・承認・試行を作らない（スナップショットの操作 0）。アダプターの書込み 0、provider の受信 0                                                                                                                                           |
| LocalCommand（用事の登録）     | 承認 1・試行 1・成功。工程（送出意図）なし。発言の受付から承認・適用の完了まで、アダプターの呼び出し（読み取り・書込み・照合）0、provider の受信 0                                                                                        |
| RemoteMutation（下書きの保存） | 工程 `1-create_draft` を送出意図つきで記録し、成功で確定。provider の受信 1・変更 1                                                                                                                                                       |
| 権限（全経路）                 | 失効した端末は 3 種の発言も承認も 401 で何も作らない。予定の読み取りの範囲がなければ Read も聞き返す。メールの読み取りの範囲がなければ返信元・対象を読まず、preview も送出もしない。種類の書込みの範囲が preview の後に外れれば承認は 409 |
| 期限（全経路）                 | 接続範囲の期限（24 時間）を過ぎると 3 種の発言も承認も 410 `expired_scope` で、何も作らず送らない。新しい接続範囲では読める                                                                                                               |

## 試験（模擬）

- connectors（`mock-provider.test.ts` に 2 件）: 目印・返信元・CC つきの保存と状態・受信記録、目印での検索（内容版が違えば 0 件）、返信元がない保存の拒否、条件のない一覧の拒否。
- Core（`draft-save.test.ts` 11 件、`qa27-paths.test.ts` 3 件）: 成功（preview の内容・display・手で書いた正規形の content_hash・保存された下書きの内容・目印）、応答の喪失 → 目印の照合 1 回で成功、時間切れ → unknown_held → 遅れた保存でも自動で照合・再送しない → 本人の照合で成功、再起動（送出意図の後は unknown_held で再送 0、本人の照合でも見つからなければ保留のまま／準備中は確かめ直しから 1 回だけ送る）、取消（送出意図の前は cancelled・要求 0／後は受付だけで reconciling、本人の照合で成功）、アカウントが違う（preview 409・display の表示用の値は null・承認の後なら preparing のまま要求 0）、下書きの範囲がない（聞き返し・承認の後なら送らない・ラベルは作れる）、返信元の版・差出人・件名の変更（D1、宛先・件名を作り直した内容版 2 の preview と hash を手書きの値で確かめ、内容版 2 の目印で 1 回だけ保存）、メールの読み取りの範囲だけがない（返信元を読まない・preview 409・送らない・下書きもラベルも聞き返す）、preview の後にその種類の書込みの範囲だけを外す（ラベル・下書きとも承認 409・承認と試行 0）、目印の照合の判定表。QA27 の 3 経路（LocalCommand は発言の前から完了まで読み取りを含む呼び出し 0）・権限・期限。試験の道具は #105 の `operation-runner-test-support.ts` にまとめた（種類ごとの呼び出しの回数・接続先の差し替え・進められる時計・発言・承認と試行の件数）。
- デスクトップ（`two-clients.test.ts` に 1 件）: 実際の Core の HTTPS と模擬 provider で、A の発言から予定・用事・下書きを順に実行し、B の確認画面（保存先のアカウント・返信元・本文）と main の確認 1 回で下書きを 1 回だけ保存する。画面へ操作 ID・hash を出さない。
- 期待値はすべて試験に手で書いた値。content_hash は手で書いた正規形の文字列の SHA-256 で、実装の正規化を使っていない。

## 統合の実行器のケース（#105 のマージの後に追加）

`tests/integration/fault-points.json` に手書きの期待値を足し、`b04-cases.mjs` で実行する（23 ケース × seed 3 回 = 69 回）。

- `QA27-remote` を、ラベルの変更から下書きの保存（`operation: draft_reply`）へ置き換えた。要求 1・変更 1・承認 1・試行 1、状態の履歴 awaiting_approval → approved → preparing → dispatching → reconciling → succeeded、工程 `1-create_draft` が confirmed_success。provider の真の下書き（宛先・件名・本文・返信元・目印）を `provider_drafts`、確定 intent の hash を手書きの正規形 `content_canonical` の SHA-256 と照合する（`{operation_id}` だけをその試行の操作 ID に置き換える）。
- `QA27-auth`・`QA27-expiry` を足した。用事と下書きの操作を作って preview を出した後、失効した端末（401）・期限切れの接続範囲（410 `expired_scope`）で 3 種の発言と 2 種の承認を送り、操作 2・承認 0・試行 0・受信 0・アダプターの書込み 0。auth は予定の読み取りの範囲がないときの Read の聞き返しも確かめる。
- `QA27-local` は、発言の受付の前からアダプターの呼び出し（読み取りを含む）を数える。
- 下書きの保存の `X05-after-dispatch-draft`・`X06-draft`・`X07-draft`・`X08-draft` を足した。手順・状態の履歴・回数は同じ番号のラベルのケースと同じで、工程は `1-create_draft`、照合は目印。
- 証拠（`evidence-b04-simulated.json`）を作り直し、`tests/test-map.json` の QA27 を `simulated`（範囲は product_scope）、X05〜X08 に下書きの記録を足した。

## 判断してほしい点（2026-10-23、提案どおりで決定）

1. **件名と宛先の決め方**: 件名は「Re: 」＋返信元の件名、宛先は返信元の差出人だけ、CC は空とした。全員への返信・件名の編集は B04 の範囲外と考えた。
2. **書込みと読み取りの範囲を種類ごとに見る**: `writable_kinds`・`readable_kinds` を接続の値に足した。ラベルの範囲だけを外しても下書きは作れ、その逆も同じ。Read は予定の読み取りの範囲がなければ聞き返す（従来は接続が active なら読んでいた）。
3. **目印が同じで返信元が違う下書き**: Buddy の作成物として説明できないので、成功にせず結果不明（unreadable）に留める。
4. **QA27 の「期限」**: 端末の接続範囲の期限（24 時間）と読んだ。preview には期限がない（ADR 0029 の残件のまま）。

## 残ること

- 実機・実 API・本物の OS 確認ダイアログ・Electron の画面の操作。下書きの送信（X10 の 2 工程）は B14。
- メールの読み取りの範囲は、照合（lookup）の読み取りでは確かめていない（照合は参照だけで、範囲がなければ provider 側で読めない前提）。
