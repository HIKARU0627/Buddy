# ADR 0148: B13-04 候補を起点にした自動承認の最終ガード（判定に使った版の記録と送出直前の照合）

- 日付: 2026-11-26
- 状態: B13-04（親 #24）の保存側の部分。Core の候補の生成から `judgeAutoExecution` を呼んで操作を作る配線、ラベル・下書きの書込み、取り消しの補償の中身は未着手。実データ・実機・実 API は未実施。
- 根拠: 設計 11 §5A・§5B（F05）、設計 08 §1・§3・§9、設計 06 B13（依頼の固定 ID・版と関連解析の完了を実行直前にも検査する）、ADR 0103・0146・0147。原本の参照手順は `docs/design/README.md`。
- 対象: `packages/storage/migrations/0015_auto_candidate_guard.sql`、`packages/storage/src/operation-store.ts`・`operation-commands.ts` の作成時の自動承認・LocalCommand の適用・送出意図、`packages/storage/src/candidate-guard.test.ts`。契約（`packages/contracts`）は変えない。

## 背景

ADR 0103 は実行直前の照合（`finalGuard`）を、DB を読む口を注入する純粋な関数として置き、transaction への配線を B13 に残した。ADR 0147 は方針による自動承認の件数と安全停止を保存したが、候補を起点にした自動承認が「判定に使った依頼と関連解析の版」を記録せず、承認から送出までのあいだに依頼の取消や新しいメールの公開があっても止められなかった。依頼の一度だけの記録（`request_entity_operations`）を書く経路も無かった。

## 決めたこと

| 対象                           | 決定                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 判定に使った版の置き場         | 承認の行（`approvals`）に、候補・依頼の ID と版・関連解析の集合と版・集合の hash・公開世代の 7 列を足す（0015）。7 列はそろって持つか持たず、持つのは `policy_auto` だけ。記録の後は変えない（trigger）                                                                                                                                   |
| 版の読み方                     | 作成の命令は候補の ID・アカウント・カレンダーだけを渡し（`candidate_origin`）、版は保存層が候補の行から読んで写す。Core が渡す版を信用しない                                                                                                                                                                                              |
| 作成時の照合                   | 件数を数える前に照合し、拒否した判定は自動承認に数えない。理由は、候補が無い（`candidate_not_found`）・閉じた候補（`candidate_closed`）・依頼の無い候補（`candidate_without_request`）・関連解析の無い候補（`related_analysis_missing`）と、下の共通の照合                                                                                |
| 共通の照合                     | 依頼: 無い（`entity_not_found`）・版の変化（`request_revision_changed`）・取消・完了・抑止・作成済み（domain の `autoCreationReasons`）。関連解析: 同じ集合の最新の版と比べ、無い（`analysis_not_found`）・版・集合の hash・世代の変化・ready でない（`analysis_not_ready`）。新しい版が ready に戻っても旧版の資格は通さない（ADR 0103） |
| 一度だけの記録                 | 承認と同じ transaction で `request_entity_operations` に（依頼・操作・アカウント・カレンダー）を書く。送出が失敗しても行は残し、同じ依頼から自動でやり直さない（U302）                                                                                                                                                                    |
| 送出直前の照合                 | LocalCommand の適用（`applyLocal`）と RemoteMutation の送出意図（`recordDispatchIntent`）で、承認の行の版を使って共通の照合をやり直す。自分の操作の一度だけの記録は作成済みに数えない。拒否しても操作は承認済み・準備中のまま残る                                                                                                         |
| 依頼が先に消えたとき           | 依頼が期限で消え、一度だけの記録も一緒に消えても、承認の行は操作と一緒に 90 日まで残るので `entity_not_found` で拒否する（照合を素通りしない）。依頼があるのに自分の一度だけの記録が無いときは `candidate_link_missing`                                                                                                                   |
| 本人の依頼を起点にした自動承認 | 7 列を持たず、依頼の版は従来どおり `workflows` の版で照合する（ADR 0030）                                                                                                                                                                                                                                                                 |

## 原本に決めがない項目

- 自動実行が失敗したとき、同じ依頼から自動でやり直すかは書かれていない。二重実行を避けるため、一度だけの記録を承認の時点で書き、失敗しても残すとした（U302）。
- 本人が閉じた候補（不要・解決済み）からの自動実行は、11 §5A の抑止（依頼の `recreation_suppressed`）とは別に、作成時に止めるとした（U303）。送出直前には候補の状態を見ない（照合は依頼と関連解析の版だけ。ADR 0103 と同じ範囲）。
- 公開世代は関連解析の行の値どうしを比べる。同期の公開世代の正本との照合は、同期の公開で計画を無効にする処理（B08-06）と一緒に足す。

## 対象外

- Core の候補の生成から `judgeAutoExecution` を呼び、方針・許可の版と安全停止の件数を入れて操作を作る配線と、作る内容の組み立て。
- ラベル・下書きの connector の書込み、取り消しの補償の操作の中身と、対象の現在版の検査（利用者の編集を上書きしない）。
- 照合で拒否した操作の後始末（取消にするか、本人に知らせるか）と画面（B13-05）。
- 候補の `operation_ids` の読み出し（U282。承認の行の `candidate_id` から読める形になった）。

## 試験（模擬だけ）

- `packages/storage/src/candidate-guard.test.ts`: 期待値はすべて手書き。版の写しと一度だけの記録、同じ依頼・操作・アカウントの二度目の拒否（件数に数えない）と別アカウント・別の操作、取消・完了と抑止・依頼の版・新しい ready の版・同じ集合で未完了の新しい版・関連解析の削除・閉じた候補、依頼の無い候補・未知の候補・形の誤り、承認の後の取消と依頼の消失と記録の欠けによる適用の拒否、準備と送出意図のあいだの新しい版の公開による送出の拒否、本人の依頼を起点にした自動承認、7 列の trigger。
- 送出直前の照合を外した実装と、最新の版でなく最古の版と比べる実装で、試験がそれぞれ 2 件失敗することを確かめた。

**模擬の期待値だけ**。Core の配線・connector の書込み・画面・実データ・実機・実 API は未実施で、合格扱いにしない。`tests/test-map.json` の X21〜X24・X39〜X41・X61〜X65 は、Core の配線の統合試験で更新する。
