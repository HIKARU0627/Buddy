## 判断（原本に決めなし。2026-10-29、本人が司令塔に判断を委任して決定）

`docs/b00/contract-map.md` の U99〜U103 に同じ内容を記録した。

1. **返し方の正本（U99）**: 端末が持つ（質問 107 は端末ごとの切り替えボタン）。記録がなければ声、あるのに読めない・形が違うなら文字。中枢は持たず、Live を閉じる理由（output_mode_text）で知る。理由: 返し方は表示・入出力の好みで、承認・実行権限・処理状態の正本ではない。端末の設定だけで同意・リース・予算を満たした扱いにはしない。
2. **会話の操作の適用先（U100）**: 「会話の終了」は Live を閉じるまでで、会話（session_id）の終了は作っていない。流れの区切り（UI-05）と合わせて決めるため、`session.end` の命令は足さなかった。「記録しないで」は接続を閉じるまで（記録しない会話の開始は B06・UI-08）。
3. **声の結果の届け先と画面（U101）**: 画面は今の流れのキャンバスへ置く。次回の文脈要約へ含めることは、文脈（ConversationContext）の組み立てが未実装なので未対応。既定の方針では方式 C の 4 操作も承認の対象を作らず「画面で全文を確かめる」案内にする（暫定の文字起こしを承認可能な入力へ昇格させない）。この案内の画面への表示は未了（U120）。
4. **Live の文字起こしの整理（U102）**: 断片の連番（0 から。provider が持たなければ null で、欠落を確かめられないので変更は進まない）、発話の開始・終了候補（provider の抽象のイベント。端末の VAD の報告経路は未）、対象のターンの窓 2 秒（先の委譲が使ったターンは候補から外す）、確定を待つ上限 5 秒、方針の版 `1`。値は仮の値として採用し、実機試験（#132・#133）の遅延分布・誤対応率・聞き返し率で再評価する。確定待ちの期限に達しても入力の確定とはしない。
5. **一時保留（U103）**: 上限 30 秒（仮の値。実機試験で再評価。発話の追加で延ばさない）、関係の出所は解釈の `relation`・`target_workflow_id`（なければ分からない）、会話の操作は別件として保留を解く、Live が閉じたら保留は捨てる。

## 失効した依頼の終端状態（Codex の P1・P2-2）

保留の破棄（30 秒の上限・時計の異常・Live の終了）・訂正・取消で失効した依頼は、終端状態（`dropped`・`superseded`・`cancelled`）を一度だけ持つ。解釈の復帰・判定・保存の準備の入口と、保存の直前（precommit。変更でなくても）で検査し、失効していれば聞き返しも保存もしない（保存の直前で止まった依頼は保留へ戻さない）。Live が閉じたときは、保留の集合にある依頼を解釈中・保存の準備中も含めて失効させる。保留されていない依頼の遅着の結果は、従来どおり画面へ回す。保留の上限は最も早い保留の開始（`held_at_mono_ms`）から数え、新しい発話で保留が増えても先の期限を延ばさない。

## 保存の命令を送った後の依頼（Codex の P1）

保存の準備中（命令をまだ DB へ送っていない。`committing`）と、保存の命令を DB へ送信済み（応答待ち。`dispatched`）を状態で区別する。送信済みの依頼は、新しい発話の保留にも Live の終了による破棄にも入れず、応答を待って保存結果をそのまま扱う（成功なら保存されたものとして声か画面へ届け、「破棄した」とは言わない）。保存の応答が失敗・不明のときは従来どおり自動再送しない。送信済みの依頼への訂正・取消は送出前の操作ではなく保存後の操作として扱う（訂正は別の依頼として進め、取消は保存済みの依頼への取消と同じく新しい実行をせず聞き返しに留める）。この判定は保留集合が空でも行い、対象が送信済み・保存済みなら、解釈が intent と取消を同時に返しても関係を優先して新しい実行へ進めない（対象がなければ通常の依頼として扱う）。失効した依頼は、Live の情報が既に外れて世代を読めない場合も画面へ出さない（届け先の判定の先頭で `revision_current` を確かめる）。

## 会話の操作と保留の優先順（Codex の「その他」）

会話の操作として照合された発話（「もう終わり」を含む）は、まず保留を別件（`new`）として解いて再開し、その後に接続の操作（読み上げの停止・会話の終了・記録しない・文字で返す・無音の延長）を適用する。再開した依頼は保留から外れるため、接続を閉じる操作の後に来る「Live の終了による保留の破棄」の対象にはならない（保存の準備中なら保存を続け、送信済みなら応答を待つ。結果は Live が閉じていれば画面へ回る）。終了時の破棄は、閉じる時点でまだ保留に残っている依頼にだけ当たる（今の実装では会話の操作が先に保留を解くので、通常は残らない）。
