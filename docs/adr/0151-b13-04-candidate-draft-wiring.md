# ADR 0151: B13-04 気づきの候補から返信の下書きを自動で保存する配線

- 日付: 2026-11-26
- 状態: B13-04（親 #24）の Core の配線の部分。ADR 0149・0150 の配線に、返信の下書きの保存（`draft_reply`、RemoteMutation）を足す。本文を作る口の中身（モデルによる文章の生成）、予定の書込み、取り消しの補償の中身、候補の生成の入口からの呼び出しは未着手。実データ・実機・実 API は未実施。
- 根拠: 設計 11 §5・§5A・§5B（F05）、設計 05（`reply_draft` の振り分け）、設計 08 §1・§9、設計 04、設計 06 B13、ADR 0004・0033・0053・0146・0148・0149・0150。原本の参照手順は `docs/design/README.md`。
- 対象: `apps/core/src/candidate-auto-execution.ts` とその試験。契約（`packages/contracts`）・保存層・マイグレーションは変えない。

## 背景

ADR 0150 までの配線は、判定表の 4 行のうち用事の登録とラベルの付与だけ操作を作り、返信の下書きの保存は判定が通っても `not_wired` を返していた。会話から作る下書きの保存（`api-turns.ts`、ADR 0033）は本人の発言から本文を受け取るが、候補を起点にした自動実行には本文を受け取る口が無かった。

## 決めたこと

| 対象                  | 決定                                                                                                                                                                                                                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本文の受け取り        | 本文を作る口（`composeReply`）を Core の口として受け取る。口に渡すのはアカウント・元のメールの ID・依頼の要約だけで、口が返す文の前後の空白を除いて本文にする。口が無ければ `composer_unavailable`、空・null・例外なら `body_unavailable` で作らない（U308）                              |
| 宛先と件名            | 会話からの下書きと同じく、Core が返信元の読み取りから決める（`replyFields`）。宛先は差出人だけ、CC は空、件名は「Re: 」を付けた値。本文を作る口に宛先や件名を作らせない（ADR 0004）。差出人か件名が読めなければ `reply_fields_unreadable` で作らない                                      |
| 照合できない provider | 下書きの保存は作成物の目印で照合する。目印で下書きを探せない provider（`findDrafts` が無い）では、実行担当と同じく作らない（`draft_unreconcilable`）                                                                                                                                      |
| 掃除のゲート          | ラベルと同じく、保存期限の掃除が済むのを待ち、貸し出しを持った区間で接続・許可の版・返信元を読み直し、本文を作る口を呼ぶ。本文を作る口は元のメールを読むので、ゲートが閉じていれば口も呼ばない（`retention_blocked`）。ラベルと共通の手順（`withRetentionLease`・`readMailTarget`）にした |
| 接続の確かめ          | 接続は有効・同じアカウント・`mail.draft.create` の書込みと `mail.message` の読み取りが許可の範囲内であること（`connection_unavailable`）。返信元が読めなければ `target_not_found`                                                                                                         |
| 確定 intent           | 会話からの下書きと同じ形。対象は元のメールの ID と今の版、許可の版は読み直した値、照合は目印（`operation_marker`）、外部の宛先は空（下書きは送らない）                                                                                                                                    |
| 作成の命令と一度だけ  | 用事・ラベルと同じ手順（ADR 0149）。一度だけの記録は保存層が `draft_reply` として残す                                                                                                                                                                                                     |

## 原本に決めがない項目

- 自動で保存する下書きの本文を何が作るかは書かれていない（U308）。設計 05 は `reply_draft` の振り分け（裏の文章、P0、枠 A）を定めるが、候補を起点にした自動の下書きでその生成を呼ぶか、どの入力を渡すかは決めていない。ここでは口だけを用意し、生成の中身は入口とあわせて決める。
- 判定の事実「同じスレッドに Buddy の下書きがまだない」（`draftExists`）は呼び出し側が渡す。Core はここで provider の下書きを探し直さない。同じ依頼からの二度目は一度だけの記録が止める。

## 対象外

- 本文を作る口の中身（モデルの呼び出し・予算・出力の検査）と、候補の生成の入口からの呼び出し。
- 予定の書込み、取り消しの補償の操作の中身と対象の現在版の検査、照合で拒否した操作の後始末と画面（B13-05）。

## 試験（模擬だけ）

- `apps/core/src/candidate-auto-execution.test.ts`: 期待値はすべて手書き。下書きだけ方針で有効なときに操作を作ること（本文を作る口へ渡す値、経路、許可の版、確定 intent の全体、実行の開始、一度だけの記録）。作らない場合として、口が無い・空・null・例外、目印で探せない、provider が無い、差出人が読めない、掃除のゲートが閉じている（口を呼ばない）。

**模擬の期待値だけ**。本文の生成・候補の生成の入口からの呼び出し・実際のメールへの保存・画面・実データ・実機・実 API は未実施で、合格扱いにしない。

## 残ること

- B13-04 の残り: 本文を作る口の中身と候補の生成の入口からの呼び出し、予定の書込み、取り消しの補償と対象の現在版の検査、照合で拒否した操作の後始末。
- B13-05: 安全停止・自動実行の一覧・取り消しの画面。
- U304〜U308 の本人の確認。
