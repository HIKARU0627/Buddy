# B00: 契約のファイル化

状態: **一部ファイル化・全体は未完了**。初回はラベル変更の契約経路、入力根拠、予算記録、候補モデル一覧、検証ツールを作成しました。Core / UI / DB / 外部 API の実装は含みません。
根拠: 非公開原本の設計 06、設計 09 §6〜7（[参照方法](../design/README.md)）。

## 最初の作業

1. [契約対応表](contract-map.md) を設計本文と突き合わせて、個々の契約・24 intent の一覧に展開する。B00-01 で台帳・24 意図・F01〜F05 の対応と未決事項 U01〜U10 を記録済み。契約ファイルの作成は 2 以降。
2. ID / 版 / 時刻 / 金額 / エラー / null の意味を共通化する。ワイヤの版番号は設計 07 に従う。
3. 入力確定 → 解釈 → 実行条件判定 → 承認 → 操作結果・イベントの一本を、schema・期待結果・検証コマンドまで通す。
4. 音声、予算、同期、関連解析、記憶など残る契約に展開する。
5. OpenAPI、domain の境界、storage のマイグレーション案を揃える。
6. 対応表から漏れと矛盾をレビューし、終了条件を判定する。

各作業で、対象本文の再確認 → 契約案 → 正常 / 拒否データ → 検証 → 横断整合の順に進める。
形式検査と、意味・権限・状態遷移の検査を分ける。まだ実装がない遷移は期待結果として記録し、試験を実行済みにしない。

## 初回に作成したもの

- `packages/contracts/schemas/buddy.schema.json`: 共通表現・入力・ラベル変更・受付と状態・予算の記録形式。24 intent は名前の一覧まで、固有引数は label_mail だけ。
- `packages/contracts/openapi.yaml`: 操作取得、preview / approve / cancel / reconcile / retry、イベント再取得の部分契約。bootstrap・sessions・音声・同期等は未ファイル化。
- `packages/contracts/src/generated.ts`: Schema から生成。生成差分を CI で拒否。
- `packages/contracts/fixtures/`: 正常／拒否例と H01。`workflow-label.json` は遷移の期待結果で、実行済み試験ではない。
- 検証ツール: 厳格な生 JSON、JCS / H01、Schema・OpenAPI、生成型、局所的な不変条件を検査。F01 / F02 の記録形式を検査したことと QA41 / QA42 の統合合格は別。
- モデル候補: 音声・即時判断・文章解析・高度相談・端末内 ASR を役割で分離。採用前に評価が必要で、実行可能な deployment manifest は未作成。

契約ファイル化はモデルの本採用より先に進めます。正解例の本人確認は並行可能です。次は共通表現（B00-02）で版の型と未決事項 U01・U03・U04・U08 を解決し、label_mail の意味検証・最終ガード、残る意図と API、F03〜F05、保存案へ広げます。全終了条件が揃うまでは B01 の着手可能と判定しません。

今回のファイル形式の選択と、未実装の実行境界は [ADR 0002](../adr/0002-contract-validation.md) と [初回の境界仕様](boundaries.md) にまとめています。
