# B07 の完了判定

B07（#12）の予算予約・最大負担 M・精算・月跨ぎについて、B07-06（#115）の模擬の統合試験と証拠を記録します。**親 Issue の完了条件 4 項目は、模擬の範囲ですべて観測できました。** 実 API・実請求・実機・HTTP の経路・画面は未実施で、実請求との照合は B15 です。B07-05（#114、利用状況の API・超過の承認・M 超過の確認。PR #136）は先に入り、B07-07（#116、クレジットの区分と保留）は MA03〜MA06 の模擬の試験を同じ実行器へ足しました（下の「B07-07: クレジットの区分と保留」。[ADR 0042](../adr/0042-b07-credit-split-and-hold.md)）。B07 全体を閉じるかは本人の判断です（下の「未実施・残る判断」）。

根拠は設計 05（予約と最大負担の区別 F02、費用の計算の単価の管理 D15、クレジットの追補）、09 の X18・QA20・QA42・X53・MA03〜MA06、01（設定・運用）、ADR 0006・0034〜0037、本人の判断（2026-10-23、#12 のコメント）。この PR では原本を新しく読んでおらず、既存の ADR と契約の fixture に取り込み済みの規則だけを使いました。既存の判断は変更していません。

## B07-07: クレジットの区分と保留

設計 05 の追補（通常料金・クレジット・追加の支出を分け、上限は通常料金の R と M で守る。周期と予算月は別。不明・失効・枯渇は購入残高へ移らず保留。共有の組織は専有できると主張しない）と 09 の MA03〜MA06 を、予算の門・DB worker・模擬の有料 provider・メモリの残高の観測でつないで確かめます。設計は [ADR 0042](../adr/0042-b07-credit-split-and-hold.md)。マイグレーションは 0008 を足しました（観測の採用の表と、予約のクレジットの結び付け・見積もりの列と trigger。番号は B06 の予定と重なるので、マージ順に付け替えます）。

B07-07 では原本（設計 05 のクレジットの追補・09 の MA03〜MA06・技術検証の再選定の節）を権限のある接続で読み取りだけ行い、全文は写していません。原本に決めがないことは ADR 0042 に「原本に決めなし」と書き、未決事項 U49〜U52 として [契約台帳](../b00/contract-map.md)に記録しました。

- 突き合わせの規則 `creditFindings`（`tests/integration/b07-support.mjs`）は、予約の行だけから、実装の判定とは別に数えます: 周期のない行にクレジットがない・精算済みは実費 = クレジット + 追加の支出・クレジットは M を超えない・周期は Claude の LLM の枠だけ（音声・検索の枠でない）・未精算の行に区分がない・周期ごとのクレジットの合計は観測した最も大きい残高を超えない。毎回すべての世界で確かめ、この規則自体が誤りを検出できることは `b07-support.test.mjs` で確かめます。

- 感度は、受付の残りから未精算の M を引かない・音声と検索を対象から外さない・精算で M の上限を外す欠陥を一時的に入れて、該当の試験が落ちることで確かめました（コミットしていません）。

`pnpm test` / `pnpm run check` は実行器を自動で含みます。24 ケースを seed `7, 1007, 20261023` で並べ替えて 3 回、計 72 回実行します。seed は、ケースの実行の順序と、同時に受付へ送る要求の順序だけを固定します。予約の ID は予約ごとの連番です（秘密ではない）。

- 突き合わせの規則は `findings`（`tests/integration/b07-support.mjs`）です。予約の行は SQL で直接読み、provider の受信（request_id・予約）と provider 自身の真の usage を使い、(1) 同じ要求を二度受信しない、(2) 受信は送出意図のある予約だけで予約の取り違えがない、(3) 送出意図があって受信のない予約は usage 不明だけ、(4) provider の usage で精算した予約の実費は provider の真の usage と同じ、(5) 照合 ID の使い回しがない、(6) 送出意図または受信のある予約が解放（released）になっていない、(7) 枠・予算月ごとの使用量（精算済みは実費、未精算は M、解放は 0）が上限以内、を確かめます。同時の受付（`wave`）では、精算の前に受付の命令がそろうので、M の合計も上限以内であることを確かめます。この規則自体が、上限の超過・二重の受信・取り違え・実費の食い違い・照合 ID の使い回し・送った予約の解放を検出できることは `b07-support.test.mjs` で、手で作った不正な記録を使って確かめます。
- 実行器の感度は、製品のコードに一時的に欠陥を入れて確かめました（コミットしていません）。受付の M の上限の判定を 1 ずらすと X18・X53 が、usage 不明のときに provider へ送り直すようにすると 19 件が失敗しました。
- 競合の勝ち負けは命令の並びで決まるので、X18 の境界の同時の予約と追加予約の競合は、ケースの並べ替えに任せず、投入順の両方（c → d と d → c、v1 → v2 と v2 → v1）を明示して実行し、投入した順序もケースの観測に記録して検査します（証拠の予約の行で、勝つ予約が順序で入れ替わることを確認済み）。
- 待ち合わせは、関門（`barrier`）・provider の受信の知らせ・手で発火する timer と手で進める時計で行い、固定の sleep を使いません。受付の命令は、すべての要求が関門に着いてから DB worker へ送ります。
- 模擬の有料 provider と予算の門・DB worker は同じプロセスで、HTTP の経路（B07-05）は通しません。再起動は DB worker だけを閉じて開き直す模擬で、OS の電源断や実機の試験ではありません。
