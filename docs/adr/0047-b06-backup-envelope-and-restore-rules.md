# ADR 0047: B06 のバックアップの中身と世代・鍵の運用・復元の 6 段階・復元の後の保留（domain の純粋な規則）

- 日付: 2026-10-24
- 状態: B06-05（#141、親 #11）の判断。`packages/domain/src/` の `backup-plan.ts`・`backup-keys.ts`・`restore-plan.ts`・`restore-aftermath.ts` の純粋な関数と、手書きの期待値（`tests/fixtures/backup-restore-cases.json`）による模擬の試験だけ。スナップショットの取得・暗号化・鍵の包みと開封（HKDF・AES-GCM の計算）・ファイルの削除・復元の実行・DB の差し替え・trigger は Core と storage（B06-06・B06-08）。実際のバックアップと鍵の復元・実機の Mac mini は未実施（B15）。
- 根拠: 設計 03（バックアップ・復元・忘却と再取り込み・保存期限）、08 §3・§4、09（X15・X16・X17・T06）、ADR 0008・0012・0016〜0019・0040・0043、本人の判断 J1〜J6（2026-10-24、#11 のコメント）と司令塔の判断（同日、#11 の 2 つ目のコメント）、B06-01（PR #148）の Codex の最終確認の P3（#141 のコメント）、PR #154 の Sonnet のレビュー（P1 1 件・P2 7 件・P3 9 件。Codex の利用上限による代わり）と、それに対する本人の判断（U78。端末）・司令塔の判断（安全停止・配備）。原本は権限のある接続で読み取りだけ行い、全文は写していない。原本に決めがないことは「原本に決めなし」と書き、docs/b00/contract-map.md の U73〜U78 に記録した。
- ADR 0040 で決めたこと（封筒・6 段階・3 種類の結果・7 状態の隔離・解除の 2 条件・3 つの鍵の包み）は変えていない。変えたのは次の 2 点で、どちらも下の「判断が要る点」に挙げた: (1) 復元の直後の記録の検査で、承認の失効を**印の有無・経路によらず**検査する（B06-01 の P3。ADR 0040 の表の文言「承認は失効」を全操作に広げた）。(2) LocalCommand の `approved`・`preparing` を、復元の後に**承認待ちへ戻す**（ADR 0040 の表は「そのまま」。J3 で承認を失効させると、承認済みのまま再承認の経路がなくなるため）。

## 決めたこと

### バックアップの中身（`backup-plan.ts`）

| 対象                             | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 含めないデータ（03）             | 生音声・記録しない会話・OAuth トークン・API キーは表ではない（保存しない・KeyStore）。封筒の `excluded_data` に 4 つを必ず記録し、`included_storage_modes` に `private` を入れない（`backupManifestProblems`）                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 含めない表（U73）                | 短命の運用データ 10 表: `source_items`（本文キャッシュ 24 時間・元サービスが正本）、`sync_batches`・`sync_staging`（進行中の同期）、`event_outbox`（DB の世代に結び付く）、`command_scopes`・`command_receipts`（接続範囲。復元の後に取り直す）、`pairing_sessions`・`pairing_claims`（5 分・秘密の hash）、`async_context_guards`（進行中の非同期処理。記録がないので復元の後の遅着は破棄される）、`home_network_reports`（端末の最新の報告）。除外した表が持つ暗号文（`sealed_blobs` の `owner_table`）も写しから消す                                                                                                         |
| 付帯クレジットの観測             | B07-07 のマイグレーション 0008 の `budget_credit_observations`（採用済みの残高の観測。本文なし・書き換え・削除不可）は、予算の記録と同じく**含める**。復元した後の扱いは下の「付帯クレジットの観測と復元」                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 必ず含める表                     | `schema_meta`・`forget_ledger`・`forget_ledger_items`。忘却台帳の 2 表は除外できない（ADR 0040 の `required_table_excluded`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 未知の表                         | 含める・含めないのどちらの一覧にもない表があれば、**バックアップを取らない**（`unknown_table`）。何が入っているか分からない表を黙って含めも捨てもしない。表を足すマイグレーション（B06-06 の 0008 以降）は一覧に必ず載せる。試験がマイグレーションの `CREATE TABLE` と一覧を照合する                                                                                                                                                                                                                                                                                                                                            |
| 鍵が中身を覆うか                 | 封筒を書く前に、DB の暗号文が使うデータ鍵がすべて封筒の `data_key` の包みと同じ ID か、台帳の鍵の包みが DB に記録した台帳の鍵と同じ ID かを確かめる（`backupKeyCoverageProblems`）。データ鍵の入れ替えの途中で 2 つの鍵の暗号文がある DB は、包みが 1 つしかないので実機を失うと読めない。取らずに知らせる（CLI で包み直す）                                                                                                                                                                                                                                                                                                    |
| 古いバックアップの期限（U74）    | 期限は**世代の数 × 1 日**（1 日 1 回の設計なので、初期 7 世代は 7 日）。作成からちょうどその時間で消す。バックアップが止まっていても延ばさない。時計が戻ったときは最終確認時刻で判定する（ADR 0043 の U54 と同じく消し続ける）。**ただし期限内の封筒が 1 つもなくなるときは、成功した最新の 1 つを期限を過ぎても残す**（司令塔の判断。`last_backup_kept`。失敗が続いても手元のバックアップを 0 にしない）。残した封筒には `needs_new_backup` を立て、忘却の世代が古ければ `awaiting_replacement` も付ける。期限と忘却は、その封筒から復元するときに段階 2・3 で当てる。読めない・別の系譜などの封筒は「成功した最新」に数えない |
| 世代の数                         | 期限内の封筒のうち新しい方から `keep_generations` 個を残し、残りを消す（`beyond_generations`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 忘却を古いバックアップへ当てる   | 忘却の世代が今の台帳より古い封筒は、**今の世代のバックアップができてから**消す（`forgetting_superseded`）。まだないときは残して `needs_new_backup` を立てる（`awaiting_replacement`。ADR 0040 の「新しいバックアップを作ってから」）。残した古い封筒から復元しても、段階 3 で台帳を当てるので忘れた内容は戻らない                                                                                                                                                                                                                                                                                                               |
| 復元に使えない封筒               | 封筒が読めない・別の系譜（`ledger_id` が違う）・今より先の作成・台帳より新しい世代（台帳の巻き戻りの疑い）は、世代の数に数えず、復元にも使わない。**ただし期限は当てる**（Sonnet の P2-4）。起点は封筒の作成時刻と、Core が渡すファイルの更新時刻（`file_modified_at`）の早い方（読める方）。どちらも読めなければ消さずに `age_unknown` で知らせる。台帳より新しい世代だけは、巻き戻りの証拠として**30 日**（`BACKUP_GENERATION_AHEAD_MAX_DAYS`）まで残して知らせる。台帳を確認できないときは、忘却の世代による置き換えを判定しない（`forgetting_checked: false`）。同じ ID の封筒が 2 つあれば計画しない                       |
| 封筒の除外の表（Sonnet の P2-6） | `excluded_tables` は短命の 10 表（`BACKUP_EXCLUDED_TABLES`）の部分集合で、重複がなく辞書順であること（`excluded_table_unknown`・`excluded_tables_duplicate`・`excluded_tables_unsorted`）。業務の表・予算・存在しない表を除外した封筒を拒否する                                                                                                                                                                                                                                                                                                                                                                                 |
| 本人への知らせ（P3-8）           | 計画は `notices`（バックアップの ID と理由だけ）を返す: 期限を過ぎて残した最新の 1 つ（`last_backup_kept`）・台帳より新しい世代（`generation_ahead_of_ledger`）・期限を判定できない封筒（`age_unknown`）。`RetentionNotice`（キャンバス向け）の対象の種類にバックアップがないので、運び方は U40（UI-05）・B06-08                                                                                                                                                                                                                                                                                                                |

### 鍵の運用（`backup-keys.ts`。B06-01 の P3）

| 対象                                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 包みの一部の欠け・取り違え           | 3 つの包みが用途ごとにちょうど 1 つ・同じ復旧キー・形が正しく、**3 つの鍵の ID が互いに違う**こと（`keyWrapProblems`。`key_id_reused` は Sonnet の P2-3）。欠け（`key_wrap_missing`・`key_wrap_count`）、同じ用途が 2 つ（`key_wrap_duplicated`）、知らない用途、別の復旧キー（`recovery_key_mismatch`）、用途をまたいだ同じ ID を拒否する。用途の包みを推測で選ばない（`keyWrapFor` はちょうど 1 つのときだけ返す）                                                                                                                                                                                                                           |
| 包む鍵の導き方（U76）                | HKDF-SHA256(ikm = 復旧キーの 32 バイト, salt = 包みの `kdf.salt` の 16 バイト, info = `buddy/backup/key-wrap/v1` ‖ 0x00 ‖ purpose ‖ 0x00 ‖ key_id, L = 32)。用途を info に入れるので用途ごとに鍵が変わる                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| AES-GCM の追加認証データ（U76）      | `buddy/backup/key-wrap/v1` ‖ 0x00 ‖ purpose ‖ 0x00 ‖ key_id ‖ 0x00 ‖ recovery_key_id。包みを別の用途・別の鍵の ID・別の復旧キーの欄へ入れ替えると認証タグが合わず開けない（試験で node:crypto により確かめた）                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 台帳の用途別の鍵                     | HKDF-SHA256(ikm = `ledger_hmac_key`, salt = 空, info = `buddy/ledger/source-id/v1` または `buddy/memory/dedupe/v1`, L = 32)。ADR 0040 の info のとおりで、salt は原本・ADR 0040 に決めがなく空にした（RFC 5869 で 32 個の 0 と同じ）                                                                                                                                                                                                                                                                                                                                                                                                           |
| 復旧キーの確認値（U76）              | HKDF-SHA256(ikm = 復旧キー, salt = 空, info = `buddy/recovery-key/check/v1`, L = 4) を大文字の 16 進 8 桁（`RecoveryKeyRecord.check_value`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| HKDF の入力の検査                    | domain は入力（salt・info・長さ）を組み立てて検査する（`backupHkdfInputProblems`: sha256・salt は 0 か 16 バイト・info は `buddy/` で始まる 1〜1024 バイト・長さ 1〜32）。計算は Core。domain は Node の Buffer・TextEncoder を使わず、値は ASCII だけ                                                                                                                                                                                                                                                                                                                                                                                         |
| 復旧キーの文字列                     | Crockford base32 の 52 文字（4 × 13）の先頭 256 ビット。末尾の 4 ビットは 0。入力は**先に ASCII の英数字・空白・- だけに絞り**（`toUpperCase` が `ı` を I、`ſ` を S にするので。Sonnet の P3-1）、区切り・空白を無視し、小文字と Crockford の読み替え（I・L → 1、O → 0）だけを許す。U・文字数の違い・末尾のビットが 0 でないものは読まない                                                                                                                                                                                                                                                                                                     |
| 設定のやり直しで鍵を保つ             | ある鍵は作り直さない（`reuse`）。包み直しだけ。台帳に項目がある・台帳の鍵を記録したのに KeyStore にない（**欠落**）、KeyStore の鍵が記録と違う（**取り違え**）、台帳に項目があるのに鍵を記録していない、ときは新しい鍵を作らずに止める（作ると台帳と記憶の HMAC を照合できず、忘れた元情報の再取り込みを止められない）。データ鍵は CLI が作らない（ADR 0040）                                                                                                                                                                                                                                                                                  |
| 台帳の鍵の記録                       | Core は台帳と記憶の HMAC に使っている鍵の ID を DB（`schema_meta`）に記録する（B06-06・B06-08 で列・キーを足す。ADR 0040 の `ForgetLedgerFile` は鍵の ID を持たない）。同じ系譜の中では台帳の鍵は変えない                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 既存の台帳に対する鍵の欠落・取り違え | 復元の段階 1 で、封筒の台帳の鍵の ID が中枢の記録・KeyStore と違えば拒否する（理由は既存の `ledger_lineage_mismatch`＝別の HMAC の空間。契約の理由を増やさない）。中枢の台帳に項目があるのに鍵の記録がなければ `latest_ledger_unconfirmed`                                                                                                                                                                                                                                                                                                                                                                                                     |
| 復元で鍵を入れる順序                 | **足すだけで上書き・削除をしない**（`keyInstallPlan`）。封筒の鍵を自分の ID で足す → 読み戻して確かめる → DB を差し替え、同じ transaction で今使う鍵の ID を記録する → 使わなくなった既存の鍵は消さずに残す。差し替えより前のどこで失敗しても、この計画で足した鍵だけを消せば元どおり（稼働中の鍵と DB は変わらない）。足した鍵・残す鍵は**用途と ID の組**（`KeyRef`）で指す（Sonnet の P2-3）。同じ ID で素材が違う鍵（取り違え）・素材を比べていない鍵・別の ID の台帳の鍵・**同じ ID の鍵が別の用途で KeyStore にある**（`key_material_conflict`）・ID が重なる包みのときは入れない。順序の入れ替えは `keyInstallOrderProblems` で見つける |

### 復元の 6 段階（`restore-plan.ts`）

| 段階                 | 判定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 台帳の確認         | 封筒の意味の検査に通らなければ `manifest_invalid` だけ。中枢の台帳の系譜が違う（中枢がなく全部の複製が違うときも）・封筒の台帳の鍵が違う → `ledger_lineage_mismatch`。中枢の台帳の連鎖が壊れている → `ledger_chain_invalid`。使える台帳（同じ系譜・連鎖が正しい・全体）で ADR 0008 の `restoreReasons`（最新は「知っている最新」と使える台帳の head の大きい方）。使える台帳の、封筒の世代の hash が封筒と違う → `backup_ledger_hash_mismatch`。同じ持ち主の台帳が 2 つ → `latest_ledger_unconfirmed`。通れば最も新しい台帳（同じ世代は中枢を優先）を段階 3 で当てる |
| 2 期限切れの削除     | 開けない（復旧キーの確認値の不一致・包みの認証の失敗・鍵の入れ方の衝突・本体の hash の不一致）→ `backup_unreadable`。時計が最終確認時刻・復元の開始・バックアップの作成より前、または読めない → `clock_regression`（期限を判定できない。03）。開けて時計も正しいのに、削除を作業用の DB に当てた記録（`purge_applied_at`）がない・復元の開始より前 → `expiry_purge_failed`（契約に足した理由。Sonnet の P2-5）。当てた時刻が今より先 → `clock_regression`                                                                                                            |
| 3 忘却の適用         | 段階 1 で選んだ台帳の head まで当てていなければ `forget_apply_failed`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 4 DB の検証          | 版がこのコードより新しい → `schema_newer_than_code`（ADR 0016）。整合性・外部キー・取り出した DB と封筒の版の不一致・操作の隔離の計画が立たない（読めない状態・経路）・**表の一覧に未知の表・必須の表の欠け**・**DB の中の `store_generation`・`ledger_id` が封筒と違う、忘却の世代が段階 3 で当てた台帳の head と違う**（Sonnet の P2-6。封筒と中身の取り違え）→ `db_integrity_failed`。SQLite の内部の表（`sqlite_*`）は Core が除いて渡す                                                                                                                         |
| 5 作り直し・6 照合   | 作り直しの失敗は `rebuild_failed`。外部の照合は失敗で止めず、再認証が済むまで `pending`（OAuth トークンは封筒にないので、復元の直後はいつも `pending`）                                                                                                                                                                                                                                                                                                                                                                                                              |
| 結果の組み立て       | `buildRestoreResult` が契約の形を作る。止まった段階より後は `not_run`。段階の順序・止まった後の実行・理由の段階の組・`after_restore` の有無・世代の更新・保留と隔離の件数・時刻の逆転（期限切れの削除の `clock_regression` だけ許す）が食い違う入力は組み立てない。組み立てた結果は契約の Schema と意味検査に通る（試験で照合した）                                                                                                                                                                                                                                  |
| settings_only（U75） | 台帳の確認で止まり、理由が「最新の台帳がない・確認できない・台帳が巻き戻った」の 3 つだけで、本体を開けて設定を読めたときだけ。系譜・連鎖・hash・封筒の不一致は、別の・壊れた・書き換えたバックアップの印なので設定も戻さない。戻す表は `deployments` だけ（本文・個人の内容・認可・実行の状態・予算を持たず、他の表を参照しない）。戻すときも `active` は `evaluated` に落とす（下の「配備」）。`user_directives`（会話に由来し忘却の対象になり得る）・`home_networks`（端末を参照）・`safety_breaker`（停止の状態を古い値へ戻し得る）は戻さない                    |

### 復元の後の保留（`restore-aftermath.ts`）

| 対象                                     | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| J3 承認はすべて失効                      | 経路・状態・印の有無によらず、有効な承認を 0 にする（`approvals_revoked_count` は全操作の合計）。検査（`restoredOperationProblems`）と契約の意味検査（`scripts/contract-tools.mjs`）は、印のない LocalCommand・終端の操作でも `valid_approval_count > 0` を `approval_not_revoked` で拒否する（B06-01 の P3）                                                                                                                                                                                                                                                                                                                                                                                        |

### 付帯クレジットの観測と復元（B07-07 の 0008 との関係）

`budget_credit_observations` を含めたバックアップから戻すと、古い観測で残高を多く見ないかを確かめた。

- **何が失われるか**: 復元した DB の採用済みの観測と予約の行は、バックアップの時点まで。その後に採用した観測（残高の減少・枯渇）と、その後の受付・精算（台帳から引く消費の見積もり `credit_estimate`）は失われる。ADR 0042 の残り（観測した残高 − 観測の時刻以後の精算 − 未精算の M）は、**古い観測と、消えた精算のせいで実際より多く見え得る**。そのまま受け付けると、provider が購入残高・後払いから引く要求を通し得る（ADR 0042 が禁じること）。
- **ADR 0042 の守りだけでは閉じない点**: 採用は前へだけ進む（trigger）が、復元は表ごと古い状態に戻すので、その守りの外にある。本人の観測ファイルが中枢に残っていれば、次の読み込みで新しい観測を採用できる。ただし、ファイルの観測がバックアップより後・復元より前のものだと、その観測の後に精算して消えた消費は、やはり数えられない。
- **閉じる側に倒した形**: (1) 予算の保留（`restoreBudgetHold`）で、保留の月が今月の間は本人が確かめるまで有料の受付を止める（クレジットを充てる要求を含む）。(2) 予約中の行は使用量不明にして、M を台帳の残りから確保し続ける（未送信として解放しない）。(3) **それに加えて**、観測の時刻が復元の時刻以後の観測を新しく採用するまで、クレジットを充てない（`restoreCreditReasons` の `credit_restore_unverified`。ADR 0042 の `credit_unknown` と同じ側）。本人が月を確かめた後でも、古い観測から求めた残りでは受け付けない。復元の後に観測した残高は、復元の前に provider が引いた分をすべて含むので、その後の残りは多く見えない。
- **採用の連番**: `observation_seq` は INTEGER PRIMARY KEY なので、復元した DB の最大の続きから振り直される。復元の前の DB で使った番号と重なり得るが、番号を参照するのは同じ DB の予約の行（`credit_observation_seq`・`credit_settled_seq`）だけで、どちらも同じスナップショットから戻るので DB の中では食い違わない。番号を DB の外（ログ・知らせ・端末）で観測の同一性に使わない前提（B07 の実装は今そうしている）。
- **残る限界**: 復元の直前まで provider へ送っていた要求の消費が、復元の後の最初の観測より遅れて残高に反映されると、その分だけ残りが多く見え得る（provider の反映の遅れ。原本に決めなし。請求の照合 B15 で確定する）。

## 判断が要る点

1. **承認の失効を全操作で検査する**（B06-01 の P3 の反映）: 契約の意味検査を変えた。印のない LocalCommand・終端の操作に承認が残る記録も拒否する。
2. **LocalCommand の承認済み・準備中を承認待ちへ戻す**（U77）: ADR 0040 の表は「そのまま」だった。そのままにすると、承認が失効した承認済みの操作を本人が再承認できない。
3. ~~古いバックアップを世代の数 × 1 日で消す（U74）~~: **司令塔の判断で確定**（2026-10-24）。成功した最新のバックアップは期限を過ぎても 1 つ残す。忘却と期限は、そのバックアップにも当てる（復元の段階 2・3）。
4. **settings_only で戻すのは `deployments` だけ**（U75）: 実質は「新規開始」に近い。`user_directives` の「今後は」の指示や `safety_breaker` を戻す案もあるが、忘却・停止の状態に触れるので外した。
5. **台帳の鍵の取り違えの理由に `ledger_lineage_mismatch` を使う**（U76）: 契約の理由を増やさなかった。専用の理由（例: `ledger_key_mismatch`）を足す案もある。
6. **安全停止の理由を契約に足した**（司令塔の判断の反映）: 既存の理由で表すと誤った原因を見せるので、`SafetyState.stop_reason` に `restored_from_backup` を足した（DB の CHECK は B06-06）。
7. **期限切れの削除の未実行の理由を契約に足した**（Sonnet の P2-5）: 既存の `backup_unreadable`・`clock_regression` では表せないので `expiry_purge_failed` を足した。
