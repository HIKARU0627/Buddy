## 由来の位置を保存する形

今の保存で足りるかを調べた。

- 候補の由来の辺（`derivations`）は元情報の `remote_id` だけで、予定のカレンダー・接続・口座・取得集合を持たない。
- 元情報の行（`source_items`）は口座と取得集合を持つが、カレンダーの ID を持たない。さらに、行は取得から 24 時間の期限（`source_body`）で行ごと消える（`expiry-store`）。候補は閉じてから 97 日まで残る（U280）ので、`source_items` に列を足しても、根拠を取り直す時にはたいてい無い。
- 予定の ID は、招待された同じ予定なら別の口座のカレンダーでも同じになる。口座・接続を知らずにすべての接続を探すと、別の口座の写しを根拠にしてしまう（口座の付け替えも見分けられない）。

足りないので、候補の側に別の表を足した（U684）。

| 対象        | 決定                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 表          | `candidate_origin_locations`（0026）。候補と由来の元情報ごとに 1 行: 提供元・接続・口座・取得集合・資源の種類（calendar・mail）・カレンダーの ID（メールは空文字）・メールの引用の位置（件名か本文と、コードポイントの範囲。引用そのものは持たない）。本文・題・引用は持たない                                                                                                                |
| 書く時      | 候補の作成（`candidate.create`）と同じ transaction で、由来の辺の後に書く（`locations` は省略できる）。由来の辺のある元情報だけを受ける trigger、書いた後は変えない trigger。予定の重複の取り込みは、この接続・口座・取得集合と予定を読んだカレンダーを控える。メールの取り込みの入口は、口座を渡されたときだけ控え、引用の位置は抄録と同じ根拠（要約の根拠、無ければ最初の根拠）の位置を写す |

| 0026 より前 | 位置を持たない候補は取り直さず、未確認のまま（期限・本人の操作で終わる）。推測で取り直し先を作らない                                                                                                                                                                                                                                                                                          |

カレンダーの ID は本人の口座のアドレスと同じことがある（主カレンダー）。口座の ID・カレンダーの ID を平文で持つのは、ADR 0144 の封の方針（口座の識別は封筒に入れる）とは異なるが、`connections` の取得対象（選んだカレンダー）・`request_entity_operations` の `calendar_id` と同じ扱いにした。`events.get` に要る値そのものなので、HMAC では代えられない（U684）。寿命は候補の題・抄録と同じ（閉じてから 7 日）。

## 取り直し（Core）

## 端末（apps/desktop）

- main の `CandidateBridge.evidence(ref)`: 参照から候補 ID を引き、`POST /v1/candidates/{candidate_id}/evidence` を接続範囲付きで送る。200 で形が正しく同じ候補の根拠なら confirmed（引用・未読・抄録）。409 は一覧を読み直して changed。422 は一覧を読み直して `entry_not_found`。503・結果が分からない・形の違う 2xx・別の候補の根拠は unconfirmed（ログはコードだけ）。ほかの拒否は `core_rejected`。ロック・切断をまたいだ根拠は渡さない。引用は main に持たない。
- 画面: 気づきの行に「根拠を見る」（状態を変えないので対応済みの行にも出す。結果待ちの行は出さない）。押すたびに取り直し、行の下に、確かめた根拠（引用・「元の情報の一部は未読です」・作ったときの抄録・「引用の位置は示せません」）、または「根拠を確かめられませんでした（未確認）」「根拠の元が変わったか、気づきの状態が変わりました（未確認）」を出す。未確認・変わったときは引用を出さない。閉じる・一覧から消える・ロックで引用を捨てる。別の行を開いた後の前の行の答えは反映しない。

## 利用者: ブリッジ（ADR 0143 の Muse の窓口）

ブリッジ（`apps/bridge`）は `POST /bridge/v1/candidates/{id}/evidence` を Core の根拠の経路へ中継する。そのまま渡すと、取り直した予定の題・メールの引用・抄録（本文に当たる値）が外部の LLM の窓口へ出るので、ブリッジの側で落とす（U689）。渡すのは候補 ID・依頼の ID と版・確かめられたこと（`evidence: confirmed`）・照合できた引用の数・未読の部分の有無・抄録があるか・落としたこと（`body_withheld`）だけ。未確認（503）・変わった（409）などの拒否はそのまま中継する。形の違う 200 は渡さず 502 にする。

## 残り

- Outlook（B09）: connector に 1 通を ID で読む口（本文・フォルダー）が無い。足すときにつなぐ（U682）。
- メールの引用の本文の作り方と版（U683）: 抽出を製品につなぐ（U546）ときに、抽出の入力と同じ本文の作り方を `mailText` に渡し、ラベルの変化（既読など）で変わらない版を決める。
