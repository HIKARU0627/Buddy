### 追いつきの流れ

1. 起動のとき（最初の同期の前）に複製を読む。読めれば、その head が「最後に保存できた世代」。ファイルがなければ世代 0。読めなければ世代 0 から取り直し、次の保存で退避する。
2. 接続が live になるたび、または知らせ（今の複製がその世代と hash をまだ持っていないもの）を受けたら、head（系譜・世代・entry_hash）を `POST /v1/forget-ledger/sync` に送る。
3. `entries`: 検査に通れば保存し、`has_more` なら返った head からもう 1 頁取る。`has_more` が偽なら止める（中枢の head に届いた）。項目が 0 件なら保存しない（余分に書かない）。
4. 検査に通らない・200 でない・契約の形でない・送れない・保存できない: 何も保存せず、理由を残して止める。次の同期は、最後に保存できた世代から。
5. `diverged`: 上の U405。`replica_ahead`: 上の U406。

### 復元の後の扱い

復元（`restore run`）は台帳の系譜（`ledger_id`）を変えず、DB の世代（`store_generation`）を新しくする（ADR 0040）。中枢が起動し直すので、端末は接続し直し（bootstrap で新しい `store_generation` を受ける）、live になったところで必ず同期する。端末は自分の複製を「最新」とみなさず、中枢の答えに従う。

- 復元が台帳を保った・進めた: 端末の head は中枢の連鎖の途中にあり、続きを受け取る（`x16-restore-ledger-kept-continues-to-newer-head`）。
- 中枢が古い台帳に戻された: `replica_ahead`。端末は巻き戻さない。知らせが中枢の古い head を指しても、持っている世代なので何も取らない（`x16-restore-core-rolled-back-replica-not-rolled-back`）。
- 戻された中枢で新しい忘却が起きた（枝分かれ）・別の中枢（別の系譜）: `diverged`。端末の複製を退避して残し、中枢の台帳を世代 0 から取り直す（`x16-restore-branch-after-rollback-old-replica-set-aside`・`x16-replica-diverged-lineage-new-hub-old-set-aside`）。

## 範囲を区切った理由と残り

- **知らせの運び方**（U403・U40）: 購読（`EventStreamMessage`）に知らせを足すか、別の経路かは UI-05 が決める。運ばれるまでは、接続のたびの同期だけが働く。
- **端末の複製を復元の材料にすること**: `restore check` は今、中枢の DB と台帳のファイルだけを見る。端末の複製（と退避したファイル）を中枢へ持ち込んで「知っている最新」に入れる手順は B15（実機の復元）で作る。そのとき退避したファイルを材料に含めるかを決める（U405）。
- **退避したファイルの片付け**: 自動では消さない。枝分かれ・登録し直しが繰り返されると増える。見直しで 8 個の上限を置いた（下の「見直しの追記」。U405）。
- **diverged・replica_ahead を本人に知らせるか**: 中枢が忘却を失った疑いだが、今は画面に出さない（U409）。画面に出すかは UI-10 か B15 で決める。
- **頁ごとに全体を書き直すこと**（U408）: 台帳が大きくなると書き込みが増える（最初の同期で 2 乗に増える。規模の見積もりは下の「見直しの追記」）。件数が増えたら取り直しの間の保存の間隔か追記の形式を検討する。
- **実機**: Windows・macOS の実機の userData への保存・rename の置き換え・ディレクトリの fsync の省略は未実施。

| 6. 大きさの上限と契約の最大のずれ        | 上限を契約から導くことはしない。契約の台帳は 10 万件までだが、1 件の配列（忘れた対象・HMAC）に上限がないので、ファイルの最大の大きさは契約から決まらない（上の例の形で 10 万件は約 65 MB で、64 MiB の上限にほぼ届く）。上限は 64 MiB のまま、上限を超えるファイルは unreadable にせず too_large として読まず、退避も置き換えもしない（`forget_ledger:replica_too_large`。次の同期でも大きさだけを確かめる）。上限を超える複製は書かない（次の起動で読めないファイルを作らない）。どちらの場合も、端末は新しい忘却を受け取れなくなるが、正しい複製を失わない。上限を上げるか、形式を変えるかは U408 で決める                                                                                                                                                                                                              | U408 |
| 7. 読み込みのときに device_id を照合する | 照合する。読んだ複製の持ち主（`device_id`）が今の登録の端末 ID と違えば（登録し直した）、連鎖はそのまま使い（自分の head を送るので `replica_ahead` の判定は働く）、次に保存するときに前のファイルを退避してから今の端末 ID で書く（`forget_ledger:replica_other_device`）。連鎖は中枢の台帳の写しなので、持ち主が違っても中身は使えるが、ファイルの持ち主は復元の材料として意味がある（U404）ので、前の持ち主のファイルを上書きしない。保存する物がなければ、前の持ち主のファイルのまま残る。照合は接続した後の最初の同期で 1 回（端末 ID は接続の状態から取る。分からなければ照合しない）                                                                                                                                                                                                                               | U404 |

追加した理由のコード: `forget_ledger:diverged_repeated`・`set_aside_limit`・`replica_unavailable`・`replica_too_large`・`replica_other_device`（U409。台帳の中身は出さない）。
