# ADR 0021: 端末のペアリング・端末の一覧と失効・最初の端末の CLI の承認

- 日付: 2026-10-21
- 状態: B03-02（#63）の判断と実装。中枢の画面で始めるペアリング（ワンタイムコード・申請・承認・トークンの 1 回だけの受取り）、端末の一覧と失効、最初の端末の CLI の承認、証明書の変更での再登録を作った。試験は 127.0.0.1 の模擬（模擬の KeyStore・一時ディレクトリの DB・子プロセスの CLI）だけで、macOS 実機・Tailscale 上の接続・実際の端末（B03-05）からの接続は未実施。
- 根拠: 設計 02（端末登録と接続）、07 §2・§3、06 B03、ADR 0009（U15・ペアリング）・0012・0018・0020、Issue #63 の本人の判断（2026-10-21: 最初の端末は登録済みの端末が 0 台のときだけ buddy-core の CLI で承認）。設計本文は今回の作業環境に取得できず、Issue #63 の要約と ADR に基づく。原本との照合はレビューで行う。

## 流れ

1. 中枢の画面の端末が `startPairing` で開始する。中枢は 8 桁のコードと証明書の指紋（ADR 0020）を返す。
2. 登録する端末は、最初の接続で中枢の証明書を受け取り、指紋を本人が中枢の表示と比べる。合えば、その証明書を信頼の起点にして指紋でピン留めした新しい接続で `claimPairing` を送る（申請用の秘密の SHA-256 とコード）。
3. 中枢の画面の端末が `decidePairingClaim` で承認・拒否する。
4. 端末は `pickupPairingToken` で申請用の秘密と交換にトークン（256 ビット）を 1 回だけ受け取る。

最初の端末（中枢の画面の端末がまだない）は、1 と 3 を中枢のマシンの `buddy-core first-device start | approve` で行う（下の「最初の端末」）。

## 決めたこと

### コード・申請・トークン

| 対象             | 決定                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| コード           | `randomInt` による 8 桁（0 埋め、一様）。有効 5 分、連続 5 回の失敗で無効（02 の設計初期値、0001 の CHECK）                                                                                                                                                                                                                              |
| コードの保存     | **HMAC-SHA256 にする**。鍵は Core の起動ごとの 32 バイトの乱数でメモリだけに置き、`HMAC(鍵, "buddy/pairing-code/v1" + NUL + コード)` を `pairing_sessions.code_hash` に置く（下の「コードの hash を HMAC にした理由」）                                                                                                                  |
| 有効なペアリング | 一つだけ。開始すると、まだ使っていない前のペアリングを使用済み（`used = 1`）にする。申請はコードだけを送りペアリング ID を送らないため、照合と失敗の数え上げの相手を一つに決める                                                                                                                                                         |
| コードの照合     | DB worker の 1 つの transaction の中で、最新のペアリングと照合値を `timingSafeEqual` で比べる。順は domain の `checkPairingCode` と同じ（使用済み → 期限切れ → 回数の上限 → 不一致）。不一致は残り回数を減らして commit する。合えば使用済みにして申請（pending）を作る。理由はどれも外へは 410 `pairing_failed`                         |
| 申請用の秘密     | 端末が作る 256 ビットの base64url（43 文字）。申請では ASCII の 43 文字の SHA-256（小文字の 16 進）だけを送る（契約の記述に追記）。中枢は 32 バイトで保存し、受取りでは送られた秘密の SHA-256 を `timingSafeEqual` で比べる。同じ hash の申請は二度受け付けない                                                                          |
| 申請の有効期限   | **申請を受け付けた時刻から 5 分**（`PAIRING_CLAIM_TTL_MS`）。承認と受取りはこの前だけ。期限は時刻で判定し、status を expired に書き換えない。ペアリングの期限（開始から 5 分）とは別に数え、開始からは最長 10 分で終わる。契約 fixture の token_pickup（期限ちょうどで 410）はこの期限で再現する                                         |
| 承認・拒否       | pending かつ期限の前で、ペアリングの開始時の指紋と今の指紋が同じときだけ。決め済みは 409 `conflict`、無い・期限切れ・証明書の変更は 410 `pairing_failed`                                                                                                                                                                                 |
| トークンの受取り | 経路の検査（`claim_secret`）で秘密を照合した後、domain の `tokenPickup`（承認前 409、使用済み・拒否・期限切れ 410）で決め、同じ条件を transaction の中でもう一度確かめて、端末の登録（`devices.token_hash` はトークンの ASCII の SHA-256 だけ）と申請の consumed を同じ transaction で書く。トークンは応答にだけ入れ、DB・ログに置かない |
| 受取りの成否不明 | COMMIT の成否が分からないとき（unknown）はトークンを返さない（自動で再送しない）。登録されていた場合は、本人が失効して登録し直す                                                                                                                                                                                                         |
| hub_local        | 受取りの接続元が中枢と同じマシンなら hub_local の端末として登録する（設計の「中枢と同じマシンのクライアント」）。`pairing_claims` に列を足さず（マイグレーションを足さない）、受取りの接続で決める                                                                                                                                       |

### コードの hash を HMAC にした理由

8 桁のコードは 1 億通りしかなく、素の SHA-256 は DB・バックアップの写しから数秒で総当たりできる。HMAC の鍵をプロセスのメモリだけに置けば、有効な 5 分の間に DB を読まれてもコードは分からない。鍵は起動ごとに作り直すので、再起動で未使用のペアリングは照合できなくなる（再起動の後は開始からやり直す。接続範囲が再起動で無効になるのと同じ扱い）。データ鍵（KeyStore）から鍵を導く案は、Core がデータ鍵を保持しない方針（ADR 0019）と合わないので採らなかった。

### 中枢の画面（hub_screen）

`hub_screen` の検査は「認証した端末が hub_local で、かつ今の接続元が中枢と同じマシン」のときだけ満たす（ADR 0020 の読み取り「中枢のマシンの外から hub_local の端末のトークンで接続された場合を区別していない」の見直し）。同じマシンの判定（`isSameMachine`）は、接続元がループバック（127.0.0.0/8・::1）か、待ち受けのアドレスと同じ IP のとき。中枢は 1 つの IP アドレスだけで待ち受けるため、同じマシンのクライアントが中枢のアドレスへ接続すると接続元も同じアドレスになる。Tailscale の経路では他のマシンが中枢のアドレスを名乗れないことを前提にする。

### 最初の端末

| 対象             | 決定                                                                                                                                                                                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 条件             | 登録済みの（失効していない）端末が 0 台のときだけ。承認の transaction の中でも 0 台であることを確かめる（`require_no_active_devices`）                                                                                                                                                                           |
| CLI              | `buddy-core first-device start` がペアリングを開始し、コード・指紋・期限・ペアリング ID を標準出力に出す。端末が申請した後、`buddy-core first-device approve --pairing-id <id>` で承認する。拒否は終了コード 7（`devices_registered`・`claim_not_found`・`claim_not_same_machine`・`https_not_configured` など） |
| 経路             | **ローカル制御チャネル（ADR 0012）を使い、DB を直接開かない**。端末の申請は動いている Core の HTTPS に届くので、Core が動いていることが前提になる。DB を CLI から直接開くと、DB worker を単一の書き手にする方針（ADR 0018）と単一起動のロックに反する                                                            |
| 同じマシンの申請 | CLI で承認できるのは、CLI で開始したペアリングへの、中枢と同じマシンからの申請だけ。どちらも Core のメモリに記録し、再起動で失う（やり直す）                                                                                                                                                                     |
| 制御チャネル     | 命令 `pairing_first_start`・`pairing_first_approve`（`pairing_id` だけを持つ）を足した。要求の厳格な検査（未知の項目・型・UUID）は ADR 0012 と同じ。応答は非同期で作れるようにした（DB を引くため）                                                                                                              |

ADR 0012 は制御チャネルで「本文・秘密は扱わない」としていた。今回、`pairing_first_start` の応答にだけワンタイムコードを載せる。コードは本人が端末に入力するための表示（中枢の画面に出すのと同じ値）で、有効 5 分・1 回だけ・5 回の失敗で無効になる。制御チャネルは同じマシンの同じ利用者だけが接続できる（Unix socket は 0600、ADR 0012）。要求には秘密を載せない。Core のログ（標準エラー）にはコードを出さない。

### 証明書の変更

中枢の証明書が変わったら自動で承認せず、再登録にする。

- 端末（B03-05・試験用のクライアント）はピン留めした指紋と違う中枢へ要求を送らない（ADR 0020）。新しい証明書を自動で受け入れない。
- 中枢は、起動時（HTTPS の受付の前）に、今の証明書と違う指紋のペアリングで登録した有効な端末を失効し、接続範囲を無効にする（`devices.revoke_certificate_mismatch`。端末の登録時の指紋は `pairing_claims` → `pairing_sessions.certificate_fingerprint` から求める。マイグレーションは足していない）。失効できなければ起動しない（`store_recovery_failed`）。
- 開始時と違う指紋のペアリングの申請は、承認も受取りもできない（410）。
- 全端末が失効するので、最初の端末の CLI の承認からやり直せる。

### ログ

ログには ID（pairing_id・claim_id・device_id）と理由コードだけを出し、コード・申請用の秘密・その hash・トークン・その hash を出さない。拒否の本文は ApiError だけ。試験でログと DB のファイルを検査する。

### 申請の接続（試験用のクライアント）

登録前の端末は中枢の証明書を持たない。試験用のクライアント（`apps/core/src/pairing-test-support.ts`）は次のように接続する。

1. 最初の接続では TLS の確立で見えた証明書だけを受け取り、HTTP の要求を 1 バイトも書かずに閉じる。この接続の検証の結果は信頼に使わない（この接続だけ `rejectUnauthorized: false`。要求を送らないので、なりすましの中枢に渡る情報はない）。
2. 証明書の DER 全体の SHA-256 を、本人が中枢の画面・CLI の表示と比べたとみなす。違えば申請しない。
3. 受け取った証明書を信頼の起点（`ca`）にし、比べた指紋を `checkServerIdentity` でピン留めした新しい接続で申請・受取りを送る（検証を無効にしない。ADR 0020 のピン留めクライアント）。

製品の端末側（B03-05）も同じ形にする。アプリ全体で証明書の検証を無効にしない。

### 自宅判定の既定（B03-03 まで）

自宅判定は B03-03 で作る。それまでの既定は安全側で、認証した端末は B03-01 の既定（hub_local の端末だけ免除）のまま、登録前の申請・受取り（端末なし）は中枢と同じマシンからの接続だけを免除で通す（最初の端末の登録のため）。他のマシンからの申請は 403 `outside_home_network`。試験は B03-01 の注入できる環境（`RequestEnvironment`）で自宅判定を満たして通す。

B03-03 の統合後は、Core の環境で `pairing.environment.homeNetwork` の上に B03-03 の自宅判定（[ADR 0022](0022-b03-home-network-check.md)）を重ねる。登録前の同じマシンからの申請・受取りの免除はそのまま残し、別のマシンからの申請・受取りは本文の `home_fingerprint` と Tailscale の直接経路で判定する。

## api-server の変更

経路の処理は B03-04（ADR 0023）と同じ `ApiServerOptions.handlers`（operationId → 処理、`ApiHandlerRequest` は経路・認証した端末・本文・パスの値・クエリー・接続元）で渡し、拒否は `apiErrorResponse` で作る。Core はペアリングの処理と B03-04 の経路の処理を一つの handlers にまとめ、環境は「安全側の既定 → ペアリングの判定 → 注入した環境（試験）」の順に重ねる（WSS の検査も同じ環境を使う）。この Issue では `ApiErrorCode` に `pairing_failed` を足しただけで、経路の検査の順（ROUTE_CHECKS）は変えていない。

## 契約の変更

意味の追記だけで、形（型・必須・enum）は変えていない。生成型は `pnpm run contracts:generate` で作り直した。

- `PairingClaimRequest` の記述: `claim_secret_hash` の定義（`claim_secret` の ASCII の 43 文字の SHA-256 の小文字の 16 進）。
- `PairingClaim` の記述: `expires_at` は申請の期限（受付から 5 分）。
- OpenAPI の記述: `startPairing`（有効なペアリングは一つ）、`claimPairing`（失敗はどれも 410）、`decidePairingClaim`（決め済み 409・無効 410）、`pickupPairingToken`（拒否・証明書の変更も 410、秘密の不一致 401）、`listDevices`（失効も含めて登録順）、`revokeDevice`（接続を閉じる・無い端末 409・失効済みは時刻を変えない）。

DB のマイグレーションは足していない（0001 の `pairing_sessions`・`pairing_claims`・`devices`・`command_scopes` で足りる）。

## 読み取り（レビュー対象）

原本に明記がなく、実装で決めた点です。

- **申請の有効期限**: 申請の時刻から 5 分にした（上の表）。原本・ADR 0009 に申請の期限の定めはない。
- **コードの hash を HMAC にする**: 上の理由のとおり。再起動で未使用のペアリングは使えなくなる。
- **有効なペアリングは一つだけ**: 申請にペアリング ID がないための判断。中枢の画面で開始し直すと、前のコードは使えなくなる。
- **「登録済みの端末」は失効していない端末**: 最初の端末の CLI の条件で、失効した端末は数えない。全端末を失効すれば CLI からやり直せる（証明書の作り直しの後もこの経路で再登録する）。
- **証明書の変更で端末を失効する**: 前の証明書で登録した端末は、端末の側でも接続を拒否するため使えない。中枢でも失効して一覧に出し、CLI の承認の条件（0 台）を満たせるようにした。ペアリングによらず入れた端末（試験で直接入れたもの）は対象にしない。
- **hub_local は受取りの接続元で決める**: 申請に列を足さないための判断。CLI で承認した申請を中枢の外から受け取った場合は hub_local にならない（権限は広がらない）。
- **存在しない端末の失効は 409**: 契約の `revokeDevice` の応答に 404 がないため、対象の状態の不一致として 409 `conflict` にした。
- **request_id の再送（X04）**: ペアリングの経路では、同じ request_id の再送を保存済みの受付結果へ写す処理（`replayDecision`）をまだ行っていない。開始の再送は新しいペアリングを作り、前のものを無効にする。承認の再送は 409。
- **ロック状態**: ロック状態の正本（B03-04 以降）がないため、製品の既定（unknown）では `startPairing`・`decidePairingClaim`・`listDevices`・`revokeDevice` は 403 `device_locked` になる。最初の端末の CLI の承認と、申請・受取りは影響を受けない。
- **最初の接続の証明書の受取り**: 試験用のクライアントは証明書を受け取るだけの接続で `rejectUnauthorized: false` を使う（要求は送らない）。製品の端末（B03-05）で同じ形にするかは B03-05 で確かめる。
- **tests/test-map.json**: X04（端末の偽装）のうち、他の端末の接続範囲・失効した端末の接続範囲の 410 と失効したトークンの 401 を模擬で確かめたが、X04 全体ではないので `product_test` は not_run のまま。

## 残ること

- 自宅判定（B03-03）。申請時の自宅の指紋の項目は B03-03 で足す。
