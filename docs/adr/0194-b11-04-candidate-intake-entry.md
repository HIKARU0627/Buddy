# ADR 0194: B11-04 候補の取り込みの入口（予定の重複を製品につなぐ、メールの抽出の結果の入口）

- 日付: 2026-11-27
- 状態: B11-04（親 #23、Issue #271）の残り (2) の判断と実装。予定の重複からの候補を、同期の公開の後の処理として製品の配線につないだ。メールの抽出の結果からの候補は入口だけを作り、製品の抽出がまだ動いていないので製品にはつないでいない（U546）。根拠を取り直す `fetchEvidence`・`checkEvidence` の connector への接続（残り (1)）と、U283・`Snapshot.candidates`・一覧の続き（残り (3)）は未着手。実 API・実機・実データは未実施。

## 試験（模擬だけ）

- `apps/core/src/calendar-candidate-intake.test.ts`（7 件）: 実際の DB（マイグレーション済みの SQLite）の候補の保存と結び、読み取りの口は合成の予定を頁ごとに返す。基準は 2030-10-09T03:00:00Z（日本時間 12:00）・Asia/Tokyo で、期待値は手で書いた。重なる 2 つの予定から候補が 1 つだけでき、識別子（手で書いた材料の SHA-256）・題（時刻だけ）・期限・由来・読み取りの範囲（選んだカレンダー、いまから 14 日後まで、頁を追う）が合い、予定の題が DB に残らないこと。辞退・空き時間・勤務場所の予定から作らないこと。再同期・却下の後に作り直さないこと、世代 1 の公開で初回取り込みになること、`shouldRun` の判断。始まった重複を作らず、続いている重複の候補を解決しないこと。時刻の変更・取り消し・辞退で resolved になり、由来を読めなかった候補・カレンダーの選択を外したときは触らないこと。記録しない会話の間は読まず作らず、出た後の公開で作ること、読み取りの間に区切りが変わると保存しないこと。拒否側（タイムゾーン・接続の種類と状態・取得対象・読み取りの口・窓が空・読み取りの失敗・頁の上限・鍵・掃除のゲート・由来の予定が未同期）。予定の写し方（ずれ付きの時刻の UTC への変換・終日・繰り返しの回・出欠・空き時間・読めない状態と時刻）。
- `apps/core/src/mail-candidate-intake.test.ts`（2 件）: 抽出した依頼が 1 つの候補になり、同じメールの再同期は `duplicate`、fyi は理由付きで候補にしないこと。フィルターで外した・失敗・送らなかった抽出、記録しない会話、区切りの変化では作らないこと。
- `apps/core/src/sync-scheduler.test.ts`（1 件を追加）: 公開の後の知らせに、対象・差分の数・公開後の取得集合が渡ること。`apps/core/src/retention-entries.test.ts`: 新しい取り込みを掃除のゲートを通す入口の表に足し、Core が渡すゲートの数を 10 にした。
- `packages/connectors/src/google-connector.test.ts`（2 件を追加）: 空き時間・種類・本人の出欠だけを写し、ほかの参加者を写さないこと、参加者の一覧の形が違えば拒むこと。
- 空き時間の判定・記録しない会話の照合・由来を読んだかの条件を一時的に壊して、試験が失敗することを確かめた。

**模擬の期待値だけ**。実際の Google Calendar・実 OAuth・実機・本人の実データでの確かめは未実施で、合格扱いにしない。

## 範囲の外と残り

- (1) 根拠を取り直す `fetchEvidence`（根拠の経路）・`checkEvidence`（保守）の connector への接続: 未着手。メールの候補は製品で作られていない（U546）。予定の重複の候補は、取り込みの回に重複の解消を確かめる（U545）が、根拠の経路は、候補の由来（予定の `remote_id`）からカレンダーを引けない（`source_items` にカレンダーの ID が無い）ので作れない。どちらも保存の形（由来の行にカレンダーやメッセージの位置を持つか）を決めてから行う。
- (2) の残り: メールの抽出の結果の入口を製品の抽出につなぐこと（抽出の配線は実 API の承認の後。B15）。カレンダーの選択を外した・接続を切ったときの予定の重複の候補を取得範囲外で resolved にすること（U545）。
- (3) U283（依頼 ID の解決と保存）、`Snapshot.candidates` の充填（端末は一覧の経路だけを使い、スナップショットの候補を読んでいない。イベントの流れに候補の変化を載せるかと一緒に決める）、一覧の続き（`next_cursor` を受けるクエリー。表示順が全体の並べ替えなので、頁ごとの続きの意味を決める必要がある）: 未着手。
- 新しい候補の通知（OS 通知・読み上げ）は B11-05 の配線で、ここでは出さない。

## 見直しでの修正（2026-11-27）

見直し（重大 0・中 6・軽微 4・要確認 1）を受けて直した。上の表は直した後の形。

- 続く理由で止まった回が毎分読み直していた: 続く理由で止まった回を次の差分のある公開まで回さず、鍵とタイムゾーンを読む前に確かめるようにした。Core は Google の接続だけを呼ぶ（U547）。
- 保存境界の照合が保存の直前の 1 回だけだった: 下書きを送る前ごとと、解消の遷移を書く前ごとに照合する（メールの入口も同じ）。
- 解消が接続を区別していなかった: 由来の元情報の行がこの接続の口座・取得集合にある候補だけを解消する。保存に読み取りの命令 `candidate.origin_scopes` を足した。
- 一時的に判定から外れた予定で解消していた: 解消の根拠を、重複の判定に使えた予定に限った。辞退から参加に戻しても作り直さない点を U545 に書いた。
- 忘れた予定から候補が作り直され得る: 候補の作成に通す既存の照合の関数は無い。U548 と ADR 0136 の追記に記録した（忘却の公開ゲートは閉じたままなので今は表に出ない）。
- 取得範囲外の resolved: 元情報の行は同期・期限・忘却のどれでも行ごと消え、理由が残らないので区別できない。U545 に理由を書き、実装しない。
- 走っている間の公開を捨てていた: 印を立て、終わった後にもう 1 回回す。
- 読む範囲が同期の保存した範囲より先へ出ていた: 同期が最後に全量を照合した走査の窓の終わりで切る。走査の結果に種類と窓の終わりを足した（`sync-executor`・`graph-sync-executor`）。
- connector が追加の項目の形の違いで頁全体を拒んでいた: 追加の項目（参加者・空き時間・種類・出欠・accessRole）は、形が想定外なら無しとして読む。
- タイムゾーンが変わると終日を含む重複の識別子が変わる: U549 に記録した。
- 共有のカレンダー・他人のカレンダー: events.list の accessRole が owner のカレンダーだけを使う（U550）。

追加した試験（模擬だけ、期待値は手で書いた）: `calendar-candidate-intake.test.ts` に 5 件（判定から外れただけの予定・写しの食い違い・別の口座と取得集合では解消しない／下書きの途中・遷移の前の区切りの変化／続く理由とやり直す理由・読む前の鍵とタイムゾーン／走っている間の公開／全量の照合の窓での打ち切り・本人の持ち物でないカレンダー・窓を知らない取り込み）、`mail-candidate-intake.test.ts` に 1 件（2 つ目の下書きの前の区切りの変化）、`candidate-store.test.ts`（`candidate.origin_scopes`）、`sync-executor.test.ts`（走査の結果の種類と窓の終わり）、`sync-scheduler.test.ts`（知らせの項目）、`google-connector.test.ts`（形の違いを無しとして読む・accessRole）。口座の照合・遷移の前の照合・全量の照合の窓・印・accessRole の条件を一時的に壊して、試験が失敗することを確かめた。
