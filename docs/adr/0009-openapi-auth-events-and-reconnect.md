## 責務の分け方

1. **形式**: OpenAPI 3.1.2（`packages/contracts/openapi.yaml`）が経路・要求・応答・エラーの正本で、本文は JSON Schema の定義を参照します。未知の項目・型違い・重複キーは 422（invalid_input）です。本文で端末 ID を名乗っても受け付けません（X04）。
2. **経路の検査**: 各経路の `x-buddy-core-checks` に、Core が行う検査を順番どおりに書きました。`packages/domain/src/api.ts` の `ROUTE_CHECKS` と同じ表であることを試験で確かめます。検査は、上限サイズ → 端末トークン（または申請用の秘密）→ 自宅判定 → 接続範囲 → ロック解除 → 画面操作 → 中枢の画面 → 音声所有権 → 版の順で、最初に満たさない検査の拒否を返します（`admitRequest`）。
3. **状態遷移**: 対象の存在・所有・状態遷移の可否は、その後に domain の各規則（`operations.ts`・`audio.ts`・`budget.ts` など）で判定します。`allowed_actions` は表示の補助で、認可ではありません。

| 拒否                                                                                                 | HTTP | コード                                                                                                        |
| ---------------------------------------------------------------------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------- |
| 端末トークン・申請用の秘密がない・失効                                                               | 401  | unauthenticated                                                                                               |
| 自宅判定の不成立・ロック中／ロック状態不明・画面操作でない・中枢の画面でない・音声所有権なし         | 403  | outside_home_network・device_locked・screen_operation_required・hub_screen_required・audio_ownership_required |

| 古い接続範囲・取り消し期限の経過・ペアリングの無効                                                   | 410  | expired_scope・undo_expired・pairing_failed                                                                   |

画面操作が必要な経路は、要求ヘッダー `Buddy-Input-Origin` を Electron main が限定 IPC の種類から付けます。Renderer が任意に指定できる値ではありません。

## 経路ごとの読み取り

原本に明記がなく、設計の文から読み取った点です（レビュー対象）。

- **停止はいつでも**: `stopIo` はロック中・音声の起点・旧版でも受け付けます（接続範囲が古いときだけ新しい接続で送り直させる）。`closeLiveSession` も接続範囲・ロックを問いません。中枢はリース切れでも自分から閉じます。
- **ロック中の表示**: `getSnapshot` はロック中も拒否せず、管理情報だけ（`management_only`）を返します。会話・候補・操作を含めないことを意味検査します。
- **ロック解除を求める経路**: 会話・発言・preview・取消・照合・端末と連携の一覧です。承認・再試行・取り消し・安全停止の解除・入出力の再開・表示の移動・端末の失効・取得対象の変更・接続解除は、さらに画面操作を求めます。
- **中枢の画面だけ**: ペアリングの開始と承認、OAuth の開始です。OAuth の戻り先が中枢の loopback になるためです。端末の失効も中枢の画面だけにしました（本人の判断 2026-10-21、B03-07。乗っ取られた端末に他の端末を締め出させないため。[ADR 0021](0021-b03-device-pairing-and-revocation.md)）。
- **認証前の上限**: 02 の「認証前のサイズ制限」を 16 KiB にしました（設計初期値）。ワンタイムコードは 8 桁にしました（02 は桁数を定めていない）。
- **申請の経路名**: 承認と拒否を一つの `/decision` にしました。

## 再接続・イベント・停止

- **再送**（X04）: 同じ接続範囲・request_id・同じ内容は保存済みの受付結果へ、内容が違えば 409 です（`replayDecision`）。古い接続範囲の命令は経路の検査で 410 になり、新しい依頼として受け付けません。
- **イベント**（X11）: スナップショットの後のイベントは、event_id の重複と、対象ごとの state_revision が進まないものを捨てます。連番の飛びだけでは欠落と判定しません。DB 世代が違えば再スナップショットです（`applyEvents`）。WSS では `resnapshot_required` を送って閉じます。
- **リース**（X13）: 期限は更新要求を送った時点の単調時計から数え、遅れて届いた応答の受信時刻から足し直しません。中枢の再起動・接続範囲の変化・入出力世代の前進・時計の不整合でもリースを捨てます（`leaseReasons`）。
- **停止の到達**（X14）: 応答のない端末は、リースの期限を過ぎても確認済みにしません。`lease_expired` は端末が自分で止まる期限で、全端末の停止確認（`all_confirmed`）には数えません（`ioStopProgress`）。
- **API の版**: `Bootstrap.api_version` の major が端末の対応する major と一致するときだけ使います（`apiCompatibility`）。

## ペアリング

中枢のロック解除済みの画面で開始すると、ワンタイムコードと中枢の証明書の指紋が出ます。登録する端末は、TLS で見えた指紋を中枢の表示と本人が比べた後で申請します。コードは有効 5 分・連続 5 回失敗で無効（02 の設計初期値）で、失敗のたびに残り回数を減らします（`checkPairingCode`）。外へ返すコードは理由によらず pairing_failed です。トークンは 256 ビットで、端末は OS の保護領域に、中枢は照合用の hash と失効状態だけを持ちます。

## 残ること

- HTTP サーバー（Fastify は候補）・TLS と証明書の固定・端末トークンの保存・自宅判定・WebSocket の実装は B01〜B03 で行います。
- 会話の発言を後から取得する経路、気づきの本文（根拠を見る）の経路、通知の ACK の経路は、まだ定義していません。必要な工程（B03・B10・B11）で追加します。
- provider ごとの OAuth の戻り先・トークン更新・権限の取り消しは B08・B09 で決めます。
- 実機・実 API・実際のネットワークでの試験は行っていません。
