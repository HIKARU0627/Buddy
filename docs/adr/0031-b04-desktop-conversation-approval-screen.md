## 決めたこと

| 対象             | 決定                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IPC のチャネル   | `desktop.turn_submit`（文字入力の発言）・`desktop.operation_preview`（承認表示の準備）・`desktop.operation_approve`（承認）・`desktop.operation_cancel`（取消）・`desktop.operation_reconcile`（照合）の 5 つ。どれも登録済みでロック解除済みの端末なら使える（中枢の画面の端末に限らない）。再試行（retry）の画面操作は作らない（下の「判断してほしい点」）                                            |
| 受付の規則       | ロック解除済み → 前面（画面操作）の順（`DESKTOP_PAIRING_SCREEN_CHANNELS` に足した）。加えて、入出力が止まっている間（この端末の停止・来客・全体停止）は発言と承認だけを `input_stopped` で拒む（実行を増やさない取消・照合・内容の確認は止まっていても使える）。形式は `DesktopIpcRequest` の Schema で先に検査し、未知の項目（操作 ID・hash など）は `invalid_request`                                 |
| 参照だけを渡す   | 画面へ渡すのは参照（`ref`・`preview_ref`）だけ。操作 ID・内容版・content_hash・preview_id・口座 ID・会話 ID・発言 ID・予定の ID は main の `OperationBridge` が持ち、画面へも IPC へもログへも出さない。`DesktopConnectionView.operations` を中枢の `OperationSnapshot` から `DesktopOperationEntry`（参照つき・版は state_revision だけ）へ変えた。参照は端末ごとに別で、ロック・切断で捨てる          |
| 発言の結果       | 中枢の `TurnResponse` を `DesktopTurnResult` に写す。予定の照会は件数だけ（`calendar_event`・`calendar_overlap` の数と `more_count`。予定の本文を取る経路は B04 にない。ADR 0029 の 50 件上限の残りは `more_count`）。承認が要る操作は `operation_ref`（一覧の同じ操作の参照）で指す。聞き返しは中枢の決まった文をそのまま出す                                                                          |
| 会話の作り方     | 接続範囲ごとに 1 つの会話（保存モード normal）を最初の発言で作り、以後はそれを使う。会話が中枢にない（409）なら捨てて、次の発言で作り直す。会話の作成の結果が分からないときは、発言を送っていないので、もう一度送れる                                                                                                                                                                                   |
| 承認表示の準備   | `POST /v1/operations/{id}/preview`。確定 intent から `DesktopOperationPreview`（変更先・対象・変更の項目）を作り、preview_id・内容版・hash・状態版・接続範囲は main が `preview_ref` の裏に持つ。同じ操作の前の確認は捨てる。承認待ちでない・結果不明の保留中の操作には出さない                                                                                                                         |
| 承認（D2）       | `preview_ref` を受けると、(1) 確かめた内容が今も同じか（承認待ちのまま・hash と内容版が同じ・状態版が進んでいない）→ (2) main の OS の確認ダイアログを **1 回だけ**（`confirmAdmin`。ダイアログの値は main が preview から作った値で、画面から受け取らない）→ (3) 確認の最中に内容・状態が変わっていないか → (4) 確認を使い切って `approve` を 1 回送る。やめる・閉じる・前面でなくなった場合は送らない |
| 結果不明         | 承認・取消を送って届いたか分からない（`unknown`）ときは `outcome_unknown` を返し、その操作を保留（`delivery_unknown: true`）にする。保留の間は承認・取消・照合・確認のどれも送らせず（`entry_not_found`）、自動では送り直さない。中枢の操作の状態版が進んだ（イベントで知った）ときに解く。照合（reconcile）は参照だけで再送ではないので、結果が分からなくても保留にせず、本人がもう一度押せる          |
| 世代と通し番号   | ADR 0026 と同じ形。main は応答を返すときに表示の権限の世代（ロック・切断で進む）を照合し、またいだ内容は返さない。画面（`useWorkState`）も世代をまたいだ応答を捨てる。操作の一覧は main が通知する値が正で、承認の確認は操作が承認待ちでなくなった・結果不明の保留になったときに画面が閉じ、main も状態版・hash の違いで `preview_stale` にする                                                         |
| 画面の構成       | 端末の画面の本体の先頭に、`WorkPanel`（`screens/work/`）を置く。上から「会話」→「変更の確認」（確認を開いている間だけ）→「確認が必要な操作」→「処理中の操作」→「終わった操作」。接続の欄の「中枢で進んでいる操作」は、処理状況と二重になるので外した                                                                                                                                                    |
| 変更の確認の内容 | 設計 01 の承認画面の必須の内容: 操作の種類・アカウント（変更先）・対象・変更の前後（項目・変更前・変更後の表）・影響（種類ごとの決まった文）。変更前は中枢が確かめた事実から言えることだけ（付けるラベルは付いていない・外すラベルは付いている・新しく作るものは「なし」）                                                                                                                              |
| 処理状況の文言   | `operationStatus`（`state/work-state.ts`）が状態ごとの 1 文・記号・色を決める。承認待ち／承認しました。実行を待っています／実行を準備しています／実行しています／結果を確認しています／完了しました／結果を確認できませんでした／実行されませんでした／取り消しました／内容が更新されたため、この操作は使われません。理由のコード・API の名前は出さない                                                 |
| 結果不明の見せ方 | 「結果を確認できませんでした」（danger・⚠）と「実行されたかどうか分かりません。自動では送り直しません。「照合」を押すと…」。ボタンは「照合」だけで、再送・再試行は出さない。「確認が必要な操作」に入れる                                                                                                                                                                                                |
| ボタンの重さ     | 1 画面に primary は 1 つ。確認を開いていない間は「送る」、開いている間は「承認する」が primary で「送る」は secondary。「内容を確認」「取り消す」「照合」は secondary（sm）、「閉じる」は ghost。押せないボタンは置かず、状態に合わないものは出さない                                                                                                                                                   |
| ロック中・停止中 | ロック中・ロック状態不明では、会話・確認・操作の内容を持たず（ロックで捨てる）、状態帯とフッターだけを出す。停止中は発言の欄と承認を出さず理由を言い、取消・照合は使える。接続していない間は発言の欄も操作の一覧も出さない                                                                                                                                                                              |
| 文言・読み上げ   | 数と単位の間は U+00A0。失敗・拒否は `role="alert"`、受け付けた知らせと進行中の 1 行は `role="status"`。操作の結果の文言は押した行（確認を開いている間は確認の欄）のすぐ下に 1 回だけ出す。発言は Ctrl／⌘ + Enter でも送れる（IME の変換中は送らない）                                                                                                                                                   |

## 判断してほしい点

1. **再試行（retry）の画面操作を作らなかった**: Issue の範囲は「発言・preview・承認・取消・照合」。未実行（not_executed）は「変更は行われていません」と言うだけにした。本人の明示の再試行が要るなら、次の作業で足す（Core の `POST /v1/operations/{id}/retry` は ADR 0030 にある）。
2. **予定の照会は件数だけ**: `ResultView` の `item_refs` は ID だけで、予定の題名・時刻を取る経路が B04 にない。件数・重なりの件数・ほか n 件（`more_count`）だけを見せた。題名・時刻を見せるには、予定の本文を許可範囲内で取る経路（B07 の同期）が要る。
3. **変更前の値**: 中枢の確定 intent は変更前の値を持たない。ラベルは「付けるラベルは付いていない・外すラベルは付いている」（ADR 0029 の no_change 判定と同じ前提）、新規作成は「なし」と書いた。実際の現在値を見せるなら、preview の応答に対象の現在値を足す契約の変更が要る。
4. **アカウント**: 確定 intent は口座 ID だけで表示名を持たない。変更先（模擬のメール・Gmail・Microsoft のメール・Buddy の用事）を見せた。口座の表示名（メールアドレスなど）を出すなら、接続の一覧（`/v1/connections`）からの取得を足す。
5. **承認の確認は 1 回で使い切る**: 承認を送った（受け付けられた・結果不明・拒否された）後は確認を捨てる。やり直しは、内容を確かめ直して新しい確認を出す。
6. **停止中の取消・照合**: 実行を増やさないので止めなかった。止めるなら `desktop.operation_cancel`・`desktop.operation_reconcile` も `input_stopped` の対象にする。
