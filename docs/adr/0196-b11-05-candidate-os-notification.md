## 決めたこと

### 入・切の設定（U580・U585・U586）

| 対象       | 決定                                                                                                                                                                                                                                                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保存先     | 中枢の DB の 1 行の表 `candidate_alert_settings`（マイグレーション 0025）。`os_notification`（`on`・`off`）と 1 ずつだけ進む版。**行がなければ切・版 0**（ADR 0073 の既定 OFF）。すべての端末で同じ値（U580）                                                                                                                |
| DB の守り  | 保存してよい記憶の種類の設定（0024）と同じ trigger: 最初の INSERT は版 1 だけ、行があれば INSERT（INSERT OR REPLACE を含む）を作る前に拒む、版は 1 ずつだけ進む、DELETE を拒む                                                                                                                                               |
| 経路       | `GET /v1/candidates/alert-settings`（端末トークン・自宅・ロック解除。端末の main が後ろで読むので画面操作は求めない）と `POST /v1/candidates/alert-settings`（接続範囲つきの本人の画面操作。音声・チャット・中枢の自動の処理からは 403）。版が今と違えば、**入にするときも切にするときも 409**（同じ要求の再送も 409。U586） |
| 古い表示   | main が設定の版ごとに参照（`DesktopCandidateAlertView.ref`）を作って画面へ渡し、画面の参照と違えば中枢へ送らずに `preview_stale`（ADR 0191 の設定の参照と同じ）。409・結果不明は送り直さず、main が設定を読み直す。画面は読み直しが終わるまで選択を押させない                                                                |
| 復元       | 設定はバックアップに含める。復元の後始末（7d）で、入なら切にして版を 1 進める（ADR 0038・U494 と同じ考え。バックアップの後に本人が切った通知を戻さない。U585）。0025 より前のバックアップには表がないので、表があるときだけ                                                                                                  |
| 最後の保証 | 送出意図を書く命令（`candidate.alert_intent`）は、同じ transaction で設定を読み、切なら・判定を始めた時点の版と違えば書かない                                                                                                                                                                                                |

### 通知の判定と運び方（U582〜U584・U587〜U590・U594）

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| きっかけ             | 候補の作成（`candidate.create` が `created`）と状態の遷移（`candidate.transition`）が書けた後。DB worker の口（`DbWorkerClient.onCandidateWrite`）が知らせ、Core の `candidate-alerts.ts` が受ける。取り込み（予定の重複・調査の完了・メールの入口）のどこから作っても同じ口を通る。取り込みの層は通知を出さない（ADR 0119 のまま）                                                                |
| まとめ方             | 同じ時機の書込み（同じ取り込みの回）を 1 回の判定にまとめ、OS 通知の知らせは 1 通（「新しい気づきが N 件あります」）。1 通の上限は 1000 件（U584）                                                                                                                                                                                                                                                 |
| 判定                 | 設定が切なら何もしない（知らせも送らない）。入なら、新しく作った候補ごとに配信の記録（`deliveries`、0001）を読み、domain の `candidateAlertDecision`（trigger は `new_candidate`、根拠は作った直後なので `valid`）で決める。再取得・再接続・端末移動・初回取り込み（U279）・既に配信の記録がある識別子・閉じた候補は出さない。判定はコード（domain と保存層）だけが持ち、LLM・端末は正本にならない |
| 送出意図と記録       | 出すものは、知らせを送る前に送出意図（`intent_saved`、端末を決めない・`os_notification`）を書く（設計 08 §7）。購読へ渡せたら `delivered`、購読がない・渡せなかったら `delivery_unknown`。どちらも鳴らし直さない（U583）                                                                                                                                                                           |
| 知らせ               | WSS の `notice` に `CandidateNotice`（`schema`・`notice_id`・`occurred_at`・`alert_count`）を足した。**題・期限・種類・候補 ID・通知の識別子を含めない**（ADR 0073・設計 11 §4。根拠のない本文は載せない）。開いている購読へだけ送り、溜めない・再送しない（ADR 0187・U168）。流れの表示の後始末・起動の設定の受け取り口へは渡さない                                                               |
| 件数だけの知らせ     | 入の間は、OS 通知を出さない遷移（開く・扱わない・再通知の設定・期限切れ・スヌーズの終わり・予定の重複の解消）でも `alert_count: 0` の知らせを送る（端末がトレイの new の件数を読み直す）。設定を変えた直後は、入・切のどちらでも 1 通送る（U594）                                                                                                                                                  |
| 複数の端末           | 開いている購読すべてへ同じ知らせを送り、各端末が前面・ロックを見て出す。記録は識別子ごとに 1 行（U582）                                                                                                                                                                                                                                                                                            |
| 記録しない会話       | 記録しない会話の間は OS 通知を出さず、送出意図も書かない（件数の知らせは送る）。取り込みはもともと記録しない会話の間に候補を作らない（ADR 0194・U540）。調査の完了など別の入口で作られた候補も同じに止める（U588）                                                                                                                                                                                 |
| 再通知               | 本人の指定した再通知（スヌーズの終わり）の OS 通知はまだ出さない。根拠を取り直す経路が製品に無く、`candidateAlertDecision` が `source_not_confirmed` で止めるため。再通知の ID の作り方も決めていない（U587）                                                                                                                                                                                      |
| 入にしたときの既存分 | 入にした時点で既にある気づきは通知しない。入にした後に作られた候補だけ（U590）                                                                                                                                                                                                                                                                                                                     |
| 忘却・掃除           | 候補の行を消すとき（解決・却下から 97 日の掃除、忘却の削除）に、同じ識別子の配信の記録も消す（`policy` の保持 `candidate_key` のとおり。U591）。配信の記録は識別子と状態だけで、本文を持たない                                                                                                                                                                                                     |
| ログ                 | 件数と理由のコードだけ（題・候補 ID・識別子を出さない）。判定の失敗は候補の保存の失敗にしない                                                                                                                                                                                                                                                                                                      |

| 設定の画面   | 標準の端末画面（従来の窓）の「気づき」の欄の頭の下に、選択「新しい気づきを OS の通知で知らせる」と説明（通知に題・差出人・本文を出さない・ロック中は出さない・すべての端末で同じ設定）を置く。設定の場所は、記憶の種類の設定（記憶の欄の上）・レシートの設定（家計簿の欄）と同じく、その機能の欄に置いた。設定を読めていない間は選択を出さない |
| IPC          | `desktop.candidate_alert_setting`（`{ settings_ref, os_notification }`。ロック解除済みの前面の画面操作。中枢の設定を変えるだけなので入出力の停止中も受け付ける）。従来の窓と状態の層だけ（キャンバス・入力バー・島には渡さない）。応答は `DesktopCandidateView`（`alert` を足した）。画面は preload の IPC だけを使う                          |

## Issue #283 の P2 の OS 通知の項目との対応

- 「通知の ON/OFF（既定 OFF、ADR 0073）の保存先の決定が前提」: 中枢の 1 行の表に決めた（U580）。既定は切のまま。
- 「`candidateAlertDecision`（ADR 0119）」: 新しい候補の判定に配線した。再通知（`user_reminder`）は根拠の経路が無いので未配線（U587）。
- 「トレイの new の件数も同じ」: 同じ設定に連動させ、既定では出さない（U581）。
- 残り: 実機（macOS・Windows）での OS 通知とトレイの確かめ、再通知の OS 通知、音声通知との記録の共有（B05）。

## 原本に決めがない項目（未決事項）

U580〜U594（`docs/b00/contract-map.md`）。いずれも安全側の暫定で、試験で固定した。本人が決めたら変える。U543（予定の重複の初回取り込みの判定）は、この機能より前に同期していた DB の最初の回でも OS 通知が 1 通にまとまる（U584）ことを追記した。

## 残ること

- 実機（macOS・Windows）での OS 通知とトレイ（メニューバー）の件数の表示・押したときの動き・通知の許可がないときの見え方。
- 本人の指定した再通知（スヌーズの終わり）の OS 通知（U587。根拠の経路と再通知の ID と一緒に）。
- 音声通知との配信の記録の共有（B05、ADR 0073）。
- 状態の層（キャンバスのモード）の気づきの画面への設定の配置。
