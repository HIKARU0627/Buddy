## マイグレーション 0006

0001 の CHECK は変えられないので、0005 の前例どおり予約の表を同じ列と新しい列で作り直し、値を移しました。予約を参照する `live_sessions` も新しい表を指す形で作り直し、子の表を先に消してから親の表を消します（どの時点でも外部キーの違反を作らない）。0001 は変えていません。

## DB worker の予算の命令

`DbWorkerClient.budget(op)`（メッセージ `type: 'budget'`）。書込みは 1 つの短い BEGIN IMMEDIATE の transaction で、判定は domain の純粋な規則に任せ、最終の保証は 0006 の制約に置きます。provider への通信は transaction に入れません（H04。呼び出し側が transaction の外で行い、結果を次の命令で渡す）。書込みの応答を失ったら成否不明（unknown）で、クライアントは broken になります（既存の命令と同じ）。

| 命令                                       | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `budget.calendar_advance`・`calendar_read` | transaction の中で保存した状態を読み、`advanceBudgetMonth` で進める。初めての起動と月の替わりだけ 1 行を足す。時計の戻り（`clock_regressed`）・食い違った状態（`invalid_calendar_state`）・範囲の外の時刻（`invalid_time`）は書かずに拒否する                                                                                                                                                                                                                                                                         |
| `budget.admit`                             | transaction の中で、(1) 同じ request_id の予約、(2) 予算月の状態、(3) 同じ月の行と、月を問わず M 超過の確認待ちの行、(4) 超過枠へ回すなら同じ request_id の生きている承認を読み、`admitBudget`・`admitWithOverage` で決めてから挿入する。予算月は保存した状態の今月だけで、要求の月が違えば `budget_month_not_current`、今の月のタイムゾーンで次の月の始まりを越えていれば `calendar_stale`（先に進める）、状態がなければ `calendar_not_initialized`。超過枠で受け付けたら、同じ transaction で承認を consumed にする |
| 同じ request_id の受付                     | 同じ内容（要求した枠・起点・profile・単価の版・通貨・月・計上した枠（通常か超過）・R・M）なら保存済みの予約を返す（`duplicate`）。COMMIT の直後に worker が落ちた後の送り直しで二重に受け付けない（QA28 と同じ型）。違う内容は `request_conflict`。保存済みの予約がもう reserved でなければ `duplicate_request` で受け付けない                                                                                                                                                                                        |
| `budget.top_up`                            | 版の CAS（`UPDATE … WHERE reservation_revision = 期待の版 AND status = 'reserved'`）。判定は `topUpReservation`（追加分だけを検査）。超過の承認で受け付けた予約は、承認が 1 つの M に固定されている（本人の判断）ので追加予約しない（`approval_fixes_max_liability`）                                                                                                                                                                                                                                                 |
| `budget.settle`                            | provider の照合 ID は `provider名:ID` で保存し、provider をまたいで一意にする。`manual` は provider の名前に使えない。同じ照合 ID が別の予約に使われていれば `reconciliation_id_used`（一意制約が最終の保証）。判定は `settleReservation`（同じ値は `duplicate`、違う値は `settlement_conflict`、解放済みは `released`）。クレジットの区分は B07-07 までの初期の規則（クレジット 0・追加の支出＝実費、ADR 0034）                                                                                                      |
| `budget.mark_unknown`・`release_unsent`    | usage 不明は R と M を保持する。二度目は変化なし。解放は `releaseUnsent` で、Core が「送っていない」と渡しても、会話の接続（`live_sessions`）を作った予約は送った可能性があるので解放しない                                                                                                                                                                                                                                                                                                                           |
| `budget.settle_manual`・`review_overrun`   | `settleManually`・`reviewOverrun` で判定する。端末からの要求（`request`）は受付（`command_receipts`）を同じ transaction で書き、同じ要求の再送は保存済みの結果（`replayed`）、照合値・命令 ID・対象が違えば `request_conflict`                                                                                                                                                                                                                                                                                        |
| `budget.request_overage`                   | pending の承認を作る。期限内の同じ承認の再要求（二度押し）は保存済みの承認を返し、値が違えば `approval_conflict`。期限を過ぎた承認は expired にしてから新しい承認を作る。受付済みの request_id には作らない                                                                                                                                                                                                                                                                                                           |
| `budget.approve_overage`                   | 画面で見せた request_id と M が記録と一致するときだけ決める（`approval_mismatch`）。pending → approved・rejected。同じ決定の二度押しは変化なし（承認は 1 件）。使用済み・期限切れには決めない                                                                                                                                                                                                                                                                                                                         |
| `budget.summary`                           | 今月（保存した状態）と、未精算か M 超過の確認待ちが残る前の月の行、pending の承認を 1 つの読み取り transaction で読み、`summarizeUsage` で集計する。今月より後の月の行は `future_month` で拒否する                                                                                                                                                                                                                                                                                                                    |
| 独立の consume の命令                      | 作らない。承認の使用は受付と同じ transaction で行う（別の命令にすると、承認を使わずに超過枠の予約ができる隙間ができるため）                                                                                                                                                                                                                                                                                                                                                                                           |

## tz データの更新と保存した予算月の始まり（U23）

ADR 0035 の状態の検査は、保存した月の始まりを tz データで求め直して一致を確かめます。OS の tz データの更新で過去の月の始まりが変わると、保存した記録と食い違います。原本に決めはありません。

決定: **記録は書き換えず、食い違いは `invalid_calendar_state` として有料の受付と月の進行を止める（閉じた側に倒す）**。

- 記録はどの月にどの予約を数えたかの根拠なので、求め直した値で書き換えない。
- 記録を正本にして受け付け続けると、domain の状態の検査（形だけ正しく食い違った状態を拒否する）を保存の側で迂回することになる。食い違いは稀（政府の急な規則の変更の後追い）で、止まっても予算を超えることはない。予算の最終の保証を省略しない（AGENTS.md）。
- 止まっている間は、状態の「予算保留」として本人に見せる。始まりを確かめ直して記録を足す経路（本人の確認）は B07-04 で作る（時計の戻りを解く経路と同じ場所）。

## domain の修正

B07-02 の Codex のレビュー P3（#112 のコメント）: `advanceBudgetMonth` は保存した状態があるとき、現地の年が 10000 年になる時刻を `invalid_time` にせず、9999 年 12 月のまま受け付けていた。保存した状態がない経路にそろえ、今の月のタイムゾーンで現地の暦年が範囲（1970〜9999）の外なら `invalid_time` にした。範囲は今の月のタイムゾーンで見る（設定を変えても今の月はまだ前のタイムゾーン）。`budget-rules.json` に回帰の 3 件（東京の状態で 10000 年になる時刻・その 1 ミリ秒前・UTC の状態で設定が東京）を手で足した。
