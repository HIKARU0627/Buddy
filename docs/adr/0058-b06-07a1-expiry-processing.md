### 時計の状態ファイル

| ファイルの状態                              | 起動（最初の掃除）の扱い                                                                       | ゲート                               |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------ |
| 読めて形が正しい                            | 最終確認時刻を読み込む。時計がそれより前なら巻き戻り（期限は最終確認時刻で判定し、延ばさない） | 掃除が済み、巻き戻っていなければ開く |
| 無い・DB を新しく作った起動（初めての起動） | 今を最終確認時刻にしてファイルを新しく作る                                                     | 開く                                 |
| 無い・既存の DB                             | 作らない。判定できないものとして扱う                                                           | `clock_state_missing` で閉じる       |
| 読めない・形が違う                          | 書き換えない（壊れた状態を黙って作り直さない）                                                 | `clock_state_invalid` で閉じる       |

判定できない間も掃除そのものは動く。個人の内容（発言・元情報・記憶・派生物）は消し続け、予算の記録と 0010 より前の行の埋め直しは止める（U54 と同じ側。U140）。ファイルが無い・読めないのを直すのは採り直しだけで、掃除の job は作らない。

### 消せなかった理由の分け方（U137。本人が 2026-10-31 に決定）

| 分類                            | 理由                                                                                                                                                                                                                                                                     | 扱い                                                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| expected_hold（失敗に数えない） | `not_due`・`compensation_open`・`month_has_open_rows`・`calendar_invalid`・`task_content_not_migrated`・`unknown_held`・`operation_not_finished`・`completed_at_missing`・`operation_not_found`・`row_not_found`・`memory_not_found`・`not_active`・`not_review_pending` | 計画の側でも保留にしている理由、または行がもうない。何もしない                                                                                                      |
| transient（失敗に数える）       | `database_busy`・`database_full`・`worker_halted`・`worker_closed`・`worker_unavailable`・`worker_timeout`・`durability_mismatch`・`commit_failed`・`transaction_failed`、成否不明（`unknown`）、投げられた例外、**表にない理由**                                        | 記録を `failed` にしてゲートを閉じ、次の周期にもう一度試す。原因が分からないものでゲートを開けない                                                                  |
| permanent（隔離）               | `constraint_violation`・`row_unreadable`                                                                                                                                                                                                                                 | その行だけを `use_blocked`（`undeletable`）に入れる。ゲートは開く。隔離は状態を持たず、毎回の失敗から作る（原因が解ければ次の掃除で外れる）。後ろの行の削除は続ける |

分類は理由の集合で決める: transient が 1 つでもあれば transient、すべて expected_hold なら expected_hold、それ以外（permanent を含む）は permanent。隔離が 1000 件を超えたら、個々の行ではなく仕組みの異常として失敗に数えてゲートを閉じる。予算の月は 1 つの transaction で消すので、恒久の原因ならその月の行だけを隔離する。

### AO レビューの指摘への対応（P1・P2 ×2）

| 指摘                                                | 対応                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P1 操作の本文由来の期限を 90 日にしている           | 操作の確定内容（`operation_content`）を由来にする派生物の期限は、完了から 7 日（`operation_body`）。本文がもう消えていれば期限切れ、完了していない操作は期限なし。90 日は本文のないレシートの期限で由来には使わない。7 日ちょうどで派生物が消えること、本文が先に消えていれば即座に消えること、未完了には期限がないことを試験で固定                                            |
| P2 派生物を由来にたどるときも保存済み期限を反映する | 由来として返す派生物の期限にも、その派生物自身の保存した期限（影モードの `expires_at`・依頼の `delete_at` など）との小さい方を適用。発言（7 日）→ 影モード（1 日）→ 気づきで、1 日ちょうどに二段とも同じ掃除で消える（どちらの順でも）試験を足した                                                                                                                             |
| P2 記憶の削除命令を domain の補正済み期限に合わせる | `memory.delete_due`／`memory.continue` の期限を、保存した削除日と見直し日＋30 日の小さい方に補正（domain の `sweepPlan` と同じ）。30 日を超えて延ばされた保存値は 30 日ちょうどで消える。削除日が NULL の見直し待ちは 0001 の CHECK（有効な記憶だけが NULL）で作れないので、実 SQLite では CHECK が拒否することを試験で示した（命令の側は NULL なら見直し日＋30 日として扱う） |
