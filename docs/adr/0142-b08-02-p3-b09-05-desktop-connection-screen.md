# ADR 0142: B08-02 P3・B09-05 デスクトップの接続画面（連携アカウント: 取得範囲の選択と表示）

- 日付: 2026-11-23
- 状態: B08-02 P3（親 #16 [B08]）＋ B09-05（親 #17 [B09]）。同じ画面を共有するため 1 つの実装にした（ADR 0133 の「B08-02 P3 の画面は B09-05 と共有のため後回し」の回収）。デスクトップの契約・main の経路・画面と模擬試験まで。接続の作成・OAuth・トークン保存は B03-04 で、本 ADR では扱わない。実アカウント・実 API は未実施。
- 根拠: 設計 01（接続・端末: 主に見せるもの＝選択アカウント／カレンダー、取得範囲、権限、端末、最終接続。主な操作＝対象選択、接続解除、追加権限、端末登録・失効、明示再開）、設計 04（接続・権限: Outlook は接続時にアカウント種別を特定し、拒否の理由と利用できる範囲を表示する。取得する対象: 本人が接続時に選んだフォルダー／ラベル、カレンダー。新しいカレンダー・フォルダーは自動で追加しない。初期値は受信トレイ＋過去 90 日）、設計 06（B08＝対象選択と参照、B09＝アカウント種別・委任権限・カテゴリ一覧・選択フォルダー・取得範囲と組織拒否の状態表示）、ADR 0072（B09-01: GraphAccountState と画面の語彙、拒否された接続は active にしない）、ADR 0086（B08-02 P1: 取得範囲の規則と「中枢の画面での選択と表示」）、ADR 0087（ConnectionTargets に期間・サイズの 4 項目。設計の初期値が上限）、ADR 0088・0089（保存と中枢の経路）、ADR 0132（B11-05: デスクトップの候補画面の作法＝参照だけを画面へ渡す・結果不明は送り直さない・409 は読み直して preview_stale）、ADR 0134・0138・0140（Graph 側の接続の形）、contract-map の「接続と取得範囲の選択」の行と X37。
- 対象: `packages/contracts/schemas/buddy.schema.json`（DesktopIpcChannel に 2 チャネル、DesktopIpcRequest／DesktopIpcResponse の分岐、DesktopConnectionEntry・DesktopProviderConnectionsView の新設。生成型は `packages/contracts/src/generated.ts` へ再生成）、`packages/contracts/fixtures/schema-cases.json`（+10 件）・`desktop-ipc-cases.json`（受付 +8 件）、`packages/domain/src/desktop.ts`（チャネル・受付・役割表）、`apps/desktop/src/main/connections-bridge.ts`・`connections-bridge.test.ts`・`connections-link.test.ts`（新設）、`apps/desktop/src/main/core-link.ts`（CONNECTIONS_CHANNELS・handleConnectionsIpc・世代のリセット）、`apps/desktop/src/main/electron/main.ts`（振り分け）、`apps/desktop/src/preload/preload.cts`（チャネル表）、`apps/desktop/src/renderer/state/connections-state.ts`・`connections-state.test.ts`・`use-connections-state.ts`（新設）、`apps/desktop/src/renderer/screens/hub/ConnectionsPanel.tsx`・`ConnectionsPanel.test.tsx`（新設）、`apps/desktop/src/renderer/screens/hub/HubPanels.tsx`（「連携アカウント」タブ）・`HubPanels.test.tsx`、`apps/desktop/src/renderer/App.tsx`、期待値の追随（`apps/desktop/src/main/preload.test.ts`・`window-roles.test.ts`、`scripts/desktop-ipc.test.mjs`・`scripts/canvas.test.mjs`）、`docs/b00/contract-map.md`（デスクトップの行を追加）。中枢（Core）・保存層・connector は変更なし（経路は ADR 0089 で完成していた）。新しい Core モジュールは無いので retention-entries への登録は不要。`tests/test-map.json` は変えていない（X37 は specified のまま。設計 09 の対応付けを推測で足さない。ADR 0132 と同じ）。

## 在庫確認（済んでいたもの）

- 規則・保存・中枢の経路は完成していた。domain の FetchScope（validateFetchScope・FETCH_SCOPE_LIMITS＝メール 90 日／カレンダー過去 30 日・未来 90 日／添付 10,000,000 バイト、種類は pdf・text）と保存層の connection-targets-store、Core の GET /v1/connections・GET／PUT /v1/connections/{id}/targets（許可版の CAS、409／422／503）・GET …/sync（ADR 0086〜0089・0136）。
- デスクトップには提供元の接続の画面が無かった。レンダラーの画面は budget／candidates／canvas／device／hub／pairing／work で、中枢の画面（HubTabs）のタブは端末の登録・登録済みの端末・自宅のネットワーク・このマシンの接続だけ。device の ConnectionSection は中枢との接続の欄で、提供元の接続とは別。
- 本当の残件は、デスクトップの契約（IPC）・main の経路・画面の 3 層だけだった。

## 設計の根拠が無い・不足する部分（推測で作らなかった）

- **対象の発見と表示名**: 見つけたカレンダー・フォルダー／ラベルの一覧（未選択を含む）を中枢から画面へ渡す経路は契約・保存・Core のどこにも無い。Google 側の connector にカレンダー・ラベルの列挙は無く、Graph 側には listMailFolders／listCategories／readAccount があるが Core の経路が画面へ出していない。ConnectionSummary の targets は ID だけで、表示名は契約に無い。このため画面は「今保存されている対象のうちの選択（外す・戻す）と、期間・添付の範囲の変更」までで閉じ、新しい対象の追加は接続時（B03-04）とし、対象は ID のまま表示する（推測で名前を作らない）。発見の経路（connector の列挙＋Core の経路＋契約）は残件。
- **同期の状態の表示**: GET /v1/connections/{id}/sync（ADR 0136）は中枢にあるが、デスクトップの契約に載せる設計の根拠（01 接続・端末の「最終接続」は端末の項目）が薄いため、今回は載せなかった。残件。
- **接続解除・追加権限**: 設計 01 の接続・端末の操作に含まれるが、接続のライフサイクルと OAuth は B03-04 の担当（ADR 0089 の disconnectConnection は中枢の経路のみ）。この画面の操作は対象選択だけにした。

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 画面の置き場所       | 中枢の画面（HubTabs）に「連携アカウント」タブを足す（設計 01 の接続・端末。ADR 0086・0089 の「中枢の画面での選択と表示」）。タブの中身は任意の ReactNode（home と同じ作法）で、渡さなければタブを出さない。App は mode が live の間だけ内容を持ち（useConnectionsState の shown）、接続を待つ間は欄だけ出して操作を止める                                                                                                                                                                                                                                         |
| IPC の契約           | 2 チャネルを足す: `desktop.connections_list`（ロック解除済みの一覧。前面は求めない）と `desktop.connection_targets_update`（ロック解除済みの画面操作）。応答は表示用の値 `DesktopProviderConnectionsView`（fetch・entries・list_seq）1 つにまとめる（候補の DesktopCandidateView と同じ作法。既存の DesktopConnectionView は中枢との接続の表示で別物なので名前を分けた）。行は `DesktopConnectionEntry`（ref・provider・status・access・granted_scopes・targets・graph_account・delivery_unknown）。接続 ID・permission_revision・scope_revision は契約に出さない |
| 受付と役割           | domain の受付表: 一覧は DESKTOP_UNLOCKED_CHANNELS、変更は DESKTOP_PAIRING_SCREEN_CHANNELS（画面操作）。変更は保存そのものが送信ではなく、実際の取得は中枢の走査の調停（scheduler・保持のゲート）を通るため、入出力の停止中も受け付ける（candidate_state・中枢の管理操作と同じ）。窓の役割は候補と同じく従来の窓と状態の層だけ（キャンバス・入力バーには渡さない）。中枢の画面かどうかは main が handleAdminIpc と同じ探り（claims の経路）で確かめ、中枢の画面でなければ hub_screen_required で断る                                                               |
| OS の確認            | 取得範囲の変更に OS の確認ダイアログは挟まない。値は画面に見えていて、本人の明示の「保存する」で送られ、上限を超えて広げることはできず、今の保存値に無い対象も足せない（広げられるのは接続時の選択だけ）。承認・失効のような他端末への操作とは性質が違うため、候補の状態変更（ADR 0132）と同じ扱いにした                                                                                                                                                                                                                                                          |
| main の経路          | ConnectionsBridge（candidate-bridge と同じ作法）: 一覧は GET /v1/connections を読み、読めなければ前の値のまま fetch を stale（読めたことがなければ unavailable）にする。変更は一覧で読んだ permission_revision を expected_permission_revision にして PUT し、保存できたら読み直す。409 は読み直して preview_stale、結果不明（unknown・5xx・形の違う 2xx）はその接続を保留（delivery_unknown）にして自動では送り直さない。参照・版は main の中だけ。世代（ロック・切断）で reset する                                                                             |
| 画面からの追加の拒否 | main は、送られた targets に今の保存値に無い calendar_id・mail_container_id が含まれていたら、中枢へ送らず invalid_request で拒否する（発見の経路が無い以上、画面から新しい対象を足す経路を作らない）。期間・添付の範囲は domain の validateFetchScope で送る前に確かめる（正本は中枢と保存層の検査）                                                                                                                                                                                                                                                             |
| 画面の編集           | 下書きは保存値から作り、保存値が変わったら作り直す（カードの key に保存値を含める）。対象はチェックで外す・戻すだけ（候補の一覧は出さない）。数値は文字列で持ち、送る形にできない（範囲外・読めない）下書きは保存させない。変更が無ければ保存ボタンは押せない。Microsoft の接続は graph_account をそのまま出す: アカウント種別（個人／職場・学校）、委任（本人の委任された権限）、拒否の理由は ADR 0072 の 5 語彙を文言に直し（理由のコードは出さない）、カテゴリは「案の表示だけ」                                                                               |
| 文言                 | 理由のコード・API の名前・内部の ID は画面に出さない（候補と同じ）。取得できていないことを「連携しているアカウントはまだありません」と言わない。対象が ID のままであることと、選べる対象は接続時に決まることを欄に書く                                                                                                                                                                                                                                                                                                                                            |

## 残ること

- 対象の発見（未選択のカレンダー・フォルダー／ラベルの一覧と表示名）: connector の列挙（Google は新規、Graph は既存の listMailFolders・listCategories・readAccount の中枢への露出）と Core の経路・契約が要る。揃えば、この画面から対象を足せるようになる。カテゴリの一覧の表示（B09-05 の設計 06 の項目）もこの経路待ち（現状は category_updates の「案の表示だけ」の表示のみ）。
- 同期の状態（最終取得・走査の状態）の表示: 中枢の GET …/sync はある。デスクトップの契約に載せるかは表示の設計と合わせて判断する。
- 接続の作成・OAuth・トークン保存・接続解除・追加権限は B03-04。それまでは接続が 1 件も無い環境ではこの画面は空の一覧になる（接続を作る製品の経路が無いため）。
- 実アカウントでの確認（Google・Microsoft の実接続での表示と保存）は B15 と本人の承認。
