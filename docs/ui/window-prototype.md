# UI-02 窓の基盤の試作の記録（キャンバス・状態の層・入力バー）

[ADR 0032](../adr/0032-ui-canvas-stream-and-window-roles.md) の 3 つの窓（キャンバス・状態の層・入力バー）を、開発用のフラグで作る試作（Issue #94、親 #92）の記録です。**製品の試験の合格ではありません。** 既定のデスクトップは今の 1 つの窓（従来の窓）のままです。

記録は次の 3 つに分けます。

- **模擬**: Electron を起動しない試験（`pnpm test`）。
- **実機**: この Mac で開発用の手順で起動して確かめたこと。OS への入力は Orca のコンピューター操作（CGEvent の合成の入力・アクセシビリティ）で送り、届いたかは自分で起動した Electron のページに付けたイベントの記録（Chrome DevTools Protocol）で確かめた。**物理のキーボード・マウスでの操作ではない。**
- **未実施**: 確かめていないこと。理由を書く。

### 役割の区別の仕方（決めたこと）

- 役割の正本は **main の対応表**（窓を作ったときの webContents の ID → 役割）。受付は送信元の webContents の ID でこの表を引き、表にない・閉じた窓は役割が分からないので拒否する。
- preload へは窓を作るときの引数 `--buddy-window-role=<役割>` で渡す。preload と画面はこれを画面の切り替えと多重の防御にだけ使う。画面・preload の申告で受付を広げない（画面が別の役割の URL へ移っても、main は送信元の窓の役割で判断する）。
- 3 つの窓と従来の窓は、同じ sandbox・contextIsolation・preload・CSP（特権スキームの応答の見出しと画面の meta）を使う。違いは役割の引数だけ（試験で確かめる）。
- 役割に合わない要求の拒否の理由は `untrusted_sender`（ADR 0032 の 0014 の改め: 拒否の理由は増やさない）。

## 実機（macOS 27.0.1、内蔵の 1 画面 1280 × 832 pt、Electron 44.9.0、2026-10-22）

起動: `apps/desktop` で `pnpm run build` の後、`electron . --buddy-ui=canvas --use-mock-keychain --user-data-dir=<一時ディレクトリ> --remote-debugging-port=<空きのポート>`。中枢には接続していない（未登録）。ほかに動いているデスクトップアプリ・Core には触れていない。窓の段・位置・共有の状態は CoreGraphics の `CGWindowListCopyWindowInfo` で読んだ。

| 確かめたこと                       | 結果                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 3 つの窓ができる                   | できた。キャンバスは段 −2147483624（デスクトップの段の 1 つ下。WindowManager の壁紙と同じ段）・0,0 から 1280 × 832。状態の層は段 3（floating）・(1224, 367) 56 × 128。入力バーは段 3・(360, 760) 560 × 56                                                                                                                                                                                                                                              |

## ADR への影響（ADR 0032 に追記した）

- **キャンバスが Finder のデスクトップの窓・ウィジェットより下にある**。macOS では、デスクトップのアイコン・ウィジェットがキャンバスの上に描かれ、キャンバスの位置のクリックは Finder が受けると見込む（未確認）。ADR 0032 の前提「AI の部品をキャンバスに置き、ユーザーも動かす・閉じる」を macOS で満たすには、キャンバスをデスクトップの段より上に置く（通常の窓の段の一番下に置き、ほかのアプリの前に出さない）か、操作するときだけ段を上げるかを決める必要がある。**判断が要る**（UI-06 の前に決める）。
- 「デスクトップの層の窓はキー入力を受けにくい」という見込みは、Electron の文書と段の観察から、**マウスも受けない見込み**に広げる必要がある（未確認）。入力はパネル型の入力バーで受けられることは確かめた（IME を含む）。
- 状態の層がキャンバスから覆えないこと、画面共有（ScreenCaptureKit）から守る設定が効くことは確かめた。
