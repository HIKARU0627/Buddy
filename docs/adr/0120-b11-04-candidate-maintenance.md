# ADR 0120: B11-04 気づき（候補）の保守（P3 の一部）

- 日付: 2026-11-14
- 状態: B11-04（親 #23、Issue #271）の P3 のうち、時間による遷移・根拠の再確認の結果の反映・保持の掃除を 1 回回す処理。取得（根拠を許可範囲から取り直す connector）・定期の呼び出しの配線・API の経路（P2）は未着手。実メール・実 API・実機は未実施。
- 根拠: 設計 11 §4・§5B、設計 03 保存と忘却、ADR 0073・0116（時間による遷移・根拠の失効・保持の段階）・0118（保存と `candidate.sweep`）・0119。原本の参照手順は `docs/design/README.md`。
- 対象: `apps/core/src/candidate-maintenance.ts`、`candidate-maintenance.test.ts`。契約・マイグレーションは変えない。

## 決めたこと

| 対象         | 決定                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 入口         | `runCandidateMaintenance(ports)` が 1 回の保守を行い、`MaintenanceReport`（遷移した候補の ID・資格を失効した候補・忘却の要求・掃除した ID・書かなかったものと理由）を返す。時計は注入し、時計の巻き戻りの保留（`checkClock`）は呼び出し側が先に行った時刻を渡す                                                                                                                               |
| 順序         | (1) 活動中（new・seen・acted・snoozed）の候補を一覧して、domain の `candidateDueEvent` が返す遷移（`deadline_passed`・`snooze_elapsed`）を DB worker へ渡す。書く前に DB worker が行を読み直して同じ判断になるかを確かめる。(2) 遷移しなかった候補だけ、注入された `checkEvidence` で根拠を取り直し、`evidenceDecision` で遷移へ変える。(3) `candidate.sweep` で閉じた候補の保持を掃除する    |
| 根拠の再確認 | 取得範囲外・削除は `source_out_of_scope` で resolved、予定の重複の解消は `overlap_resolved` で resolved。新しい版・取り直せないときは状態を変えず、資格を失効した候補として返す（U275）。取り直しの失敗（例外）は解決せず「未確認」として扱う。忘却の観測は物理削除の要求として返すだけで、削除は忘却の計画が行う。`checkEvidence` が無ければ再確認を行わない                                 |
| 書かないもの | 別の経路が先に遷移させた（`state_mismatch`）・時計の再確認で「まだ」だった（`event_not_due`）・読めない時計やタイムゾーンは、書かずに理由を返す。1 件の拒否で残りを止めない。一覧が失敗しても掃除は行う。一覧は keyset の続き（`next_after`）で全頁を読み、先頭の候補が活動中に残っていても上限の外の候補に届く。頁数の上限（既定 100）で読み切れなかったときだけ `truncated`（残りは次の回） |
| 閉じた候補   | 閉じた候補は一覧の対象外で、根拠を取り直さない（掃除だけが触る）。期限切れで先に遷移した候補も、その回では根拠を取り直さない                                                                                                                                                                                                                                                                  |

## 試験（模擬だけ）

`apps/core/src/candidate-maintenance.test.ts`（6 件）: 基準を 2030-10-09T03:00:00Z（日本時間 12:00）に固定し、期待値は手で書いた。期限切れ・スヌーズの終わり（1 秒前後）・今日の日付の期限が日本時間の 0 時（15:00:00Z）で過ぎること、初回取り込みの過去の期限と未来の期限は動かないこと、同じ時刻の再実行で何も変わらないこと、根拠の再確認の全種類（取得範囲外・削除・有効・新しい版・取り直せない・忘却・例外・重複の解消）と、遷移・閉じた候補で再確認しないこと、掃除（7 日・97 日・1 日前を残す）、頁の大きさ 1 でも古い期限切れ・スヌーズの候補に届くこと、一覧の失敗・別の経路が先に動かした遷移・読めない時計とタイムゾーン。実際の DB の保存の命令と結んだ。

**模擬の期待値だけ**。根拠を許可範囲から取り直す実際の connector・定期の呼び出し・実機は未実施で、合格扱いにしない。

## 残ること

- `checkEvidence` の実装（B08・B09 の connector から許可範囲で取り直す）と、`runCandidateMaintenance` を掃除の job と起動時へ配線すること。
- 一覧・根拠の再取得・状態の変更の API の経路（P2。契約の変更を伴うので直列）。
- 忘却の物理削除との接続の試験（`forget-store` が保守の後の空の封筒の候補も消せること。B11-03 の試験で確認済みの範囲を超える結合）。
