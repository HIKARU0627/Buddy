## 本人の決定（2026-11-03）

| 項目                       | 決定                                                                                                                                                                 | 記録 |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 保存モードの切り替えの経路 | 流れの経路に `POST /v1/stream/storage-mode` を足し、切り替えで区切りを開き直す。記録しない会話の出入りもここへ寄せる（UI-01 の方針どおり、画面は会話 ID を持たない） | U170 |

## 決めたこと

| 対象                    | 決定                                                                                                                                                                                                                                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 発言の由来              | `TurnRequest` に `origin`（`segment_id`・`segment_generation`）を必須で足す。`segment_id` は会話の ID、`segment_generation` は `POST /v1/sessions` の応答の `segment_generation`。端末が見ていた区切りを表す（ADR 0045 の P2-1）。                                                                                   |
| 会話の作成の応答        | `SessionReceipt` に `segment_generation` を必須で足す。端末はこの値を作成の直後の発言の `origin` に入れる。                                                                                                                                                                                                          |
| 由来の照合              | `postTurn` は、`origin.segment_id` が経路の `session_id` と一致し、`origin.segment_generation` が保存境界の保持者の今の世代（`StorageModeGate.origin().segment_generation`）と一致するときだけ発言を処理する。形が違う由来は Schema で 422、古い世代・別の会話の由来は 409 `conflict`。**発言は 1 件も保存しない**。 |
| 世代の意味              | 世代は保存境界の保持者が持つ番号で、記録しない区切りに入る・出るたびに進み、Core の再起動をまたいでも戻らない（ADR 0059）。再起動の後は端末が新しい世代を受け取り直すまで発言は 409 になる（古い区切りの発言を新しい区切りに混ぜない）。                                                                             |
| 流れの経路              | `POST /v1/stream/turns` は、内部で呼ぶ `postTurn` に、流れの会話の ID と今の世代を `origin` として渡す。端末は `StreamTurnRequest` に由来を足さない（UI-01。流れの区切りは Core が選ぶ）。                                                                                                                           |
| 入口の整理（2b で実装） | `POST /v1/stream/storage-mode` を保存モードの唯一の入口・出口にし、`private` の出入りもここへ寄せる。`POST /v1/sessions` は `normal`／`extended` の会話の作成だけに残し、`private` は受け付けない（503）。記録しない会話の `session_id` を返す経路は作らない。**2b で実装済み**（下の「2b の実装」）。               |
| マイグレーション        | 足さない。由来の世代は保存境界の保持者のファイル（`clock-state.json` の `storage_boundary`）と会話の作成の応答だけで扱い、DB の列を増やさない。                                                                                                                                                                      |

## 2b の実装（2026-11-03）

| 対象             | 実装                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約             | `StorageModeChangeRequest`（`request_id`・`command_scope_id`・`storage_mode`）と `StorageModeChangeResponse`（`request_id`・`segment`）を足した。端末は会話・区切りの ID を送らない（余分な欄は Schema で 422）。経路の検査は流れへの発言と同じ（`command_scope`・`unlocked`）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 経路             | `POST /v1/stream/storage-mode`（`postStreamStorageMode`）。`normal` ⇔ `extended` ⇔ `private` の切り替えを 1 つの経路にまとめ、`private` の出入りもここへ寄せた。`POST /v1/sessions` は `normal`／`extended` だけを作り、`private` は 503 のまま（理由を「入口は流れの経路」に変えた）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 失敗の応答       | `private` の出入りで世代を書けない（`persist_unavailable`・`persist_failed`）・停止中（`closed`）は 503 `dependency_unavailable` で、状態も区切りも動かさない。`private` の遷移の規則の拒否（すでに private・private でない・判別できないモードなど）は 409 `conflict`。`private` から出る途中で `exitPrivate` は確定したが会話の作成に失敗したときは、出口を戻さず、使えない区切りを捨てて 503 を返す（次の要求でゲートの今の状態から作り直す）。作り直せるまでの新しい発言は 503 で保存しない（黙って `normal` の会話を作って、端末が `private` の表示のまま発言を DB へ残さない）。次の保存モードの切り替えが成功した時点で解く。`normal` ⇔ `extended` は保存境界の保持者を書かないので、会話の作成の失敗だけが応答になる。同じモードへの切り替えは、経路では何も動かさずに今の区切りを 200 で返す（保存境界の遷移そのものは同じモードを拒否する）。                                                  |
| 区切りの開き直し | 成功したら `StreamSegment` を新しい保存モードで差し替える。`private` へ入るときは `private_started`、出るときは `private_ended`、`normal` ⇔ `extended` は `storage_mode_changed`。`private` の出入りでは要約をつながない。`normal` ⇔ `extended` は `nextCarriedSummary` の規則の範囲でだけつなぐ。区切りの発言の期限は UI-05 の `recordTurn`（api-turns の `onTurnRecorded` が渡す保存時点の `turns.expires_at`）で足し、この時点の時計から作り直さない（保存から応答までの待ちでも、並行した応答が逆順でも延ばさない）。要約を確定する前に、旧区切りで保存中の発言が終わるのを待つ。`private` は `enterPrivate`・`exitPrivate` が世代を進めて区切りを開き、`normal` ⇔ `extended` は出る先の保存モードで会話を作り直す（会話の保存モードは DB の `sessions.storage_mode`。保存境界の保持者は書き換えない）。                                                                                             |
| 会話の作り方     | `private` へ入るときは会話を作らない（区切りの ID は保存境界の保持者が作る）。`private` から出るときは、記録しない区切りの間は会話を作れないので、先に `exitPrivate` で出てから出る先の保存モードで会話を作る。`normal` ⇔ `extended` のときは、出る先の保存モードで会話を作る（区切りと会話は 1 対 1）。会話の作りの `request_id` は要求ごとに新しく振る（端末の `request_id` を渡すと、DB の受付レシートが 7 日残るので、再起動をまたいだ再送で前の会話が返り、由来の控えが無いままその会話を区切りにして以後の発言がすべて 409 になる。切り替えの重複は Core の控えで防ぐ）。会話の作成に失敗したときは、記録しない会話は作らず、今の区切りを残す。`private` から出た後に会話の作成が失敗したときは、使えない private の区切りを捨て、作り直せるまでの新しい発言を 503 にする（黙って `normal` の会話を作って、端末が `private` の表示のまま発言を DB へ残さない。次の切り替えが成功した時点で解く）。 |
| 記録しない発言   | 記録しない区切りが開いている間、`postTurn` は DB の `sessions` を引かずに 503 で断る（RAM の保持は 2c）。`POST /v1/sessions` は `private` の会話を作らないので、`private` の `session_id` を返す経路はない。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 再送             | 同じ `request_id` と同じ内容の切り替えは同じ応答を返し、内容が違えば 409。切り替えを二度行わず、世代を二度進めない（Core の RAM。再起動で失われる）。控えは流れの発言の受付（UI-05 の `accepted`）と同じ仕組みにそろえ、端末・接続範囲（`command_scope_id`）・`request_id` の組で識別して受付レシートの有効期間（7 日）だけ保つ（件数では捨てない）。流れへの発言は、最初に受け付けた区切りの会話と**そのときの世代**を控え、保存モードを切り替えた後の再送でもその由来をそのまま渡す（今の世代を渡すと `request_hash` が変わり、`private` の出入りの後に 409 になる）。応答の `segment` は今の区切り（表示用）。                                                                                                                                                                                                                                                                                        |
| 保存境界の遷移   | domain の遷移は足さない。`private` の出入りは `enterPrivate`・`exitPrivate` が世代を進めて時計の状態ファイルに書く。`normal` ⇔ `extended` は会話ごとの保存モード（DB の `sessions.storage_mode`）で表し、保存境界の保持者を書き換えない（2a の会話ごとの由来。2c の保存先の判定は会話のモードを使う）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 排他             | 保存モードの切り替えと UI-05 の自動の区切りは 1 本の鎖で直列にする（同時の切り替えで保存境界の状態と今の区切りが食い違わない）。記録しない区切りでは自動の区切りを起こさない（会話を作れず、すべての要求が 503 になる）。作り直し待ちの 503 は、自動の区切りの判定より前に返す（区切りのループで古い区切りに保存しない）。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

## この段階に含めないもの

- 保存先の書き込みを許可表（22 行）へ結び付けること、遅れて届いた結果へ由来を渡して保存の直前に照合すること、記録しない区切りの RAM の保持（2c）。
- 独立した確認（最小の操作記録。2d）。
- UI-05 の画面（状態の層のパネルの切り替えの形）。
- 実機の Mac mini・実際の Live・実 API・実請求（B15・UI-05）。

## 試験（模擬だけ）

- `SessionReceipt` の `segment_generation` が返り、契約の Schema を通る。
- 正しい由来の発言は 200。形の違う由来（欠落・余分な欄）は 422。古い世代・別の会話の由来は 409 で、発言・依頼・操作が 1 件も増えない。
- 流れの経路が内部の `postTurn` に流れの会話の ID と今の世代を渡す。
- 2b: 流れの経路から `private` へ入ると区切りが `private_started` になり、`clock-state.json` の `storage_boundary` が `private_open: true` になる。会話は作らない。
- 2b: `private` の間の発言は 503 で、DB の `sessions` を引かない。`private` から出ると `private_ended` になり、要約はつながらない。
- 2b: `normal` → `extended` で会話の保存モードが `extended` になり、区切りが `storage_mode_changed` になって期限内の由来だけの要約をつなぐ。保存境界の欄は書かない。同じモードへの切り替えは区切りも世代も動かさない。
- 2b: `private` の世代を書けないときは 503、規則の拒否は 409 で、次の発言は切り替えの前の区切りと世代のまま。
- 2b: `private` から出る途中で会話の作成だけが失敗したときは 503 の後に、同じモードの要求で入り直せる（使えない区切りを残さない）。その間の新しい発言は 503 で、会話も作らず発言も保存しない。切り替えが成功すれば発言は通る。
- 2b: 要約の期限は保存の時点で確定した `turns.expires_at` を使い、応答を待つ間に時計が進んでも延びない。並行する 2 件の応答が逆順でも、早い期限が残る。
- 2b: `normal` → `extended` を挟んで同じ `request_id`・接続範囲・本文を再送すると、元の `turn_id` を返す（由来は最初に受け付けた会話と世代のまま）。内容が違えば 409。
- 2b: `normal` → `private` → `normal` を挟んだ同じ要求の再送も、保存済みの元の `turn_id` を返す（今の世代を渡すと 409 になるところを、最初の由来で通す）。内容が違えば 409。
- 2b: 同じ接続範囲で 256 件を超えた後も、保存モードの切り替えと発言の再送は元の結果を返す（件数で控えを捨てない）。
- 2b: `private` の区切りでは自動の区切りを起こさず、発言も 503 のまま。切り替えは自動の区切りと同じ排他で直列になる。
- 2b: 同じ `request_id` でも接続範囲が違えば別の要求（前の範囲の控えを再送と取り違えない）。
- 2b: 切り替えの応答を受け取る前に Core が再起動し、同じ `request_id` で切り替えを再送しても、出る先の会話を新しく作る（受付レシートの前の会話を区切りにしない）。その後の発言は 200 で保存される。
- 2b: `POST /v1/sessions` の `private` は 503。保存モードの切り替えの要求に会話の ID を足すと 422。
- 既存の会話・流れ・Live の試験が通る（由来を足しても既存の経路が壊れない）。
- 期待値は手で書く。実装の関数から期待値を作らない。

## 引き継ぎ

- 2c: `StorageModeGate` の命令（`write`・`hold_in_ram`・`discard_private_ram`・`begin/end_private_canvas`・`open_segment`）を Core の保存先へ結び付ける。記録しない区切りの発言を RAM で受け取り、出たときに捨てる。結果の由来は処理の開始時に控え、保存の直前に `originRejection` で照合する。`postTurn` の 503 を RAM の経路へ置き換える。
- 2d: 独立した確認の Core の経路と最小の操作記録（`record_minimal_operation`）。
