# ADR 0130: B11-04 気づき（候補）の一覧・根拠の再取得・状態の変更の経路（P2）

- 日付: 2026-11-21
- 状態: B11-04（親 #23、Issue #271）の P2。3 つの API の経路と、その処理（`apps/core/src/api-candidates.ts`）を足した。根拠を許可範囲から取り直す実 connector、本人のタイムゾーンの出所、画面（B11-05）は未着手で、製品の配線では 3 経路とも 503 で閉じる。実メール・実 API・実機は未実施。
- 根拠: 設計 11 §4・§5B、設計 07 §2、ADR 0073（候補の契約）・0115（表示順）・0116（遷移・根拠の失効）・0118（保存）・0119（生成）・0120（保守）。原本の参照手順は `docs/design/README.md`。
- 対象: `packages/contracts`（`CandidateEvidenceRequest`・`CandidateStateCommand`・3 パス・fixture）、`packages/domain/src/api.ts`（`ROUTE_CHECKS`）、`packages/storage`（`readDerivationsByArtifact`、`candidate.get` の `origins`）、`apps/core`（`api-candidates.ts`・`api-routes.ts`・`core.ts`）。マイグレーションは変えない。B08-06（同期の公開 transaction での解析計画の無効化・走査の公開）は main に無く、今回は触れない。

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 経路と検査           | `GET /v1/candidates`（`listCandidates`）は `device_token`・`home_network`・`unlocked`（題と期限の原文を含む読み取り）。`POST /v1/candidates/{candidate_id}/evidence`（`getCandidateEvidence`）は `COMMAND`（許可範囲から取り直すので接続範囲を求める。外部変更を起こさないので画面操作は求めない）。`POST /v1/candidates/{candidate_id}/state`（`changeCandidateState`）は `SCREEN`（本人の画面操作だけ）。正本は domain の `ROUTE_CHECKS`                                                                                  |
| 接続範囲は本文で示す | 経路の検査の `command_scope` は本文の `command_scope_id` を読む（api-server の `buildContext`）。本文の無い GET では常に 410 になるので、根拠の再取得は `postCanvasContent` と同じく POST にし、本文 `CandidateEvidenceRequest`（`request_id`・`command_scope_id`）を新設した。状態変更の本文 `CandidateStateCommand` にも `command_scope_id` を必須で入れた（他の命令の本文と同じ）。B11-04 の作業指示の GET・`command_scope_id` 無しの形からの変更                                                                        |
| 状態変更の本文       | `CandidateStateCommand` は `request_id`・`command_scope_id`・`event`（open・act・dismiss・snooze・resolve の 5 つだけ。時計・観測の遷移は受け付けない）・`expected_state`（6 状態）・`snooze_until`（`UtcTime` か null）。すべて必須で `additionalProperties: false`                                                                                                                                                                                                                                                        |
| 一覧の絞り込み       | new・seen・acted だけを一覧に出し、snoozed・dismissed・resolved は件数（`counts`）だけ。U270 の提案 (a) を暫定で採用した                                                                                                                                                                                                                                                                                                                                                                                                    |
| 一覧の並び           | domain の `orderCandidates` の見出しの順に平らにする。見出しそのものは応答に入れない（`CandidateListResponse` は配列だけ）。`orderCandidates` が拒否したら 503                                                                                                                                                                                                                                                                                                                                                              |
| 一覧の読み方         | `candidate.list` を keyset で全頁読む（1 頁 1000 件・100 頁。保守と同じ）。頁数の上限で切れたら読んだ分を返し、`next_cursor` に続きの位置（`{received_at, candidate_id}` の JSON を base64url にした不透明な文字列）を入れる。読み切ったら null。経路の表は任意のクエリーを持てないので、続きを読む経路は今回作らない（`next_cursor` は「まだある」ことの知らせだけ）                                                                                                                                                       |
| 一覧の失敗           | 題の封筒を開けない・題の中身（`{title, deadline_original_text}`。`candidateTitlePayload` と対）が読めない・期限があるのに原文が無い行が 1 つでもあれば、一覧全体を 503 にする（黙って落とさない）。保存の読み取りの失敗・データ鍵が読めないときも 503。候補が 0 件なら鍵を読まない                                                                                                                                                                                                                                          |
| 形の変換             | `request_revision`・`related_analysis` の版と世代は保存の整数を 10 進の文字列にする。`operation_ids` は空の配列（U282 の暫定 (a)）                                                                                                                                                                                                                                                                                                                                                                                          |
| 根拠の観測と応答     | 有効（available）: 200 で `CandidateEvidence`（根拠の位置・未読・保存済みの抄録。本文全体は返さない）。新しい版（revised）: 状態を変えず 409。取り直せない（temporarily_unavailable・ポートの例外）: 状態を変えず 503。取得範囲外・削除: `source_out_of_scope` で遷移を試みて 409。予定の重複の解消: `overlap_resolved` で遷移を試みて 409。忘却: 物理削除は忘却の計画の仕事なので遷移させず 409。終端の候補の取得範囲外・削除（遷移なし）: 409。遷移の成否は本文に出さない（状態が変わった・変わり得たとして読み直させる） |
| 根拠の補足           | 有効と答えたのに根拠の位置・未読の別が無いポートの答えは 503。抄録の封筒を開けない・200 文字を超えるときも 503。存在しない候補は 422（契約に 404 は無い。`getConnectionTargets` と同じ）。取り直しのポート（`fetchEvidence`）が無ければ 503                                                                                                                                                                                                                                                                                 |
| 状態変更の応答       | 成功したら `candidate.get` で読み直して `CandidateSnapshot` を 200。`candidate_not_found` → 422。`snooze_` で始まる理由 → 422（ただし `snooze_now_invalid` は中枢の時計の問題なので 503）。`state_mismatch`・`time_backwards`・`transition_not_allowed`・`event_not_due` → 409。成否不明（`unknown`）・それ以外 → 503。snooze で `snooze_until` が無い・いまより後でない、snooze 以外で `snooze_until` がある → 422。拒否の応答には `request_id` を入れる                                                                   |
| 由来の読み出し       | 根拠の取り直し先を引くため、`candidate.get` の値に由来の辺（`origins`）を足した。`derivations` を `artifact_kind='notification_candidate'` で読む（`readDerivationsByArtifact`。並びは source_kind・source_id・created_at）。候補が無いときは `{ candidate: null, origins: [] }`                                                                                                                                                                                                                                            |
| 根拠の取り直しの口   | `fetchEvidence(candidate, origins)` を注入する（保守の `checkEvidence` と同じ扱い）。実 connector は B08・B09 の担当で、`core.ts` は渡さない                                                                                                                                                                                                                                                                                                                                                                                |
| データ鍵             | Core はデータ鍵をメモリーに持ち続けない（`OpenedStore` は自宅の HMAC の鍵だけを持つ）ので、`dataKey` は要求ごとに鍵の保管庫から読む関数にした（`api-turns.ts` の `loadKey` と同じ）。B11-04 の作業指示の「起動時に読み込んだ dataKey を渡す」からの変更                                                                                                                                                                                                                                                                     |
| 本人のタイムゾーン   | `startHttps` のスコープに本人の IANA タイムゾーンの出所が無い（発言の解釈・流れの区切りは UTC からのずれ `utcOffset` だけ、予算の設定の `timeZone` は予算月の用途）。端末の既定や予算月のタイムゾーンで黙って置き換えず、`zone: () => null` で配線した。一覧・状態変更・根拠の観測による遷移は 503 で閉じる                                                                                                                                                                                                                 |

## 試験（模擬だけ）

- `apps/core/src/api-candidates.test.ts`（6 件）: 実際の DB（マイグレーション済みの SQLite）に P1 の `persistCandidateDrafts` で種を入れ、経路の処理を直接呼ぶ。基準は 2030-10-09T03:00:00Z（日本時間 10 月 9 日 水曜 12:00）・Asia/Tokyo で、期待値は手で書いた。一覧の順序（今日の予定の重複が先頭、今日・明日・今週・それ以降、同じ期限は受信の新しい順、期限不明、初回取り込みの過去）、1 件の形の全体、絞り込みと件数、頁の上限と続きの位置、封筒が壊れた行・鍵・タイムゾーンの欠落で 503、状態変更の正常系（open・dismiss・snooze・resolve）と拒否系（終端・acted への act・古い expected_state・過去といまちょうどのスヌーズ・時刻の欠落と余分・時計の遷移・無い候補・タイムゾーン無し・成否不明）、根拠の観測の全種類とポートの例外・根拠の位置の欠落・無い候補・ポート無し。
- `packages/storage/src/candidate-store.test.ts`: `candidate.get` の `origins`（2 つの由来の並び）と、無い候補の `{ candidate: null, origins: [] }`。
- 契約: `candidate-cases.json` に `CandidateStateCommand` の許可 2 件・拒否 3 件、`api-cases.json` に 3 経路の要求・応答・拒否の期待値。

**模擬の期待値だけ**。経路を HTTPS で通した結合（`api-route-order.test.ts` は処理の無い経路として 503 を見る）、実 connector の取り直し、画面、実機は未実施で、合格扱いにしない。

## 残ること

- 本人の IANA タイムゾーンの出所を決めて `zone` に配線すること（決まるまで 3 経路は製品で 503）。
- `fetchEvidence` の実装（B08・B09 の connector から許可範囲で取り直す）。
- B08-06 の公開 transaction での解析計画の無効化（main に入った後に、根拠の観測との関係を確かめる）。
- `Snapshot` の `candidates` の充填（今回は触らない）。
- 一覧の続きを読む経路（`next_cursor` を受け取るクエリー。任意クエリーの仕組みが要る）。
- 画面（B11-05）。
