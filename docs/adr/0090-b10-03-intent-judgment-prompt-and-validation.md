## 決めたこと

| 対象                             | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 指示文の構成                     | 固定部分（`INTENT_SYSTEM_MESSAGE`、版は `INTENT_PROMPT_VERSION = '1'`）と変わる部分（基準日・候補・直前の依頼・発話）を別の message にする。固定部分に発話・候補を入れず、先頭を一定にして自動キャッシュを当てやすくする（当たる保証はない）。固定部分の文面と例は仮置きで、変えたら版を上げる。モデルの採否は B10-07、文面の調整は B15 以降                                                                                                                                          |

| 入力の検査                       | 空・2,000 文字超・不正な基準日・候補 20 件超・直前の依頼 5 件超は**モデルへ送らない**（切って送ると意図が変わる）。送らなかったことは `sent: false` で区別する                                                                                                                                                                                                                                                                                                                        |
| 出力                             | 契約の `WireResponse`（全項目必須・`additionalProperties: false`）をそのまま使う。provider へ送る wire schema は codec が作る（P2）。ローカルでは契約の JSON Schema を完全に検証する（QA01）                                                                                                                                                                                                                                                                                          |
| 意味の検証（QA03）               | schema の後に、意図の許可されない引数、`unclear` に引数が付く、**渡していない候補**の `target_candidate_id`、暦に存在しない日付・範囲外の時刻、終了が開始より前（秒を省略した日時は 00 秒として正規化し、日付だけの値と日時は精度が違うので比べない）、`relation: new` に対象の依頼が付く、**渡していない依頼**の `target_workflow_id`、雑談・一般の質問以外の `reply_text` を `invalid_semantics` にする。理由コードは診断用で、利用者には出さず、契約の `ModelOutcome` にも入れない |
| 必須の引数の不足                 | 意味検証の失敗にしない。意図を保ったまま足りない項目を `null` にした出力は通し、Core が意図表（`checkIntentArgs`）で聞き返しにする（文脈不足は聞き返し。実行へ進まない）                                                                                                                                                                                                                                                                                                              |
| 失敗と `unclear`                 | モデルが `unclear` と答えたことと、判定に失敗したこと（拒否・打ち切り・schema 不正・意味不正・timeout・利用不可・中断）を別の型にする（`IntentJudgment` の `unclear` と `failed`）。`unclear` は「それやめて」のような新しい意図を持たない取消・訂正のために `relation` と `target_workflow_id` を保つ。失敗は原因の種類と `retryable` を持つ                                                                                                                                         |
| 再送                             | 1 回の判定で送るのは 1 回だけ。timeout・不正な出力の後に、自動の送り直し・JSON の修復・上位モデルでの再試行をしない（ADR 0070、設計修正案 v1.2 P01・P02）                                                                                                                                                                                                                                                                                                                             |

## 試験（模擬だけ）

`packages/ai/src/intent-judgment.test.ts`（手書きの期待値。契約の JSON Schema を正本にする）:

- 固定部分が 24 意図すべてを含み、発話・基準日が入らないこと。変わる部分の書式を手書きの文字列と照合。区切りを壊そうとする発話が囲みの外へ出ないこと。
- 入力の検査で止まったとき、アダプターを呼ばないこと。
- QA01: 余分なキー・欠損・null・存在しない意図・型違いが `invalid_schema` になり、意図として扱われず、送信が 1 回であること。
- 拒否・打ち切り・途中の JSON・空・timeout・利用不可・中断が `unclear` にならず、再送されないこと。モデルが `unclear` と答えた場合は失敗にならないこと。
- QA03: 意味検証の各理由が `invalid_semantics` になり、usage が残ること。必須の引数が足りない出力は通ること。

**模擬のみ**。実 API・実請求・実機・実 endpoint の能力確認・モデルの採否は未実施で、合格扱いにしない。
