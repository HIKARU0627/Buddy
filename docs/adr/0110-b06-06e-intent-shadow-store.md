- 根拠: 設計 03（保存期限・忘却と再取り込み）、設計 10 §5、設計 09 X48、ADR 0008・0018・0040・0092、`packages/storage/migrations/0001_initial.sql`（`intent_shadow`）、`packages/storage/src/expiry-store.ts`・`forget-store.ts`（既存の掃除と閉包）、本人の決定 D4（2026-11-01、既定 OFF）。非公開の原本は写していない。
- 対象: `packages/storage/src/intent-shadow-store.ts`（新規）、`db-protocol.ts`・`db-worker.ts`・`db-client.ts`・`index.ts`、`intent-shadow-store.test.ts`・`db-worker.test.ts`、`docs/b00/contract-map.md`（U260）。由来の辺は既存の `derivation-store.ts` の `writeDerivation` を使う。

## 決めたこと

| 対象                    | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 命令                    | `intent_shadow.save`（1 入力の比較の記録を 1 行）と `intent_shadow.count`（campaign ごとの件数）。store ごとのファイルに分け、`DbWorkerClient.intentShadow` から 1 命令 1 往復。                                                                                                                                                                                                                                                                                                                                                                                       |
| 上限（原子性）          | `save` は `BEGIN IMMEDIATE` の transaction の中で、(1) 書込みの前提、(2) 同じ組の有無、(3) campaign ごとの件数、(4) INSERT と由来の辺の順に判定する。件数の確認と INSERT が同じ transaction なので、Core の事前の確認（ADR 0092 の開始前・送る直前）とは別に、保存側でも 300 件を超えない。                                                                                                                                                                                                                                                                            |
| 書込みの前提            | Core の判断を信じ切らず、保存側でも次を確かめ、通らなければ書かない（`IntentShadowRejection`）。(1) 観測した保存モードの `record_shadow` が許可され、保存期限（`turn_retention_days`）が決まっている（記録しない会話では書かない。`shadow_not_permitted`）。(2) `(input_id, request_revision)` が `input_snapshots` にあり、`turn_id` が結び付いている（`input_not_found`。`turn_id` が NULL の記録は、発言を忘れても閉包に入らない）。(3) `expires_at` が `turns.expires_at` と 1 ミリ秒も違わず一致する（`expiry_mismatch`。比較の待ち時間で記録だけ長く残さない）。 |
| 前提と `duplicate` の順 | 前提を先に見る。発言を忘れて結び付けが外れた後の再送は、すでに行があっても `duplicate` ではなく前提の拒否にする（消えた発言を指す記録を受け付け直さない）。                                                                                                                                                                                                                                                                                                                                                                                                            |
| 由来の辺                | INSERT と同じ transaction で `derivations` に `artifact_kind='intent_shadow'`・`artifact_id=record_id`・`source_kind='turn'`・`source_id=input_snapshots.turn_id` を 1 本書く。期限の掃除（`expiry-store` は `derivations` から派生物を拾う）と忘却の閉包の対象にするため。辺がないと、行を書いても掃除の計画にも閉包にも入らない（ADR 0092 の「由来の辺」がこれ）。                                                                                                                                                                                                   |
| 同じ組                  | `(campaign_id, input_id, request_revision)` が同じ保存は書かずに `duplicate`。`record_id` が違っても増やさない（表の一意制約が正本）。再送・再起動の後の再保存で二重にしない。                                                                                                                                                                                                                                                                                                                                                                                         |
| 判定の順                | `duplicate` を `limit_reached` より先に見る。すでにある行は「上限で書けなかった」のではなく、内容が変わっていない。上限に達した campaign へ同じ組を再送しても `duplicate`。                                                                                                                                                                                                                                                                                                                                                                                            |
| 結果の語                | `saved`（書いた）・`duplicate`（同じ組があった）・`limit_reached`（上限で書かなかった）。どれも書込みの失敗ではない。拒否（形の不正・`worker_halted`・耐久設定の不一致）と、成否不明（COMMIT の失敗）は `ok: false` で分ける（Core は `failed` に対応づける）。                                                                                                                                                                                                                                                                                                        |
| `limit` の範囲          | 1〜300 の整数だけを受ける。設定や呼び出し側が 300 を超える値を渡しても、保存側は書かない（`limit_invalid`）。300 は Core の `SHADOW_MAX_INPUTS` と同じ値を storage 側にも写しで持つ（storage は `@buddy/contracts` に依存しない）。                                                                                                                                                                                                                                                                                                                                    |
| `judgments` の列        | 表の列にならない部分（`schema`・`primary`・`shadows`・`used_for_execution`）を JCS の JSON（`canonicalIntentJson`）で置く。行から `IntentShadowRecord` を組み直せる。契約の意味検査は Core が行う（保存側は形の最低限だけを見る）。                                                                                                                                                                                                                                                                                                                                    |
| 実行に使わない印        | `used_for_execution` が `false` でない記録は書かない（契約の `const false`。影の判定を実行に使わない規則を保存側でも破らせない）。                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 時刻                    | `recorded_at`・`expires_at` は UTC の ISO 8601（末尾 `Z`）だけを受け、ミリ秒で行に置く。`expires_at > recorded_at` は保存側でも確かめ、表の CHECK が最後に保証する。DB は時計を持たず、呼び出し側の値を信じる。                                                                                                                                                                                                                                                                                                                                                        |
| 既存の掃除・閉包        | 書き方は既存の `expiry-store`（`intent_shadow` は期限を持つ派生物）、`forget-store`（`input_snapshots` との結合で発言に帰属）に合わせた。行の形を変えないので、掃除・閉包・復元の経路はそのまま働く。                                                                                                                                                                                                                                                                                                                                                                  |
| campaign の開始・停止   | 保存しない。件数は `COUNT` で導ける。開始日時・上限・実費の上限の置き場と、実費の合計の正本は U260 に記録し、B15 の設定の読み込みと一緒に本人が決める。                                                                                                                                                                                                                                                                                                                                                                                                                |

## 試験（模擬だけ）

- `packages/storage/src/intent-shadow-store.test.ts`: 保存で件数が 1 増える・campaign ごとに数える。同じ組の再保存（`record_id` 違いを含む）は `duplicate` で行が増えない。版が違えば別の行。上限で書かない（`limit_reached`）。**299 件から 2 件保存して 1 件だけ**保存。一意制約が表にある。`limit` の範囲（0・301・1.5）。契約に合わない記録（`used_for_execution`・期限の前後・版・`shadows` 空・ID の形・outcome・schema）を書かない。書込みを止めた worker は書かず件数は読める。`judgments` の列の中身とミリ秒。DB を開き直しても件数が引き継がれ、再保存で二重にならない。**書込みの前提**（記録しない会話・知らない保存モード・入力の版がない・発言に結び付いていない・期限が 1 ミリ秒違う・発言を忘れた後）で書かない。**期限の掃除**が `expires_at` の 1 ミリ秒前は残し、ちょうどで消す。**発言の忘却**で、その発言を入力にした比較の記録が閉包で消える（`turns` の行が消え、`input_snapshots.turn_id` が外れる）。
- `packages/storage/src/db-worker.test.ts`: クライアントと worker の間で `count` → `save` → 再送（`duplicate`）→ `count` が往復する。

**模擬のみ**。実 API・実請求・実機・実 endpoint は未実施で、合格扱いにしない。
