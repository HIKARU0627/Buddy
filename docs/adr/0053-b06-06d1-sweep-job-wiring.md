## 実行の順序

1. `retention.sweep_rows`（操作と予算の月）。
2. `sweepPlan`（時計・最終確認時刻・行）。
3. `retention.purge_undo_records`（計画が読めたときは毎回。補償の記録を先に片付ける。90 日の削除の計画の有無に依らない）。
4. 本文の削除の計画があれば `retention.erase_due_bodies`、90 日の削除の計画があれば `retention.purge_due_operations` を `next` で繰り返す。
5. 予算の月の計画があれば `budget.purge_month`（月ごとに 1 回）。
6. `SweepRecord` を作り、`startupGate` の結果を `CoreHandle.retention.gate()` に置く（ここでゲートが開く）。
7. 記録の確定の後に、削除が 1 件以上あれば `retention.checkpoint` →（間隔を過ぎていれば）`retention.vacuum` → `retention.checkpoint`（記録の外。下の「PR #164 のレビュー後の修正」）。

## 原本に書いてあること（ADR から）

- 03 保存期限: 期限処理は起動時・復帰時に検索やクラウド送信より先に行い、起動中も定期実行する。時計が巻き戻ったら期限を延ばさず、整合するまで自動利用を止める。
- J4: 予算の記録は月ごとにまとめて消し、不明は消さない。J5: 完了から 7 日で本文、90 日でレシート。ADR 0043 の `sweepPlan`・`startupGate` が判定を持つ。
- ADR 0040・0048: `secure_delete` に加えて `wal_checkpoint(TRUNCATE)` と定期の `VACUUM` を、マイグレーションの外の job で行う。

## 再レビュー（Codex）後の修正: 送出と掃除の直列化

ゲートの確認の後、送出意図の保存の応答を待つ間に定期の掃除が始まると、閉じたゲートを越えて送れてしまった。保存の後に止めると、送っていない操作に結果不明が残るので、保留は必ず `dispatch_intent` より前で行う。

- **貸し出し（lease）**: `RetentionSweeper.lease()` が、ゲートの確認と貸し出しの登録を**同じ同期の区間**で行う。ゲートが閉じている・掃除が動いている（または貸し出しの終わりを待っている）・停止中なら `null`。取れた貸し出しは、送信が終わるまで（`consumeDispatchPermit` と `send` の後。結果の保存の前）持つ。
- **順序（送出側）**: ① 準備権の前に `idle()` の後で `gate().cloud_send` を確かめる（閉じていれば何も記録せず、5 分後に最初から） → 準備権 → 対象の確かめ直し → ② `idle()` の後で `lease()`（取れなければ送出意図の前で止めて 5 分後に最初から） → `dispatch_intent` → 許可の消費 → 送信 → 貸し出しを返す → 結果の保存。
- **順序（掃除側）**: `runOnce` は記録を `running` にしてゲートを閉じ、貸し出しがすべて返るまで待ってから本体（`retention.sweep_rows` 以降）に入る。待っている間は新しい貸し出しをしない（飢餓を防ぐ）。貸し出しを持つ送出が終わらない場合、掃除は遅れ、記録が古くなって（`sweep_stale`）ゲートは閉じる。安全側。
- 停止（`close()`）は貸し出しを待っている掃除も中断する（失敗の記録は作らない）。
- 最終の記録の確定の前にも中断を確認する（最後の削除命令を待っている間に停止しても `completed` にしない）。
- 後始末は `checkpoint` と `VACUUM` の保留を別々に持つ。間隔で延期した VACUUM は、削除のない次の掃除へ引き継ぐ。VACUUM の後の checkpoint が busy なら、checkpoint だけを保留に戻す（VACUUM の成功時刻は戻さない）。

試験（模擬）: 送出意図の保存の後・送る前で止め、そこで始まった掃除が本体に入らず、送出が 1 回だけ行われてから掃除が完了すること（掃除が貸し出しを待たない旧コードでは落ちる）／確かめ直しの間にゲートが閉じたとき、送出意図の前で止まり工程の記録がなく、開けば 1 回だけ送ること／ゲートが閉じていると予定の照会は聞き返し、用事の登録（LocalCommand）は進み、掃除の本体を待つこと／停止が掃除の終わりを待ってから DB を閉じること。

### 再レビュー（Codex、head 9a0681b）の P2 2 件

マイグレーション・ADR の番号・U 番号は増やしていない。判断の意味は変えず、計画と命令の食い違いと取りこぼしを直した。

| `purgeUndoRecords` が 90 日の削除の計画に依存（30 日を過ぎた記録が残る） | 取り消しの記録の掃除を、レシートの計画の有無に依らず毎回（計画が読めたとき）呼ぶ。期限は 30 日（`RETENTION_RULES.undo_window`）で、90 日のレシートより早い。消した件数は削除に数えるので、checkpoint・VACUUM の後始末も続く                                                                                                                                                                                                                              |
| 計画が保留した行を、バッチが選び直して消す                               | storage の命令を domain の読み取りと同じ範囲にそろえた。`completed_at` が UTC の 4 桁の年（0000-01-01T00:00:00Z〜9999-12-31T23:59:59.999Z）に収まらない操作は、`dueOperations` が選ばず、`finishedOperation`（1 件ずつの命令）も `completed_at_missing` で拒む。`readSweepRows` の `isoOrNull` も同じ範囲で null にする（計画の `deadline_unreadable` と命令が同じ側になる）。拒否の理由は期待する保留の `completed_at_missing` なので、ゲートは閉じない |

試験（模擬）: sweeper は、90 日の削除の計画がなくても取り消しの記録の掃除が呼ばれ、消した後に後始末が続くこと（修正を外すと落ちる）。storage は、範囲の下限ちょうど・下限の 1 ms 前・Date の範囲外の完了の時刻を、正常な期限超過の操作と混ぜた実 SQLite で、本文の削除・90 日の削除ともに保留の行を選ばず、1 件ずつの命令も拒むこと（修正を外すと落ちる）。

### 再レビュー（Codex）の P2: 検索の実行区間も掃除と直列化

発言の入口（`planTurn`）はゲートを一度確かめるだけで、その後の接続の確認や予定の取得を待つ間に定期の掃除が始まると、記録が `running` でゲートが閉じた後でも検索が実行された。送出側（実行担当）と同じ貸し出し（`RetentionSweeper.lease()`）を使う。判断の意味は変えていない（新しい ADR・U・マイグレーションなし）。

- `createTurnRoutes` の `retention` に `lease` を足し、`planTurn` が `ready()` の後に、ゲートの確認（検索・クラウド送信・自動利用）と貸し出しの取得を**同じ同期の区間**で行う。検索・計画（予定の照会・下書き・ラベル）が終わる（`finally`）まで持つ。
- 貸し出しが取れないのは、`ready()` の後に別の掃除が始まったとき。その掃除が済むのを待って確かめ直す（最大 3 回）。取れなければ、検索せず `blocked` の聞き返し。
- 貸し出し中に始まった掃除は本体に入らず、検索が終わるまで待つ（記録は `running`、ゲートは閉じたまま）。検索が止まったままなら掃除は遅れ、記録が古くなって（`sweep_stale`）ゲートは閉じる。安全側。
- 試験（模擬）: 予定の取得の途中で止め、そこで始まった掃除が本体に入らず、検索が終わってから完了すること。貸し出しを無効にすると落ちる。
