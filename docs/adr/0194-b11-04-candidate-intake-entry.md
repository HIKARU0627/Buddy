# ADR 0194: B11-04 候補の取り込みの入口（予定の重複を製品につなぐ、メールの抽出の結果の入口）

- 日付: 2026-11-27
- 状態: B11-04（親 #23、Issue #271）の残り (2) の判断と実装。予定の重複からの候補を、同期の公開の後の処理として製品の配線につないだ。メールの抽出の結果からの候補は入口だけを作り、製品の抽出がまだ動いていないので製品にはつないでいない（U546）。根拠を取り直す `fetchEvidence`・`checkEvidence` の connector への接続（残り (1)）と、U283・`Snapshot.candidates`・一覧の続き（残り (3)）は未着手。実 API・実機・実データは未実施。
- 根拠: 設計 11 §4・§5B、設計 04 気づきの作成（予定重複）、設計 03 保存と忘却（記録しない会話）、ADR 0059・0190（保存境界）、0073・0115〜0120・0130・0131（候補）、0136・0137（同期の走査と周期）、0160（公開の後の取り込み）。原本（非公開 Notion）はこの作業環境に無いので読んでいない。原本の不足は推測で埋めず、決めていない点は U540〜U547 に暫定として置いた。
- 番号: ADR は 0194、未決事項は U540〜U547。
- 対象: `apps/core/src/calendar-candidate-intake.ts`（新設）、`mail-candidate-intake.ts`（新設）、`retention-entries.test.ts`（掃除のゲートの入口の表）、`core.ts`（配線）、`sync-scheduler.ts`（公開の後の知らせに公開の結果を渡す）、`sync-executor.ts`（`toFetchScope` を公開）、`packages/connectors/src/adapter/google-calendar.ts`（空き時間・種類・本人の出欠を写す）、各試験、`docs/b00/contract-map.md`。契約（schema・OpenAPI・生成型・fixture）とマイグレーションは変えない。`api-turns.ts`・`turn-ports.ts` は触らない。

## 決めたこと

| 対象               | 決定                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| いつ回すか         | 同期の周期（`sync-scheduler`）が予定の取得集合を公開した後（`onPublished`）。差分があった公開、またはその取得集合でまだ終わっていない回（起動の後の最初・作らずに終わった回・やり直す下書きがあった回）だけで、差分の無い毎分の公開では予定を読み直さない（U547）。`onPublished` の 3 つ目の引数に公開の結果（差分の数と公開後の取得集合）を足した                                 |
| どこから読むか     | 接続の今の取得対象（`connections.get` で読み直す。Google・有効・取得対象が完全なときだけ）の、選んだカレンダーだけを、いまから取得の窓（`calendarWindow`）の終わりまで `events.list`（singleEvents・showDeleted）で読み直す。窓とカレンダーを広げない。1 つのカレンダーで 40 頁（1 頁 250 件）を超えたら、その回は作らない（一部だけで判断しない）。掃除のゲート（ADR 0053）を通す |
| 何を残すか         | 予定の題・参加者・本文は保存しない。使うのは時刻・状態・本人の出欠・空き時間の別・識別子だけ。候補の題は時刻だけの定型（ADR 0119）。由来は同期が保存した予定の `remote_id`（`source_item`）。connector は参加者の一覧から本人（self）の出欠だけを写し、ほかの参加者・アドレスは写さない                                                                                            |
| 重複と候補         | domain の `findScheduleOverlaps`（期間はいまから窓の終わり）。まだ始まっていない重複（時刻付きは開始がいま以降、終日は開始の日付が本人の今日以降）だけを下書きにする（U541）。空き時間（transparency が transparent）・勤務場所・誕生日の予定は空き時間として扱う（U542）。重複を探すのは 1 つの接続の選んだカレンダーの中だけ（U544）                                             |
| 二重に作らない     | 識別子は ADR 0117 の `notificationKey`（予定の参照と重複の期間）。同じ識別子の候補は状態によらず作らない（再同期・再接続・却下の後も。保存側の `candidate.create` が `duplicate` を返す）                                                                                                                                                                                          |
| 初回取り込み       | 公開の後の取得集合の世代が 1（初めて差分を公開した）のとき、初回取り込みの印を付ける（一覧にだけ載せる。通知の判定は ADR 0117 の `candidateAlertDecision`）（U543）                                                                                                                                                                                                                |
| 重複の解消         | 活動中の予定の重複の候補のうち、由来の予定をすべて今回読み、識別子が今の重複（始まって続いているものを含む）に無いものを resolved にする。由来の予定が取り消されていれば `source_out_of_scope`、ほかは `overlap_resolved`。由来の予定を今回読めなかった候補（窓の外へ移った・選択を外したカレンダー・別の接続）には触らない（U545）                                                |
| 記録しない会話     | 記録しない会話の間は予定を読まず、候補も作らない（次の公開で、差分が無くてもやり直す）。読み取りを始めたときの区切り（保存境界の保持者の区切りの ID と世代）を控え、保存の直前に今の区切りと照合する（`api-turns.ts` の `originCurrent` と同じ照合）。変わっていたら保存しない。保存境界の保持者が無い組み立てでは記録しない会話として扱う（U540）                                 |
| メールの抽出の結果 | 入口 `intakeMailExtraction` を作った。フィルターで外した・抽出できなかったメールからは作らず、記録しない会話の間・抽出を始めたときから区切りが変わったときは作らない。下書きと保存は ADR 0119 の `mailCandidateDrafts`・`persistCandidateDrafts` をそのまま使う。製品では抽出の入口そのものがまだ動いていないので、つないでいない（U546）                                          |
| 失敗               | 1 回の取り込みの失敗（読めない・鍵が無い・タイムゾーンが無いなど）は同期の周期を止めない（`onPublished` は待たずに呼ばれ、例外は記録して捨てる）。由来の予定がまだ同期に無い（`origin_not_found`）・保存の成否不明があれば、次の公開でやり直す。ログは件数だけで、題・時刻・識別子を出さない                                                                                       |

## 試験（模擬だけ）

- `apps/core/src/calendar-candidate-intake.test.ts`（7 件）: 実際の DB（マイグレーション済みの SQLite）の候補の保存と結び、読み取りの口は合成の予定を頁ごとに返す。基準は 2030-10-09T03:00:00Z（日本時間 12:00）・Asia/Tokyo で、期待値は手で書いた。重なる 2 つの予定から候補が 1 つだけでき、識別子（手で書いた材料の SHA-256）・題（時刻だけ）・期限・由来・読み取りの範囲（選んだカレンダー、いまから 14 日後まで、頁を追う）が合い、予定の題が DB に残らないこと。辞退・空き時間・勤務場所の予定から作らないこと。再同期・却下の後に作り直さないこと、世代 1 の公開で初回取り込みになること、`shouldRun` の判断。始まった重複を作らず、続いている重複の候補を解決しないこと。時刻の変更・取り消し・辞退で resolved になり、由来を読めなかった候補・カレンダーの選択を外したときは触らないこと。記録しない会話の間は読まず作らず、出た後の公開で作ること、読み取りの間に区切りが変わると保存しないこと。拒否側（タイムゾーン・接続の種類と状態・取得対象・読み取りの口・窓が空・読み取りの失敗・頁の上限・鍵・掃除のゲート・由来の予定が未同期）。予定の写し方（ずれ付きの時刻の UTC への変換・終日・繰り返しの回・出欠・空き時間・読めない状態と時刻）。
- `apps/core/src/mail-candidate-intake.test.ts`（2 件）: 抽出した依頼が 1 つの候補になり、同じメールの再同期は `duplicate`、fyi は理由付きで候補にしないこと。フィルターで外した・失敗・送らなかった抽出、記録しない会話、区切りの変化では作らないこと。
- `apps/core/src/sync-scheduler.test.ts`（1 件を追加）: 公開の後の知らせに、対象・差分の数・公開後の取得集合が渡ること。`apps/core/src/retention-entries.test.ts`: 新しい取り込みを掃除のゲートを通す入口の表に足し、Core が渡すゲートの数を 10 にした。
- `packages/connectors/src/google-connector.test.ts`（2 件を追加）: 空き時間・種類・本人の出欠だけを写し、ほかの参加者を写さないこと、参加者の一覧の形が違えば拒むこと。
- 空き時間の判定・記録しない会話の照合・由来を読んだかの条件を一時的に壊して、試験が失敗することを確かめた。

**模擬の期待値だけ**。実際の Google Calendar・実 OAuth・実機・本人の実データでの確かめは未実施で、合格扱いにしない。

## 範囲の外と残り

- (1) 根拠を取り直す `fetchEvidence`（根拠の経路）・`checkEvidence`（保守）の connector への接続: 未着手。メールの候補は製品で作られていない（U546）。予定の重複の候補は、取り込みの回に重複の解消を確かめる（U545）が、根拠の経路は、候補の由来（予定の `remote_id`）からカレンダーを引けない（`source_items` にカレンダーの ID が無い）ので作れない。どちらも保存の形（由来の行にカレンダーやメッセージの位置を持つか）を決めてから行う。
- (2) の残り: メールの抽出の結果の入口を製品の抽出につなぐこと（抽出の配線は実 API の承認の後。B15）。カレンダーの選択を外した・接続を切ったときの予定の重複の候補を取得範囲外で resolved にすること（U545）。
- (3) U283（依頼 ID の解決と保存）、`Snapshot.candidates` の充填（端末は一覧の経路だけを使い、スナップショットの候補を読んでいない。イベントの流れに候補の変化を載せるかと一緒に決める）、一覧の続き（`next_cursor` を受けるクエリー。表示順が全体の並べ替えなので、頁ごとの続きの意味を決める必要がある）: 未着手。
- 新しい候補の通知（OS 通知・読み上げ）は B11-05 の配線で、ここでは出さない。
