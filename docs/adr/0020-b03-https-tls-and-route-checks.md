# ADR 0020: 中枢の TLS 証明書・HTTPS の受付・経路検査の基盤

- 日付: 2026-10-21
- 状態: B03-01（#62）の判断と実装。中枢の自己署名証明書（秘密鍵はキーチェーン）、`node:https`（TLS 1.3 以上）の受付、端末トークンの照合、上限・形式・Origin・接続数・認証前の頻度の拒否、ROUTE_CHECKS の順の経路検査、`getBootstrap` と接続範囲（command_scope）の発行・無効化、DB worker の端末・接続範囲の命令を作った。試験は 127.0.0.1 の模擬（模擬の KeyStore・一時ディレクトリの DB・子プロセスの CLI）だけで、macOS 実機のキーチェーン・Tailscale 上の接続・実際の端末からの接続は未実施。
- 根拠: 設計 02（端末登録と接続・主な通信契約・保存と秘密情報）、07 §2・§3・§6、06 B03、X04、ADR 0009（経路の検査順・U15）・0012・0017・0018・0019。下の「本人の判断」は 2026-10-21 の決定。設計本文は今回の作業環境に取得できず、Issue #62 の要約と ADR に基づく。原本との照合はレビューで行う。

## 本人の判断（2026-10-21）

| 対象         | 決定                                                                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| HTTPS・WSS   | HTTPS は `node:https`（TLS 1.3 以上）。WSS は `ws`。B03-01 は受付の土台だけで、配信は B03-04                                                                       |
| Fastify      | 採らない（下の「Fastify を採らない理由」）                                                                                                                         |
| 証明書       | Node 標準の暗号機能で自己署名する。秘密鍵はキーチェーン（KeyStore の別の項目）に置き、平文をディスクに残さない。証明書（公開部分）はデータディレクトリに置いてよい |
| 指紋         | 証明書の DER 全体の SHA-256。定義を契約の記述に足す。有効期限は長くし、更新では全端末の再登録が要る                                                                |
| 証明書の検証 | アプリ全体で検証を無効にしない。試験用のピン留めクライアントは指紋を照合し、合わなければ要求を送らない                                                             |

## Fastify を採らない理由

- 経路は OpenAPI の約 30 本で、経路の表（`apps/core/src/api-routes.ts`）と照合の関数（`matchRoute`）で足りる。表が OpenAPI と同じであることは試験で確かめる。
- 経路ごとの検査は domain の独自の表（`ROUTE_CHECKS`・`admitRequest`）が正本で、Fastify の hook・plugin の順序に検査の順を委ねると、表との一致を別に保証する必要がある。
- 形式の検査はすでに Ajv（8.20.0、desktop と同じ版）と JSON Schema を正本にしている。Fastify の schema の仕組みは、重複キーの拒否（厳格な JSON の読み取り）・本文を読む前の上限・認証前に本文を読まないことを、こちらの順に合わせて差し込む必要がある。
- 依存を増やさず、TLS・接続数・上限・Origin の扱いを `node:https` の上で直接書いて試験する方が、検査の順を追いやすい。

## 決めたこと

### 証明書と秘密鍵

| 対象                 | 決定                                                                                                                                                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 鍵                   | ECDSA P-256（`prime256v1`）。`@buddy/platform` の `TlsKeyStore` が `generateKeyPairSync` で作り、キーチェーンの汎用パスワード項目（サービス名 `dev.buddy.core`・アカウント名 `tls-key-v1`）に PKCS#8 の DER を正準の base64 で保存し、読み戻して確かめる |
| 鍵の検査             | 読み出し時に正準の base64・PKCS#8 の DER・P-256 の EC 秘密鍵であることを検査する。不正な保存値は上書きしない（`tls_key_format_invalid`）。鍵の値はログ・例外・理由に入れない（`TlsPrivateKey` は JSON・inspect・文字列化で `[redacted]`）                |
| 証明書の組み立て     | `apps/core/src/der.ts` で DER を組み立て、`crypto.sign('sha256', tbs, { dsaEncoding: 'der' })` で署名し、`X509Certificate` で読み戻して検証する（署名・鍵の一致・自己発行・CA でない・有効期間）                                                         |
| 証明書の中身         | v3、16 バイトの乱数の通し番号、ecdsa-with-SHA256、subject・issuer は `CN=Buddy Core`、基本制約 CA:FALSE（重要）、鍵の用途 digitalSignature（重要）、拡張鍵用途 serverAuth、subjectKeyIdentifier。宛先（IP アドレス・名前）は入れない                     |
| 有効期間             | 開始は作成の 1 日前（端末の時計の遅れ）、期限は RFC 5280 §4.1.2.5 の「期限を定めない」値 `99991231235959Z`                                                                                                                                               |
| 指紋                 | 証明書の DER 全体の SHA-256 の小文字の 16 進 64 桁（契約の `Hash`、`PairingSession.certificate_fingerprint` の記述に追記）。`X509Certificate#fingerprint256` からコロンを除いて小文字にした値と同じ                                                      |
| 置き場所             | 秘密鍵はキーチェーンだけ。証明書はデータディレクトリの `tls-certificate.pem`（0600、アトミックに置き換える）。データディレクトリに秘密鍵の平文を置かない（試験で確認）                                                                                   |
| 作り直し             | 鍵がなければ鍵と証明書を作る（`key_and_certificate`）。鍵があって証明書がなければ同じ鍵で証明書を作り直す（`certificate`）。どちらも指紋が変わるので、全端末の再登録が要る（ログと CLI の `certificate_creation` で知らせる）                            |
| 拒否                 | 鍵と証明書が合わない（`tls_certificate_mismatch`）・証明書が読めない（`tls_certificate_invalid`）・鍵を読めない（`tls_key_unavailable:<理由>`）ときは上書きせずに起動を拒否する                                                                          |
| 鍵保護が使えないとき | TLS の鍵を取得できなければ `CoreStartError('tls_unavailable')`（終了コード 5）で起動を拒否し、HTTPS を開かない。データ鍵の起動前検査に通らなければ、TLS の鍵には触れない                                                                                 |

### 待ち受け

| 対象              | 決定                                                                                                                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 既定              | `--https-host` を渡さなければ HTTPS を開かない（B01・B02 の CLI と試験の動きを変えない）。ポートの既定は 47443（`--https-port`、0 は OS が選ぶ）                                                                                           |
| アドレス          | IP アドレスを正規化し、ループバックと Tailscale の範囲だけを受け付ける（他は `https_config_invalid`。B03-07 で変更、下の「B03-07 の変更」）。製品は Tailscale のアドレスを渡す（見つける処理は後の Issue）                                 |
| Core への組み込み | `startCore({ https: { host, port, tlsKeyStore, environment?, limits? } })`。起動の順は「起動時の回復 → TLS の身元 → HTTPS の待ち受け → 制御チャネル → running」、停止は「受付停止 → HTTPS → 制御チャネル → DB worker → ロック」            |

### 要求の処理順

1. 接続数の上限を超えた接続の要求は 429 `rate_limited`（接続を閉じる）。Core が受付中でなければ 503
2. Origin ヘッダーのある要求（ブラウザーからの要求）は 403 `forbidden`。WebSocket の切り替えも同じ
3. 接続元ごとの認証前の頻度の上限に達していれば 429 `rate_limited`（端末トークンを照合する前）
4. 経路の照合。ない経路は 404、方法違いは 405（どちらも `invalid_input`）
5. 端末トークンの照合。`Authorization: Bearer <43 文字>` の形式でなければ DB を引かない。トークンの ASCII の SHA-256 で devices を引き、未登録・失効は未認証。認証できなかった要求は頻度の数に入れる
6. 宣言の長さ（Content-Length）が上限（端末トークンを求める経路は 256 KiB、認証前の経路は 16 KiB）を超えたら、本文を読まずに 413 `payload_too_large`
7. 端末トークンを求める経路で未認証なら、本文を読まずに 401（宣言の長さは上限内なので、`admitRequest` の結果と同じ）
8. 本文を上限まで読む。超えた時点で読むのをやめて 413（切り詰めた本文を処理しない）
9. 形式の検査。パスの値・クエリー（未知・重複は拒否）・`Buddy-Input-Origin`（画面操作の経路で必須）・Content-Type・UTF-8（BOM を含めて拒否）・厳格な JSON（重複キー）・JSON Schema。不正は 422 `invalid_input`（`api.ts` の「形式の検査はこの前に別に行う」に合わせる）
10. 経路の検査（`admitRequest`、ROUTE_CHECKS の順）。文脈は経路の検査にある欄だけを求める
11. 経路の処理。B03-01 は `getBootstrap` だけ。他の経路は検査を通った後に 503 `dependency_unavailable` で閉じる

拒否の本文は `ApiError`（code・message・request_id）だけです。request_id は形式に合う本文のものだけを返し、トークン・hash・本文を返しません。応答には `Cache-Control: no-store`・`X-Content-Type-Options: nosniff` を付けます。

### 端末と接続範囲

| 対象               | 決定                                                                                                                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 端末トークン       | 256 ビットの乱数の base64url（43 文字、契約の `DeviceCredential`）。照合用の hash はトークンの ASCII の 43 文字の SHA-256（`deviceTokenHash`、`devices.token_hash` の 32 バイト）。契約の記述に追記した                    |
| device_id          | 認証の結果から決める。本文に `device_id` があれば契約にない項目として 422、クエリーも 422。名乗るヘッダーは見ない。他の端末の接続範囲を使うと 410                                                                          |
| getBootstrap       | 認証した端末に新しい接続範囲を発行し、同じ端末の有効な接続範囲を同じ transaction で無効にする（再接続で無効）。期限は発行から 24 時間（`RETENTION_RULES.command_scope`、0001 の CHECK と同じ）。端末の last_seen_at も更新 |
| 接続範囲の判定     | 認証した端末のもの・今回の起動（core_instance_id）で発行・失効していない・発行の時刻以後で期限の前、のすべてを満たすときだけ current。それ以外は stale（410 `expired_scope`）。時計が発行より前へ戻ったときも stale        |
| 端末の失効         | `device.revoke` で端末を失効し、その端末の有効な接続範囲を同じ transaction で無効にする（経路は B03-02）                                                                                                                   |
| Bootstrap の他の欄 | `api_version` は `1.0`（OpenAPI の info.version の major.minor）。`capabilities` は空。`io_state` は安全側の値（ロック状態 unknown・入力不可・`waiting_wake_word`・text・epoch 0）                                         |

DB worker には、操作の命令とは別のメッセージ（`type: 'device'`）で次の命令と照会を足しました（`packages/storage/src/device-store.ts`）。書込みは 1 つの短い BEGIN IMMEDIATE の transaction で、命令ごとに耐久設定を読み戻し、書込みを止めた worker（halted）は書きません。COMMIT の失敗は成否不明（unknown）で、以後の書込みを止めます（ADR 0018 と同じ）。

| 命令・照会                  | 内容                                                                   |
| --------------------------- | ---------------------------------------------------------------------- |
| `device.insert`             | 端末を登録する（ペアリング B03-02 と、試験で端末を入れる手段）         |
| `device.revoke`             | 端末を失効し、有効な接続範囲を無効にする                               |
| `device.find_by_token_hash` | 照合用の hash で端末を引く（結果に hash を含めない）                   |
| `scope.issue`               | 接続範囲を発行し、同じ端末の有効な接続範囲を無効にする（最長 24 時間） |
| `scope.find`                | 接続範囲を引く                                                         |

マイグレーションは足していません（0001 の `devices`・`command_scopes` で足りる）。

### WSS

`/v1/events/stream` は `ws` の `WebSocketServer({ noServer: true, perMessageDeflate: false })` で受け、HTTP の要求と同じ検査（Origin・頻度・端末トークン・本文なし・経路の検査）を通った要求だけを切り替えます。配信（`EventStreamMessage`）は B03-04 で、今は切り替えた直後に 1013（Try Again Later）で閉じます。切り替えの要求でない GET は 422 です。拒否は HTTP の応答（ApiError）で返します。

## 検査順の実行時の試験

`apps/core/src/api-route-order.test.ts` は、経路の表（`API_ROUTES`）と ROUTE_CHECKS の経路の集まりが同じことを確かめた上で、登録した全 29 経路に HTTPS で要求を送ります。

- 検査をすべて満たす要求（getBootstrap は 200、WebSocket は切り替えて 1013、他は 503）。
- 経路にない検査をすべて満たさない要求（結果は変わらない）。
- 経路の検査を一つずつ・二つずつ満たさない要求（全部の組）。返る拒否が「表の順で最初に満たさない検査」の拒否であること。二つずつの組で、どの二つの検査も表の順に優先されることが分かる。

満たさない状態は、端末トークン（送らない）・接続範囲（発行していない ID）・`Buddy-Input-Origin`（voice）を実際の要求で、自宅判定・ロック状態・中枢の画面・音声所有権・版・申請用の秘密を注入した環境で作ります。拒否の期待値（状態とコード）は試験に手で書き、`admitRequest` から作っていません。本文・パスの値は契約 fixture（`api-cases.json`）の合成値です。合計 424 件の要求を送ります。

## 読み取り（レビュー対象）

原本に明記がなく、実装で決めた点です。

- **未実装の経路を 503 で閉じる**: 契約の `ApiError.code` に 501 相当のコードがなく、OpenAPI の各経路の応答にも 501 がないため、検査を通った後に 503 `dependency_unavailable` を返す。端末（B03-05）がこの 503 を自動で再試行しないよう、B03-04 までに経路を埋めるか、契約に「未実装」のコードを足すかの判断が要る。
- **証明書の期限を定めない**: RFC 5280 の期限を定めない値にした。端末は名前ではなく指紋で照合するため、期限による入れ替えは安全性を増やさず、入れ替えは全端末の再登録を伴うだけになる。鍵の漏えいなどで入れ替えるときは、鍵の項目を消して再起動し、全端末を再登録する（手順は B03-02 以降で整える）。
- **証明書に宛先を入れない**: Tailscale のアドレスが変わっても指紋が変わらないようにした。端末は Node の既定の名前の照合を使わず、`checkServerIdentity` で指紋を照合する（信頼の起点は中枢の証明書 1 枚、`ca`）。
- **初回（ペアリング）の接続**: 登録前の端末は中枢の証明書を持たないため、信頼の起点（`ca`）を渡せない。申請の接続（B03-02・B03-05）では、TLS で見えた証明書の指紋を本人が中枢の表示と比べた後に申請を送り、以後は受け取った証明書を信頼の起点にする必要がある。この接続の作り方（検証を無効にしない形）は B03-02・B03-05 で決める。
- **認証前の頻度**: 「認証できなかった要求」を数え、上限に達した接続元はトークンを照合する前に拒否する（トークンの推測を続けさせない）。正しいトークンを持つ端末も同じ接続元なら窓が過ぎるまで 429 になる。Tailscale では端末ごとにアドレスが違う前提。
- **未認証の要求の本文を読まない**: 端末トークンを求める経路では、未認証の要求の本文を読まずに 401 を返す。宣言の長さがない（chunked）未認証の要求は、本文の大きさによらず 401 になる（413 より先に 401）。
- **形式の検査を経路の検査より先にする**: `api.ts` の注記に合わせた。認証した端末の要求は、自宅判定・接続範囲などより先に 422 になり得る。
- **自宅判定の既定**: B03-03 までは中枢と同じマシンの端末（hub_local）だけが通る。製品で B03-01 のまま使うと、他の端末は bootstrap も 403 になる（安全側）。
- **Origin の拒否のコード**: 契約の 403 の説明にある `forbidden` を使った。
- **接続数・頻度・時間の値**: 設計に数値がないため上の表の値にした。
- **Bootstrap の io_state と capabilities**: 正本（B03-04・B05）がないので安全側の値にした。`voice_state` は停止の値にできない（stop_scope が none）ため `waiting_wake_word` にしたが、入力は不可（input_permitted: false）。
- **中枢の画面の判定**: 端末の hub_local（登録時に決まる）だけで判定した。中枢のマシンの外から hub_local の端末のトークンで接続された場合を区別していない（B03-02 で見直す）。
- **TLS のセッションの再開**: TLS 1.3 のセッションチケットは既定のまま。再開した接続ではクライアントの `checkServerIdentity` が呼ばれないが、再開には中枢のチケットの鍵が要るため、別の中枢へは再開できない。
- **tests/test-map.json**: X04 の一部（古い接続範囲の 410・端末 ID の偽装）を模擬で確かめたが、X04 全体（同じ request_id の再送・内容違いの 409 を HTTP で）ではないので `product_test` は not_run のまま。

## B03-07 の変更（独立したセキュリティレビューの指摘、#75）

試験は 127.0.0.1 の模擬だけで、実機・Tailscale 上の接続は未実施。

- **M1 最初の要求までの期限**: 何も送らない TLS の接続が、Node の `headersTimeout` の確認の間隔（既定 30 秒）まで切れず、接続の枠（32 本）を約 30 秒占められた。TLS の確立（`secureConnection`）から最初の要求のヘッダーがそろうまでに `headersTimeoutMs`（10 秒）を過ぎた接続を、接続ごとの時計で応答せずに切るようにした。アイドルの時間切れ（`socket.setTimeout`）ではなく確立からの期限にしたのは、ヘッダーを少しずつ送り続ける接続も同じ時間で切るため。最初の要求・WSS の切り替えが届いたら時計を外し、その後は keep-alive の時間切れ（5 秒）と WSS の ping に任せる。TLS の確立までは従来どおり `handshakeTimeout`（10 秒）。認証前の要求は応答の後に接続を閉じるので、2 件目以降のヘッダーの遅延は認証した端末だけが起こせる（Node の確認の間隔は変えていない）
- **M2 待ち受けのアドレス**: 16 進の IPv4-mapped（`::ffff:0:0`・`0:0:0:0:0:ffff:0:0`）が全アドレスの拒否をすり抜けていた。domain の `listenAddressDecision`（`packages/domain/src/listen-address.ts`、Node の API を使わない）でアドレスを正規化してから、許可する範囲（ループバック 127.0.0.0/8・::1、Tailscale 100.64.0.0/10・fd7a:115c:a1e0::/48）を列挙して判定する形に変えた。zone（`%`）つきは拒否する。理由コードは `https_host_not_ip_address`・`https_host_unspecified`・`https_host_not_allowed`。待ち受けは正規化した形（IPv4-mapped は IPv4、IPv6 は RFC 5952 の形。`ApiServer.host` も同じ）
- **L1 認証した端末の頻度**: 認証前の要求だけを数えていたため、正しいトークンを持つ端末（乗っ取られた端末を含む）は bootstrap（接続範囲の発行で DB に書く）などを際限なく送れた。端末トークンで認証できた要求（WSS の切り替えを含む）を端末（device_id）ごとの固定の窓で数え、上限に達した端末は窓が過ぎるまで 429 `rate_limited`（接続を閉じる）にした。認証前の頻度（接続元ごと）とは別に数え、互いに影響しない。
  - **仮の値: 60 秒で 300 件（`deviceWindowMs`・`deviceMaxRequests`）**。設計に数値がない。正しい端末の通常の使い方は、再接続 1 回で bootstrap・スナップショット・イベントの数ページ・購読の切り替えの数件、自宅の指紋の報告は数分に 1 件、WSS の ping は HTTP の要求ではないので数えない。起動直後のまとまった読み込みや短い間の再接続の繰り返し（1 分に 10 回の再接続で約 50 件）にも十分な余裕を残し、DB へ書く要求を 1 台あたり平均で毎秒 5 件までに抑える。実際の端末（B03-05）の要求の数を見て見直す。
  - 経路の検査順の試験（`api-route-order.test.ts`）は同じ端末で約 400 件を送るので、試験の間だけ上限を上げた（認証前の頻度と同じ扱い）。
