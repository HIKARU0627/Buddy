# ADR 0026: 中枢の画面の端末で申請の承認と端末の失効を行う

- 日付: 2026-10-21
- 状態: B03-06（#74）の判断と実装。2 台目以降の端末の申請の承認・拒否と、端末の一覧・失効を、中枢の画面の端末（hub_screen）の HeroUI の画面で行えるようにした。中枢に承認待ちの申請の一覧の経路を足した。試験は模擬（CI の 3 OS）。実機（Mac mini・Tailscale・別のマシン）は未実施で、手順は [docs/b03/device-check.md](../b03/device-check.md) の D・E。
- 根拠: 本人の判断（2026-10-21、PR #73 のレビューの後）「2 台目以降の承認・失効は中枢の画面の UI で行う（CLI は作らない）」（ADR 0025 の「本人の承認」）。その後の本人の判断で、端末の一覧と失効だけはローカルの制御チャネルの CLI（`buddy-core device list`・`device revoke`）でも行える（1 台目の受取りが失敗したときの復旧の手段。承認はできない。ADR 0021 の追記）。画面の約束は ADR 0024（UI レビュー 1 回目の後の骨格と約束）。

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 申請の一覧の経路     | `GET /v1/pairing/claims`（`listPairingClaims`）。経路の検査は `device_token`・`home_network`・`unlocked`・`hub_screen`（domain の `ROUTE_CHECKS`）。返すのは承認待ちの申請の claim_id・端末名・OS・申請と期限の時刻・確認コードだけで、申請用の秘密・その hash・コードは返さない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 確認コード           | `SHA-256("buddy/pairing-claim-check/v1\0" + claim_secret_hash の 16 進)` の先頭 8 桁。中枢（storage の `pairingClaimCheck`）と端末（申請した main）がそれぞれ求め、両方の画面に出す。本人は同じ確認コードの申請だけを承認する（同じ時刻に来た別の申請を取り違えない）。申請用の秘密そのものは出さない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 画面を出す端末       | main が中枢に一覧の経路を問い合わせ、200 なら中枢の画面の端末（`DesktopConnectionView.hub_screen = true`）、403 `hub_screen_required` なら違う、と決める。判定は中枢（ADR 0021 の hub_local・同じマシン）が持ち、画面・main は推測しない。違う端末には Tabs・一覧・ボタンを出さない。決まらなかったとき（送れない・結果不明・503・429・形の違う 200）は 2・4・6 秒後に問い合わせ直し（最大 3 回、接続し直すと数え直す。接続が変わったら古い結果を捨てる。CR-L1）                                                                                                                                                                                                                                                                                                                                     |
| IPC                  | `desktop.claims_list`・`desktop.claim_decide { ref, decision }`・`desktop.devices_list`・`desktop.device_revoke { ref }`・`desktop.pairing_open`。一覧はロック解除済み、承認・拒否・失効・ペアリングの開始は画面操作（ADR 0014 の再開と同じ判定）。main は中枢へ `scoped`・画面操作の要求として送る                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 参照（ref）          | 画面に申請 ID・端末 ID を渡さない。main が一覧ごとに不透明な UUID の参照を作り、ID との対応を main だけが持つ。同じ申請・端末には一覧を取り直しても同じ参照を使う（確認を開いている間の取り直しで参照が古くならない）。一覧から消えたもの・切断で対応を捨てる。知らない参照は `entry_not_found` で拒否する                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 重い操作の確認       | **本人の判断（2026-10-22、Codex のレビューの High の後）**: 承認・拒否・失効の確認は、画面の中のダイアログではなく、main が OS の確認ダイアログ（親ウィンドウ付きの非同期の `dialog.showMessageBox`）で行う。画面（renderer）が侵害されても、本人の確認なしには送れないようにするため。表示する端末名・OS・申請の時刻・確認コードは main が中枢から受け取った一覧の値で、制御文字・書字方向の制御文字を取り除く（自己申告の値なので、確認コードの見比べを求める文を必ず入れる）。「やめる」を既定・取り消しにし、同時に表示するのは 1 つまで（2 つ目は `confirmation_pending`）。ロック・切断・接続のやり直しで AbortSignal により閉じ、送らない。確かめたときだけ POST する（「やめる」は `confirmation_declined`）。確認の部品は注入し、試験は模擬で確かめる。停止（ADR 0014）だけは確認を挟まない |
| 操作の結果           | 承認・拒否・失効ができたら、欄の先頭に知らせ（`role="status"`）を出す。失敗は押した行の下（`role="alert"`）。どちらもタブの切り替え・「一覧を更新」・次の操作で消す（UI レビュー 3 回目 R1-M1）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 結果が分からないとき | 承認・拒否・失効の要求の結果が分からない（送った後に切れた）ときは `outcome_unknown` を返し、自動で再送しない。参照は残し、本人が「一覧を更新」で確かめてから押し直せる。適用はできたが、その後の一覧の取り直しだけが失敗したときは、拒否にせず `list_refreshed: false` の ok を返す（画面は前の一覧からその行を除き、「〜を承認しました。一覧を更新できなかったため、…」と出す。コードレビュー CR-L2）                                                                                                                                                                                                                                                                                                                                                                                              |
| 表示の権限の世代     | main は、ロック・切断・接続のやり直しで世代を進め、管理の入口の応答を返すときにも照合する。ロックをまたいだ一覧・ワンタイムコードは返さない（`device_locked`・`not_connected`）。画面も世代（ロック・中枢の画面でなくなったとき）をまたいだ応答を捨てる（Codex のレビュー Medium 1）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 一覧の要求の順       | main と画面の両方で、一覧の要求に通し番号を付け、後から始めた一覧・変更の操作（承認・拒否・失効）に追い越された古い一覧では、表示も参照の対応表も戻さない（main は `list_superseded` で返し、画面は何も出さない。Codex のレビュー Medium 2）。結果が分からなかった参照は、一覧を更新するまで操作させない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 一覧の更新           | 中枢は新しい申請を知らせないため、画面は承認待ちの申請を 3 秒ごとに取り直す（`CLAIMS_REFRESH_MS`）。端末の一覧は「一覧を更新」と操作の後に取り直す。操作の結果の文言は押した行のすぐ下に出し、タブの切り替えと「一覧を更新」で消す（定期の取り直しでは消さない）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| コードの表示         | ペアリングの開始の応答（`desktop.pairing_open`）にだけワンタイムコードと指紋を入れ、ログ・他の応答には出さない。指紋は端末の画面・CLI と同じ 4 桁区切り・4 行で、最後の組（端末に入力してもらう 4 桁）に下線を引く。期限が切れた・申請に使われた（コードを出した後の申請が届いた。コードは 1 回だけ使える）コードは表示に残さない（CR-L6）                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 端末で入力する宛先   | ペアリングの開始の応答（Core の `PairingSession`・画面の `DesktopPairingSession`）に `hub_endpoint`（中枢の HTTPS の待ち受けのアドレスとポート。Core の設定の値で、待ち受けは具体的な IP アドレス）を足し、中枢の画面の「新しい端末を登録する」に出す。登録する端末の「中枢の宛先」「ポート」に入れる値を、別の手段で調べなくてよい（UI レビュー 3 回目 R1-M2）                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 接続を待つ間         | 前に中枢の画面と確かめた端末は、接続が切れても画面がタブと最後の一覧を残し、操作を止めて「中枢との接続を待っています」と出す。判定の正本は main で、接続していない間の `hub_screen` は false のまま（契約の意味検査 `hub_screen_without_connection`）。画面の前の確認は表示だけに使う（UI レビュー 3 回目 R1-M5）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 失効の経路           | 失効（`revokeDevice`）を中枢の画面だけに限る変更（`hub_screen` を経路の検査に足す）は、本人の判断で別の Issue（#75）で行う。このブランチでは `ROUTE_CHECKS` の失効を変えない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## 画面

中枢の画面の端末では、端末の画面（ADR 0024 の骨格）の本体を Tabs にする。状態帯・停止・フッターは他の画面と同じ。

| タブ                 | 内容                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 端末の登録（申請 n） | 申請の一覧（端末名・OS・確認コード（大きな等幅）・申請の時刻・期限と残り時間、承認する・拒否する）と、「新しい端末を登録する」（ペアリングを始める・コードを出し直す。端末で入力する宛先とポート・コード・期限と残り時間・指紋の 4 × 4 の格子）。申請が 1 件以上あるときは申請の一覧を先に置き、「ペアリングを始める」を primary にしない。件数をタブに出す（UI レビュー 3 回目でタブの名前を中身に合わせた） |
| 登録済みの端末       | 端末名・状態（中枢（このマシン）・有効・失効済み（○・muted））・OS・中枢と同じマシンか・登録（日付つき）・最終接続または失効の時刻。失効は他の有効な端末だけに出す                                                                                                                                                                                                                                            |
| このマシンの接続     | 中枢との接続の欄（ADR 0025）。「この端末」は登録する側の端末の案内と取り違えるため、タブの名前を変えた（UI レビュー 2 回目 R1-M6）                                                                                                                                                                                                                                                                            |

## 読み取り（レビュー対象）

- **一覧の取り直しの間隔**: 3 秒。中枢から申請の通知を配る経路を足すより小さな変更で、申請は 5 分で切れるため。配信（ADR 0023）に申請のイベントを足すかは後続で判断する。
- **確認コードの長さ**: 8 桁（32 ビット）。同じ時刻に来た申請の取り違えを防ぐためのもので、秘密ではない（申請用の秘密の hash から求めるため、秘密は推測できない）。
- **一覧の経路の lock 状態**: 一覧も `unlocked` を求める（端末名が出るため）。
- **中枢の画面かの判定のやり直し**: 接続のたび・ロックを解いたとき・経路が 403 `hub_screen_required` を返したときに問い合わせ直す。

## 残ること

- 実機の確認（device-check の D・E）。
- 失効を中枢の画面だけに限る経路の変更（#75）。
- 自宅の登録の UI。
