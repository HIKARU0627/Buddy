# ADR 0042: B07 の付帯クレジットの区分と保留（MA03〜MA06）

- 日付: 2026-10-24
- 状態: B07-07（#116）の判断と実装。domain の純粋な規則（`budget-credit.ts`）、契約の追加（設定の `credit`・残高の観測の一覧・予算保留の `credit_hold`）、DB worker の予算の命令の変更（受付の保留・精算の区分・周期の台帳）、Core の予算の門と観測ファイルの読み込み、手での精算の区分の受け付け、模擬の試験。**マイグレーションは足していない**（既存の予約の列で足りる。0008 は B06 の予定のまま）。模擬の試験だけで、実 API・実請求・Console の実残高との照合・実機は未実施。残高を取得する公式の手段が決まるまで、観測は本人がファイルに書く。
- 根拠: 設計 05（モデル再選定 A 案と Claude Max の付帯クレジットの追補）、09（MA03〜MA06）、決定事項 D16、ADR 0002・0006・0034〜0037・0039、本人の判断（2026-10-23、#12 のコメント）。原本は権限のある接続で読み取りだけ行い、全文は写していない。原本に決めがないことは「原本に決めなし」と書く。ADR 0006・0034〜0037・0039 で決めたことは変えていない（予約の `credit_applied`・`additional_spend`・`credit_cycle_id` は ADR 0034 の契約の列のまま、中身の決め方を足した）。

## 原本の決め（要約）

| 対象                 | 原本の決め                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 区分                 | 通常料金の利用額・付帯クレジットの消費・クレジット適用後の支出を分ける（設計担当判断）                                                                             |
| 上限                 | 既存の R と M は通常料金で確保し、枠（LLM・会話の保護・検索・音声・影モード）の停止条件は維持する。クレジットがあるから費用 0 として無制限に実行する設計にはしない |
| 周期と予算月         | クレジットの請求周期と Buddy の予算月は別に管理する。予算月の更新で残高を 100 ドルに戻さない。未使用分は周期末に失効して繰り越さない                               |
| 不明・失効・枯渇     | 購入クレジットや後払いへ自動で移さず、Buddy 側で Claude の処理を保留する。購入残高があると provider 側は処理を続けるので、エラーを待つだけの設計は不可             |
| 共有の組織           | 同じ組織の他用途と残高を共有する。専用 workspace の上限と Core の上限を併用し、利用額を照合できなければクレジット充当を確定表示しない。専有できるとは主張しない    |
| 対象外               | 音声・Luna・検索にクレジットは充てない。本文・応答の実料金が不明なものを 0 円と確定しない                                                                          |
| 取得手段             | 残高を取得する非公開の API を推測して実装しない。導入時に公式の取得手段を確認する                                                                                  |
| 実残高の照合（MA06） | Console の実残高との照合は、模擬試験とは別の証拠にする                                                                                                             |

## 判断が要る点

1. **観測を本人がファイルへ書く方式**: 残高を取得する公式の手段が決まるまでの暫定。本人が書き忘れると Claude の処理は保留になる（閉じた側）。書き方の補助（CLI）や、公式の取得手段が決まった後の自動の取得は、導入時に決める。
2. **M の全額が残りに収まるときだけ受け付ける**: 残りが M に少し足りないだけの要求も保留する（購入残高へ移らないための保守的な規則）。要求ごとの M を小さくするか、M の見積もりを下げる必要がある。許容するなら、足りない分の扱い（保留のまま／追加の支出として別の承認）を決める。
3. **周期が終わった後の精算はクレジット 0**: 周期の終わりの直前に受け付けて、終わりの後に usage が届いた分は、クレジットで賄えたか確認できないので追加の支出として記録する（実費を多く見せる側）。請求の照合（B15）で確定する。クレジット側の失効の扱い（使った時刻が周期内なら充てる）を採るなら、usage に使った時刻を持たせる必要がある。
4. **共有の組織の古さの上限は設定の値**: 長くすると他の用途の消費を見逃しやすく、短くすると本人が頻繁に観測を書く必要がある。
5. **台帳は保守的な二重計上を含む**: 観測より前に受け付けて観測の後に精算した予約は、観測した残高に含まれていても引く。クレジットを少なく見積もる側なので、保留は増えても過大な充当はしない。
6. **周期の固定の trigger がない**: マイグレーションを足さない代わりに、受付で書いた周期を精算まで変えない保証はコードだけ。B06 のマイグレーションが入った後で足す（下の残ること）。

## 残ること

- 残高を取得する公式の手段の確認と、観測の自動の取得（導入時）。観測を書く CLI。
- `credit_cycle_id` を受付から精算まで固定する trigger・クレジットが正の行は周期ありを確かめる trigger・周期の列の索引（次のマイグレーションで。B06 の 0008 が入った後）。
- 利用状況（`BudgetUsageSummary`）・画面へのクレジットの表示（キャンバス UI。本人の判断）と、手での精算の入力欄（クレジット・周期）。
- 実請求との照合と Console の実残高の確認（B15。MA06 の別の証拠）。アダプター（B05・B10）が有料の要求を門へ渡すときに、profile の ID・サービスを正しく渡すこと（クレジットを充てる profile の指定は設定で、要求の申告に頼らない）。
- 課金が一定のブロック単位の provider（ADR 0035）は表せないまま。
