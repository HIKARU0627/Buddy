# ADR 0177: レシートの写真からの家計の記録の候補（家計簿 段階 3 の一部）

- 日付: 2026-11-26
- 状態: 家計簿の段階 3 の部分。メールの届かない支出を、レシートの写真 1 枚から補う。本人が家計簿の欄で外部への送信を入にしたときだけ、本人が選んだ写真を、その都度の画面操作で外部のモデルの画像の読み取りへ送り、手入力の欄（ADR 0167）に入れる値の候補を返すところまでを作った。記録を作るのは、本人が入力欄で中身を確かめて「足す」を押したときだけ。**模擬の試験だけ**で、実 API・実機・実在のレシートは未実施。外部のモデルの読み取りの口（provider の実装と profile）はまだなく（U368）、製品の起動では設定が「使えない（unavailable）」のまま。
- 根拠: 本人の決定（段階 3: メールの届かない支出をレシートの写真から補い、本人の手間を減らす。画像を外部へ送るかは本人の判断が要るので、既定は切・本人が明示的に入にしたときだけ・その都度の操作で一枚だけ、という暫定の判断で作る）、AGENTS.md（LLM は記録の正本にならない。保存・承認・忘却・予算・世代の最終ガードを省略しない。結果不明の外部変更を自動で再送しない）、ADR 0037・0038・0053・0070・0158・0164・0167・0171。原本（非公開 Notion）に家計簿の決めはない（U318 以降と同じ）。
- 対象: `packages/domain/src/household-receipt.ts`（画像の検査・応答の読み直し）・`household.ts`（`householdHasLongDigits`）・`desktop.ts`（チャネルと停止中の拒否）・`api.ts`（経路の検査）、`packages/contracts`（JSON Schema・OpenAPI・生成型・fixture）、`apps/core/src/household-receipt.ts`（経路と予算の門への口）・`api-household.ts`・`api-routes.ts`・`budget-gate.ts`（送る直前の単価の版と token の実費）・`core.ts`（配線）、`apps/desktop`（`household-bridge.ts`・`core-link.ts`・`electron/main.ts`・preload・renderer の `state/household-receipt.ts`・`household-state.ts`・`screens/household/HouseholdPanel.tsx`）。マイグレーションは足していない。

## 背景

手入力（ADR 0167）と会話の一言（ADR 0171・0174）で現金の支出を足せるが、レシートの金額・日付・店名を本人が読み取って入れる手間が残る。写真から読むには、端末の中で文字を読む仕組みがないので、外部のモデルの画像の読み取りへ写真を送る必要がある。写真には店名・金額・品目が写り、外部の提供元へ渡る。外部への送信は本人の判断が要る事柄で、原本にも決めがない。

既存の仕組みを調べた結果は次のとおり。

| 対象                     | 分かったこと                                                                                                                                                                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LLM の呼び出しの口       | `packages/ai` の `LlmAdapter.complete(ModelCommand)` は文字の `messages` だけで、画像を送る形がない。結果は `AdapterResult`（応答・timeout・利用不可・中断と、分かる範囲の usage）。1 回の呼び出しで送るのは 1 回だけで、自動で送り直さない（ADR 0070・0080） |
| 意図の判定・メールの抽出 | `model-interpreter.ts`・`mail-extraction.ts` は `ModelCallGuard`（受付 → 送る → 精算・解放）の口を通すが、製品の配線ではまだ模擬の解釈で、予算の門（`BudgetGate`）にはつないでいない                                                                          |
| 予算の門                 | `BudgetGate.run` が受付（予約 R・最大負担 M）・送出意図・期限・中断・精算・usage 不明の保持をまとめる。送る関数は一度だけ呼び、usage が分からなければ予約を保持する。会話（Live）は `live-budget.ts` でこの門につないでいる                                   |
| 外部への送信の同意       | 音声の同意（`ExternalSendConsent`、ADR 0038）は中枢が正本だが、中枢へ同意を送る経路は未実装で、既定は missing（開かない側）。端末は OS の確認ダイアログで 1 回だけ同意を取る（ADR 0050）                                                                      |
| 保存期限の掃除の門       | 外部へ送る前に、掃除が済んで `cloud_send` が開いていることを確かめ、貸し出しを取る（ADR 0053。予定の照会・下書き・ラベル・調査・Live）                                                                                                                        |
| 経路の検査               | `ROUTE_CHECKS` の画面操作（端末トークン・自宅判定・接続範囲・ロック解除・画面操作）。要求の本文の上限は 256 KiB（`MAX_CONTROL_JSON_BYTES`）                                                                                                                   |
| 端末のファイル           | 書き出しの取り込み（ADR 0164）は main が OS のファイル選択で選ばせ、画面へはパスも中身も渡さない。main は世代（ロック・切断）を await の後に照合する                                                                                                          |
| `ExtractionResult` v2    | 同期したメールからの抽出の形で、写真には使わない                                                                                                                                                                                                              |

## 決めたこと

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 送るかどうか         | 既定は切（送らない）。本人が家計簿の欄の「送る設定にする」を押し、main の OS の確認ダイアログで「送る設定にする」を選んだときだけ入にする（「やめる」が既定）。入のあいだも、送るのは本人が「写真を選んで読む」を押し、OS のファイル選択で選んだ写真 1 枚だけで、その都度の画面操作に限る（U363）                                                                                                                                                                                                |
| 設定の置き場所       | 中枢のメモリーにだけ持ち、中枢を起動し直すと切に戻る。家計簿の月ごとの合計（`GET /v1/household/months`）の `receipt_reading` で今の値（on・off・unavailable）を返す。変更は `POST /v1/household/receipt-setting`（本人の画面操作）で、望む値をそのまま送る（今と同じなら変えない）。切にすると、送っている途中の読み取りを止める（U364）                                                                                                                                                         |
| 読み取りの口         | 中枢の起動の設定で渡す `ReceiptImageReader`（`read(command, cancellation) → AdapterResult`。`LlmAdapter` と同じく 1 回の呼び出しで 1 回だけ送り、自動で送り直さない）と profile。出力の上限（`output_limit_tokens`）が決まっていない profile は使わない。口がなければ設定は unavailable で、入にもできない。provider の実装は作っていない（U368）                                                                                                                                                |
| 画像の検査（端末）   | main は選ばれたファイルを 20 MiB まで読み（超えたら読まない）、開く前に頭のバイト列から形式（JPEG・PNG）と縦横（1 辺 12,000・5,000 万画素まで、短い辺 64 以上）を確かめる。開いた写真を長い辺 1280（収まらなければ 1024）に縮め、品質を下げながら JPEG にし直し、180 KiB に収まったものだけを送る。JPEG にし直すことで、撮影の位置などの付帯情報を送らない（U365）                                                                                                                               |
| 画像の検査（中枢）   | 受け取った画像を、JPEG・180 KiB まで・長い辺 1600 まで・短い辺 64 以上で確かめ直し、合わなければ 422 で送らない（端末の検査を信用しない）                                                                                                                                                                                                                                                                                                                                                        |
| 送る前の最終の確かめ | 中枢は次の順に確かめ、どれかが合わなければ送らない: 読み取りの口がある → 設定が入（でなければ 403 `external_send_consent_required`）→ 同じ `request_id` を前に受け付けていない・読み取り中の二つ目でない（409）→ 画像の検査（422）→ 本人のタイムゾーンで今日が決まる（503）→ 保存期限の掃除の門（`cloud_send` と貸し出し。503）→ 待ちの後に設定をもう一度（403）→ 予算の門（`BudgetGate.run`）。経路の検査（端末トークン・自宅判定・接続範囲・ロック解除・画面操作）はその前に api-server が行う |
| 予算                 | 本人の依頼（`owner_request`）の LLM の枠へ計上する。予約の量は、入力が設定の `max_input_tokens`（指示文と画像 1 枚の上限）、出力が profile の上限。予算を予約できなければ 422 `budget_held` で送らない。usage は予約に固定した単価の版で実費にし（`BudgetGate.modelUsageAmount`。ai の `planUsageSettlement`）、usage がない・不完全なら 0 円にせず予約を保持する（U367）                                                                                                                        |
| 結果不明             | 送ったか・応答が届いたか分からない（timeout・利用不可・読み取りの口の例外・中断）は 503 にし、自動では送り直さない。同じ `request_id` はもう受け付けない（中枢は 1,024 件まで覚える）。端末は要求ごとに新しい `request_id` を付けるので、本人がもう一度押せば新しい読み取りになる（予算をもう一度使う）                                                                                                                                                                                          |
| 応答の読み直し       | 外部の応答は信用しない入力として扱う。断った（refused）・打ち切られた（truncated）・厳格な JSON でない（重複したキーを含む）なら候補にしない。決まった形（`readable`・`receipt_count`・`currency`・`total`・`date`・`time`・`merchant`・`payment`・`items` だけ）を確かめ、domain の `readHouseholdReceiptReply` で家計の記録の検査（`householdContentErrors`）をし直す（U366）                                                                                                                  |
| 候補にしない結果     | 読めない（`readable` が false・枚数 0）、レシートが二枚以上、通貨が JPY でない（外貨・不明）、合計がない・0 以下・上限（9,999,999,999 円）を超える、品目の金額の和が合計と 1 円でも違う、店名・支払い手段・品目名のどこかに 12 桁以上の数字の並び（カード番号・口座番号らしいもの。区切りのハイフン・空白と全角の数字も数える）、形の違い（U366）                                                                                                                                                |
| 候補の中身           | 金額（合計）・日付・時刻・店名・支払い手段だけ。向きは支出、分類は未分類（中枢が店名の規則を当てる）。日付が読めない・今日より後なら空、時刻・店名・支払い手段も記録の検査に合わなければ空にする。品目は合計との突き合わせにだけ使い、候補に入れない（端末へ返さず、メモにも入れない）                                                                                                                                                                                                           |
| 保存しないこと       | 中枢は画像も応答も保存せず、ログ・診断へも出さない。受け取った画像のバイト列は処理の終わりに 0 で埋める。端末の main は、選んだ写真と縮めた画像を、送った後・送らなかったときとも 0 で埋めて捨て、一時ファイルを作らない。候補は main に持たず、画面のメモリーにだけ置く（閉じる・入力欄で開く・ロック・切断で捨てる）。base64 の文字列は 0 で埋められないので、参照を手放して捨てる                                                                                                             |
| 端末の経路           | IPC の `desktop.household_receipt_setting`（入・切。入にするときは OS の確認ダイアログ）と `desktop.household_receipt_read`（写真を選んで読む。payload なし）。どちらもロック解除済み・前面の画面操作で、読み取りは入出力の停止中は受け付けない（`input_stopped`。domain の `DESKTOP_EXTERNAL_SEND_CHANNELS`）。写真を選ぶ間・縮める間にロック・停止・切断があれば送らない。送っている間にロック・切断したら結果を渡さず、結果不明にする。標準の窓だけで、キャンバス・入力バーは使えない         |
| 確定                 | 候補の欄の「家計簿の入力欄で開く」で、手入力の欄に値を入れて開く（本人が入れている途中の欄があれば開かない。同じ候補から二度開かない）。欄の頭に「レシートの写真から読んだ値を入れました。まだ記録していません。…」。記録は本人が「足す」を押したときだけ、既存の `desktop.household_add`（`POST /v1/household/entries`、出所 `manual`）で作る。読み取りの結果をそのまま記録にする経路は作らない                                                                                                 |
| 同意の記録           | 入にするときの OS の確認だけで、外部への送信の同意の記録（`ExternalSendConsent`、ADR 0038）には書かない。中枢を起動し直すと切に戻るので、入にするたびに確かめを出す（U369）                                                                                                                                                                                                                                                                                                                      |

## 退けた案

| 案                                                               | 退けた理由                                                                                                                                                                           |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 端末の main が外部のモデルへ直接送る                             | 予算の門・保存期限の掃除の門・provider の資格情報は中枢にある。端末から送ると、予算の予約・精算と usage 不明の保持を通らない                                                         |
| 読み取りの結果をそのまま記録にする（確かめの画面だけ出す）       | LLM を記録の正本にしない境界に反する。会話の一言（ADR 0171）と同じく、手入力の経路（本人の画面操作と `request_id`）だけで作る                                                        |
| 写真・読み取りの結果を暗号化して保存し、後から見直せるようにする | 保存する理由がない（候補は入力欄に入れるまでの値）。保存すれば忘却・期限・バックアップの扱いが増え、写真という大きな個人の情報を中枢に残す。必要になれば `sealed_blobs` で別に決める |
| 設定を家計簿の設定の表（`household_settings`）に足して保存する   | 列を足すマイグレーションが要る（この作業ではマイグレーションを足さない）。切に戻る側は安全側で、起動し直したときに入にし直す手間だけが残る（U364 の (b)）                            |
| 品目を候補（メモ）に入れる                                       | 端末へ返す情報が増える。品目名は読み違いが多く、記録の検査（長さ・数字の並び）にも当たりやすい。今は合計との突き合わせにだけ使う                                                     |
| 合計と品目の和が違うときに、合計だけで候補にする                 | 合計か品目のどちらかを読み違えた可能性がある。どちらが正しいか決められないので、候補にせず本人に入れてもらう（U366）                                                                 |
| 縮めずに元の写真を送る                                           | スマートフォンの写真は数 MB あり、中枢への要求の本文の上限（256 KiB）を超える。撮影の位置などの付帯情報も送ってしまう                                                                |
| HEIC を受ける                                                    | Electron の `nativeImage` が OS によって開けない。今は JPEG・PNG だけにして、HEIC は JPEG に書き出してから選んでもらう（U365）                                                       |

## 原本に決めがない項目

- U363: レシートの写真を外部のモデルへ送るか（既定は切・本人が入にしたときだけ・その都度の操作で一枚だけ）。
- U364: 設定の置き場所（中枢のメモリーだけ。起動し直すと切）。→ ADR 0179 で、家計簿の設定の表に保存する形に変えた。
- U365: 選ぶファイルと送る画像の形式・大きさの上限。
- U366: 読み取りの結果を候補にする条件（円の合計・品目の和・一枚・長い数字の並び・日付）と、品目を候補に入れないこと。
- U367: 予算の枠と予約の量、usage が分からないときの扱い。
- U368: 読み取りの provider と profile（未実装）。
- U369: 入にするときの同意の記録と、設定を端末ごとにしないこと。
- U370: 長い数字の並びの広い区切りと向きを変える制御文字の拒否を、レシートの応答だけにするか、家計の記録全体へ広げるか（追補で追加）。

## 対象外

- 読み取りの provider の実装（画像を送る codec・構造化出力の形・画像の token の数え方）と、製品の起動での配線（U368）。
- 写真の EXIF の向き（回転）の補正、HEIC、複数の写真・長いレシートの分割、品目ごとの記録、分類の推定。
- 端末の中での文字の読み取り（ローカルのモデル）。
- 突き合わせによる二重の登録の防止（段階 3 の残り）。

### 1. 端末が待つのをやめた後・ロックした後に送らない（高）

### 2. カード番号の区切りの種類（中）

直す前は、長い数字の並びの検査（`householdHasLongDigits`）が区切りとして空白・`-`・`－` しか数えず、`4111.1111.1111.1111`・`4111/1111/…`・`4111−1111…`（U+2212）・`4111‐1111…`（U+2010）・`4111ー1111…`（長音記号）・`4111*1111…` が候補として返っていた。

レシートの読み取りの応答の検査（`readHouseholdReceiptReply`）では、domain の `receiptHasLongDigits` で確かめる。NFKC にそろえた後、数字と数字の間の記号・句読点・空白（`\p{P}`・`\p{S}`・`\p{Z}`・`\s`）、書式の文字（幅のない空白など。`\p{Cf}`）、結合の文字（`\p{M}`）、長音記号（ー・ｰ）をすべて区切りとして数え、12 桁以上の並びがあれば候補にしない。日付と時刻（「2030/11/25 12:34」）も 12 桁になるので候補にしないが、本人が手で入れられる。

手入力・会話の一言・取り込みなど、家計の記録全体の検査（`householdContentErrors`）には広げていない。広げると、本人のメモの「2030/11/25 12:34」のような日付と時刻（12 桁）が拒まれる（U342 で、すでに「2026-11-26 1230」が拒まれることを記録している）。広げるかどうかは U370 に記録した。

再見直しで確かめられた点を直した。この追補は、上の追補の該当の項（1. の送り始めるまでの期限の数え始め、3. の読み取りの口が返らないときの扱い、4. の付帯情報の検査の範囲、5. の `not_sent` の説明）より優先する。試験はすべて模擬で、実 API・実機・実在のレシートは未実施のまま。

### 1. 返らない読み取りの口で保存期限の門が閉じたままになる（中）

直す前は、予算の門が期限（受付から `profile.timeout_ms`）で 503 を返しても、画像を 0 で埋める・掃除の貸し出しを返す・読み取り中の印（`inFlight`）を外す処理は、読み取りの口の Promise が終わるまで呼ばれなかった。中断に応じず返らない口だと、中枢を起動し直すまで、以降の読み取りが 409 になり、画像が 0 で埋められず、貸し出しが返らなかった。貸し出し中に始まった定期の掃除は貸し出しの返却を待つ（`RetentionSweeper` の `#waitForLeases`）ので、その間は保存期限の門（`cloud_send`）が閉じたままになり、検索・クラウドへの送信・自動利用のすべてが止まり、期限切れの削除も進まなかった。

| 対象             | 決定                                                                                                                                                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 待つ上限         | 送り始めてから `profile.timeout_ms` + 5 秒（domain の `RECEIPT_READER_RETURN_GRACE_MS`）。予算の門の期限は受付から `profile.timeout_ms` で、受付は送り始める前なので、上限は予算の門の期限に 5 秒以上を足した時刻になる                                                     |
| 強制する層       | 読み取りの口を包む層（`readWithin`）。上限を過ぎても返らない口を時間切れ（`timeout`。usage は分からない）として扱い、後から返った結果は捨てる。予算の門が後ろで待つ送信（遅れて届いた usage の精算）もこの時点で終わる。予約は usage 不明のまま残り、本人の手での精算に回る |
| 上限を過ぎたとき | 中身を出さない記録（理由の名前 `reader_not_returned` だけ）を出し、画像のバイト列を 0 で埋め、掃除の貸し出しを返し、読み取り中の印を外して次の読み取りを受ける                                                                                                              |
| 画像のバイト列   | 読み取りの口がまだ参照している可能性があっても、上限の時点で 0 で埋める（推奨の案）。その後に口が外部へ送る内容は壊れるが、結果は捨てるので構わない。埋めずに参照を手放す案は、口が参照を持ち続ける間、画像がメモリーに残るので退けた                                       |

`ReceiptImageReader` の約束（中断されたらすぐに送るのをやめて返す）は残す。上限は約束を守らない実装への備えで、上限までは画像を埋めず貸し出しも返さない（約束を守る口では動きは変わらない）。上の追補の 3. の「掃除が止まる（実装の約束で防ぐ）」は、この上限で置き換えた。上限までの間は、返らない口が貸し出しを持つので、定期の掃除が本体に入らず保存期限の門が閉じ、レシートの読み取りだけでなく、検索・クラウドへの送信・自動利用のすべての外部への送出が止まり、期限切れの削除も進まない。この状態は、送り始めてから最長で 65 秒（`profile.timeout_ms` の上限 60 秒 + 5 秒）に限られる。

### 2. 付帯情報の検査の範囲（低〜中）

直す前の `receiptJpegHasMetadata` は、最初の走査の始まり（SOS）で判定をやめていた。走査と走査の間（プログレッシブ JPEG）にある APP1、画像の終わり（EOI）の後ろに付いた APP1 を持つ 2 枚目の JPEG（MPF などの形）、COM・APP11（JUMBF）を通し、そのまま外部へ送っていた。

| 対象         | 決定                                                                                                                                                                                                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| たどる範囲   | SOI から EOI まで。走査の後の符号化されたデータは、詰めの 0x00（FF 00）・RST（FF D0〜FF D7）・埋めの 0xFF を飛ばしてたどり、次の区切りから続ける                                                                                       |
| 拒む区切り   | APP1・APP13（これまでどおり）に、APP11（JUMBF など）と COM（コメント）を足した（外部へ送らない側）。どれも main の JPEG のし直しでは付かないはずのもので、撮影・編集の記録を持ちうる。APP0（JFIF）・APP2（色の情報）・APP14 などは送る |
| EOI の後ろ   | バイトが一つでもあれば送らない（`image_metadata_present`）。main の JPEG のし直しでは付かない                                                                                                                                          |
| 読めないとき | 走査がない・EOI がない・区切りの長さが 2 未満か末尾を超える・二つ目の SOI は `image_unreadable`                                                                                                                                        |

端末の main（JPEG にし直した後）と中枢（422）の両方が同じ検査（`receiptSendImageErrors`）を使う。契約の説明（`DesktopHouseholdReceiptView` の画像の理由・OpenAPI の読み取りの経路）も合わせた。

### 3. 名前付きパイプを選ぶと止まる（低）

直す前は、開いてから fstat していたので、拡張子が .jpg の名前付きパイプ（FIFO）を選ぶと、open が書き手が現れるまで返らなかった（その前のコードは stat で `isFile()` を先に確かめていたので、後退だった）。`apps/desktop/src/main/receipt-image-file.ts` を次のようにした。

- 開く前に stat（`bigint`）でふつうのファイルかを確かめ、そうでなければ開かない（`unreadable`）。
- 開いた後の fstat で、開く前の stat と `dev`・`ino` が同じかを確かめ、違えば読まない（`unreadable`）。
- POSIX では `O_NONBLOCK` で開き、確かめた後に名前付きパイプへ差し替わっても open で止まらない（ふつうのファイルの読み方は変わらない）。Windows では付けない。

### 4. 端末の時間切れと中枢の期限の関係を固定する（低）

| 対象                           | 決定                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 送り始めるまでの期限の数え始め | 経路の処理を始めた時刻から、要求が届いた時刻（api-server が要求を受けた時刻。本文を読む前）に改めた。`ApiHandlerRequest` に `receivedAt`（単調時計のミリ秒）を足し、`abortOnCloseRoutes` に挙げた経路（読み取りだけ）にだけ付ける。ほかの経路の要求には付けず、動きを変えない。本文の受け取り・端末トークンの照合・経路の検査も 10 秒に含む                         |
| 確かめる間隔                   | `ApiLimits` に `connectionsCheckingIntervalMs`（30 秒。Node の既定と同じ値）を足し、`createServer` の `connectionsCheckingInterval` に明示した。既定の動きは変えない                                                                                                                                                                                                |
| 関係                           | 要求が届くまで（`requestTimeout` 15 秒 + 確かめる間隔 30 秒）+ 送り始めるまで 10 秒 + 読み取りの期限の上限 60 秒 + 返らない口を待つ猶予 5 秒 = 120 秒 < 端末の 150 秒。domain の `receiptHubWorstCaseMs`・`receiptTimingFits` で計算し、試験は `DEFAULT_API_LIMITS` の値から確かめる                                                                                |
| 上書きとの関係                 | `core.ts` の `https.limits` で `requestTimeoutMs`・`connectionsCheckingIntervalMs` を上書きできる。上書きで関係が破れる（和が 150 秒以上、または `requestTimeoutMs` が 0 の期限なし）なら、起動は止めず、レシートの写真の読み取りだけを使えなくする（unavailable）。記録は理由の名前 `receipt_timing_exceeds_client_timeout` だけ。ほかの経路は上書きのとおりに動く |

端末の 150 秒は、TLS の確立の後に要求を書き始めてから数える（`hubRequest`）ので、TLS の確立の期限は関係に含めない。要求が届くまでの上限には `requestTimeout` を使う（Node は `headersTimeout` を `requestTimeout` より長くできないので、ヘッダーが届くまでもこの上限に収まる）。10 秒に本文の受け取りを含めたので、遅い回線で 10 秒以内に本文が届かなければ送らない（503 `not_sent`）。

### 5. `not_sent` の説明（低）

`ApiError` と `DesktopHouseholdReceiptView` の `not_sent` の説明から「予算の予約は解放した」を除き、「送出意図の前に止めた（外部へ送っていない・費用はかかっていない）」までにした。予算の門の受付の結果が DB で分からない（admission_unknown）ときは予約が残っている可能性がある（送出意図のない予約は、再起動の照合で解放される）。

### 6. 試験の抜け（低）

次の試験を足した。時間に頼る試験（`api-server-abort.test.ts` の 200 ms の待ち）は、中断の事象（`abort`）が経路の処理へ届くのを待つ形に改めた。

### 試験（模擬だけ）

- `scripts/household-receipt.test.mjs`: 付帯情報を全体で確かめること（正常なプログレッシブの形と大きな走査のデータは送る、走査の間の APP1・APP13、EOI の後ろの 2 枚目の JPEG と 0 の埋め、COM、APP11、APP0 の後の APP1、APP1 が二つは送らない、長さが 2 未満・長さが末尾を超える・EOI がない・走査がないは読めない）。端末の時間切れの関係を `DEFAULT_API_LIMITS` から確かめる（120 秒、44.999 秒と 45 秒の境目、0 の期限なし）。合成の JPEG の大きさの埋めを EOI の前に移した（Core・端末の試験も同じ）。
- `apps/core/src/household-receipt.test.ts`: 中断に応じず返らない読み取りの口で、上限を過ぎると貸し出しが返り、画像が 0 で埋められ、次の読み取りを受け、記録は理由の名前だけ。実際の `RetentionSweeper` で、貸し出し中に始まった掃除が上限の後に終わり、ゲートが開く。実際の `BudgetGate` で、返らない口でも上限の後に門の後ろの処理が終わり、予約が usage 不明で残る。実際の `BudgetGate` で、送出意図の後に端末が接続を切ると予約が usage 不明で残り、503 `dependency_unavailable` になる。送り始めるまでの期限を要求が届いた時刻から数える。受付の期限の上書きで関係が破れると unavailable。
- `apps/core/src/api-server-abort.test.ts`: まとめた本文（Buffer）を、挙げた経路では経路の処理の前に 0 で埋め、挙げていない経路では埋めない。挙げた経路にだけ要求が届いた時刻が付き、経路の処理を始めた時刻より前。
- `apps/desktop/src/main/hub-transport.test.ts`: `hubRequest` の本文の Buffer を、応答・時間切れ・中断の後に 0 で埋める。
- `apps/desktop/src/main/household-link.test.ts`: 送っている途中の読み取りの要求が、`DesktopCoreLink.ioStateChanged`（入出力の停止）から `stopReceipt` に届いて切られ、結果不明になる。許されている間の通知では切らない。
- `apps/desktop/src/main/receipt-image-file.test.ts`: 名前付きパイプ（FIFO）を開かずに読めないと返す（Windows ではファイルの名前で名前付きパイプを作れないので、`process.platform` で飛ばす）。開く前と開いた後で `dev`・`ino` が違えば読まない。

期待値は手で書いた。直す前のコードで失敗することを確かめた試験: domain の付帯情報（走査の間の APP1・APP13、EOI の後ろの 2 枚目と埋め、COM、APP11、走査の後の長さが末尾を超える形、EOI がない形）、Core の 6 件（返らない口の 3 件・要求が届いた時刻からの期限・まとめた本文の 0 埋め・要求が届いた時刻が付くこと。組み立てた JavaScript の修正の箇所を一時的に戻して確かめた）と受付の期限の上書き、端末の 3 件（`ioStateChanged`・本文の 0 埋め・`dev`・`ino` の照合。同じく一時的に戻して確かめた）と名前付きパイプ（直す前の組み立てたコードで止まることを確かめた）。付帯情報の APP0 の後の APP1・APP1 が二つ・長さが 2 未満、実際の `BudgetGate` での送出意図の後の切断は、直す前のコードでも通る（抜けていた試験を足した）。

### 残ること

- 返らない口が上限の後に返した usage は精算しない（usage 不明のまま、本人の手での精算に回る）。
- 本文の受け取りを 10 秒に含めたので、遅い回線では送れないことがある。実機で確かめる（`docs/household/README.md` の項目 L）。
- `O_NONBLOCK` と `dev`・`ino` の照合を、macOS・Windows の実機で確かめる。

## 追記（ADR 0179）

本人の判断で U364 の暫定を (a) から (b) に変え、レシートの写真の読み取りの入・切を家計簿の設定の表（`household_settings`）に保存するようにした（[ADR 0179](0179-household-bill-delete-and-receipt-setting.md)、マイグレーション 0022）。既定は切のままで、入にすると中枢を起動し直しても入のまま。読み取りの口がなければ、保存した値によらず unavailable。変える要求（`POST /v1/household/receipt-setting`）は利用通知の取り込みの入・切と共通の設定の版（`expected_settings_revision`）で照合し、違えば 409。入にするときの OS の確認ダイアログと画面操作だけの経路は変えていない。この ADR の「設定の置き場所」「同意の記録」の行と U364 の記述のうち「起動し直すと切に戻る」は、ADR 0179 の決定が優先する。手順書の項目 L の L12 も ADR 0179 に合わせて変えた。
