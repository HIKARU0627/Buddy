# ADR 0173: 会話の一言からの家計の記録の候補を、キャンバスの入力バーと音声へ広げるか（家計簿 段階 3 の一部）

- 日付: 2026-11-26
- 状態: 調べた結果、**今は広げない**。U346 の暫定 (a)（候補を出すのは標準の窓の会話の欄だけ）を続ける。あわせて、広げる条件と、条件がそろったときの経路・音声の数字の聞き違いの扱いを決めておく。コード・契約（JSON Schema・OpenAPI・IPC）・窓の役割の表・試験は変えない。実データ・実機は未実施。
- 根拠: 本人の決定（段階 3: メールの届かない支出を会話の一言から補い、本人の手間を減らす）、ADR 0032・0041・0050・0052・0162・0167・0171。原本（非公開 Notion）に家計簿の決めはない（U318 以降と同じ）。
- 対象: 判断だけ（この ADR と `docs/b00/contract-map.md` の U346・U350・U351）。

## 背景

ADR 0171 で、標準の窓（従来の 1 つの窓）の会話の欄に「コンビニで 500 円使った」と書くと、端末が決まった規則（`readHouseholdUtterance`）で読み、家計簿の欄の手入力の入力欄に値を入れて開けるようにした。キャンバスの入力バーと音声で同じことを言ったときにも候補を出せれば、本人の手間がさらに減る。そこで、窓の役割・IPC の許可・音声の経路を調べ、広げられるかを確かめた。

## 調べたこと

| 対象                     | 分かったこと                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 窓の組み立て             | `apps/desktop/src/main/window-roles.ts` の `uiWindowMode` は、配布版（`app.isPackaged`）では必ず標準の窓 1 つにする。キャンバス・状態の層・入力バーの 3 つの窓は、開発の起動で `--buddy-ui=canvas`（または環境変数 `BUDDY_DESKTOP_UI=canvas`）を付けたときだけの試作（ADR 0032）。`rolesForMode` はどちらか一方の組み立てだけを作るので、キャンバスの組み立てでは標準の窓が存在しない                                                                                       |
| 家計簿の欄の置き場所     | 家計簿の欄（`HouseholdPanel`）を描くのは標準の窓だけ（`renderer/App.tsx`）。窓の役割の表（`DESKTOP_ROLE_CHANNELS`）は家計簿の 8 つのチャネルを状態の層にも入れているが、状態の層のパネル（`StatusPanel`）に家計簿の欄はない（状態の層の家計簿の画面は ADR 0162 で対象外）。キャンバスと入力バーは家計簿のチャネルを使えない（キャンバスの部品が家計の記録の変更・削除に見せかけられないようにするため。ADR 0162）。キャンバスの組み立てには、手入力の入力欄を開ける窓がない |
| 入力バー                 | 入力バーの窓が使えるのは `desktop.get_state`・`desktop.turn_submit`・`desktop.canvas_summon` だけ。発言の本文は入力バーの画面と main が持つので、一言を読むこと自体はできる。読んだ候補を開く先がない                                                                                                                                                                                                                                                                       |
| 音声                     | 音声レンダラーは、キャンバスの組み立ての開発の起動で `--buddy-voice=mock` を付けたときだけ作り、端末の中の模擬の中枢と話す。製品の起動では音声を始めない（U91、ADR 0050）。声の文字起こしは中枢がサイドバンドで受け（`apps/core/src/live-conversation.ts`）、端末の main・画面には文字起こしの本文が届かない（音声レンダラーとの限定 IPC にも、状態の層への通知にも本文はない）。声の依頼の結果は、本文を複製しない結果の表示（`ResultView`）で画面へ回る（ADR 0052）       |
| 声の文字起こしの確かめ方 | 中枢は Live の文字起こしと端末の ASR の結果を `compareTranscripts` で比べ、完全一致（NFC と前後の空白の除去だけ）のときだけ進め、それ以外はすべて聞き返す（ADR 0041、U36）。違いの説明として数字・日時・否定・宛先の違い（`number_differs` など）を出すが、一致しても聞き違いがないことの証明にはならない（QA08）                                                                                                                                                           |

## 決めたこと

| 対象               | 決定                                                                                                                                                                                                                 |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 今の扱い           | 入力バーと音声からは候補を出さない。U346 の暫定 (a) を続ける。ADR 0171 の振る舞い（標準の窓の会話の欄）は変えない                                                                                                    |
| 広げない理由 1     | 配布版で本人が使う会話は標準の窓の会話の欄だけで、そこでは既に候補を出している。入力バーと音声は開発の起動の試作にしかなく、今広げても本人の手間は減らない                                                           |
| 広げない理由 2     | キャンバスの組み立てには家計簿の欄がなく、標準の窓も同時には開かない。候補を読めても開く先がない。開く先を作るには、キャンバスの組み立てで家計簿の欄をどの窓に置くかという、まだ決めていない画面の設計が要る（U350） |
| 広げない理由 3     | 音声は製品の起動で使えず（U91）、端末に文字起こしの本文が届かない。候補を作るには、中枢から端末へ声の発言の本文か候補の値を返すよう契約を変える必要がある（U351）                                                    |
| 新しい口を作らない | 入力バー・キャンバスの窓に家計簿の欄・家計簿のチャネルを足さない（ADR 0162 の役割の表のまま）。画面から main へ候補を渡す要求のチャネルも作らない                                                                    |
| 案内も出さない     | 入力バーに「標準の窓の家計簿の欄から入れてください」とは出さない。キャンバスの組み立てでは標準の窓を開けず（起動し直しが要る）、案内が手間を減らさないため                                                           |

## 広げるときの経路（条件がそろったときの方針）

### 入力バー（U350）

条件は、キャンバスの組み立てを配布版で使うようになり、その組み立てで家計簿の欄（手入力の入力欄を含む）をどの窓に置くかが決まること。そのときは次の形にする。

| 対象           | 方針                                                                                                                                                                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 読む場所       | main。入力バーからの `desktop.turn_submit` を main が受け付け、中枢が発言を受け付けた（応答が ok）ときだけ、main が送った本文を `readHouseholdUtterance` で読む。入力バーの画面は候補を作らず、送りもしない                                                            |
| 偽の送りを防ぐ | 画面から main へ候補を渡す要求のチャネルを作らない。候補の元は main 自身が受け付けて中枢へ送った本文だけなので、別の窓が候補を偽って送る入口そのものがない。送信元の窓の役割の検査（`untrusted_sender`）は今のまま                                                     |
| 渡す先         | 家計簿の欄を描く窓（役割の表で `desktop.household_add` を使える窓）だけに、main から通知で候補の値を渡す。通知の宛先は役割ごとの通知の表（`DESKTOP_ROLE_NOTIFICATIONS`）で絞り、通知のチャネルは IPC の契約（JSON Schema）に足す。キャンバスの窓・入力バーへは送らない |
| ロックと切断   | ロック解除済みで中枢に接続しているときだけ渡す。main はロック・切断・入出力の停止で世代を進め、送った時と世代が違う候補は渡さずに捨てる。受け取った窓も、ロック・切断で捨てる（ADR 0171 と同じ）。保存せず、中枢へも送らない                                           |
| 中身の検査     | 受け取った窓は、届いた値を手入力の入力欄の読み方（金額・日付の形、店名の検査 `householdMerchantErrors`）で読み直し、合わない値は欄に入れない。記録は本人が「足す」を押したときだけ `desktop.household_add` で作り、中枢は今までどおり中身を検査し直す                  |

### 音声（U351）

条件は、製品の起動で音声が使えること（U91）と、声の発言から読んだ値を端末へ返す経路を決めること（中枢が `readHouseholdUtterance` で読んで候補の値だけを返すか、確定した発言の本文を返して端末で読むか。どちらも契約の変更で、候補は中枢の DB に置かない）。そのときは次の規則にする。

| 対象                   | 規則                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 読む文                 | 中枢が確定した声の発言のうち、`compareTranscripts` が proceed（Live の文字起こしと端末の ASR の完全一致）になった文と、聞き返しの後に本人が確かめた文だけ。Live の文字起こしだけの文・ASR の結果がない文・比較が聞き返しのままの文からは候補を作らない                                                                                                                                   |
| 数字・日付の食い違い   | 比較の違いに数字（`number_differs`）か日時（`datetime_differs`）があれば、候補にしない。理由は「音声の聞き取りで金額か日付が食い違いました。家計簿の欄から入れてください。」とする（家計簿の欄から入れるよう書くのは ADR 0171 の「候補にしない」と同じ）                                                                                                                                 |
| 一致しても確かめる     | Live と ASR が同じ聞き違いをすると、比較では見つからない（例: 「500 円」と「5000 円」、「1 万円」と「10 万円」）。一致は聞き違いがないことの証明ではない（QA08）。そのため、音声からの候補では入力欄の頭に「音声から読んだ値です。聞き違いがあり得るので、金額と日付を確かめてから足してください。まだ記録していません。」と書き、本人が「足す」を押すまで記録しない（文字の候補と同じ） |
| 漢数字                 | ASR が「五百円」のように漢数字で書いた金額は、`readHouseholdUtterance` が今までどおり読めない金額として候補にしない（漢数字を数に直す規則は足さない。読み違いの入口を増やさないため）                                                                                                                                                                                                    |
| 置き場所・ロック・確定 | 入力バーと同じ（家計簿の欄を描く窓のメモリーだけ。ロック・切断で捨てる。記録は「足す」の `desktop.household_add` だけ）                                                                                                                                                                                                                                                                  |

## 退けた案

| 案                                                                                    | 退けた理由                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 入力バーの画面が候補を読み、新しい要求のチャネルで main へ送り、main が標準の窓へ渡す | キャンバスの組み立てでは標準の窓が存在せず、渡す先がない。画面から候補を送る口は、別の窓が候補を偽って送る入口にもなる。main が自分で受け付けた本文から読めば、この口は要らない                                          |
| 状態の層のパネルに手入力の入力欄を足し、そこで候補を開く                              | 状態の層は状態・停止・確認の一覧の層（ADR 0032）で、キャンバスの組み立てで家計簿の欄をどこに置くかは、その組み立ての画面の設計として別に決める（U350）。試作の組み立てのためだけに作っても、配布版の本人の手間は減らない |
| キャンバスに候補の部品を出す                                                          | キャンバスは AI が置く物を描く窓で、家計簿のチャネルを渡さない（ADR 0162）。キャンバスの部品が家計の記録の入力に見せかけられないよう構造で防いでいる境界を崩す                                                           |
| 入力バーに「標準の窓の家計簿の欄から入れてください」と案内する                        | キャンバスの組み立てでは標準の窓を開けない（起動し直しが要る）ので、案内が本人の手間を減らさない                                                                                                                         |
| 音声の候補を Live の文字起こしだけから作る                                            | 聞き違いを比べる相手がなく、数字の聞き違いをそのまま入力欄に入れてしまう                                                                                                                                                 |
| 音声の数字の食い違いを、規則で片方に寄せて候補にする（例: ASR の値を正とする）        | どちらが正しいかを端末も中枢も決められない。比較の規則（U36）が聞き返す側へ倒しているのと同じく、候補にせず本人に入れてもらう                                                                                            |

## 原本に決めがない項目

- U346（更新）: 候補を出すのは標準の窓の会話の欄だけのまま。広げない理由をこの ADR の調べで書き足した。
- U350: キャンバスの入力バーからの候補の経路（main が受け付けた本文から読み、家計簿の欄を描く窓へ通知で渡す）。
- U351: 声の発言からの候補と、数字の聞き違いの扱い。

## 対象外

- コード・契約・IPC のチャネル・窓の役割の表・試験の変更。
- キャンバスの組み立てでの家計簿の欄の置き場所（U350 の前提。キャンバスの組み立ての画面の設計として決める）。
- 製品の起動での音声の経路（U91）。

## 試験

実装を変えないので、新しい試験はない。今の境界は既存の模擬の試験で確かめている。

- `scripts/canvas.test.mjs`: キャンバスの窓と入力バーが使えるチャネルの一覧（家計簿のチャネルを含まない）。
- `apps/desktop/src/main/window-roles.test.ts`・`preload.test.ts`: 配布版の起動では開発用のフラグ・環境変数を無視して必ず標準の窓にすること、標準の窓が家計簿のチャネルを使えること。
- `apps/desktop/src/renderer/state/household-candidate.test.ts`: 候補は受け付けられた発言だけから出し、中枢へは本文だけを送り、ロックと切断で捨てること（ADR 0171）。

実データ・実機・実際の音声は未実施で、合格扱いにしない。

## 残ること

- U346・U350・U351 の本人の確認。
- キャンバスの組み立てを配布版で使うと決めたとき、家計簿の欄の置き場所と一緒に U350 を決め直し、その時点で実装と試験（ロック中に渡さないこと、別の窓からの送りを受けないこと、確定せずに閉じても記録しないこと、二度押しでも一度だけ送ること）を足す。
- 製品の起動での音声の経路（U91）が決まったとき、U351 の規則で実装と試験（数字・日付が食い違う比較では候補にしないこと、漢数字の金額を読まないこと）を足す。
