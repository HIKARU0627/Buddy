# ADR 0014: デスクトップの型付き IPC の契約

- 日付: 2026-10-20
- 状態: B01-03（#45）の判断。Electron の main・preload・UI レンダラーの実装（B01-04 #46）、音声レンダラーの IPC（B05）、Core とクライアントの通信（B03）は未実装。
- 根拠: 設計 10 §1・§1A、07 §2・§5、01 いつも見える状態・停止・取消・終了、02 処理の配置・モジュールと責務（停止）。renderer と main の間の IPC を packages/contracts の JSON Schema に定義し main で Ajv により検査することと、B01 ではデスクトップと Core を接続しないことは本人の決定（ADR 0012）に従う。原本の参照手順は docs/design/README.md。

## 決めたこと

| 対象           | 決定                                                                                                                                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約の置き場所 | `buddy.schema.json` の `DesktopIpcRequest`・`DesktopIpcResponse`・`DesktopIpcNotification`・`DesktopStatusBar`（と `DesktopIpcChannel`）。型は生成型を使い、手で書かない                                                                              |
| 3 つの別の操作 | クライアントの終了（`desktop.client_quit`）、この端末の入出力停止（`desktop.io_stop`）、中枢の停止を別の操作にする。中枢の停止はデスクトップから送らないので、チャネルを作らない。来客モード・全体停止の開始と解除も Core が必要なので B03 以降で足す |
| 限定 IPC       | UI レンダラーに公開するのは下の 5 チャネルだけ。端末トークン・端末 ID・任意の URL や HTTP の実行・中枢の停止を表すチャネルと項目を作らない。未知のチャネル・未知の項目・型違いは schema（`additionalProperties: false`）で拒否する                    |
| 受付の規則     | 受け付けてよいかは `packages/domain/src/desktop.ts` の `admitDesktopRequest` が決める。domain は contracts の型を import せず、チャネル・電源のイベント・拒否の理由の一覧が schema と一致することを試験で確かめる                                     |
| 再利用         | `DeviceIOState` の列挙を `LockState`・`IoStopScope`・`VoiceState` に切り出し、状態欄からも同じ定義を参照する。値の範囲は変えていない                                                                                                                  |

## チャネル

要求は `{ channel, request_id, payload }` で、引数のない要求の payload は null です（空の object の生成型は、何でも代入できる空の型になり lint も拒否するため）。応答は同じ `request_id` と `channel` を返します。

| チャネル              | payload              | いつ受け付けるか                                                                                      | 成功時の応答       |
| --------------------- | -------------------- | ----------------------------------------------------------------------------------------------------- | ------------------ |
| `desktop.get_state`   | null                 | いつでも（ロック中・不明は内容を隠した状態欄を返す）                                                  | 状態欄の値         |
| `desktop.io_stop`     | null（範囲は local） | いつでも。DB・AI・ネットワークの応答を待たずに端末で止める                                            | 停止後の状態欄の値 |
| `desktop.io_resume`   | `expected_io_epoch`  | ロック解除済み → 画面操作 → この端末の停止（local）→ 期待する io_epoch の一致、をすべて満たすときだけ | 再開後の状態欄の値 |
| `desktop.window_hide` | null                 | いつでも。トレイに残り、入出力の状態は変えない                                                        | なし               |
| `desktop.client_quit` | null                 | いつでも。中枢は止めない                                                                              | なし               |

後から足したチャネルは、それぞれの ADR にあります（B03 は ADR 0025・0026・0022、B04-05 は ADR 0031）。UI-02 では、デスクトップの層のキャンバスを前に出す `desktop.canvas_summon`（payload は null、ロック解除済みの画面操作だけ、成功時の応答はなし。状態の層と入力バーの窓だけが使える）を足しました（ADR 0032 の「キャンバスを呼ぶ・戻す」）。UI-04 では、状態の層のパネルを出す・しまう `desktop.status_panel`（payload は `{open}`、ロック中・不明・停止中でも受け付ける、成功時の応答はなし。状態の層の窓だけが使える）を足しました（ADR 0032 の「UI-04 の状態と停止の層」）。

main から UI レンダラーへの通知は 2 種類です。

- `desktop.state_changed`: 端末状態（ロック・停止・入出力の許可など）が変わったときの状態欄の値。
- `desktop.power_event`: main が記録した電源・ロックのイベント（`lock_screen`・`unlock_screen`・`suspend`・`resume`・`shutdown`）と観測時刻（UTC）、出どころ（`os_event` は OS からの通知、`os_query` は main が OS へ問い合わせた結果）。記録の通知で、停止・再開の命令ではありません。

拒否は理由コードだけで、本文・文言を含めません。

| 理由                        | 意味                                                                      |
| --------------------------- | ------------------------------------------------------------------------- |
| `invalid_request`           | 形式の不正・未知のチャネル。request_id・channel を確かめられなければ null |
| `untrusted_sender`          | 送信元が main の作った UI レンダラーの主フレームでない                    |
| `device_locked`             | ロック中、またはロック状態が取得できない                                  |
| `screen_operation_required` | ウィンドウが表示中かつ前面にない                                          |
| `not_stopped`               | 入出力が止まっていない                                                    |
| `core_required`             | 来客モード・全体停止の解除。中枢の操作が必要（B03 以降）                  |
| `io_epoch_mismatch`         | 期待する io_epoch が現在と違う（古い画面・重複した操作）                  |

## 状態欄と端末状態

- `DesktopStatusBar` は、ロック中・ロック状態不明のとき `visibility: hidden` とロック状態だけを持ち、中枢・表示先・音声・保存モード・予算・安全停止の項目を schema の形で持てません（01）。
- ロック解除済みのときは、停止の範囲・入出力の許可・io_epoch・音声状態・中枢との接続（`not_connected` は B01 の既定、`connected`、`unreachable`）・最終確認時刻・表示先・保存モード・予算保留・安全停止を持ちます。中枢が正本の値は接続中だけ値を持ち、未接続・接続不能では null（不明）にします。音声状態の null は音声機能がまだないこと（B05 まで）です。
- 意味検査（`semanticErrors`）: 停止中に入出力を許可しない、音声状態と停止の範囲の矛盾、中枢に接続していないのに中枢の値がある・接続中なのに値がない、停止・再開の応答が停止・再開を反映していない、問い合わせ（`os_query`）の記録がロック状態以外を報告する、を拒否します。
- 端末状態の遷移は `nextDesktopIoState` です。入出力が許可されている状態から止めたときだけ io_epoch を 1 進めます（ADR 0005: io_epoch は端末が停止時にその場で進める）。再開では進めません。既に止まっていれば範囲も世代も変えず、来客モード・全体停止を local で上書きしません。

## 読み取り（レビュー対象）

原本に明記がなく、設計の文から読み取った点です。

- **画面操作の判定**: main は UI レンダラーの操作が本人のクリックかを確かめられません。「送信元が UI レンダラーの主フレーム」かつ「ウィンドウが表示中かつ前面」を画面操作の条件にしました。中枢の `Buddy-Input-Origin` を main が限定 IPC の種類から付ける方針（ADR 0009）と同じく、Renderer が自分で「画面操作です」と申告する項目は作りません。
- **送信元の検査はすべてのチャネル**: 停止は安全側の操作ですが、送信元の検査は停止にも適用します（Electron の送信元検査を省く例外を作らないため）。
- **スリープ**: `suspend` ではこの端末の入出力を止め、ロック解除済みだったならロック状態を unknown にします。`resume`（スリープからの復帰）だけでは解除済みに戻さず、`unlock_screen` か main の問い合わせで解除を確かめます（07 §2 の「取得不能なら解除済みと扱わない」、07 §5 の「スリープ復帰でリースを捨てる」）。`shutdown` でも入出力を止めます。
- **来客モードの音声状態**: 来客モードも全端末の停止なので、状態欄の音声状態は「全体停止中」（`global_stopped`）にします。
- **ロック解除後の表示**: 01 は「ロック解除後にも『この端末で再開する』を押すまで受付・表示を再開しない」とします。B01 の画面は状態欄だけなので状態欄は解除後に表示し、会話・候補などの内容（B02 以降）は再開まで隠すことを後続で守ります。
- **再開の条件のうち登録済み端末**: 設計は「登録済み・ロック解除済み端末の画面操作」とします。B01 は端末登録（B03）がないため、登録の検査は Core の `resumeIo`（ADR 0009）で行い、デスクトップの規則には入れていません。

## 残ること

- Electron の main での Ajv の検査・送信元の検査・preload の公開・トレイ・powerMonitor の接続は B01-04（#46）で実装します。実機（Windows / macOS）での試験は未実施です。
- 起動直後の入出力の扱い（停止の状態で起動して画面の再開を求めるか）と、io_epoch をクライアントの再起動で巻き戻さないための保存は、#46 の実装時に決めます。中枢へ報告する B03 以降は巻き戻しを拒否します（ADR 0005）。
- 来客モード・全体停止・端末の失効・中枢のリース喪失による停止と、その解除のチャネルは B03 で Core と接続するときに足します。
- 音声レンダラーへの限定 IPC（start・stop_playback・close_voice_session・suspend_io・play・set_silence_timeout。10 §1）は B05 で定義します。
