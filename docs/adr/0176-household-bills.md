# ADR 0176: 請求のメールを請求予定として支払い済みと分ける（家計簿 段階 2 の一部）

- 日付: 2026-11-26
- 状態: 家計簿の段階 2 の残りの部分。カード会社の請求のお知らせメール（今回の請求の金額と引き落とし日を知らせるメール）を、家計の記録（支払い済みの利用）とは別の「請求予定」として取り込み、家計簿の欄で月の支出の合計と分けて見せる。**模擬の試験だけ**で、実在のメール・実機・実 API での確かめは未実施。
- 根拠: 本人の決定（段階 2: 請求のメールは「請求予定」として支払い済みと分ける。本人の手間を減らし、できるだけ早く取り込む。実機・実データでの確かめは後でまとめて行う）。ADR 0158（保存と暗号化）・0159（送り主の確かめと本文の読み取り）・0160（同期したメールからの取り込み）・0163（取り込みの入・切）・0165（定期の支出）・0166（予算）・0170（取得集合ごとの基準）。原本（非公開 Notion）に家計簿の決めはない。
- 対象: `packages/domain/src/household-bill.ts`（新規）・`household-notice.ts`（年のない日付の範囲を引数にする）、マイグレーション 0021、`packages/storage`（`sealed-blob.ts` の用途、`household-content.ts` の請求予定の暗号文、`household-store.ts` の `household.bill_record`・`household.bill_list`、`policy.ts`）、`packages/domain/src/backup-plan.ts`、`apps/core/src/household-bills.ts`（新規）・`household-mail-intake.ts`・`api-household.ts`・`core.ts`、`packages/contracts`（`HouseholdBill`・`HouseholdMonthBills`、`HouseholdMonth.bills`、`DesktopHouseholdView.bills`）、`scripts/contract-tools.mjs`（意味検査）、`apps/desktop`（橋渡しと画面の「請求予定」）。

## 背景

カードで払った利用は、利用通知メールから家計の記録（支出）として記録している（ADR 0159・0160）。カード会社は、その月の利用をまとめた請求の金額と引き落とし日も、請求のお知らせメールで知らせる。請求の金額は、記録済みの利用の合計を後から知らせるものなので、家計の記録として月の支出に足すと二重の計上になる。一方で、いつ・いくら口座から引き落とされるかは、本人が家計を見るうえで知りたい値である。これまでは請求の件名のメールを読まずに捨てていた（ADR 0159 の件名の規則）。

| 対象                 | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保存の形             | 家計の記録（`household_entries`）とは別の表 `household_bills` に、請求予定を 1 件 1 行で置く（マイグレーション 0021、DB の版 21、STRICT の表 64）。家計の記録を読む処理（月の集計・予算・定期の支出・書き出し・重なりの印・書き出しの取り込みの突き合わせ）は、この表を読まないので、請求予定が支出に混ざらない（U357）                                                                                                                                                                                                                                                   |
| 平文に置くもの       | 出所の種類（`mail_bill` だけ）・出所の鍵（SHA-256）・月（引き落とし日の月）・作成時刻だけ。会社の表示名・金額・引き落とし日は暗号文（`sealed_blobs` の用途 `household_bill`。持ち主は請求予定、版は 1）に入れる。用途を足すために `sealed_blobs` を 0011・0016・0019 と同じ方法で作り直す                                                                                                                                                                                                                                                                                 |
| 行の扱い             | 画面からの変更・削除はまだないので、書いた行は変えず、消さない（DB の trigger で拒否する）。行の出所の鍵が残るので、同じメールから二つ目を作らない。バックアップには含める（家計簿の正本の一部）。保存期限の分類（`policy.ts`）は、家計の記録と同じ「本人が消すまで残す」（`until_user_deletes`）。消す操作を作るときは、DB の trigger を外すマイグレーションが要る（U360）                                                                                                                                                                                               |
| 送り主の確かめ       | 利用通知と同じ規則（ADR 0159・0160）。送信元のドメインの一覧と、Gmail の一番上の認証結果の DMARC か同じ会社の DKIM の合格。送り主の確かめに落ちたメールは、件名だけを見て本文を読まない                                                                                                                                                                                                                                                                                                                                                                                   |
| 件名                 | 利用通知の件名（`householdNoticeSubjectKind` が usage）・速報の件名は、これまでどおり利用通知として扱う。それ以外の件名で（速報の件名は利用通知の速報と同じく読まない）、「請求」「口座振替」「利用代金」「利用明細」の語か、支払い・引き落としの金額・予定・日の語があり、宣伝（キャンペーン・ポイント・割引など）・手続き（本人確認・ログイン・登録・変更など）・引き落としの失敗と督促（できませんでした・残高不足・未入金・督促・再引落など）・訂正のお知らせ（訂正・修正・お詫び・再送・取消）・速報の語がない件名を、請求のお知らせとして本文を読む                 |
| 本文の読み取り       | 本文を NFKC にし、請求の金額の項目（ご請求金額・お支払い金額・お引き落とし金額・口座振替金額・ご利用代金請求額など。前に「今回」「当月」などが付いてもよい。「前回」の付く項目は読まない）と、引き落とし日の項目（お支払日・お引き落とし日・口座振替日・お支払期日など）を読む。項目名の後の括弧の補足（「(予定)」「(12 月分)」）と、値が次の行にある書式も読む。括弧の補足に前回・前月・先月などがある項目（「ご請求金額(前回)」）は読まない。飾りの記号を取るのは項目名の判定のときだけで、値には元の行を使う（次の行の「-1,000円」は取消として読み、請求予定にしない） |
| 読まない請求         | 金額の項目がない（会員サイトで見るよう促すだけのお知らせ）・0 円・外貨・取消（負の金額）・読めない金額・二つの金額の項目が食い違う・引き落とし日がない・読めない・二つの引き落とし日が食い違うときは、請求予定にしない。理由の名前だけをログに残し、金額・会社名・メールの ID は残さない。金額の項目がない・本文を平文にできないときも同じ（U361）                                                                                                                                                                                                                        |
| 引き落とし日の年     | 年のある日付はそのまま。年のない日付（12/10・1 月 6 日）は、受信日の前の年・同じ年・翌年のうち、受信日の 31 日前から 92 日先までに入る年にする。範囲は 124 日分で 1 年より短いので、入る年は多くても一つ。どれも入らなければ読まない（U359）                                                                                                                                                                                                                                                                                                                              |
| 同じ請求             | 同じメール（出所の鍵）からは一つだけ。別のメールでも、同じ月に同じ会社・同じ引き落とし日・同じ金額の請求予定があれば作らない（確定のお知らせと引き落とし前のお知らせ）。ただし、同じ請求かの判定と記録が一つの transaction ではないので、別の口座に同じメールが同時に届くと、二つできる余地がある（どの合計にも入らないので家計の数字は狂わない。実在のメールで起きるかを確かめてから、transaction にまとめるかを決める）。金額の違う請求は、別の請求予定として作る（どちらが正しいかは決めない。U358）                                                                   |
| 取り込みの入・切     | 利用通知と同じ取り込みの中で読むので、本人が取り込みを止めている間は読まない（ADR 0163）。初めて取り込むときと再開のときは、その時点の同期済みのメールを読まない（取得集合ごとの基準。U327・U334・ADR 0170）                                                                                                                                                                                                                                                                                                                                                              |
| API                  | 1 か月（`GET /v1/household/months/{month}`）が `bills`（`HouseholdMonthBills`: 引き落とし日がその月の請求予定の一覧・合計・読めなかった数・上限 100 件で切ったか）を返す。並びは引き落とし日・会社の表示名・金額の順。メールの ID・請求予定の ID は返さない。請求予定を読めないときは、記録を読めても 503 にする。請求予定がないように見せないための判断で、その間は家計簿の欄の月の表示も CSV の書き出しも止まる（記録は読めても、請求予定が読めない月は出さない）。月ごとの合計・定期の支出・予算の応答は変えない                                                       |
| 意味検査             | 請求予定の引き落とし日がその月で暦に実在すること、並びの順、合計が金額の和であることを契約の検証ツールが確かめる                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 画面                 | 家計簿の欄で、出している月の記録の後に「請求予定」を出す。請求予定の合計と、会社・金額・引き落とし日の行。請求予定は利用の記録を後からまとめて知らせるもので、支出の合計・予算・定期の支出には入れていないことを書いておく。なければ「この月に引き落とされる請求予定はありません。」。読めていなければ出さない。読めなかった請求予定・上限で切ったことは知らせる                                                                                                                                                                                                          |
| 端末の経路           | 新しい IPC のチャネルは足さない。main が 1 か月の読み取りの `bills` を `DesktopHouseholdView.bills` に写して渡す（ID はもともと持たない）                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 画面の操作を作らない | 請求予定を消す・直す操作は作らない（U360）。請求予定はどの合計にも入らないので、誤った請求予定が残っても家計の数字は狂わない。誤りの種類（読み違い・訂正のお知らせ・別のカード）は実在のメールで確かめないと分からず、操作の形を先に決めると作り直しになる。作るときは、既存の分類の変更・削除と同じく内容版で照合する（版の列を足すマイグレーションと、削除を拒否する DB の trigger を外すマイグレーションが要る）                                                                                                                                                       |

## 退けた案

| 案                                                                   | 退けた理由                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 家計の記録（`household_entries`）に新しい向き（`bill`）を足す        | 記録を読む処理（月の集計・分類ごとの支出・予算の比べ方・定期の支出・CSV の書き出し・重なりの印・書き出しの取り込みの突き合わせ・店名の規則・手入力と中身の変更）のすべてで除外が要る。一つでも漏れれば二重の計上になる。向きと分類の対応（ADR 0158）と契約の `HouseholdDirection` も変わり、影響が広い |
| 家計の記録に新しい状態（`scheduled` など）を足す                     | 状態は今「有効か削除済みか」だけで、読み取りは `active` を読む。状態を足すと、同じ除外の漏れの心配が残るうえ、削除の trigger・内容版の照合・出所の鍵の規則が請求予定にも及ぶ                                                                                                                           |
| 振替（`transfer`）の記録として入れる                                 | 振替は実際に動いたお金（引き落とし済み）を表す（U321）。予定を振替にすると、引き落としの前に振替の合計に入り、書き出しの取り込みで入る実際の引き落としの行と二重になる                                                                                                                                 |
| 保存せず、画面を開くたびにメールを読み直す                           | 開くたびに Gmail を読む通信が増え、同期の掃除でメールの行が消えると請求予定も消える。ロック解除の画面の読み取りから外部を読むことになり、取り込みのゲート（ADR 0160 の掃除のゲート）の外になる                                                                                                         |
| 同じ会社・同じ引き落とし日なら新しいお知らせで置き換える             | 同じ会社のカードを二枚持ち、引き落とし日が同じ場合に一方が消える。どちらが正しいかを読み取りの規則で決められない（U358）                                                                                                                                                                               |
| 請求予定の金額を月の支出に足し、利用通知の記録と突き合わせて差し引く | 利用通知で記録できない利用（外貨・取消・通知を有効にしていないカード）があり、差し引く対象を決められない。二重の計上の危険が大きい                                                                                                                                                                     |

## 原本に決めがない項目

- U356: 請求のお知らせの件名・本文の書き方と送信元（実在のメールで確かめる）。
- U357: 請求予定の保存の形（家計の記録と別の表）。
- U358: 同じ請求の判定と、金額の違う二通目の扱い。
- U359: 年のない引き落とし日の年の決め方。
- U360: 請求予定を消す・直す画面の操作を作らないこと。
- U361: 0 円・外貨・取消・読めない金額・食い違う金額の請求のお知らせを請求予定にしないこと。
- U362: 請求予定を引き落とし日の月に出し、月ごとの合計・定期の支出・予算・CSV の書き出しに入れないこと。

## 試験（模擬だけ）

件名・本文・送り主・会社名・金額はすべて合成で、実在の会社のメールの文面は写していない。期待値はすべて手で書いた。

- `scripts/household-bill.test.mjs`（10 件）: 件名の種類（請求・支払い・引き落とし・口座振替・利用代金・利用明細を読み、件名だけ似た宣伝・引き落としの失敗・督促・変更・訂正・修正・お詫び・再送・取消・速報・利用通知の件名は読まない）、次の行がマイナスの金額（`-`・`－`・`−`）なら取消として読み請求予定にしないこと、項目名の後の括弧に前回・前月・先月があれば読まないこと、請求のお知らせを利用通知として読まないこと、同じ行と次の行の書式・全角の値・括弧の補足・前回の金額を読まないこと、引き落とし日の年（92 日先と 93 日先・31 日前と 32 日前・年またぎ・年のある日付・暦にない日付）、金額（0 円・外貨・取消・読めない・食い違い）、引き落とし日がない・食い違う・金額の項目がない・宣伝の件名、出所の鍵の材料（家計の記録の出所と別）、中身の検査と同じ請求の判定、月の請求予定の並びと合計（月の外を入れない）。

## 残ること

- 実在の請求のお知らせで、件名・項目名・日付の書き方・送信元のドメインを確かめ、足りない書き方を合成の例で足す（`docs/household/README.md` の項目 K）。
- 請求予定を消す・直す操作（U360）。作るときは、版の列を足すマイグレーションと、内容版の照合が要る。
- 訂正のお知らせ（件名に「変更」「訂正」「修正」「お詫び」「再送」「取消」が入るもの）と速報は今は読まない。実在のメールで種類を確かめてから扱いを決める（U358）。
- 家計簿全体が忘却（forget-store）の対象外であることは、この ADR より前からの状態で、請求予定もその中にある。扱いは忘却の工程で決める（U360 の行に記録）。
- Outlook のメールは利用通知と同じく読まない（U329）。
